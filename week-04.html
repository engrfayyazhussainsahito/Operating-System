CPU Scheduling

How the OS decides which ready thread gets the CPU next, from FCFS and shortest-job-first through round robin and multilevel feedback queues to Linux's fair scheduler and real-time policies, with exact worked Gantt traces.

What you will be able to do

By the end of this week you will be able to:

  • Compute waiting, turnaround and response times from a Gantt chart for a given set of arrival times and bursts
  • Trace FCFS, SJF, SRTF, round robin and a multilevel feedback queue by hand without arithmetic mistakes
  • Explain why SRTF minimizes average waiting time, and why it cannot be implemented exactly
  • Choose a round-robin quantum by weighing context-switch overhead against responsiveness
  • Compute CPU shares and virtual runtime updates under Linux CFS from nice values
  • Apply the rate-monotonic utilization bound and the EDF test to a periodic task set

In Week 2 a process moved between the ready, running and waiting states, and in Week 3 we saw that the kernel really schedules threads, not whole processes. One question was left open each time: when several threads are ready and there is only one CPU (or fewer CPUs than threads), which one runs next? This chapter is about the answer. The timer interrupt from Week 1 gives the kernel the mechanism to take the CPU away; the scheduling algorithm is the policy that decides where it goes.

We build up in order of sophistication. First the vocabulary and metrics, then four classical algorithms evaluated on one process set so that every number can be compared, then multilevel feedback queues, which are the ancestors of what real kernels do. Finally we look at how Linux schedules (fair-share by virtual runtime) and how real-time systems schedule (deadlines). Assignment 1 is due this week: your shell uses fork, exec and wait, and the first listing below uses the same trio to measure what the scheduler did to a program. Week 5 then tackles what happens when the threads you schedule share data.

The scheduling problem and how to judge it

CPU bursts and the ready queue

Almost every program alternates between computing and waiting for I/O. A stretch of computing is a CPU burst; a stretch of waiting is an I/O burst. A text editor has tiny CPU bursts (a keystroke) separated by long I/O bursts (waiting for the human). A video encoder has long CPU bursts. Measurements across many systems show the same shape: a great many short bursts and a few long ones. That fact drives most scheduler design, because a scheduler that favours short bursts keeps interactive programs snappy.

The scheduler only chooses among threads in the ready state, which the kernel keeps in a ready queue (a data structure, not necessarily FIFO). The part of the kernel that actually switches to the chosen thread is the dispatcher: it performs the context switch, switches to user mode and jumps to the right instruction. The time it takes is the dispatch latency.

Scheduling decisions happen at four moments: (1) a thread blocks for I/O (running to waiting), (2) a timer or other interrupt moves it from running to ready, (3) an I/O completes (waiting to ready), (4) a thread exits. Decisions 1 and 4 are forced, since the CPU is free. A scheduler that acts only then is non-preemptive (cooperative). One that may also act at 2 and 3 is preemptive: it can take the CPU from a running thread. Every modern general-purpose OS is preemptive.

Three times and four goals

Suppose a job arrives at time A, first gets the CPU at time S, needs a total of B units of CPU, and finishes at time F.

Waiting, turnaround and response time

Turnaround time = F - A: everything from arrival to completion. Waiting time = turnaround - B: the time spent sitting in the ready queue (assuming the job does no I/O). Response time = S - A: how long until the job is first run. For an interactive user this is the delay before anything visibly happens.

Schedulers are also judged by CPU utilization (fraction of time the CPU is busy), throughput (jobs finished per unit time) and fairness (no job starves). No algorithm wins on all of them, so the design question is always "which metric do I care about?"

The supermarket

Picture one checkout lane. FCFS is a single queue: whoever arrived first goes first, so one person with a overflowing trolley delays everyone. Shortest-job-first is the "10 items or fewer" lane: average waiting falls, but the person with the huge trolley may wait forever. Round robin is a cashier who scans ten items for you, then moves to the next customer: nobody waits long to start, but everybody takes longer to finish.

Measuring it yourself

The following program runs a command and reports what the kernel recorded. The relevant numbers are CPU time (the sum of the burst lengths), and the number of voluntary context switches (the process blocked) versus involuntary ones (the scheduler preempted it). The structure is exactly the fork, exec, wait pattern from Assignment 1.

/* mytime.c: run a command, then report wall time, CPU time and context switches. */
#define _DEFAULT_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s cmd [args...]\n", argv[0]); return 2; }
    struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        execvp(argv[1], &argv[1]);
        perror("execvp");
        _exit(127);
    }
    int status;
    struct rusage ru;
    if (wait4(pid, &status, 0, &ru) < 0) { perror("wait4"); return 1; }
    clock_gettime(CLOCK_MONOTONIC, &b);
    double wall = (b.tv_sec - a.tv_sec) + (b.tv_nsec - a.tv_nsec) / 1e9;
    double user = ru.ru_utime.tv_sec + ru.ru_utime.tv_usec / 1e6;
    double sys  = ru.ru_stime.tv_sec + ru.ru_stime.tv_usec / 1e6;
    fprintf(stderr, "wall %.3fs  cpu %.3fs  off-cpu %.3fs  voluntary %ld  involuntary %ld\n",
            wall, user + sys, wall - user - sys, ru.ru_nvcsw, ru.ru_nivcsw);
    return WIFEXITED(status) ? WEXITSTATUS(status) : 1;
}

Compile with gcc -Wall -pthread mytime.c -o mytime. On a two-CPU machine ./mytime sleep 1 prints wall 1.002s cpu 0.001s off-cpu 1.000s voluntary 2 involuntary 0: one long I/O-style wait, no preemption. Running one shell loop that counts to 300000 gives wall 0.396s cpu 0.385s off-cpu 0.011s voluntary 1 involuntary 1: a CPU-bound job almost never blocks. Starting three of those loops at once on the two CPUs gives, for example, wall 0.575s cpu 0.349s off-cpu 0.226s voluntary 1 involuntary 60: with three hogs and two CPUs, the scheduler preempted the job about 60 times and it spent 0.226 s waiting in the ready queue. That 0.226 s is its waiting time, measured by the definition above.

FCFS, SJF and SRTF on one worked example

We use one process set for every algorithm in this chapter. Times are in ms and the jobs never do I/O.

Process Arrival Burst
P1 0 8
P2 1 4
P3 2 9
P4 3 5

The total work is 8 + 4 + 9 + 5 = 26 ms and the CPU is never idle, so every schedule ends at time 26.

First-come, first-served

FCFS runs jobs in arrival order to completion. P1 runs 0 to 8. P2 runs 8 to 12, P3 runs 12 to 21, P4 runs 21 to 26. Waiting time is start minus arrival here: P1 0, P2 8 - 1 = 7, P3 12 - 2 = 10, P4 21 - 3 = 18. The average is (0 + 7 + 10 + 18) / 4 = 35 / 4 = 8.75 ms. FCFS is non-preemptive and trivially fair, but suffers the convoy effect: short jobs queue behind one long job, like P2 stuck behind P1.

Shortest-job-first (non-preemptive)

SJF picks, whenever the CPU frees up, the ready job with the shortest next CPU burst. At time 0 only P1 is there, so it runs 0 to 8. At time 8 the ready jobs are P2 (4), P3 (9) and P4 (5): P2 runs 8 to 12, then P4 (5) runs 12 to 17, then P3 runs 17 to 26. Waiting: P1 0, P2 7, P4 12 - 3 = 9, P3 17 - 2 = 15. Average (0 + 7 + 9 + 15) / 4 = 31 / 4 = 7.75 ms.

Shortest-remaining-time-first (preemptive SJF)

SRTF re-decides whenever a job arrives: if the newcomer's burst is shorter than the remaining time of the running job, preempt. P1 starts at 0. At time 1, P2 arrives with burst 4, shorter than P1's remaining 7, so P2 preempts. P2 runs 1 to 5 (P3 arrives at 2 with 9 and P4 at 3 with 5, but P2's remaining 3 and then 2 beats both). At time 5 the ready jobs have remaining times P1 7, P3 9, P4 5, so P4 runs 5 to 10. Then P1 (7) runs 10 to 17 and P3 (9) runs 17 to 26.

Because P1 was preempted, waiting time is no longer "start minus arrival"; use the general formula waiting = completion - arrival - burst. Completion times are P1 17, P2 5, P3 26, P4 10. So waiting is P1 17 - 0 - 8 = 9, P2 5 - 1 - 4 = 0, P3 26 - 2 - 9 = 15, P4 10 - 3 - 5 = 2. The average is (9 + 0 + 15 + 2) / 4 = 26 / 4 = 6.5 ms.

Here is the full comparison. Turnaround is completion minus arrival and response is first-run minus arrival.

Algorithm Avg waiting Avg turnaround Avg response Completion order
FCFS 8.75 15.25 8.75 P1, P2, P3, P4
SJF 7.75 14.25 7.75 P1, P2, P4, P3
SRTF 6.50 13.00 4.25 P2, P4, P1, P3

Per process, FCFS gives turnaround 8, 11, 19, 23 (sum 61); SJF gives 8, 11, 24, 14 (sum 57); SRTF gives 17, 4, 24, 7 (sum 52). Average turnaround is the average waiting time plus the average burst, 26 / 4 = 6.5, which is why the two columns move together: 8.75 + 6.5 = 15.25, 7.75 + 6.5 = 14.25, 6.5 + 6.5 = 13.0.

SRTF is optimal for average waiting time

Among all schedulers that know each job's CPU burst in advance, SRTF achieves the minimum possible average waiting time (non-preemptive SJF is optimal among non-preemptive ones). Sketch of the proof: if a longer job runs before a shorter one, swapping them reduces the shorter job's wait by more than it increases the longer job's, so any schedule with such an inversion can be improved.

The catch: nobody knows the next burst

SJF and SRTF need the length of the next CPU burst, which the OS cannot know. The standard fix is to predict it from history with an exponential average. Let t(n) be the measured length of the nth burst and τ(n) the prediction for it. Then

τ(n+1) = α · t(n) + (1 - α) · τ(n),      0 ≤ α ≤ 1

With α = 0 history is ignored and the prediction never changes; with α = 1 only the last burst counts; α = 1/2 weighs recent and past equally. Expanding the recurrence shows that older bursts carry geometrically smaller weights, hence "exponential". The other problem with SJF and SRTF is starvation: a steady stream of short jobs can keep a long job waiting indefinitely.

Round robin and priority scheduling

Round robin

Round robin (RR) is FCFS plus preemption by the timer. Each job gets at most one time quantum q on the CPU, then goes to the back of the ready queue. We trace RR with q = 4 on the same set. One convention matters: when a new arrival and a preempted job reach the queue at the same instant, the new arrival goes first.

P1 runs 0 to 4 (4 left); during that time P2, P3, P4 arrive, so the queue is P2, P3, P4, P1. P2 runs 4 to 8 and finishes (its burst is exactly 4). P3 runs 8 to 12 (5 left), P4 runs 12 to 16 (1 left), P1 runs 16 to 20 and finishes. Then P3 runs 20 to 24 (1 left), P4 runs 24 to 25 and finishes, and P3 runs 25 to 26.

Process Completion Turnaround Waiting Response
P1 20 20 12 0
P2 8 7 3 3
P3 26 24 15 6
P4 25 22 17 9
Average 18.25 11.75 4.5

RR is worst here on average waiting (11.75 versus 6.5 for SRTF) but its response is much better than FCFS (4.5 versus 8.75), and its answer for a newcomer is bounded: with n ready jobs and quantum q, nobody waits more than (n - 1) · q before getting the CPU.

Choosing q is a trade-off. If q is huge, RR becomes FCFS. If q is tiny, you spend the time on context switches. If a switch costs c, the fraction of the CPU wasted is c / (q + c). With c = 0.1 ms and q = 10 ms the overhead is 0.1 / 10.1 = 0.99 percent; with q = 1 ms it is 0.1 / 1.1 = 9.1 percent. A good rule of thumb is that q should be longer than about 80 percent of CPU bursts, so most jobs finish their burst before being preempted. Typical values are 10 to 100 ms.

Smaller quantum does not mean shorter turnaround

Student intuition says "more sharing means better". In fact for jobs of similar length RR with a small quantum delays everyone's completion, because all jobs finish near the end. Try q = 1 on the example set: average waiting is 12.5, not an improvement over q = 4, and you pay for 23 extra switches. RR optimizes response, not turnaround.

Priority scheduling and aging

In priority scheduling each job carries a number and the CPU goes to the highest priority (by convention here, a smaller number means more urgent in some systems and larger in others; always check). SJF is priority scheduling where the priority is the predicted burst. Priorities can be set by the OS (CPU-burst history, memory needs) or externally (the nice command, the importance of the owner). It can be preemptive or not, and it has the same starvation problem as SJF. The remedy is aging: gradually raise the priority of a job the longer it waits, so that even the lowest priority job eventually runs. Priority also interacts with locks: a high-priority thread blocked on a lock held by a low-priority one is the priority inversion problem we study in Week 5.

Multilevel feedback queues

SRTF would be ideal but needs a crystal ball; RR is fair but ignores that some jobs are short. A multilevel feedback queue (MLFQ) learns from behaviour instead of predictions. It was used in the CTSS time-sharing system in 1962 and its descendants run in many Unix variants, Windows and macOS. The rules (following Arpaci-Dusseau) are:

  1. There are several queues, each at a different priority; the scheduler always runs a job from the highest non-empty queue.
  2. Jobs in the same queue are scheduled round robin, and each queue has its own quantum (short at the top, longer lower down).
  3. A new job enters the top queue.
  4. A job that uses its whole quantum is demoted one queue. A job that blocks for I/O before its quantum ends stays where it is.
  5. Periodically, every job is boosted to the top queue (priority boost) so long jobs cannot starve, and jobs that change from CPU-bound to interactive are noticed.

The idea: interactive jobs have short bursts, so they never use the full quantum and remain at the top; CPU-bound jobs use up quanta, drift down and run only when the interactive ones are idle. The scheduler approximates SJF without knowing burst lengths. Let us trace our process set with three queues: Q0 with q = 2, Q1 with q = 4 and Q2 using FCFS (run to completion). The boost period is 100 ms, longer than the whole trace, so it never fires.

Walk through it. P1 runs 0 to 2 in Q0, uses its quantum (6 ms left) and drops to Q1. P2, P3 and P4, which arrived at 1, 2 and 3, each run 2 ms in Q0 (times 2 to 8). None of them is finished, so all drop to Q1, whose queue is now P1, P2, P3, P4. Q1 runs P1 8 to 12 (it uses all 4 ms, 2 left, drop to Q2), then P2 12 to 14 (its last 2 ms, done), P3 14 to 18 (full quantum, 3 left, drop to Q2), P4 18 to 21 (only 3 left, done). Q2 then runs P1 21 to 23 (done) and P3 23 to 26 (done).

Process Completion Turnaround Waiting Response
P1 23 23 15 0
P2 14 13 9 1
P3 26 24 15 2
P4 21 18 13 3
Average 19.5 13.0 1.5

MLFQ has the worst average waiting time of all five algorithms (13.0) but the best response (1.5): every job starts within 3 ms. That is the trade-off it was built for. In a real system long-running jobs would be in the same state as P1 and P3, running at the bottom whenever nothing interactive is ready. The table below puts all five side by side.

Algorithm Avg waiting Avg turnaround Avg response Preemptive Starvation
FCFS 8.75 15.25 8.75 No No
SJF 7.75 14.25 7.75 No Yes (long jobs)
SRTF 6.50 13.00 4.25 Yes Yes (long jobs)
RR, q = 4 11.75 18.25 4.50 Yes No
MLFQ (2, 4, FCFS) 13.00 19.50 1.50 Yes Without boost

Gaming the scheduler

A job that knows rule 4 can issue a trivial I/O request just before its quantum ends and so stay in the top queue forever, monopolising the CPU. The fix is to account for the total CPU time a job uses at a level (an allotment) instead of resetting at each I/O. This is why real MLFQs keep an allotment per level, not just a quantum.

Scheduling in Linux

CFS: fairness as the goal

Linux's default scheduler for ordinary tasks (policy SCHED_OTHER, also called SCHED_NORMAL) was, from kernel 2.6.23 until 6.5, the Completely Fair Scheduler (CFS). Its goal is an "ideal" CPU that runs all n runnable tasks at once, each at 1/n of the speed. Since real hardware can run one task at a time per core, CFS tracks how far each task has fallen behind that ideal and always runs the one that has received the least.

Two ideas make this concrete. Every nice value from -20 to 19 maps to a weight; nice 0 has weight 1024 and each step changes it by a factor of about 1.25. A few entries: nice -5 is 3121, nice 0 is 1024, nice 1 is 820, nice 5 is 335, nice 10 is 110, nice 19 is 15. A task's share of the CPU is its weight divided by the total weight of all runnable tasks on that CPU. Second, each task has a virtual runtime (vruntime) that advances only while the task runs, and advances more slowly for heavier tasks:

vruntime += delta_exec × (1024 / weight)      share = weight / (sum of all weights)

CFS always runs the task with the smallest vruntime. Since heavy tasks accumulate vruntime slowly, they stay at the left of the line for longer and receive more real time. The kernel keeps runnable tasks in a red-black tree (a balanced binary search tree) ordered by vruntime; picking the leftmost node and inserting back are O(log n). A task that wakes after sleeping is placed near the current minimum vruntime, so a long sleeper cannot demand a huge catch-up burst. The target period over which every task runs once is 6 ms by default and the minimum slice is 0.75 ms (both scale up with the CPU count); with many tasks the period stretches so slices never drop below that minimum.

This toy program implements the rule with three tasks and a scan instead of a tree. Task A and B have nice 0 (weight 1024) and C has nice 5 (335). It simulates 2383 ms, the sum of the three weights, so the expected shares are exactly 1024, 1024 and 335 ms.

/* cfs.c: a toy CFS. Always run the task with the smallest virtual runtime. */
#include <stdio.h>

struct task { const char *name; int nice; double weight; double vruntime; int ran_ms; };

int main(void) {
    struct task t[3] = {
        { "A", 0, 1024, 0, 0 },     /* weight of nice 0 is 1024 */
        { "B", 0, 1024, 0, 0 },
        { "C", 5,  335, 0, 0 },     /* nice 5 has weight 335    */
    };
    const int N = 3, TOTAL_MS = 2383;           /* 2383 = 1024 + 1024 + 335 */

    for (int ms = 0; ms < TOTAL_MS; ms++) {
        int pick = 0;
        for (int i = 1; i < N; i++)             /* the kernel uses a red-black tree;  */
            if (t[i].vruntime < t[pick].vruntime) pick = i;   /* a scan is enough here */
        t[pick].ran_ms++;
        t[pick].vruntime += 1.0 * 1024.0 / t[pick].weight;   /* delta_exec * 1024 / weight */
        if (ms < 8)
            printf("ms %d: run %s  (vruntime now %.3f)\n", ms, t[pick].name, t[pick].vruntime);
    }
    for (int i = 0; i < N; i++)
        printf("%s nice %d weight %4.0f ran %4d ms = %.1f%%  vruntime %.1f\n",
               t[i].name, t[i].nice, t[i].weight, t[i].ran_ms,
               100.0 * t[i].ran_ms / TOTAL_MS, t[i].vruntime);
    return 0;
}

Notice the last column: all three tasks end with the same vruntime of 1024. That is what "fair" means to CFS. You can see the effect on a real system too. The next program starts two CPU hogs pinned to CPU 0, one at nice 0 and one at nice 5, and counts loop iterations in 4 seconds. The prediction from the weights is a ratio of 1024 / 335 = 3.06.

/* niceburn.c: two CPU hogs share one CPU; the nicer one gets a smaller share. */
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static void burn(int nice_value, int seconds) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(0, &set);
    sched_setaffinity(0, sizeof set, &set);        /* both hogs on CPU 0 */
    setpriority(PRIO_PROCESS, 0, nice_value);      /* 0 = this process */

    struct timespec t0, t;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    unsigned long long loops = 0;
    do {
        for (int i = 0; i < 100000; i++) loops++;
        clock_gettime(CLOCK_MONOTONIC, &t);
    } while (t.tv_sec - t0.tv_sec < seconds);
    printf("nice %2d: %llu million loops\n", nice_value, loops / 1000000);
    exit(0);
}

int main(void) {
    if (fork() == 0) burn(0, 4);
    if (fork() == 0) burn(5, 4);
    wait(NULL);
    wait(NULL);
    return 0;
}

One run on our two-CPU test machine printed nice 0: 4318 million loops and nice 5: 1410 million loops. The ratio is 4318 / 1410 = 3.06 and the shares are 75.4 and 24.6 percent, matching the weights 1024 / 1359 = 75.4 percent and 335 / 1359 = 24.6 percent. (The exact counts differ per machine and run; the ratio does not.) Lowering your priority with nice therefore gives a precisely calculable, not a vague, reduction.

From CFS to EEVDF

Linux 6.6 (October 2023) replaced the CFS picking rule with EEVDF (Earliest Eligible Virtual Deadline First), based on a 1995 paper by Stoica and Abdel-Wahab. It keeps weights and virtual time, but each task also has a lag (how much service it is owed) and a virtual deadline derived from its requested slice, so latency-sensitive tasks with short slices are picked sooner without heuristics. Everything in this section about weights, nice values and proportional shares still holds.

Real-time classes

Not every task wants fairness; some want deadlines. A hard real-time system must never miss a deadline (an airbag controller). A soft real-time system tolerates occasional misses (video playback). Linux offers three real-time policies that always beat SCHED_OTHER tasks: SCHED_FIFO (fixed priority 1 to 99, runs until it blocks or a higher priority task arrives), SCHED_RR (the same plus round robin among equal priorities) and SCHED_DEADLINE (declare runtime, deadline and period; scheduled by EDF). The kernel limits real-time tasks to 95 percent of each second by default (sched_rt_runtime_us = 950000 of a sched_rt_period_us of 1000000), so a runaway real-time loop cannot freeze the machine. This program prints the policy facts and tries to enter the real-time class (it needs root or a suitable rlimit; it returns to normal scheduling at once):

/* policy.c: show scheduling policies and try to enter the real-time FIFO class. */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>

static const char *name(int p) {
    switch (p) {
    case SCHED_OTHER: return "SCHED_OTHER (CFS/EEVDF)";
    case SCHED_FIFO:  return "SCHED_FIFO";
    case SCHED_RR:    return "SCHED_RR";
    case SCHED_BATCH: return "SCHED_BATCH";
    case SCHED_IDLE:  return "SCHED_IDLE";
    default:          return "other";
    }
}

int main(void) {
    printf("current policy: %s\n", name(sched_getscheduler(0)));
    printf("SCHED_FIFO priorities: %d..%d\n",
           sched_get_priority_min(SCHED_FIFO), sched_get_priority_max(SCHED_FIFO));
    printf("SCHED_OTHER priorities: %d..%d\n",
           sched_get_priority_min(SCHED_OTHER), sched_get_priority_max(SCHED_OTHER));

    struct sched_param sp = { .sched_priority = 10 };
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == 0) {
        printf("now running as: %s, priority 10\n", name(sched_getscheduler(0)));
        sched_setscheduler(0, SCHED_RR, &sp);
        struct timespec ts;
        sched_rr_get_interval(0, &ts);
        printf("SCHED_RR quantum: %ld ms\n", ts.tv_nsec / 1000000);
        sp.sched_priority = 0;
        sched_setscheduler(0, SCHED_OTHER, &sp);      /* go back at once */
    } else {
        printf("SCHED_FIFO refused: %s\n", strerror(errno));
    }
    return 0;
}

(As an ordinary user the fourth line is replaced by SCHED_FIFO refused: Operation not permitted, and the fifth line is not printed.)

For periodic tasks with period T and execution time C, the utilization is U = Σ C/T. Two classic algorithms decide whether a set is schedulable. Rate-monotonic (RM) gives a fixed priority by period: shorter period, higher priority. Liu and Layland proved in 1973 that n periodic tasks are always schedulable under RM if U ≤ n · (2^(1/n) - 1). The bound is 1.0 for n = 1, 0.8284 for n = 2, 0.7798 for n = 3 and approaches ln 2 = 0.6931 for large n. It is sufficient, not necessary: above it, some sets still work. Earliest-deadline-first (EDF) is dynamic: always run the job whose absolute deadline is nearest. For tasks whose deadline equals the period, EDF is optimal on a single CPU: the set is schedulable if and only if U ≤ 1.

Take T1 with C = 25 ms, T = 50 ms and T2 with C = 35 ms, T = 80 ms. Then U = 25/50 + 35/80 = 0.5 + 0.4375 = 0.9375, above the RM bound of 0.8284 for two tasks, so RM may fail. This script checks both:

"""Rate-monotonic versus EDF on two periodic tasks (time in ms)."""
tasks = [("T1", 25, 50), ("T2", 35, 80)]      # (name, execution time C, period T = deadline)
HORIZON = 160

def simulate(policy):
    remaining = {n: 0 for n, _, _ in tasks}
    deadline = {n: 0 for n, _, _ in tasks}
    timeline, misses = [], []
    for t in range(HORIZON):
        for n, c, p in tasks:
            if t % p == 0:
                if remaining[n] > 0:                       # previous job unfinished
                    misses.append((n, t))
                remaining[n], deadline[n] = c, t + p
        ready = [n for n in remaining if remaining[n] > 0]
        if not ready:
            timeline.append("."); continue
        if policy == "RM":
            pick = min(ready, key=lambda n: dict((x, p) for x, _, p in tasks)[n])
        else:
            pick = min(ready, key=lambda n: deadline[n])
        remaining[pick] -= 1
        timeline.append(pick[1])
    return "".join(timeline), misses

u = sum(c / p for _, c, p in tasks)
bound = len(tasks) * (2 ** (1 / len(tasks)) - 1)
print(f"U = {u:.4f}, RM bound for n={len(tasks)} is {bound:.4f}, EDF bound is 1.0")
for pol in ("RM", "EDF"):
    line, misses = simulate(pol)
    runs, i = [], 0
    while i < len(line):
        j = i
        while j < len(line) and line[j] == line[i]: j += 1
        runs.append(f"{line[i]}[{i}-{j}]"); i = j
    print(pol, " ".join(runs), "| missed:", misses or "none")

U = 0.9375, RM bound for n=2 is 0.8284, EDF bound is 1.0
RM 1[0-25] 2[25-50] 1[50-75] 2[75-100] 1[100-125] 2[125-140] .[140-150] 1[150-160] | missed: [('T2', 80)]
EDF 1[0-25] 2[25-60] 1[60-85] 2[85-100] 1[100-125] 2[125-145] .[145-150] 1[150-160] | missed: none

In the output, 1 and 2 mean T1 and T2 and a dot means idle. Under RM, T1 (shorter period) always preempts. T2 gets 25 to 50 (25 ms) and 75 to 80 (5 ms) before its first deadline at 80, a total of 30 ms, 5 ms short of the 35 it needs, so it misses. Under EDF, T2's deadline (80) is earlier than T1's second deadline (100), so T2 keeps running from 25 to 60 and finishes in time.

Multiprocessors and affinity

With several CPUs, Linux keeps a separate ready queue per CPU, because one shared queue would be a contention bottleneck and would destroy cache locality. A load balancer periodically moves tasks from busy CPUs to idle ones. Because a task that migrates loses its warm cache, the kernel prefers to keep tasks where they were (soft affinity) and lets you demand it (hard affinity, taskset or sched_setaffinity, as niceburn did). The tools to inspect all this from the shell are one-liners:

chrt -p $$                                # policy and priority of this shell
taskset -cp $$                            # CPUs the shell is allowed to use
nice -n 10 sh -c 'ps -o pid,ni,cls,comm -p $$'   # run a child at nice 10 and show it

pid 565's current scheduling policy: SCHED_OTHER
pid 565's current scheduling priority: 0
pid 565's current affinity list: 0,1
  PID  NI CLS COMMAND
  568  10  TS sh

The column CLS is the scheduling class (TS is time sharing, that is SCHED_OTHER, FF is FIFO, RR is round robin) and NI is the nice value.

Exercises

Exercise 4.1warm-up

The convoy effect

Three jobs all arrive at time 0 with CPU bursts P1 = 24, P2 = 3, P3 = 3. Compute the average waiting and turnaround times under FCFS in the order P1, P2, P3, and under SJF.

Show solution

FCFS: P1 runs 0 to 24, P2 24 to 27, P3 27 to 30. Waiting times are 0, 24, 27, average 51 / 3 = 17. Turnaround times are 24, 27, 30, average 81 / 3 = 27. SJF runs P2 0 to 3, P3 3 to 6, P1 6 to 30. Waiting times are P2 0, P3 3, P1 6, average 9 / 3 = 3. Turnaround times 3, 6, 30, average 39 / 3 = 13. The short jobs stuck behind the long one in FCFS is the convoy effect, and it costs a factor of almost six in average waiting time.

Exercise 4.2core

SJF versus SRTF

Processes (arrival, burst): P1 (0, 7), P2 (2, 4), P3 (4, 1), P4 (5, 4). Draw the Gantt chart for non-preemptive SJF and for SRTF and compute the average waiting time for each.

Show solution

SJF: P1 runs 0 to 7 (the only job when it started). At time 7 the ready jobs are P2 (4), P3 (1), P4 (4), so P3 runs 7 to 8, then P2 (tie with P4, earlier arrival) runs 8 to 12, and P4 runs 12 to 16. Waiting: P1 0, P2 8 - 2 = 6, P3 7 - 4 = 3, P4 12 - 5 = 7. Average 16 / 4 = 4.00.

SRTF: P1 runs 0 to 2. At 2, P2 arrives with burst 4 against P1's remaining 5, so P2 preempts and runs 2 to 4. At 4, P3 arrives with burst 1 against P2's remaining 2, so P3 runs 4 to 5. At 5, P4 arrives; the remaining times are P2 2, P4 4, P1 5, so P2 runs 5 to 7, P4 runs 7 to 11, P1 runs 11 to 16. Completion times: P1 16, P2 7, P3 5, P4 11. Waiting = completion - arrival - burst: P1 9, P2 1, P3 0, P4 2. Average 12 / 4 = 3.00. SRTF is better (3.00 versus 4.00), as the optimality result says.

Exercise 4.3core

Round robin with q = 2

Using the chapter's process set (arrivals 0, 1, 2, 3; bursts 8, 4, 9, 5) and a quantum of 2 ms, compute the average waiting time and average response time under round robin. Break ties so that a new arrival enters the queue before a preempted job.

Show solution

Gantt: P1 0-2, P2 2-4, P3 4-6, P1 6-8, P4 8-10, P2 10-12, P3 12-14, P1 14-16, P4 16-18, P3 18-20, P1 20-22, P4 22-23, P3 23-26. Completion: P1 22, P2 12, P3 26, P4 23. Waiting = completion - arrival - burst: P1 14, P2 7, P3 15, P4 15, sum 51, average 12.75 ms. Response (first run minus arrival): P1 0, P2 1, P3 2, P4 5, sum 8, average 2.0 ms. Compared with q = 4, response is better (2.0 versus 4.5) and waiting is slightly worse (12.75 versus 11.75), the trade-off you expect from a smaller quantum.

Exercise 4.4core

Predicting the next burst

A scheduler uses exponential averaging with α = 1/2 and an initial guess τ0 = 10 ms. The measured bursts are 6, 4, 6, 4 ms. Compute the successive predictions τ1 to τ4. What would the predictions be with α = 0 and with α = 1?

Show solution

τ1 = 0.5 · 6 + 0.5 · 10 = 8. τ2 = 0.5 · 4 + 0.5 · 8 = 6. τ3 = 0.5 · 6 + 0.5 · 6 = 6. τ4 = 0.5 · 4 + 0.5 · 6 = 5. With α = 0 every prediction stays at τ0 = 10 (history is ignored, the estimate never learns). With α = 1 each prediction equals the last measured burst: 6, 4, 6, 4. The α = 1/2 sequence 8, 6, 6, 5 tracks the average of about 5 ms while smoothing out the jitter.

Exercise 4.5core

CFS shares and vruntime

Two CPU-bound tasks share one CPU: X at nice 0 (weight 1024) and Y at nice -5 (weight 3121). (a) What fraction of the CPU does each receive, and how many ms of each in 100 ms? (b) By how much does each task's vruntime advance per ms of real running time? (c) When X has run for 1 ms, how long must Y have run for the vruntimes to be equal?

Show solution

(a) The total weight is 1024 + 3121 = 4145. X gets 1024 / 4145 = 24.7 percent and Y gets 3121 / 4145 = 75.3 percent, so in 100 ms X runs about 24.7 ms and Y about 75.3 ms. (b) vruntime advances by 1024 / weight per ms: X advances 1.0 and Y advances 1024 / 3121 = 0.328. (c) X's vruntime rises by 1.0 for its 1 ms. Y must run t ms with 0.328 · t = 1.0, so t = 3121 / 1024 = 3.05 ms. That is also the ratio of the shares, 75.3 / 24.7 = 3.05.

Exercise 4.6challenging

RM versus EDF on three tasks

Periodic tasks with (C, T) in ms, deadlines equal to periods: Set A: (1, 4), (2, 6), (1, 8). Set B: (1, 4), (2, 6), (3, 8). For each set compute U, apply the RM bound for n = 3 (0.7798) and the EDF bound, and for set B simulate RM from t = 0 to find any deadline miss.

Show solution

Set A: U = 1/4 + 2/6 + 1/8 = 0.25 + 0.3333 + 0.125 = 0.7083 ≤ 0.7798, so RM is guaranteed to work (and so is EDF). Set B: U = 0.25 + 0.3333 + 0.375 = 0.9583. This exceeds 0.7798, so the RM test is inconclusive, but 0.9583 ≤ 1 so EDF is guaranteed to work. Simulating RM for B (priorities T1 > T2 > T3 by period): T1 runs 0-1, T2 runs 1-3, T3 runs 3-4, T1 (second release at 4) runs 4-5, T3 runs 5-6, T2 (second release at 6) runs 6-8. At t = 8, T3 has received only 2 of its 3 ms but its deadline (8) has arrived, so RM misses T3's first deadline. Hence an RM bound failure is not always a miss (set A passes) but here it is, and EDF still schedules set B.

Exercise 4.7challenging

Defeating an MLFQ

In the MLFQ rules of this chapter, a job that blocks for I/O before its quantum expires stays in its queue. Describe how a CPU-bound job can exploit this to receive far more than its fair share, and give two changes to the rules that stop it.

Show solution

The job runs for almost its whole quantum (say 1.9 ms of a 2 ms quantum) and then issues a trivial I/O request such as a one-byte write. Because it blocked before the quantum ended it is never demoted, stays in Q0, and returns to the CPU almost immediately when the I/O completes, so it dominates the top queue while honest jobs wait below it. Two fixes: (1) account for CPU time cumulatively per level (an allotment), so that after the job has used, say, 2 ms in total at Q0 it is demoted no matter how often it blocks; (2) use the periodic priority boost together with allotments, so demotion is permanent until the boost. The first fix removes the incentive to game the quantum; the boost handles jobs whose behaviour changes.

Lab: a scheduling simulator

Assignment 1 builds your shell; this lab builds a tool you can check your hand traces against. The program below simulates FCFS, SJF, SRTF and round robin tick by tick on the chapter's process set and prints the Gantt chart and the three metrics. It uses one ms per tick, reads the policy from the command line, and shows how little code a policy needs once the framework exists. Save it as sched.c.

/* sched.c: tick-by-tick simulator for FCFS, SJF, SRTF and Round Robin. */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define N 4
#define MAXT 200

static const int arrival[N] = { 0, 1, 2, 3 };
static const int burst[N]   = { 8, 4, 9, 5 };

static int rem[N], first[N], done_at[N];
static int slot[MAXT];                 /* slot[t] = process running during [t, t+1), or -1 */

static int pick_shortest(const int *ready, int n) {
    int best = ready[0];
    for (int i = 1; i < n; i++)
        if (rem[ready[i]] < rem[best]) best = ready[i];   /* ties: earlier in queue */
    return best;
}

static int simulate(const char *policy, int quantum) {
    int fcfs = !strcmp(policy, "fcfs"), sjf = !strcmp(policy, "sjf");
    int srtf = !strcmp(policy, "srtf"), rr = !strcmp(policy, "rr");
    if (!(fcfs || sjf || srtf || rr)) return -1;

    int queue[64], head = 0, tail = 0;       /* ready queue (process indices) */
    int arrived[N] = { 0 }, finished = 0, cur = -1, used = 0, t = 0;
    for (int i = 0; i < N; i++) { rem[i] = burst[i]; first[i] = -1; }

    while (finished < N && t < MAXT) {
        for (int i = 0; i < N; i++)          /* admit arrivals before anything is re-queued */
            if (!arrived[i] && arrival[i] <= t) { arrived[i] = 1; queue[tail++] = i; }

        if (srtf && cur >= 0) { queue[tail++] = cur; cur = -1; }   /* re-decide every tick */
        if (cur < 0 && head < tail) {
            if (fcfs || rr) cur = queue[head++];
            else {                                                   /* sjf or srtf */
                int ready[N], n = 0;
                for (int k = head; k < tail; k++) ready[n++] = queue[k];
                cur = pick_shortest(ready, n);
                for (int k = head; k < tail; k++)                    /* remove cur from queue */
                    if (queue[k] == cur) {
                        memmove(&queue[k], &queue[k + 1], (tail - k - 1) * sizeof(int));
                        tail--;
                        break;
                    }
            }
            used = 0;
        }
        if (cur < 0) { slot[t++] = -1; continue; }                   /* CPU idle */

        if (first[cur] < 0) first[cur] = t;
        slot[t++] = cur;
        rem[cur]--; used++;
        if (rem[cur] == 0) { done_at[cur] = t; finished++; cur = -1; }
        else if (rr && used == quantum) {
            for (int i = 0; i < N; i++)      /* arrivals at time t join BEFORE the preempted job */
                if (!arrived[i] && arrival[i] <= t) { arrived[i] = 1; queue[tail++] = i; }
            queue[tail++] = cur; cur = -1;
        }
    }
    return t;
}

int main(int argc, char **argv) {
    const char *policy = argc > 1 ? argv[1] : "fcfs";
    int quantum = argc > 2 ? atoi(argv[2]) : 4;
    int end = simulate(policy, quantum);
    if (end < 0) { fprintf(stderr, "usage: %s fcfs|sjf|srtf|rr [quantum]\n", argv[0]); return 2; }

    printf("%s Gantt:", policy);
    for (int s = 0; s < end; ) {
        int e = s;
        while (e < end && slot[e] == slot[s]) e++;
        printf(" |P%d %d-%d", slot[s] + 1, s, e);
        s = e;
    }
    printf("|\n\n proc  arr  burst  done  turnaround  waiting  response\n");
    double tw = 0, tt = 0, tr = 0;
    for (int i = 0; i < N; i++) {
        int ta = done_at[i] - arrival[i], w = ta - burst[i], r = first[i] - arrival[i];
        printf("  P%d  %3d  %5d  %4d  %10d  %7d  %8d\n", i + 1, arrival[i], burst[i], done_at[i], ta, w, r);
        tw += w; tt += ta; tr += r;
    }
    printf("average turnaround %.2f, waiting %.2f, response %.2f\n", tt / N, tw / N, tr / N);
    return 0;
}

Common mistakes and debugging tips

Symptom Likely cause What to do
Waiting time is computed as start minus arrival for a preempted job The formula only works if a job runs once without interruption Use waiting = completion - arrival - burst; it is always right when there is no I/O
Average waiting and turnaround do not differ by the average burst Arithmetic error in one process, or wrong completion time Check that Σ turnaround - Σ waiting = Σ burst for the set (26 in our example)
RR trace gives a different order from the answer key Tie-breaking between a new arrival and a preempted job State your convention (arrivals first is the textbook one) and apply it consistently
SRTF trace never preempts Compared the newcomer with the running job's full burst, not its remaining time Always compare with remaining time at the moment of arrival
Gantt chart has idle gaps that should not exist Forgot jobs that arrived while another was running Rebuild the ready set at each decision point from arrivals up to that time
nice seems to have no effect Machine is idle, or the tasks are on different CPUs Pin both with taskset -c 0; niceness matters only under contention
sched_setscheduler returns EPERM Real-time policies need CAP_SYS_NICE or an rlimit Run as root or raise RLIMIT_RTPRIO for an experiment; never leave a spinning real-time task running

Key takeaways

Key takeaways

  • Waiting = turnaround - burst and turnaround = completion - arrival; response = first run - arrival. The general formula for waiting also works for preempted jobs.
  • On our process set the average waiting times are FCFS 8.75, SJF 7.75, SRTF 6.5 and RR (q = 4) 11.75; SRTF is optimal for waiting time but requires knowing future bursts, which are only predicted.
  • Round robin buys response time with extra waiting and context switches; the quantum should exceed most CPU bursts while staying small enough for interactivity.
  • MLFQ approximates SJF by demoting jobs that use full quanta; it needs allotments and priority boosts to resist gaming and starvation.
  • Linux CFS gives each runnable task a CPU share equal to weight / total weight and always runs the smallest vruntime; nice 0 to nice 5 is a ratio of 1024 to 335, about 3 to 1.
  • Real-time scheduling is about deadlines: RM guarantees U ≤ n(2^(1/n) - 1), EDF guarantees U ≤ 1.
