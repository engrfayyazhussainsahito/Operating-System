Introduction, OS Structure and System Calls

What an operating system is, how hardware protects it from programs, how programs ask it for services through system calls, and how its internals can be organised and booted.

Welcome to the course. Almost every program you have ever run, from a web browser to a ten-line script, depends on a layer of software it never mentions by name: the operating system. This week we answer three basic questions. What is an operating system for? How does it keep control of a computer that is running programs it did not write? And how does a program ask it for help? By the end you will have watched a real program talk to the Linux kernel and written your own programs that do so without any help from the C library.

Everything later in the course builds on these ideas. In Week 2 we study the process, the OS's central abstraction, and in Week 3 we add threads and communication. Scheduling, synchronisation, memory and file systems all follow, and each of them is implemented behind the system call boundary we meet today.

What is an operating system?

Think of a large hotel. Guests (programs) want rooms, meals and quiet. The hotel (the hardware) has a limited number of rooms and kitchens. The front desk and management (the operating system) decide who gets which room, make sure one guest cannot walk into another's room, and hide the messy details: a guest asks for breakfast and does not need to know how the kitchen is organised. That picture contains both roles of an OS.

Operating system

An operating system (OS) is the software that manages a computer's hardware resources on behalf of its users and programs, and provides them with a simpler, uniform interface to those resources. The kernel is the part of the OS that runs with full hardware privilege all the time; it is the core that other software calls into.

Resource manager

A computer has a finite CPU, finite memory, a few storage devices and a handful of network and display devices. Many programs want them at once. The OS acts as a resource manager: it allocates each resource, arbitrates conflicts and keeps account of usage. Its goals are usually in tension:

  • Efficiency: keep the expensive hardware busy (high CPU utilisation, high disk throughput).
  • Fairness: no program should be starved of a resource it is entitled to.
  • Protection: one program must not read, corrupt or crash another program or the OS itself.

Abstraction layer

Raw hardware is awkward. A disk is a sequence of numbered sectors that can fail in odd ways; a program wants named files that grow and shrink. A CPU is shared among dozens of programs; each program wants to believe it has the machine to itself. The OS provides abstractions: simple, idealised concepts built on top of messy hardware.

Hardware reality OS abstraction
CPU shared by many programs Process (a private virtual computer)
Physical RAM, fragmented and limited Virtual address space
Disk sectors and flash blocks Files and directories
Network card sending frames Sockets
Keyboard, mouse, printer, disk Device files, a uniform read/write interface

Kernel versus OS

People say "the OS" for different things. A Linux distribution includes the Linux kernel, the C library, shell, compilers, desktop and hundreds of utilities. Which of these is "the OS"? A practical rule: the kernel is the one program that always runs in the privileged hardware mode and is protected from everything else. System programs (a shell, ls, a window manager) are shipped with the OS but run as ordinary user programs. When this course says "the OS" without qualification it usually means the kernel and its services.

Why have a kernel at all?

Suppose every program drove the disk directly. Two programs could write to the same sector, and a buggy one could erase the file system. Putting one trusted piece of code in charge of the disk, and forcing everyone else to ask it politely, is what makes a shared computer safe and sensible.

A brief history

Operating systems evolved as hardware got cheaper and users wanted more from it.

  • No OS (1940s to early 1950s). Programmers booked the whole machine, loaded programs by hand and ran one job at a time.
  • Batch systems (1950s). A resident monitor automatically ran one job after another from a queue of punched cards. The CPU no longer waited for a human, but it still waited for slow I/O.
  • Multiprogramming and time-sharing (1960s). Keep several jobs in memory; when one waits for I/O, run another. Time-sharing switches so rapidly that each interactive user feels they own the machine. CTSS and Multics pioneered this.
  • Unix (1969 onwards). Ken Thompson and Dennis Ritchie at Bell Labs built a small, portable, time-sharing system, rewritten in C. Its ideas (files as byte streams, small tools, a shell, processes created with fork) still shape Linux, macOS and the BSDs.
  • Personal computers (1980s). MS-DOS, then Windows, Mac OS and the first Linux kernel (1991) brought operating systems to every desk.
  • Mobile, cloud and embedded (2000s onwards). Android and iOS on phones, virtual machines and containers in data centres, and tiny real-time kernels in cars and appliances.

Why C and Unix matter to you

Unix was one of the first operating systems written mostly in a high-level language, which made it portable. That is why this course uses C and the Linux/POSIX interface for its labs: the same concepts and system calls appear, with small differences, in almost every modern OS.

Hardware recap

You do not need to be a computer architect, but you must understand a few hardware features, because every OS idea this term exists either to exploit or to defend against one of them.

The CPU and its modes

The CPU fetches an instruction, executes it, and repeats. A program counter holds the address of the next instruction, and registers hold data. Most CPUs have at least two privilege modes, which we discuss fully in the next section. In user mode some instructions (halting the CPU, changing memory protection, talking directly to devices) are forbidden. In kernel mode (also called supervisor mode) everything is allowed.

Interrupts, traps and exceptions

A CPU that only ran instructions in a straight line would be useless for an OS, because it could never regain control from a program stuck in a loop. Hardware therefore provides ways to divert execution to the kernel.

  • An interrupt is an asynchronous signal from hardware: a keyboard press, a network packet arriving, a disk finishing a transfer, or the timer expiring. The CPU finishes the current instruction, saves its state, and jumps to an interrupt handler found through a table (the interrupt vector, called the IDT on x86).
  • A trap (or software interrupt) is a synchronous transfer caused deliberately by the running program, for example a system call instruction.
  • An exception or fault is a synchronous transfer caused by an error in the running instruction, such as division by zero, an illegal instruction or a page fault.

Terminology varies between books; what matters is the distinction between "caused by something outside the CPU, at any time" (interrupt) and "caused by the instruction being executed" (trap or exception).

What does an interrupt cost?

Suppose a network card raises 1000 interrupts per second and each handler takes 5 µs. CPU time spent is 1000 × 5 µs = 5 ms per second, which is 0.5% of one core. At 100 000 interrupts per second the same card would take 50% of a core, which is why high-speed devices use batching and DMA.

The timer

The timer is a hardware clock programmed by the OS to interrupt the CPU after a fixed interval. Because only the kernel may set it, the timer guarantees the kernel always gets control back, even from an infinite loop. It is the foundation of preemptive scheduling (Week 4).

I/O and DMA

Devices are slow compared with the CPU. In programmed I/O the CPU copies every byte between the device and memory, which wastes its time. With direct memory access (DMA) the OS tells a DMA controller the memory address, the length and the direction; the device then moves the whole block to or from memory by itself and raises one interrupt when finished. The CPU is free to run other code in the meantime.

The memory hierarchy

Fast memory is small and expensive; large memory is slow and cheap. Systems stack several levels so that, most of the time, data is found close to the CPU.

The hierarchy works because of locality: programs tend to reuse data they just used (temporal locality) and data near it (spatial locality). If a fraction h of accesses hit the cache, the average access time is

EAT = h × t_cache + (1 − h) × (t_cache + t_mem)

With h = 0.95, t_cache = 1 ns and t_mem = 100 ns, EAT = 1 + 0.05 × 100 = 6 ns. A 5% miss rate makes memory six times slower than the cache alone. We will reuse this style of calculation for the TLB and paging in Week 8 and Week 9.

Dual-mode operation and protection

To protect the kernel and other programs, the hardware distinguishes user mode from kernel mode using a mode bit in a CPU register. Normal application code runs in user mode. When an interrupt, trap or exception occurs, the hardware itself switches to kernel mode and starts executing kernel code at an address the kernel chose in advance. When the kernel is done, it executes a special return instruction that switches back to user mode.

Privileged instructions

An instruction is privileged if it can only run in kernel mode. Executing one in user mode raises an exception, and the kernel typically terminates the offending process. Typical privileged operations:

  • I/O instructions and access to device registers
  • Modifying memory-management registers (page-table base, protection settings)
  • Loading the timer, masking and unmasking interrupts
  • Halting the CPU and changing the mode bit directly

The mode bit alone is not enough. We also need memory protection (so a user program cannot overwrite kernel memory or another process), which uses base and limit registers or, in modern systems, paging (Week 8), and CPU protection (the timer). Together these three, dual mode, memory protection and the timer, let the kernel remain in charge.

Kernel mode is not just 'admin'

Do not confuse the hardware mode bit with the "root" user. Root is a software notion: a process owned by root still runs in user mode and must make system calls like any other. Only kernel code runs in kernel mode. Real x86 CPUs have four rings; operating systems in practice use two (ring 0 and ring 3).

System calls

A system call is the controlled entry into the kernel: the only way an ordinary program may ask for a privileged service such as opening a file, creating a process, allocating memory or sending a network message. It is a deliberate trap, so it combines the two ideas above: it switches to kernel mode, and it does so only at an entry point the kernel defined.

The path of a system call

What actually happens when your program calls write(1, "hi\n", 3)? Read the numbered steps in the figure alongside the explanation.

Key details:

  1. A number selects the service. The kernel keeps a system call table; the program passes an index (on x86-64 Linux, write is 1, getpid is 39).
  2. Parameters travel in registers (on x86-64 Linux: rdi, rsi, rdx, r10, r8, r9) or, for large data, in memory whose address is passed in a register. Passing a pointer is dangerous, so the kernel must validate every pointer and copy data across the boundary rather than trusting it.
  3. The return value comes back in a register. Linux returns a negative errno on failure, and the libc wrapper turns it into -1 plus the global errno.
  4. A system call is much more expensive than a function call: it saves and restores state, may flush parts of the pipeline, and runs kernel code. Typical cost is on the order of 100 ns to 1 µs, versus a few nanoseconds for a normal call. Hence the advice to make fewer, larger system calls, which our lab measures.

API versus system call

Programmers rarely issue system calls by hand. They use an application programming interface (API), a set of functions with documented behaviour. The two layers are different:

  • POSIX (Portable Operating System Interface) is a standard that defines an API: names such as open, read, fork and their behaviour. Any OS that implements POSIX can run the same source code.
  • System calls are the actual kernel entry points. Their numbers and conventions differ between kernels and even between CPU architectures.
  • The C library (libc) sits in between. Its wrapper functions (write, open) mostly just load registers and execute the trap instruction, but some library functions do much more: printf formats text into a user-space buffer and only calls write when the buffer is flushed. malloc calls brk or mmap occasionally, not on every allocation.

A library call is not necessarily a system call

printf, fopen, malloc and qsort are library functions. qsort never enters the kernel at all. printf may call write once for many printf calls (stdout is line-buffered on a terminal and fully buffered when redirected to a file). When you count system calls you must look at what the process really does, which is exactly what strace shows.

Observing the boundary with strace

strace is a Linux tool that runs a program and prints every system call it makes, its arguments and its return value. It is the best way to make the abstract boundary concrete. Take this program:

#include <stdio.h>

int main(void) {
    printf("Hello, OS!\n");
    return 0;
}

Compile and trace it:

gcc -Wall -o hello hello.c
strace ./hello

The output (abridged; addresses and the exact start-up calls vary by system) looks like this:

Most lines are the dynamic loader and C library setting themselves up; the line you care about is write(1, "Hello, OS!\n", 11) = 11. One printf became one write of 11 bytes to file descriptor 1 (standard output). Useful options:

strace -e trace=write ./hello      # show only write calls
strace -c ./hello                  # summary table: calls, errors, time
strace -f ./prog                   # also follow child processes
strace -o trace.txt ./prog         # save the trace to a file

Now the same output without the library. This program calls the system call directly through libc's generic syscall function:

#define _GNU_SOURCE
#include <sys/syscall.h>
#include <unistd.h>

int main(void) {
    const char msg[] = "via syscall()\n";
    long n = syscall(SYS_write, 1, msg, sizeof msg - 1);
    long pid = syscall(SYS_getpid);
    return (n > 0 && pid > 0) ? 0 : 1;
}

On x86-64 only, you can go one level lower and issue the trap instruction yourself with inline assembly. This shows there is no magic: the "call" is just registers plus one instruction.

/* x86-64 Linux only */
int main(void) {
    const char msg[] = "raw syscall instruction\n";
    long ret;
    __asm__ volatile (
        "syscall"
        : "=a"(ret)                                  /* result in rax */
        : "a"(1L), "D"(1L), "S"(msg),               /* rax=1 (write), rdi=1, rsi=msg */
          "d"(sizeof msg - 1)                        /* rdx = length */
        : "rcx", "r11", "memory");                   /* syscall clobbers these */
    return ret > 0 ? 0 : 1;
}

Operating system structures

How should the millions of lines of code in an OS be organised? Several designs are in use, each trading speed, safety, and ease of change.

Monolithic kernel

In a monolithic kernel (traditional Unix, Linux) all major services (scheduler, memory manager, file systems, drivers, networking) run in kernel mode in one address space. A call from the file system to a driver is an ordinary function call, which is fast. The price: a bug in any driver can crash the whole system, and the code base is huge and hard to reason about.

Layered

In a layered design the OS is built as levels, layer 0 the hardware and layer N the user interface, where each layer uses only the one below. Debugging is easy (verify layer by layer) but the layers are hard to define cleanly, and every request passes through many of them, so pure layering is rare. Layered thinking survives inside protocol stacks and I/O subsystems.

Microkernel

A microkernel (Mach, MINIX 3, QNX, seL4) keeps only the minimum in kernel mode: basic address-space management, scheduling and interprocess communication. File systems, drivers and network stacks run as ordinary user-mode servers and talk to clients by messages. A crashed driver can be restarted without a reboot, and the small trusted code base is easier to verify. The cost is performance: a request that is one function call in a monolithic kernel becomes several messages with mode switches and copies.

Modules, hybrids and unikernels

  • Loadable kernel modules. Linux stays monolithic but lets you load and unload code (a driver or a file system) at run time with insmod and rmmod, which gives some of the flexibility of a microkernel. The module still runs in kernel mode with full privilege.
  • Hybrid kernels. Windows NT and macOS (XNU, built on Mach and BSD) start from a microkernel design but run many services in kernel mode for speed. The result mixes ideas from both camps.
  • Unikernels. An application is linked together with only the OS library code it needs into a single specialised image that runs directly on a hypervisor, with no separation between "app" and "kernel". Images are tiny and boot in milliseconds, but there is one application per image and little isolation inside it.
Design Speed Robustness Extensibility Examples
Monolithic High Low (one bug can crash all) Modules Linux, BSD, classic Unix
Layered Medium Medium Hard to layer correctly THE system, protocol stacks
Microkernel Lower (IPC) High Easy (user servers) MINIX 3, QNX, seL4
Hybrid Medium to high Medium Medium Windows NT, macOS
Unikernel Very high, small Isolation by hypervisor One app per image MirageOS, IncludeOS

Policy versus mechanism

A useful design principle is to separate mechanism (how to do something, such as the timer interrupt and context switch) from policy (what to do, such as which process to run next). A microkernel pushes policy out to user space; even a monolithic kernel benefits from keeping the two apart, so a policy can change without rewriting the mechanism. We will see this again in scheduling.

Booting

When you press the power button, there is no operating system in RAM. How does one get there? This is the bootstrap problem.

  1. Firmware. Legacy BIOS or modern UEFI firmware, stored in non-volatile memory on the motherboard, runs first. It performs a power-on self-test (POST), initialises basic hardware, and finds a boot device. BIOS loads a tiny 512-byte boot sector (the master boot record); UEFI reads a bootloader file from a special FAT-formatted EFI System Partition and supports larger disks (GPT) and Secure Boot, which checks digital signatures on the bootloader and kernel.
  2. Bootloader. Programs such as GRUB or systemd-boot are too big for the first sector, so a staged loader brings them in. The bootloader shows a menu, loads the kernel image and, usually, an initial RAM file system (initramfs) containing drivers needed to reach the real disk, and jumps to the kernel.
  3. Kernel initialisation. The kernel switches to its full operating mode, sets up memory management and the interrupt table, starts the timer, detects and initialises devices, mounts the root file system, and creates the first user-mode process.
  4. User space. That first process (PID 1, init or systemd) starts system services and finally the login screen. From then on, the kernel mostly reacts: to system calls, interrupts and exceptions.

Part 2: write your own file reader and copier

First mycat.c, which prints a file using only open, read, write and close:

#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

#define BUFSZ 4096

int main(int argc, char *argv[]) {
    if (argc != 2) {
        const char usage[] = "usage: mycat FILE\n";
        write(2, usage, sizeof usage - 1);
        return 1;
    }
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        perror("open");
        return 1;
    }
    char buf[BUFSZ];
    ssize_t n;
    while ((n = read(fd, buf, sizeof buf)) > 0) {
        ssize_t off = 0;
        while (off < n) {                       /* write may be partial */
            ssize_t w = write(1, buf + off, (size_t)(n - off));
            if (w < 0) {
                perror("write");
                close(fd);
                return 1;
            }
            off += w;
        }
    }
    if (n < 0)
        perror("read");
    close(fd);
    return n < 0 ? 1 : 0;
}

Then mycp.c, a copier whose buffer size is chosen on the command line so you can measure its effect:

#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    if (argc < 3 || argc > 4) {
        fprintf(stderr, "usage: mycp SRC DST [BUFSIZE]\n");
        return 1;
    }
    size_t bufsz = (argc == 4) ? (size_t)atol(argv[3]) : 4096;
    if (bufsz == 0) {
        fprintf(stderr, "mycp: bad buffer size\n");
        return 1;
    }
    int in = open(argv[1], O_RDONLY);
    if (in < 0) { perror("open src"); return 1; }
    int out = open(argv[2], O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (out < 0) { perror("open dst"); close(in); return 1; }
    char *buf = malloc(bufsz);
    if (!buf) { perror("malloc"); return 1; }

    ssize_t n;
    while ((n = read(in, buf, bufsz)) > 0) {
        ssize_t off = 0;
        while (off < n) {
            ssize_t w = write(out, buf + off, (size_t)(n - off));
            if (w < 0) { perror("write"); return 1; }
            off += w;
        }
    }
    if (n < 0) perror("read");
    free(buf);
    close(in);
    close(out);
    return n < 0 ? 1 : 0;
}

Create a 1 MiB test file and trace both programs:

gcc -Wall -o mycat mycat.c
gcc -Wall -o mycp mycp.c
head -c 1048576 /dev/urandom > big.bin
strace -c ./mycp big.bin copy.bin 4096
strace -c ./mycp big.bin copy.bin 64
strace -c ./mycp big.bin copy.bin 65536
cmp big.bin copy.bin && echo identical

What to observe: with a 4096-byte buffer the summary shows 257 read calls and 256 write calls (256 full blocks, then one final read returning 0). With a 64-byte buffer there are 16 385 reads and 16 384 writes. With 65 536 bytes, only 17 reads and 16 writes. Also run strace -e trace=openat,read,write,close ./mycat /etc/hostname and match each line of output to a line in the source.

Extensions

  1. Time the three buffer sizes with time and plot or tabulate seconds against the number of system calls. At what buffer size do you stop seeing improvement, and why?
  2. Add a -n flag to mycat that numbers lines, still using only read and write (no printf), and check its syscall count with strace -c.
  3. Write a program that calls getpid one million times in a loop through the libc wrapper, and time it. Divide to estimate the cost of one system call on your machine, then compare with a loop calling an empty function.

Exercises

Exercise 1.1warm-up

System call or library call?

For each of the following, say whether it is normally a system call or an ordinary library function, and justify in one phrase: (a) read, (b) strlen, (c) fopen, (d) getpid, (e) qsort.

Show solution

(a) System call (a thin libc wrapper over the kernel entry read). (b) Library function: it only scans memory in user space. (c) Library function: it allocates a buffer in user space and calls the open system call underneath. (d) System call (the process ID is kernel data). (e) Library function: pure computation in user space, with no kernel involvement. The test is whether the operation needs a privileged service or kernel data.

Exercise 1.2warm-up

Privileged or not?

Which of these must be privileged instructions? (a) Compare the values of two registers. (b) Set the value of the timer. (c) Switch from kernel mode to user mode. (d) Disable all interrupts. (e) Add two registers. Explain briefly.

Show solution

(b), (c) and (d) must be privileged. If a user program could set the timer it could prevent the kernel from regaining control; if it could disable interrupts it could monopolise the CPU forever. Switching to user mode is done by the kernel's return-from-trap path; the reverse direction (user to kernel) is never a plain instruction but happens only through a trap. (a) and (e) are ordinary instructions that any program may use; they affect only the program's own registers.

Exercise 1.3core

Average memory access time

A CPU has a cache with access time 2 ns and main memory with access time 80 ns. On a cache miss the CPU first checks the cache (2 ns) and then goes to memory (80 ns). (a) Compute the average access time for hit ratios 90%, 98% and 99.9%. (b) What hit ratio is needed to keep the average below 4 ns?

Show solution

Use EAT = t_cache + (1 − h) × t_mem.

(a) h = 0.90: 2 + 0.10 × 80 = 10 ns. h = 0.98: 2 + 0.02 × 80 = 3.6 ns. h = 0.999: 2 + 0.001 × 80 = 2.08 ns.

(b) Need 2 + (1 − h) × 80 < 4, so (1 − h) < 2/80 = 0.025, giving h > 0.975, i.e. a hit ratio above 97.5%.

Exercise 1.4core

Interrupt load

A disk controller, using DMA, raises one interrupt for each completed 4 KiB block. The disk delivers 80 MiB/s. Each interrupt handler takes 10 µs. (a) How many interrupts per second? (b) What fraction of a CPU core is spent in the handlers? (c) How would the answer change if the device had no DMA and interrupted once per byte, with a 1 µs handler?

Show solution

(a) 80 MiB = 80 × 1024 × 1024 bytes = 83 886 080 bytes per second. Dividing by 4096 bytes per block gives 20 480 blocks, so 20 480 interrupts per second.

(b) 20 480 × 10 µs = 204 800 µs = 0.2048 s per second, about 20.5% of one core.

(c) Without DMA: 83 886 080 interrupts per second × 1 µs = 83.9 s of handler time per second, which is more than 83 cores' worth of time. This is impossible on a normal machine, which is exactly why DMA and block-sized interrupts exist.

Trace a system call

Using Figure 1.3, answer: (a) On x86-64 Linux, which register carries the system call number? (b) The program passes a pointer buf to write. Why must the kernel validate that pointer, and what could go wrong if it did not? (c) write returns -1 and errno is EBADF. At which step of the path is that decided, and who converts the kernel's result into -1?

Show solution

(a) rax. (b) The pointer was supplied by an untrusted user program. If the kernel dereferenced it blindly, a malicious program could pass an address inside the kernel (leaking or overwriting kernel data) or an invalid address (crashing the kernel). The kernel checks that the range lies in the caller's own address space and copies data across the boundary. (c) The kernel's sys_write (step 5) looks up descriptor 1 or whatever was passed, finds it is not open, and returns a negative error code (-EBADF). The libc wrapper (step 7) sees the negative value, stores its absolute value in errno, and returns -1.

Exercise 1.6core

Counting calls

A program copies a file of exactly 10 000 bytes using a loop of read(in, buf, 512) and write(out, buf, n). (a) How many read calls (including the final one that returns 0) and how many write calls does it make? (b) How many system calls in total if you add one open for each file and one close for each? (c) If the buffer were 4096 bytes instead, what are the totals?

Show solution

(a) 10 000 / 512 = 19.53, so there are 19 full reads of 512 bytes (9 728 bytes) and one partial read of 272 bytes: 20 data-returning reads, plus the final read returning 0, giving 21 reads and 20 writes.

(b) 21 + 20 + 2 opens + 2 closes = 45 system calls.

(c) 10 000 / 4096 = 2.44: 2 full reads and one partial of 1 808 bytes, so 3 data reads plus the final zero read = 4 reads and 3 writes; adding 4 for open/close gives 11 system calls. Larger buffers cut the call count by roughly 4× here.

Exercise 1.7core

Choosing a structure

Pick the most suitable OS structure for each system and justify it: (a) a general-purpose server that needs the highest I/O throughput, (b) a pacemaker controller where reliability and verifiability matter far more than speed, (c) a single-purpose network function that runs on a hypervisor and must boot in milliseconds.

Show solution

(a) Monolithic (with loadable modules, as in Linux): service-to-service calls are plain function calls with no message overhead. (b) Microkernel (for example a verified kernel such as seL4): the tiny trusted code base can be audited and a failing driver cannot corrupt the kernel. (c) Unikernel: the application and just the needed OS libraries form one small image, which boots very quickly; isolation comes from the hypervisor. Each answer trades speed, robustness, and size, as in the comparison table.

Exercise 1.8challenging

Why can't a program switch itself into kernel mode?

Imagine a CPU with a single instruction setmode k that any program may execute to enter kernel mode. (a) Show how this one instruction defeats all protection. (b) Explain how a real system call differs so that, although user code can trigger it, it does not have the same problem. (c) Why must the table of kernel entry addresses be writable only in kernel mode?

Show solution

(a) A malicious program would execute setmode k and then run its own code with full privilege: it could disable the timer, rewrite the page tables, read any process's memory, and overwrite the kernel. Mode and memory protection are meaningless if the program decides its own mode.

(b) The system call instruction does not let the program choose what runs in kernel mode. It always transfers control to a fixed address from a table that only the kernel could set up (a privileged act at boot). The program can only select which service number to request, and the kernel validates the arguments. The "door" is controlled by the kernel, so the privilege is rented, not given away.

(c) The system call instruction jumps to an address read from that table. If a user program could edit the table, it could point an entry at its own code, trigger a system call, and have its code run in kernel mode, which is exactly the problem in (a) again. Protecting the table (and the timer, and the page tables) is what keeps the entry points kernel-chosen.

Key takeaways

Key takeaways

  • An OS has two jobs: it manages resources (CPU, memory, storage, devices) fairly and efficiently, and it provides abstractions (processes, files, sockets) that hide hardware complexity.
  • The kernel is the privileged core of the OS; shells, utilities and libraries are system software that runs in user mode.
  • Hardware makes protection possible: the mode bit, privileged instructions, memory protection and the timer let the kernel stay in control, and interrupts, traps and exceptions are how control moves into it.
  • A system call is a controlled trap into the kernel: a number picks the service, arguments go in registers, the kernel validates them, and a result comes back. It costs far more than a function call, so use fewer, larger calls.
  • An API such as POSIX is a source-level contract; libc wrappers translate API calls into system calls, and some library functions (printf, malloc) mostly avoid the kernel. strace shows the truth.
  • OS structures trade speed against robustness: monolithic is fast, microkernel is isolated and verifiable, hybrids and modules compromise, and unikernels specialise.
  • Booting passes control from firmware (BIOS/UEFI) to a bootloader to the kernel to the first user process.
