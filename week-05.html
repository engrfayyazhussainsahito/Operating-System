Synchronization I

Why concurrent updates to shared data go wrong, how the critical section problem is defined, and the tools that solve it: atomic instructions, spinlocks, mutexes, semaphores and condition variables.

What you will be able to do

By the end of this week you will be able to:

  • Trace an interleaving of load, add and store instructions and compute the final value of a shared counter
  • State the three requirements of a critical section solution and decide which one a given protocol violates
  • Explain why Peterson's algorithm needs memory barriers on modern processors
  • Implement a spinlock with an atomic test-and-set or compare-and-swap operation and explain when spinning is the wrong choice
  • Describe how a semaphore works internally without busy waiting and use counting and binary semaphores correctly
  • Write correct POSIX code with mutexes, semaphores and condition variables, including the while-loop rule

In Week 3 you met threads: several flows of control inside one process that share the same heap, globals and open files. That sharing is what makes threads cheap to communicate, and it is also what makes them dangerous. In Week 4 the scheduler could pause any thread at almost any instruction and run another one. Put those two facts together and you get this week's topic: when the scheduler interrupts a thread in the middle of updating shared data, the next thread sees half-finished work.

This chapter builds the toolbox in layers. First we see the bug (a race condition) and name the problem it creates (the critical section problem). Then we look at the lowest-level solutions, atomic hardware instructions, and build locks from them. Finally we climb to the tools you will actually use every day: mutexes, semaphores and condition variables. Week 6 uses these tools to solve the classic problems, and Week 7 shows what happens when the tools themselves are used badly (deadlock).

Races and the critical section problem

Why a single line of C is not a single step

Consider two threads that each execute counter++ on a shared integer that starts at 5. You expect 7. Sometimes you get 6. The reason is that counter++ is not one machine step. A compiler turns it into three:

load  r1 <- counter      ; copy the value from memory into a register
add   r1 <- r1 + 1       ; increment the register
store counter <- r1      ; write the register back to memory

Registers belong to each thread (they are saved and restored on a context switch, see Week 2), but counter lives in shared memory. If thread T1 is interrupted after its load, thread T2 can load the same old value, and both then write back 6.

The shared whiteboard

Two clerks share a whiteboard showing the number of tickets left. Each clerk reads the number, walks to a desk, subtracts one, and walks back to write the new number. If both read "5" before either writes, both write "4" and a ticket has silently vanished. The bug is not in either clerk. It is in the gap between reading and writing.

Here is one bad interleaving, traced step by step.

Step Thread Instruction r1 (T1) r2 (T2) counter in memory
0 initial state 5
1 T1 load r1 <- counter 5 5
2 T2 load r2 <- counter 5 5 5
3 T1 add r1 <- r1 + 1 6 5 5
4 T2 add r2 <- r2 + 1 6 6 5
5 T1 store counter <- r1 6 6 6
6 T2 store counter <- r2 6 6 6

Two increments ran, the counter moved by one. This is a lost update.

Race condition

A race condition exists when the result of a computation depends on the relative timing or interleaving of operations by two or more threads, and at least one of them writes the shared data. In the C and C++ memory models an unsynchronized conflicting access is a data race, and a program containing one has undefined behaviour, not just an unlucky result.

Races are nasty because they are rare. With only two threads and a window of three instructions, most runs happen to interleave harmlessly, so tests pass and the bug ships. Of the 20 possible interleavings of two three-instruction sequences, only 2 (all of T1 before T2, or all of T2 before T1) give the right answer; the other 18 lose an update. The real machine is just very likely to pick one of the two good ones when the threads are short, and much less likely when they are long or run on different cores.

The critical section problem

The fix is to make the dangerous window indivisible with respect to other threads. We call a stretch of code that accesses shared data and must not be run by two threads at once a critical section. Every thread using shared data is structured like this:

do {
    entry section        // ask permission to enter
        critical section // touch shared data
    exit section         // announce that we are done
        remainder section // everything else
} while (true);

Figure 5.2 (listing). The general structure of a thread with a critical section.

A correct solution must satisfy three requirements.

The three requirements

Mutual exclusion: if one thread is executing in its critical section, no other thread may be executing in its critical section. Progress: if no thread is in its critical section and some threads want to enter, then only threads not in their remainder sections take part in deciding who goes next, and that decision cannot be postponed forever. Bounded waiting: there is a bound on the number of times other threads may enter their critical sections after a thread has asked to enter and before that request is granted. Nobody starves.

A solution must also make no assumption about relative speeds or the number of processors. Mutual exclusion is the one everybody remembers, but progress and bounded waiting are what separate a real lock from a trick. The simplest "obvious" scheme shows why. Suppose two threads share a variable turn and each waits for its own turn:

/* Thread 0 */                    /* Thread 1 */
while (turn != 0) ;               while (turn != 1) ;
/* critical section */            /* critical section */
turn = 1;                         turn = 0;

This guarantees mutual exclusion, but it forces strict alternation: if thread 0 finishes and then spends an hour in its remainder section, thread 1 cannot enter twice in a row. A thread in its remainder section is blocking a thread that wants in, which violates progress.

Peterson's algorithm

In 1981 Gary Peterson published a software-only solution for two threads (numbered 0 and 1) that satisfies all three requirements. Each thread announces its interest in a flag and then politely gives the other thread priority via turn.

#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

static atomic_int flag[2];   /* flag[i] = 1 means thread i wants to enter */
static atomic_int turn;      /* whose turn it is to wait */
static long counter = 0;

static void lock(int me) {
    int other = 1 - me;
    atomic_store(&flag[me], 1);      /* I want in */
    atomic_store(&turn, other);      /* but you go first if we collide */
    while (atomic_load(&flag[other]) && atomic_load(&turn) == other)
        ;                            /* wait */
}
static void unlock(int me) { atomic_store(&flag[me], 0); }

static void *worker(void *arg) {
    int me = (int)(long)arg;
    for (int i = 0; i < 200000; i++) {
        lock(me);
        counter++;
        unlock(me);
    }
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, worker, (void *)0L);
    pthread_create(&b, NULL, worker, (void *)1L);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("counter = %ld (expected 400000)\n", counter);
    return 0;
}

Compile with gcc -O2 -pthread peterson.c. If both threads set their flags at the same time, whichever thread writes turn last loses and waits. If only one thread is interested, the other's flag is 0 and the loop exits immediately, which is why progress holds. Because a waiting thread must see the other leave before it can enter, and the other will give the turn away on re-entry, bounded waiting holds with a bound of one.

Notice the declarations: the shared variables are atomic_int, and the stores and loads use the default sequentially consistent ordering. That is not decoration. If you rewrite this with plain int variables, the program is broken on modern hardware, for two reasons. First, the compiler is allowed to reorder or even delete the plain stores and loads, since in a single-threaded view they look independent. Second, even if the compiler behaves, the processor does not execute memory operations in program order. Almost every modern CPU has a store buffer: a store is parked in a queue and becomes visible to other cores a little later, while a later load can overtake it. In Peterson's algorithm, a thread stores flag[me] and then loads flag[other]. If the store sits in the buffer while the load runs, both threads can read the other's flag as 0 and both enter the critical section. On x86 this store-then-load reordering is exactly the one reordering the hardware allows; on ARM and POWER many more are allowed. The cure is a memory barrier (fence) between the stores and the loads, which is what memory_order_seq_cst inserts for you.

Where mutual exclusion came from

Edsger Dijkstra published the first correct software solution for N threads in 1965, and Donald Knuth and others refined it. Leslie Lamport's 1974 bakery algorithm lets threads take numbered tickets like customers in a bakery. Peterson's 1981 paper is famous because it showed that two-thread mutual exclusion needs only a few lines. All of these assume memory behaves sequentially, an assumption real hardware stopped granting long ago.

Hardware support: atomics, barriers and spinlocks

Atomic instructions

Since software-only solutions are fragile and slow, processors provide atomic read-modify-write instructions: the processor performs a read and a write of one memory word as a single indivisible step with respect to every other core. Two classic primitives are enough to build any lock.

Test-and-set atomically writes 1 into a word and returns the old value. Its semantics, written as ordinary code (the hardware executes it all at once), are:

int test_and_set(int *target) {
    int old = *target;
    *target = 1;
    return old;
}

Compare-and-swap (CAS) atomically compares a word with an expected value and replaces it only if they match:

bool compare_and_swap(int *value, int expected, int new_value) {
    if (*value == expected) { *value = new_value; return true; }
    return false;
}

On x86-64 these are xchg and lock cmpxchg; on ARM they are load-linked/store-conditional pairs (ldxr/stxr) or, on newer chips, a single cas instruction. In portable C you use <stdatomic.h>: atomic_flag_test_and_set, atomic_compare_exchange_strong, atomic_fetch_add, and friends. A lock built on test-and-set is only a few lines:

atomic_flag lock_word = ATOMIC_FLAG_INIT;

void spin_lock(void) {
    while (atomic_flag_test_and_set_explicit(&lock_word, memory_order_acquire))
        ;   /* the old value was 1: someone else holds it, try again */
}
void spin_unlock(void) {
    atomic_flag_clear_explicit(&lock_word, memory_order_release);
}

The first thread to run the test-and-set sees 0 and now owns the lock; every later one sees 1 and spins. The acquire and release orderings are the minimum memory barriers needed: nothing inside the critical section may drift above the acquire or below the release.

Atomic is not the same as ordered

An atomic instruction guarantees that one read-modify-write cannot be torn. It does not by itself guarantee that your other loads and stores appear in program order. Locks work because acquire and release operations also act as one-way barriers. When you write lock-free code, you must reason about both atomicity and ordering.

Atomic instructions also make some jobs lock-free outright. A shared counter does not need a lock at all: atomic_fetch_add(&c, 1) is a hardware-supported increment, and in the lab it is the fastest of all the correct versions.

Spinlocks versus mutexes

A lock that loops on an atomic instruction is a spinlock. The waiting thread does busy waiting: it burns CPU cycles asking "is it free yet?" A mutex (mutual exclusion lock), in contrast, puts the waiting thread to sleep. The kernel removes it from the run queue, runs someone else, and wakes it when the lock is released.

Which is better depends on how long the lock is held compared with the cost of a context switch, which is on the order of a microsecond or a few. Spinning is right when the critical section is extremely short and the lock holder is running on another core. It is wrong on a single core (the holder cannot run while you spin, so you waste your entire time slice) and wrong when the holder may be descheduled while holding the lock. Real systems therefore use hybrids: Linux's pthread mutex first tries an atomic compare-and-swap in user space with no system call at all (the uncontended fast path), and only when that fails does it call the kernel through the futex system call to sleep. Some mutexes spin briefly first and then block (an adaptive mutex). The kernel itself uses plain spinlocks for very short sections with interrupts disabled, because it cannot sleep in interrupt context.

A refinement matters on multiprocessors. Plain test-and-set writes the lock word on every spin, so the cache line holding it bounces between cores and floods the memory bus. A test-and-test-and-set lock spins with an ordinary read until the lock looks free, and only then attempts the atomic write, which keeps the line shared and quiet. Ticket locks go further by serving waiters in first-come order, which gives the bounded waiting that a plain spinlock lacks.

Priority inversion

Locks interact badly with priority scheduling. Suppose three tasks have high (H), medium (M) and low (L) priority. L takes a lock. H wakes up, preempts L, and then needs the same lock, so H blocks. Now M wakes up. M does not need the lock, and M has higher priority than L, so M runs and L cannot finish its critical section. H, the most important task, is stuck behind M, a less important one. This is priority inversion.

Mars Pathfinder, July 1997

Pathfinder's lander ran the VxWorks real-time kernel. A high-priority bus-management task and a low-priority meteorological task shared a data structure protected by a mutex. When a medium-priority communications task preempted the low-priority holder at the wrong moment, the bus task starved, a watchdog timer noticed that it had missed its deadline, and the spacecraft rebooted itself repeatedly. Engineers diagnosed it using a replica on Earth and fixed it by uploading a patch that enabled priority inheritance on that mutex.

The standard cure is priority inheritance: while L holds a lock that H wants, L temporarily runs at H's priority, so M cannot preempt it, and L drops back when it unlocks. POSIX offers it through the mutex attribute PTHREAD_PRIO_INHERIT. A second approach, priority ceiling, gives each lock a priority equal to the highest priority of any task that uses it.

Semaphores

Wait and signal

A semaphore, introduced by Dijkstra, is an integer variable that, apart from initialization, is touched only through two atomic operations. Dijkstra named them P (from Dutch proberen, to try) and V (verhogen, to increment). Modern APIs call them wait (or down) and signal (or post, up).

Semaphore operations

wait(S): decrement S. If the result is negative, the calling thread blocks. signal(S): increment S. If the result is zero or negative, wake exactly one blocked thread. Both operations execute atomically. In the common textbook formulation, a negative value means "this many threads are waiting".

A counting semaphore has an unrestricted integer value and tracks a pool of N identical resources: initialize it to N, wait to take one, signal to return one. A binary semaphore only takes the values 0 and 1 and behaves like a lock. Semaphores serve three different jobs, distinguished by the initial value:

Initial value Use Pattern
1 Mutual exclusion wait(S); critical section; signal(S)
0 Ordering / signalling "event happened" Thread A: signal(S). Thread B: wait(S) runs only after A signalled
N Resource counting Up to N threads inside at once

Implementation without busy waiting

The first definition of a semaphore (while (S <= 0) ; S--;) busy waits. A practical implementation gives each semaphore a queue of blocked threads, so a waiter sleeps rather than spins.

typedef struct {
    int value;
    struct thread_list *waiters;   /* queue of blocked threads */
} semaphore;

void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        add_to_queue(S->waiters, current_thread());
        block();                    /* sleep; scheduler runs someone else */
    }
}

void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        thread *t = remove_from_queue(S->waiters);
        wakeup(t);                  /* move t to the ready queue */
    }
}

The bodies of wait and signal are themselves critical sections, so on a multiprocessor they are protected by a short spinlock (or, on a single core, by disabling interrupts). That is an acceptable use of busy waiting: it lasts a handful of instructions, not the whole time a thread waits for the resource.

Semaphores have a useful property that condition variables lack: they remember. If signal runs before wait, the count goes to 1 and the later wait returns immediately, so a wake-up cannot be lost. Semaphores also lack ownership: any thread may signal, which is flexible but means a semaphore used as a lock cannot detect "unlock by the wrong thread", unlike an error-checking mutex.

The POSIX API: mutexes, semaphores and condition variables

Mutexes

POSIX threads (pthreads) provide pthread_mutex_lock and pthread_mutex_unlock, which are the tools you reach for first. The golden rule: keep the check and the update inside one critical section, as withdraw does below.

#include <pthread.h>
#include <stdio.h>

struct account {
    pthread_mutex_t lock;
    long balance;
};

static struct account acct = { PTHREAD_MUTEX_INITIALIZER, 100 };

static void deposit(struct account *a, long amount) {
    pthread_mutex_lock(&a->lock);
    a->balance += amount;
    pthread_mutex_unlock(&a->lock);
}

static int withdraw(struct account *a, long amount) {
    int ok = 0;
    pthread_mutex_lock(&a->lock);
    if (a->balance >= amount) {      /* check and update inside ONE critical section */
        a->balance -= amount;
        ok = 1;
    }
    pthread_mutex_unlock(&a->lock);
    return ok;
}

static void *teller(void *arg) {
    (void)arg;
    for (int i = 0; i < 100000; i++) {
        deposit(&acct, 10);
        withdraw(&acct, 10);
    }
    return NULL;
}

int main(void) {
    pthread_t t[3];
    for (int i = 0; i < 3; i++) pthread_create(&t[i], NULL, teller, NULL);
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    printf("final balance = %ld (expected 100)\n", acct.balance);
    return 0;
}

Every lock is matched by an unlock on the same thread, on every path, including early returns. Locking a mutex you already hold (with the default type) is undefined or deadlocks. Only the thread that locked a mutex may unlock it.

Semaphores

POSIX unnamed semaphores (<semaphore.h>) use sem_init, sem_wait, sem_post and sem_destroy. This example lets only two of six workers use a resource at a time.

#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <unistd.h>

/* A counting semaphore limits how many threads use a resource at once. */
#define NWORKERS 6
#define SLOTS    2

static sem_t slots;

static void *worker(void *arg) {
    long id = (long)arg;
    sem_wait(&slots);                       /* P / wait / down */
    printf("worker %ld enters\n", id);
    usleep(100000);                         /* pretend to use the resource */
    printf("worker %ld leaves\n", id);
    sem_post(&slots);                       /* V / signal / up */
    return NULL;
}

int main(void) {
    pthread_t t[NWORKERS];
    sem_init(&slots, 0, SLOTS);             /* pshared = 0: threads of one process */
    for (long i = 0; i < NWORKERS; i++) pthread_create(&t[i], NULL, worker, (void *)i);
    for (int i = 0; i < NWORKERS; i++) pthread_join(t[i], NULL);
    sem_destroy(&slots);
    return 0;
}

The output always shows at most two "enters" without a matching "leaves"; the exact order varies from run to run.

Condition variables and the while-loop rule

Locks answer "who may touch the data right now?" They do not answer "is the data in the state I need?" A consumer that finds the queue empty must wait until a producer adds something, and it must not hold the lock while waiting, or no producer could ever enter. A condition variable is a queue of sleeping threads attached to a mutex, with three operations:

  • pthread_cond_wait(&cv, &m): atomically release mutex m and sleep on cv; when woken, re-acquire m before returning.
  • pthread_cond_signal(&cv): wake at least one waiter, if any.
  • pthread_cond_broadcast(&cv): wake all waiters.

Unlike a semaphore, a condition variable has no memory: a signal sent when nobody waits is lost. That is why the condition itself is stored in ordinary shared variables (the predicate) protected by the mutex.

#include <pthread.h>
#include <stdio.h>

/* A one-slot mailbox: the consumer sleeps until the producer fills it. */
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  ready = PTHREAD_COND_INITIALIZER;
static int  full = 0;
static int  value;

static void *producer(void *arg) {
    (void)arg;
    pthread_mutex_lock(&m);
    value = 42;
    full = 1;                               /* change the predicate while holding the lock */
    pthread_cond_signal(&ready);            /* wake one waiter */
    pthread_mutex_unlock(&m);
    return NULL;
}

static void *consumer(void *arg) {
    (void)arg;
    pthread_mutex_lock(&m);
    while (!full)                           /* WHILE, never if */
        pthread_cond_wait(&ready, &m);      /* atomically unlock, sleep, re-lock on wake */
    printf("consumer got %d\n", value);
    full = 0;
    pthread_mutex_unlock(&m);
    return NULL;
}

int main(void) {
    pthread_t p, c;
    pthread_create(&c, NULL, consumer, NULL);
    pthread_create(&p, NULL, producer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}

The consumer works whichever thread runs first. If the producer goes first, full is already 1 when the consumer arrives and the loop never waits. That is the reason the predicate lives in a variable.

Always wait in a while loop

Re-check the predicate after every wake-up. Three things can make a woken thread find the condition false: another thread may have run between the signal and your re-acquiring the mutex and consumed the item (a "stolen wake-up"); pthread_cond_broadcast wakes every waiter although only one can proceed; and POSIX permits spurious wake-ups with no signal at all. Code using if instead of while works in testing and fails under load.

The three tools compare as follows.

Tool Remembers past signals Owner concept Best for
Mutex n/a Yes, only the locker unlocks Short critical sections
Counting semaphore Yes (the count) No Counting resources, signalling events
Condition variable No Used with a mutex Waiting for arbitrary predicates

Exercises

Exercise 5.1warm-up

Trace a lost update

A shared counter starts at 0. Thread T1 executes counter++ twice in a loop and thread T2 executes counter++ once. Each counter++ is load, add, store. The instructions run in this order: T1 load, T2 load, T2 add, T2 store, T1 add, T1 store, T1 load, T1 add, T1 store. What is the final value and how many updates were lost?

Show solution

T1 load reads 0. T2 load reads 0. T2 add makes its register 1, T2 store writes 1 (memory = 1). T1 add makes its register 0 + 1 = 1 (it still holds the stale 0), T1 store writes 1 (memory = 1, T2's update is overwritten). T1's second increment loads 1, adds 1, stores 2. The final value is 2, but three increments ran, so one update was lost.

Exercise 5.2core

Count the good interleavings

Two threads each run the three instructions load, add, store on the same counter (initial value 5). All interleavings preserving each thread's own order are equally possible. How many interleavings exist, and for how many is the final value 7?

Show solution

Choose which 3 of the 6 time slots belong to T1: C(6,3) = 20 interleavings. The final value is 7 only if the second thread's load occurs after the first thread's store, which forces one thread to run entirely before the other. There are exactly two such orders (T1 then T2, T2 then T1). In the other 18, both threads read 5, so both write 6. So 2 of 20 give 7 and 18 of 20 give 6. A bug that fails 90 percent of the time under a worst-case scheduler can still pass most real test runs, because real schedulers rarely interleave this finely.

Exercise 5.3core

Which requirement fails?

Two threads use a shared flag busy, initially 0. Entry code is while (busy) ; busy = 1; and exit code is busy = 0;. Identify the violated requirement and give a concrete interleaving.

Show solution

Mutual exclusion fails. The test of busy and the assignment busy = 1 are separate steps. Interleaving: T1 reads busy = 0 and exits its loop; before T1 sets it, T2 reads busy = 0 and exits its loop; T1 sets busy = 1 and enters; T2 sets busy = 1 and also enters. Both are in the critical section. The fix needs the test and the set to be one atomic instruction, which is exactly test-and-set. (Progress and bounded waiting do hold here for the single-threaded view, but a lock that is not exclusive is useless.)

Exercise 5.4challenging

Why does Peterson's algorithm need a barrier?

Rewrite Peterson's lock(me) with plain int flags and explain, with a concrete reordering, how both threads can enter the critical section on a processor with a store buffer.

Show solution

Plain version: flag[me] = 1; turn = other; while (flag[other] && turn == other) ;. Suppose T0 and T1 run on different cores. T0 executes flag[0] = 1 but the store waits in T0's store buffer, invisible to T1. T0 then performs turn = 1 (also buffered) and loads flag[1], which is still 0 in memory, so the while condition is false and T0 enters. Symmetrically, T1's flag[1] = 1 is buffered while it loads flag[0] and sees 0. Both enter. The load of the other thread's flag has overtaken the earlier store to one's own flag (a store-load reordering, the one reordering x86 permits). A full memory barrier (mfence, or sequentially consistent atomics) between the stores and the load drains the buffer first and prevents it. The compiler may also reorder the plain accesses, which needs a compiler barrier or atomics as well.

Exercise 5.5core

Spin or sleep?

A critical section takes 50 ns. Assume putting a thread to sleep and waking it again costs about 5 microseconds (two context switches plus system call overhead). On a multicore machine, should contended waiters spin or block? What changes if the critical section includes a disk read taking 5 ms?

Show solution

5 microseconds = 5000 ns, which is 100 times the critical section length (5000 / 50 = 100). A waiter that spins expects to wait at most about 50 ns, so spinning wastes about 50 ns of CPU while blocking wastes 5000 ns. Spin (or use an adaptive mutex that spins first). With a 5 ms critical section, a spinner would burn 5 ms = 5,000,000 ns of CPU, about 1000 times the sleep cost of 5000 ns, so blocking is clearly better. Rule of thumb: spin only when the expected wait is shorter than the cost of sleeping and waking, and only when the lock holder is running on another core.

Exercise 5.6core

Semaphore trace

A counting semaphore S starts at 2. Threads A, B, C, D call wait(S) in that order, then A calls signal(S), then B calls signal(S). Using the blocking implementation (value may go negative), give the value of S after each operation and say which threads are blocked.

Show solution

Start: 2. A waits: 1, A proceeds. B waits: 0, B proceeds. C waits: -1, C blocks (queue: C). D waits: -2, D blocks (queue: C, D). A signals: -1, value is not above 0, so C is woken (queue: D). B signals: 0, D is woken (queue: empty). Final value 0, no thread blocked; C and D now hold the two slots and the count is back to 0 because two threads are using the pool.

Exercise 5.7challenging

Priority inversion in numbers

Times are in ms. Low-priority L runs from t = 0, needs 3 ms of CPU in total, and takes a mutex at t = 1; it must hold the mutex for its last 2 ms. High-priority H arrives at t = 2 and immediately requests that mutex; it then needs 2 ms of CPU after getting it. Medium-priority M arrives at t = 2 and needs 10 ms and does not use the mutex. (a) Without priority inheritance, when does H get the mutex? (b) With priority inheritance, when?

Show solution

At t = 2, L has run 2 ms (t = 0 to 2) of which 1 ms is inside the critical section, so 1 ms remains. (a) H blocks on the mutex. Among runnable tasks M (medium) outranks L, so M runs from t = 2 to 12. Then L runs from 12 to 13 and unlocks at t = 13. H gets the mutex at t = 13 and was blocked for 11 ms. (b) With inheritance, L runs at H's priority from t = 2, finishes its last millisecond at t = 3 and unlocks. H gets the mutex at t = 3, blocked for only 1 ms, runs t = 3 to 5, and M then runs 5 to 15.

Exercise 5.8challenging

A rendezvous with semaphores

Two threads must each finish phase 1 before either starts phase 2 (a two-thread barrier). Using only semaphores, write the code and state the initial values. Then explain why initializing both to 1 would be wrong.

Show solution

Use two semaphores a and b, both initialized to 0.

T1:  phase1();  signal(a);  wait(b);  phase2();
T2:  phase1();  signal(b);  wait(a);  phase2();

Each thread announces that it finished phase 1 and then waits for the other's announcement. Because semaphores remember, the order of arrival does not matter. If both started at 1, wait(b) in T1 would succeed immediately without T2 having finished phase 1, so no synchronization would occur. A semaphore used for signalling must start at 0 so that the first wait blocks until a matching signal happens.

Exercise 5.9challenging

The if-versus-while bug

A queue is protected by mutex m and condition variable cv. Consumers run lock(m); if (queue_empty()) cond_wait(&cv, &m); item = pop(); unlock(m); and producers push then cond_signal(&cv). Two consumers C1 and C2 and one producer exist. Describe an interleaving where pop() runs on an empty queue.

Show solution

C1 locks, finds the queue empty and sleeps in cond_wait (mutex released). The producer pushes one item and calls cond_signal, waking C1, but the producer still holds the mutex until it unlocks. Before C1 can re-acquire the mutex, C2 arrives, locks it, sees the queue is non-empty (so it skips the wait), pops the item, and unlocks. C1 now re-acquires the mutex and, because it used if, does not re-check; it calls pop() on an empty queue. Replacing if with while makes C1 test the predicate again, find the queue empty and go back to sleep.

Lab: three fixes for a racy counter

You will build one C program with four modes. The racy mode shows the bug, and mutex, spin and sem fix it in three different ways. A fifth mode, atomic, shows the lock-free fix for comparison. Save the following as counter.c.

#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <semaphore.h>
#include <stdatomic.h>
#include <stdio.h>
#include <string.h>
#include <time.h>

#define NTHREADS 4
#define NITERS   1000000L

static volatile long counter = 0;          /* shared, deliberately unprotected in mode "racy" */
static atomic_long   acounter = 0;
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static atomic_flag     spin = ATOMIC_FLAG_INIT;
static sem_t           sem;

static void *worker_racy(void *arg) {
    (void)arg;
    for (long i = 0; i < NITERS; i++)
        counter++;                          /* load, add, store: not atomic */
    return NULL;
}

static void *worker_mutex(void *arg) {
    (void)arg;
    for (long i = 0; i < NITERS; i++) {
        pthread_mutex_lock(&mtx);
        counter++;
        pthread_mutex_unlock(&mtx);
    }
    return NULL;
}

static void spin_lock(void) {
    while (atomic_flag_test_and_set_explicit(&spin, memory_order_acquire))
        ;                                   /* busy wait */
}
static void spin_unlock(void) {
    atomic_flag_clear_explicit(&spin, memory_order_release);
}

static void *worker_spin(void *arg) {
    (void)arg;
    for (long i = 0; i < NITERS; i++) {
        spin_lock();
        counter++;
        spin_unlock();
    }
    return NULL;
}

static void *worker_sem(void *arg) {
    (void)arg;
    for (long i = 0; i < NITERS; i++) {
        sem_wait(&sem);
        counter++;
        sem_post(&sem);
    }
    return NULL;
}

static void *worker_atomic(void *arg) {
    (void)arg;
    for (long i = 0; i < NITERS; i++)
        atomic_fetch_add(&acounter, 1);
    return NULL;
}

int main(int argc, char **argv) {
    const char *mode = argc > 1 ? argv[1] : "racy";
    void *(*fn)(void *) = NULL;
    if      (strcmp(mode, "racy")   == 0) fn = worker_racy;
    else if (strcmp(mode, "mutex")  == 0) fn = worker_mutex;
    else if (strcmp(mode, "spin")   == 0) fn = worker_spin;
    else if (strcmp(mode, "sem")    == 0) fn = worker_sem;
    else if (strcmp(mode, "atomic") == 0) fn = worker_atomic;
    else { fprintf(stderr, "usage: %s racy|mutex|spin|sem|atomic\n", argv[0]); return 2; }

    sem_init(&sem, 0, 1);                   /* binary semaphore, initial value 1 */

    pthread_t t[NTHREADS];
    struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (int i = 0; i < NTHREADS; i++) pthread_create(&t[i], NULL, fn, NULL);
    for (int i = 0; i < NTHREADS; i++) pthread_join(t[i], NULL);
    clock_gettime(CLOCK_MONOTONIC, &b);

    long result = (fn == worker_atomic) ? (long)atomic_load(&acounter) : counter;
    double secs = (b.tv_sec - a.tv_sec) + (b.tv_nsec - a.tv_nsec) / 1e9;
    printf("%-6s expected=%ld got=%ld time=%.3fs\n", mode, NTHREADS * NITERS, result, secs);
    sem_destroy(&sem);
    return 0;
}

Build and run all modes:

gcc -O2 -Wall -Wextra -pthread counter.c -o counter
for m in racy mutex spin sem atomic; do ./counter $m; done

What to observe. On a two-core test machine the output looked like this (your numbers will differ):

racy   expected=4000000 got=2634433 time=0.007s
mutex  expected=4000000 got=4000000 time=0.283s
spin   expected=4000000 got=4000000 time=0.279s
sem    expected=4000000 got=4000000 time=0.652s
atomic expected=4000000 got=4000000 time=0.054s

The racy version loses updates and gives a different wrong answer each run, yet it is the fastest because it does no synchronization. The three fixes return exactly 4,000,000. The semaphore is usually slowest because every sem_wait and sem_post goes through the library's atomic bookkeeping and sometimes the kernel. Run each mode several times, and repeat with taskset -c 0 ./counter spin (one core): the spinlock usually becomes dramatically worse, because a spinner burns its time slice while the holder cannot run. That experiment is the practical meaning of Figure 5.3.

Why the volatile?

volatile stops the compiler from keeping counter in a register for the whole loop, which would hide the race by turning the loop into one add. It does not make counter++ atomic, and it gives no ordering guarantee between threads. Never use volatile as a synchronization tool in real code.

Extensions.

  1. Implement spin_lock with atomic_compare_exchange_strong instead of test-and-set and compare timings. Then add the test-and-test-and-set refinement (spin on a plain atomic load, attempt the exchange only when it reads 0).
  2. Vary NTHREADS from 1 to 16 and plot time against thread count for each lock. Where does each lock's cost stop growing, and why?
  3. Replace the mutex with a PTHREAD_MUTEX_ERRORCHECK mutex, deliberately unlock it from the wrong thread, and observe the error code. Then try the same mistake with a semaphore.

Common mistakes and debugging tips

Symptom Likely cause What to do
Final total is lower than expected and changes every run Unprotected read-modify-write on shared data Protect every access to the variable with the same lock, or use an atomic operation
Program passes tests but fails under load Race with a tiny window; test timing too gentle Run under valgrind --tool=helgrind or compile with -fsanitize=thread; add stress threads
A lock seems to work but sometimes two threads get in Different locks guard the same data, or one code path skips the lock Name which lock protects which variable; check all paths
Thread hangs forever after a signal Signal sent before the waiter slept, predicate not stored in a variable Keep the predicate in shared state and wait in a while loop
pthread_cond_wait returns but data is not ready if instead of while, spurious or stolen wake-up Always loop on the predicate
Hang, with a thread stuck in lock Forgot to unlock on an early return or goto Unlock on every exit path; use one exit point
Spinlock program is slower on one core Waiters burn their whole time slice Use a mutex, or make sure holders cannot be preempted
Semaphore count drifts post without matching wait, or the reverse Count them on paper; assert the value with sem_getvalue in debugging

Key takeaways

Key takeaways

  • counter++ is load, add, store; interleaving two such sequences can lose updates, and most interleavings are bad.
  • A correct critical section solution gives mutual exclusion, progress and bounded waiting.
  • Software algorithms like Peterson's need atomics and memory barriers on real hardware; the practical foundation is an atomic instruction such as test-and-set or compare-and-swap.
  • Spin only for very short waits on multicore machines; otherwise block. Priority inheritance cures priority inversion.
  • A semaphore is a counter with a queue: init 1 for a lock, 0 for signalling, N for counting resources.
  • Condition variables have no memory, so keep the predicate in shared state and always wait in a while loop.
