Main Memory

How the OS and the memory management unit share RAM among processes: base and limit registers, contiguous allocation and fragmentation, paging and page tables, TLBs, multilevel page tables, and segmentation, with worked address translations and the Midterm.

What you will be able to do

By the end of this week you will be able to:

  • Translate a logical address to a physical address using base and limit registers, a page table and a segment table
  • Place a sequence of requests in a hole list with first fit, best fit and worst fit and measure the fragmentation left over
  • Split an address into page number and offset for a given page size and compute internal fragmentation
  • Compute page table sizes and the effective access time with a TLB for a given hit ratio
  • Explain why multilevel, hashed and inverted page tables exist and what each trades off
  • Compare paging with segmentation and state which kind of fragmentation each suffers from

Until now we treated memory as a place where a process's code and data simply live. In Week 2 a process had an address space, and in Week 3 threads shared it. This week we open the box: a machine has one pool of physical RAM, many processes want their own private address spaces inside it, and the hardware and OS must map one onto the other quickly, safely and without wasting the pool.

We start with the simplest scheme (a process gets one contiguous block) and watch it break on fragmentation. Paging removes the problem by cutting memory into fixed-size pieces, and its cost is a table lookup on every access, which the TLB hides. Segmentation then offers the programmer's view of memory instead of the hardware's. The week also holds the Midterm on Weeks 1 to 7, so the last section tells you how to use the days before it. Week 9 makes this scheme "virtual" by allowing pages to live on disk, and Week 10 decides which pages to evict.

Address spaces and contiguous allocation

Logical and physical addresses

Logical and physical address

A logical address (also called a virtual address) is the address a program generates. A physical address is the address that actually reaches the memory chips. The hardware unit that converts one into the other on every memory reference is the memory management unit (MMU). The program sees only logical addresses and never learns the physical ones.

Why not let programs use physical addresses directly? Because then every program must be written (or relocated at load time) for exactly the place it will run, and nothing stops one program from reading or overwriting another's memory. With an MMU the OS can place a process anywhere, move it later, and make every access outside the process's own space trap to the kernel, the same dual-mode protection idea as in Week 1.

The simplest MMU has two registers, a base and a limit. The CPU compares each logical address with the limit and, if it is smaller, adds the base:

The OS loads these two registers when it dispatches a process (a few instructions in the context switch of Week 2); only kernel mode may change them.

Variable partitions and the hole list

With base and limit, each process occupies one contiguous block whose size is whatever it needs. As processes start and finish, free memory fragments into a list of holes, free blocks of different sizes scattered among allocated ones. A new process of size n must be placed in a hole of at least n. This is the dynamic storage-allocation problem, and three classic policies answer it:

  • First fit: take the first hole that is big enough. Fast, since the search stops early.
  • Best fit: take the smallest hole that is big enough. This must scan the whole list (unless it is sorted by size) and leaves the smallest leftover.
  • Worst fit: take the largest hole, hoping the leftover is still useful. It also scans everything.

After placing a request in a larger hole, the remainder stays on the list as a smaller hole. Here is a concrete case. Free holes, in address order, are 100, 500, 200, 300 and 600 KB, and requests of 212, 417, 112 and 426 KB arrive in that order.

Request First fit (hole used, leftover) Best fit Worst fit
212 500, leftover 288 300, leftover 88 600, leftover 388
417 600, leftover 183 500, leftover 83 500, leftover 83
112 288 (the leftover), leftover 176 200, leftover 88 388 (the leftover), leftover 276
426 fails: largest hole is 300 600, leftover 174 fails: largest hole is 300
Holes at the end 100, 176, 200, 300, 183 100, 83, 88, 88, 174 100, 83, 200, 300, 276

Only best fit places all four requests. First fit and worst fit each leave 959 KB free in total (1700 KB at the start minus the 741 KB placed), yet cannot place a 426 KB request because no single hole is that big. That is external fragmentation: enough free memory in total, but not contiguous. Best fit succeeded here by keeping the large 600 KB hole intact until it was needed. On other inputs best fit loses (it litters memory with tiny, useless slivers), which is why simulations show first fit and best fit are about equally good in practice and worst fit is usually worse.

Parking spaces

Imagine a street where cars of different lengths park and leave. After a few hours the free space is chopped into gaps, none of them as long as the bus that just arrived, even though the gaps add up to many bus lengths. External fragmentation is exactly that. Compaction is asking every driver to move their car to the front of the street, which works but takes a lot of time.

Two kinds of fragmentation, and compaction

External fragmentation wastes memory between allocated blocks. Statistics on first fit show that, given N allocated blocks, roughly another 0.5 N blocks are lost to fragmentation, so about one third of memory may be unusable (Knuth's 50-percent rule). Internal fragmentation wastes memory inside an allocated block, because memory is handed out in units larger than the request (a fixed-size partition, or the last page of a process). One cure for external fragmentation is compaction: slide all processes to one end so the holes merge into one. It is possible only if processes can be relocated at run time (base register changes), and it is expensive, since it copies memory. The other cure is to stop requiring contiguity, which is the idea of the next section.

Paging

Pages, frames and the page table

Paging divides physical memory into fixed-size blocks called frames and a process's logical address space into blocks of the same size called pages. Any page can go into any free frame, so no contiguous hole is needed and external fragmentation disappears. The OS keeps a page table for each process mapping page number to frame number. The page size is a power of two (typically 4 KB), which lets the hardware split a logical address by simply cutting its bits:

logical address (m bits) = | page number p (m - n bits) | page offset d (n bits) |
page size = 2^n bytes
physical address         = (frame number f from page_table[p]) * 2^n + d

The offset passes through unchanged, because a page and its frame have the same size. The program below does the bit-cutting for page size 4096 using a shift and a mask, which is exactly what the hardware does.

include

include

include

int main(int argc, char *argv) { long page = sysconf(_SC_PAGESIZE); / 4096 on most Linux systems */ int offset_bits = 0; while ((1L << offset_bits) < page) offset_bits++; printf("page size = %ld bytes, offset bits = %d\n", page, offset_bits);

for (int i = 1; i < argc; i++) {
    unsigned long addr = strtoul(argv[i], NULL, 16);
    unsigned long pnum = addr >> offset_bits;       /* high bits: page number */
    unsigned long off  = addr & (page - 1);         /* low bits: offset */
    printf("address 0x%lX -> page %lu (0x%lX), offset %lu (0x%lX)\n",
           addr, pnum, pnum, off, off);
}
return 0;

}

Running it on four addresses:

page size = 4096 bytes, offset bits = 12
address 0x2A7C -> page 2 (0x2), offset 2684 (0xA7C)
address 0x7FFF -> page 7 (0x7), offset 4095 (0xFFF)
address 0x12345678 -> page 74565 (0x12345), offset 1656 (0x678)
address 0x1000 -> page 1 (0x1), offset 0 (0x0)

Address 0x2A7C is 0010 1010 0111 1100 in binary. With a 4 KB page the low 12 bits are the offset (0xA7C = 2684) and the top bits, 0010, give page 2.

A worked translation

Take 16-bit logical addresses and 4 KB pages, so the page number is 4 bits (16 pages) and the offset is 12 bits. Physical memory is 32 KB, which is 8 frames. The page table of the process is:

Page 0 1 2 3 4 5 to 15
Frame 5 2 3 7 0 not in memory (invalid)

Translate logical address 0x2A7C step by step.

  1. Page number = 0x2A7C >> 12 = 2. Offset = 0x2A7C & 0xFFF = 0xA7C = 2684.
  2. Page table entry 2 holds frame 3.
  3. Physical address = 3 × 4096 + 2684 = 12288 + 2684 = 14972 = 0x3A7C.

Replacing the page number by the frame number is the whole translation: the leading hex digit changes from 2 to 3 and the rest is copied.

Internal fragmentation and page size

Paging has no external fragmentation, but the last page of each process is rarely full. A process of 72,766 bytes with 2,048-byte pages needs 35 full pages (71,680 bytes) plus 1,086 bytes, so 36 pages, and wastes 2,048 - 1,086 = 962 bytes. On average a process wastes about half a page, which suggests small pages. But the page table has one entry per page, so small pages mean large tables, and they also make disk transfers less efficient. Typical sizes are 4 KB to 8 KB; modern x86-64 CPUs support 4 KB, 2 MB and 1 GB pages, the larger ones being used for big database buffers or hypervisors.

Page table size, protection and sharing

A 32-bit address space with 4 KB pages has 2^32 / 2^12 = 2^20 pages. With 4 bytes per entry, one flat page table is 2^20 × 4 = 4 MB for every process, which is huge when most of the address space is unused. Section "Fast lookups and big address spaces" below shows how to avoid it.

Each page table entry holds more than the frame number: a valid bit (is this page mapped?), read/write/execute permission bits, and bits the OS and hardware use for later chapters (referenced, dirty). An access to an invalid page, or a write to a read-only page, makes the MMU raise a trap to the OS. Paging also makes sharing easy: two processes' page tables can point to the same frame, which is how shared libraries and, as Week 9 will show, copy-on-write fork work.

Fast lookups and big address spaces

The TLB

A page table lives in memory, so a naive access takes two memory references: one for the page table entry and one for the data. Programs would run at half speed. The fix is a small, fast hardware cache of recent translations called the translation look-aside buffer (TLB). It is searched in parallel by page number. On a hit the frame number is available at once. On a miss the hardware (or the OS, on some architectures) walks the page table and loads the entry into the TLB, evicting another. The program below simulates a 2-entry TLB with least-recently-used replacement over the page table of the worked example.

include

define PAGE_BITS 12 / 4 KB pages /

define PAGE_SIZE (1u << PAGE_BITS)

define NPAGES 16 / 16-bit logical address: 4-bit page number /

define TLB_SIZE 2

static int page_table[NPAGES]; / frame number, or -1 if not in memory /

static struct { int page, frame; unsigned last_used; } tlb[TLB_SIZE]; static unsigned clock_tick = 0, hits = 0, lookups = 0;

static int tlb_lookup(int page) { for (int i = 0; i < TLB_SIZE; i++) if (tlb[i].page == page) { tlb[i].last_used = ++clock_tick; return tlb[i].frame; } return -1; }

static void tlb_insert(int page, int frame) { / evict the least recently used entry / int victim = 0; for (int i = 1; i < TLB_SIZE; i++) if (tlb[i].last_used < tlb[victim].last_used) victim = i; tlb[victim].page = page; tlb[victim].frame = frame; tlb[victim].last_used = ++clock_tick; }

static void translate(unsigned logical) { unsigned page = logical >> PAGE_BITS, offset = logical & (PAGE_SIZE - 1); lookups++; int frame = tlb_lookup(page); const char how = "TLB hit "; if (frame >= 0) hits++; else { how = "TLB miss"; frame = page_table[page]; / extra memory access */ if (frame < 0) { printf("0x%04X page %2u page fault\n", logical, page); return; } tlb_insert(page, frame); } printf("0x%04X page %2u offset 0x%03X %s frame %d physical 0x%04X\n", logical, page, offset, how, frame, ((unsigned)frame << PAGE_BITS) | offset); }

int main(void) { for (int i = 0; i < NPAGES; i++) page_table[i] = -1; page_table[0] = 5; page_table[1] = 2; page_table[2] = 3; page_table[3] = 7; page_table[4] = 0; for (int i = 0; i < TLB_SIZE; i++) tlb[i].page = -1;

unsigned refs[] = {0x2A7C, 0x2A80, 0x0123, 0x2B00, 0x3FFF, 0x2A7C, 0x4000, 0x9000};
for (unsigned i = 0; i < sizeof refs / sizeof refs[0]; i++) translate(refs[i]);
printf("TLB hits: %u of %u lookups\n", hits, lookups);
return 0;

}

0x2A7C  page  2 offset 0xA7C  TLB miss  frame 3  physical 0x3A7C
0x2A80  page  2 offset 0xA80  TLB hit   frame 3  physical 0x3A80
0x0123  page  0 offset 0x123  TLB miss  frame 5  physical 0x5123
0x2B00  page  2 offset 0xB00  TLB hit   frame 3  physical 0x3B00
0x3FFF  page  3 offset 0xFFF  TLB miss  frame 7  physical 0x7FFF
0x2A7C  page  2 offset 0xA7C  TLB hit   frame 3  physical 0x3A7C
0x4000  page  4 offset 0x000  TLB miss  frame 0  physical 0x0000
0x9000  page  9  page fault
TLB hits: 3 of 8 lookups

Look at the pattern. The second access to page 2 (0x2A80) hits because it is in the same page as the first, which is spatial locality; the repeated 0x2A7C near the end hits because page 2 stayed in the TLB. The last reference, 0x9000, is on an invalid page: the MMU raises a page fault.

A TLB entry is tagged with an address-space identifier (ASID) so entries from different processes can coexist; without ASIDs the TLB must be flushed on every context switch, which hurts. The TLB reach is entries × page size: 64 entries of 4 KB cover only 256 KB, which is why large pages help.

Effective access time

Let the TLB lookup take t ns, a memory access take m ns, and the hit ratio be h. A hit costs t + m. A miss costs t + m (page table access) + m (data access). So

EAT = h × (t + m) + (1 - h) × (t + 2m)

With t = 10 ns and m = 100 ns, the numbers are:

Hit ratio h EAT
80% 0.8 × 110 + 0.2 × 210 = 88 + 42 = 130 ns
99% 0.99 × 110 + 0.01 × 210 = 108.9 + 2.1 = 111 ns

So at 99% the translation overhead is only 11 percent, and the TLB is what makes paging practical. Week 9 adds page faults to this formula with its own demo.

Multilevel, hashed and inverted page tables

Flat tables do not scale

On a 64-bit machine the flat table is impossible: with 48 usable address bits and 4 KB pages there are 2^36 pages, and at 8 bytes per entry the table would be 2^39 bytes, 512 GiB, for each process. Real systems must store only the parts of the table that are in use.

Hierarchical (multilevel) paging pages the page table itself. On 32-bit x86 the 20-bit page number splits into two 10-bit parts: the top 10 bits index an outer page table and the next 10 bits index an inner page table, which holds the frame number; the final 12 bits are the offset.

Each table here is exactly one 4 KB page (1024 entries of 4 bytes), a design choice that makes the tables themselves easy to allocate. A process with a small program at the bottom of its address space and a stack at the top needs only one outer table and two inner tables, 12 KB instead of 4 MB. The cost is extra memory accesses on a TLB miss: a miss now costs two table reads, and x86-64 uses four levels (9 bits each plus a 12-bit offset), so a miss can cost four reads before the data access. The TLB hit ratio matters even more.

Hashed page tables hash the page number into a table of chains; each chain element stores a page number, frame number and pointer to the next. They suit sparse address spaces larger than 32 bits. Inverted page tables keep one entry per physical frame, holding (process id, page number). The table size is proportional to RAM, not to the number of processes times their address spaces, but a lookup must search for the entry whose contents match, so a hash table speeds it up, and sharing a frame among processes becomes awkward because each frame has only one entry. IBM PowerPC and UltraSPARC used variants of this.

Segmentation

Programmers do not think of memory as a flat array of pages. They think of a main program, procedures, a stack, a heap, a symbol table, and global arrays. Segmentation gives each of these logical units its own segment. A logical address is a pair <segment number s, offset d>. A segment table maps each segment number to a base (where the segment starts in physical memory) and a limit (its length). The hardware checks that d < limit and then computes base + d.

Take a segment table with five segments:

Segment Base Limit
0 1400 1000
1 6300 400
2 4300 400
3 3200 1100
4 4700 1000

Address <2, 53> maps to 4300 + 53 = 4353. Address <3, 852> maps to 3200 + 852 = 4052. Address <0, 1222> is a trap, since 1222 ≥ 1000. Note that offset 400 in segment 1 would also trap: valid offsets run from 0 to limit - 1.

Segments are natural units for protection and sharing (a code segment is read-only and execute-only; two processes can share one segment of library code). But segments have different lengths, so allocating them is the contiguous-allocation problem again, with all its external fragmentation. Pure segmentation is therefore rare today. The 32-bit x86 combined segmentation and paging: segmentation produced a linear address, and paging translated it. Operating systems such as Linux simply set every segment to cover the whole address space (the "flat model"), and in 64-bit mode the hardware ignores base and limit for most segments.

Exercises

Exercise 8.1warm-up

Paged translation

Page size is 1 KB (1024 bytes). The page table maps page 0 to frame 4, page 1 to frame 9, page 2 to frame 5 and page 3 to frame 1; pages 4 and above are invalid. Translate logical addresses 3000, 1500 and 4100.

Show solution

3000 = 2 × 1024 + 952, so page 2, offset 952: frame 5, physical = 5 × 1024 + 952 = 5120 + 952 = 6072. 1500 = 1 × 1024 + 476, so page 1, offset 476: frame 9, physical = 9216 + 476 = 9692. 4100 = 4 × 1024 + 4, so page 4, which is invalid: the MMU traps (an addressing error or page fault).

Exercise 8.2core

How big is the page table?

(a) A 32-bit machine uses 4 KB pages and 4-byte entries. How large is a flat page table? (b) A 48-bit address space with 4 KB pages and 8-byte entries? (c) What does a two-level table with 10 and 10 index bits save for a process that uses 4 MB at the bottom of the address space and 64 KB at the top?

Show solution

(a) 2^32 / 2^12 = 2^20 entries × 4 B = 2^22 B = 4 MB. (b) 2^48 / 2^12 = 2^36 entries × 8 B = 2^39 B = 512 GiB, impossible, hence multilevel tables. (c) The 4 MB at the bottom is exactly 1024 pages, one inner table (each inner table covers 1024 × 4 KB = 4 MB). The 64 KB stack at the top falls in the last inner table: a second inner table. Plus the one outer table: 3 tables × 4 KB = 12 KB instead of 4 MB.

Exercise 8.3core

Internal fragmentation

A process needs 72,766 bytes and the page size is 2,048 bytes. How many pages does it use and how much memory is wasted? Why not choose a 1-byte page to remove the waste?

Show solution

72,766 / 2,048 = 35.53, so 36 pages. Allocated = 36 × 2,048 = 73,728. Waste = 73,728 - 72,766 = 962 bytes. A 1-byte page would need a page table entry for every byte (several bytes of table per byte of data), and the TLB could cover almost nothing. Page size balances internal waste against table size and TLB reach.

Exercise 8.4core

Effective access time

A TLB lookup takes 20 ns and a memory access 100 ns. (a) Compute the EAT for a hit ratio of 90%. (b) What hit ratio is needed to get the EAT down to 125 ns?

Show solution

(a) A hit costs 20 + 100 = 120 ns, a miss 20 + 100 + 100 = 220 ns. EAT = 0.9 × 120 + 0.1 × 220 = 108 + 22 = 130 ns. (b) EAT = h × 120 + (1 - h) × 220 = 220 - 100h. Setting 220 - 100h = 125 gives h = 0.95. A hit ratio of at least 95% is needed.

Exercise 8.5core

Segment table translation

Use the segment table of this chapter (base, limit: segment 0 1400, 1000; 1 6300, 400; 2 4300, 400; 3 3200, 1100; 4 4700, 1000). Translate <1, 100>, <4, 999>, <1, 400> and <5, 0>.

Show solution

<1, 100>: 100 < 400, physical = 6300 + 100 = 6400. <4, 999>: 999 < 1000, physical = 4700 + 999 = 5699. <1, 400>: 400 is not less than the limit 400, so a trap. <5, 0>: the table has segments 0 to 4 only, so a trap on the invalid segment number.

Exercise 8.6core

Which fit works?

Holes in address order are 300, 100, 250 and 150 KB. Requests are 120, 260, 100 and 200 KB, in that order. Apply first fit, best fit and worst fit. Which places the most requests, and what holes remain?

Show solution

First fit: 120 goes into 300 (leaves 180); 260 fits nowhere (holes 180, 100, 250, 150); 100 goes into 180 (leaves 80); 200 goes into 250 (leaves 50). Placed 3 of 4, holes 80, 100, 50, 150. Best fit: 120 goes into 150 (leaves 30); 260 into 300 (leaves 40); 100 into 100 (leaves 0); 200 into 250 (leaves 50). All 4 placed, holes 40, 0, 50, 30. Worst fit: 120 into 300 (leaves 180); 260 fails; 100 into 250 (leaves 150); 200 fails as holes are 180, 100, 150, 150. Placed 2 of 4, holes 180, 100, 150, 150. Best fit wins on this input.

Exercise 8.7challenging

Why the TLB matters more with deeper tables

With t = 10 ns and m = 100 ns, compare the EAT at a 99% hit ratio for a one-level page table (a miss costs one extra memory access) and a four-level page table (a miss costs four extra memory accesses). Then repeat for a 90% hit ratio and comment.

Show solution

Hit = 10 + 100 = 110 ns. One level, miss = 10 + 100 + 100 = 210; four levels, miss = 10 + 4 × 100 + 100 = 510. At 99%: one level 0.99 × 110 + 0.01 × 210 = 108.9 + 2.1 = 111.0 ns; four levels 108.9 + 0.01 × 510 = 108.9 + 5.1 = 114.0 ns. At 90%: one level 0.9 × 110 + 0.1 × 210 = 99 + 21 = 120 ns; four levels 99 + 51 = 150 ns. At 99% the extra levels cost 3 ns, at 90% they cost 30 ns, ten times as much. Deep tables are affordable only because the hit ratio is very high.

Lab: first, best and worst fit

You will write the allocator experiment behind the demo. The program keeps a list of hole sizes (in KB, in address order) and places requests with one of three policies, printing where each request went and what remains. Save it as holes.c.

include

include

define NHOLES 5

define NREQ 4

enum { FIRST, BEST, WORST }; static const char *names[] = { "first fit", "best fit", "worst fit" };

/ Pick a hole for a request of size n, or -1 if none is big enough. / static int choose(const int hole[], int n, int policy) { int pick = -1; for (int i = 0; i < NHOLES; i++) { if (hole[i] < n) continue; if (pick < 0) { pick = i; if (policy == FIRST) break; continue; } if (policy == BEST && hole[i] < hole[pick]) pick = i; if (policy == WORST && hole[i] > hole[pick]) pick = i; } return pick; }

int main(void) { const int start[NHOLES] = {100, 500, 200, 300, 600}; / hole sizes in KB, in address order / const int req[NREQ] = {212, 417, 112, 426};

for (int policy = FIRST; policy <= WORST; policy++) {
    int hole[NHOLES];
    memcpy(hole, start, sizeof hole);
    printf("== %s ==\n", names[policy]);
    for (int r = 0; r < NREQ; r++) {
        int h = choose(hole, req[r], policy);
        if (h < 0) { printf("  %3d KB: no hole large enough\n", req[r]); continue; }
        printf("  %3d KB: placed in hole %d (%d KB), leftover %d KB\n",
               req[r], h, hole[h], hole[h] - req[r]);
        hole[h] -= req[r];
    }
    int total = 0, largest = 0;
    printf("  holes now:");
    for (int i = 0; i < NHOLES; i++) {
        printf(" %d", hole[i]);
        total += hole[i];
        if (hole[i] > largest) largest = hole[i];
    }
    printf("\n  free total %d KB, largest hole %d KB\n", total, largest);
}
return 0;

}

  426 KB: placed in hole 4 (600 KB), leftover 174 KB
  holes now: 100 83 88 88 174
  free total 533 KB, largest hole 174 KB
== worst fit ==
  212 KB: placed in hole 4 (600 KB), leftover 388 KB
  417 KB: placed in hole 1 (500 KB), leftover 83 KB
  112 KB: placed in hole 4 (388 KB), leftover 276 KB
  426 KB: no hole large enough
  holes now: 100 83 200 300 276
  free total 959 KB, largest hole 300 KB

First fit and worst fit each leave 959 KB free, yet the largest hole is only 300 KB and the 426 KB request fails. Best fit has placed every request and leaves 533 KB, but its largest hole is only 174 KB, so a further 250 KB request would fail under best fit and succeed under the other two. Run the program on your own sequences and confirm the table from the chapter.

Extensions.

  1. Add a free_block(address, size) operation that returns memory and coalesces adjacent holes, then replay a long random sequence of allocations and frees and report external fragmentation as 1 - (largest hole / total free) after each step.
  2. Add a compaction step that triggers when a request fails although the total free memory is large enough, and count how many KB it copies.
  3. Add a next fit policy (continue searching from where the last search ended) and compare it with first fit on your random sequences.

Common mistakes and debugging tips

Symptom Likely cause What to do
Physical address off by a power of two Used the wrong number of offset bits for the page size Compute n = log2(page size) first, then shift and mask
Translated address looks right but is rejected Forgot to check the limit or valid bit before adding the base or frame Check bounds first: offset < limit, or page entry valid
Offset 400 accepted for a 400-byte segment Used offset ≤ limit Valid offsets are 0 to limit - 1
Hex arithmetic goes wrong Mixed decimal and hexadecimal Convert once; write f × 4096 + d or (f << 12) + d
EAT too low Counted the page table access for hits Hits cost t + m, misses cost t + 2m (more with several levels)
Allocation "fails" with plenty of free memory External fragmentation, no hole big enough Compare total free with largest hole; consider compaction or paging
Page table size answer too small Counted bits where bytes were needed Entries × entry size in bytes, then convert

Key takeaways

Key takeaways

  • The MMU translates each logical address to a physical address; base and limit registers give relocation and protection in the simplest form.
  • Contiguous allocation suffers external fragmentation. On holes 100, 500, 200, 300, 600 and requests 212, 417, 112, 426, first fit and worst fit fail the last request while best fit places all four.
  • Paging splits memory into equal frames and pages: no external fragmentation, but internal fragmentation of up to one page per process and a page table lookup on every access.
  • A TLB caches translations; with t = 10 ns, m = 100 ns and a 99% hit ratio the EAT is 111 ns. Multilevel, hashed and inverted tables keep huge address spaces affordable.
  • Segmentation matches the programmer's view and protects logical units, but its variable sizes bring back external fragmentation.
  • The Midterm covers Weeks 1 to 7; prepare by redoing traces by hand.
