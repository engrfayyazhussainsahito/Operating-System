Processes

What a process is, how the operating system represents it with a process control block, how it moves between states, how the CPU is switched between processes, and how Unix creates, runs and reaps them with fork, exec and wait.

What you will be able to do

By the end of this week you will be able to:

  • Distinguish a program from a process and name the four regions of a process's address space
  • Draw the five-state process model and label each transition with the event that causes it
  • List what a process control block stores and what the kernel saves and restores in a context switch
  • Compute the CPU overhead of context switching from a switch cost and a time slice
  • Predict the output and the process count of small programs that call fork
  • Explain what exec replaces, what it preserves, and why a shell needs both fork and exec
  • Explain how zombie and orphan processes arise and how wait prevents them

In Week 1 you saw that the operating system exists to share one machine among many programs safely, and that programs ask for its services through system calls. This week we give a name to the thing the OS is actually sharing the CPU among: the process. Almost everything later in the course is phrased in terms of processes. The scheduler of Week 4 chooses among them, the memory manager of Week 8 gives each one an address space, and the file system of Week 12 tracks which ones have which files open.

We start with the definition and the anatomy of a process, then follow it through its life: creation, running, waiting, being switched out, and dying. The second half is practical. You will write C programs that call fork, exec and wait, watch a zombie process appear in /proc, and finish by building a miniature shell. Week 3 then shows how processes talk to each other and how threads let one process do several things at once.

What is a process?

Program versus process

A program is a passive thing: a file on disk containing instructions and initialized data, such as /bin/ls. A process is that program in execution: the program plus all the changing state needed to run it (where it is in the code, the values of its variables, the files it has open). One program can be several processes at once. If three users each run ls, there are three processes and one program file.

Recipe and cook

A program is a recipe in a cookbook. A process is a cook actively following the recipe: they have a current step, a half-chopped onion, and a pan on the stove. Two cooks can follow the same recipe at the same time in separate kitchens with different results. The cookbook does not change; the kitchens do.

Process

A process is an instance of a program in execution. It consists of an address space (code, data, heap and stack), the CPU state (program counter, registers, stack pointer), and the kernel's bookkeeping about it: its identifier, open files, owner and scheduling information.

The address space of a process

Each process sees its own private block of memory addresses, called its address space (the hardware and OS trick behind this is Week 8). By convention a Unix process lays it out in four regions plus the kernel's part:

  • Text (code): the machine instructions. Read-only and executable, so several processes running one program can share a single physical copy.
  • Data: global and static variables. The part with explicit initial values (int g = 5;) is the initialized data segment. The part initialized to zero is the bss segment, which the program file records only as a size.
  • Heap: memory obtained at run time with malloc. It grows toward higher addresses.
  • Stack: one frame per active function call, holding local variables, arguments and the return address. It grows toward lower addresses.

You can see the regions for yourself by printing one address from each:

#include <stdio.h>
#include <stdlib.h>

int global_init = 5;                   /* data segment */
int global_zero;                       /* bss */

int main(void) {
    int local = 1;                     /* stack */
    int *heap = malloc(sizeof *heap);  /* heap */
    printf("text  (main)        %p\n", (void *)main);
    printf("data  (global_init) %p\n", (void *)&global_init);
    printf("bss   (global_zero) %p\n", (void *)&global_zero);
    printf("heap  (malloc)      %p\n", (void *)heap);
    printf("stack (local)       %p\n", (void *)&local);
    free(heap);
    return 0;
}

A run on a 64-bit Linux machine printed:

text  (main)        0x55e363d331a9
data  (global_init) 0x55e363d36010
bss   (global_zero) 0x55e363d36018
heap  (malloc)      0x55e3882d32a0
stack (local)       0x7ffd80564eac

Text, data and bss sit close together, the heap is elsewhere, and the stack is far above. Run it twice and every address changes. That is address space layout randomization (ASLR), a security feature that makes it harder for an attacker to guess where code and data live (Week 14). The order of the regions stays the same.

Process states and the PCB

The five-state model

At any instant a process is doing one of a small number of things. The classic model uses five states:

State Meaning
New The process is being created; the OS is setting up its structures
Ready It could run right now but is waiting for a CPU
Running Its instructions are executing on a CPU
Waiting (blocked) It cannot continue until some event occurs, such as I/O completing
Terminated It has finished; the OS is cleaning up

Only as many processes can be Running as there are CPU cores. On a one-core machine exactly one process is Running and the rest are Ready or Waiting.

Two transitions deserve attention. A process that finishes waiting goes to Ready, not straight to Running: the CPU may be busy with another process, and the scheduler decides who runs next. And a Running process may leave involuntarily (the timer interrupt expires its time slice, going back to Ready) or voluntarily (it asks for something slow, going to Waiting). You cannot go directly from Waiting to Running or from Ready to Waiting, since a process that is not running cannot execute the instruction that would block it.

Linux names these states a little differently. In the output of ps, R means running or ready, S is an interruptible sleep (waiting), D is an uninterruptible sleep (usually waiting on disk), T is stopped, and Z is a zombie, which we meet shortly.

The demo below lets you drive a process through these states. Try to force an illegal move (for example, send a Waiting process directly to Running) and read the explanation it gives. Then run a sequence in which the same process alternates between CPU work and I/O, and count how many times it is dispatched.

The process control block

The kernel needs somewhere to keep everything it knows about a process. That record is the process control block (PCB), also called a process descriptor or task struct (in Linux it is the C structure task_struct).

Process control block (PCB)

The PCB is the kernel data structure holding all per-process information: the process identifier (PID), the state, the saved CPU registers including the program counter and stack pointer, scheduling information (priority, time used), memory-management information (page table pointers), accounting information, the table of open files, and links to the parent and children.

A tiny model of a PCB and the legal state moves makes the picture concrete. This program encodes Figure 2.2 and rejects the illegal move from Waiting to Running:

#include <stdio.h>

/* A toy PCB and the legal state transitions from Figure 2.2. */
enum state { NEW, READY, RUNNING, WAITING, TERMINATED };
static const char *names[] = { "NEW", "READY", "RUNNING", "WAITING", "TERMINATED" };

struct pcb {
    int pid;
    enum state st;
    unsigned long pc;                  /* saved program counter */
    unsigned long regs[4];             /* saved general registers */
};

static int legal(enum state from, enum state to) {
    switch (from) {
    case NEW:     return to == READY;
    case READY:   return to == RUNNING;
    case RUNNING: return to == READY || to == WAITING || to == TERMINATED;
    case WAITING: return to == READY;
    default:      return 0;
    }
}

static void move(struct pcb *p, enum state to) {
    if (legal(p->st, to)) {
        printf("pid %d: %-10s -> %s\n", p->pid, names[p->st], names[to]);
        p->st = to;
    } else {
        printf("pid %d: %-10s -> %s  ILLEGAL\n", p->pid, names[p->st], names[to]);
    }
}

int main(void) {
    struct pcb p = { 42, NEW, 0x400000, {0} };
    move(&p, READY);      /* admitted */
    move(&p, RUNNING);    /* dispatched */
    move(&p, WAITING);    /* issued read() */
    move(&p, RUNNING);    /* illegal: must pass through READY */
    move(&p, READY);      /* I/O completed */
    move(&p, RUNNING);
    move(&p, TERMINATED); /* exit() */
    return 0;
}

Compiled with gcc -Wall, it prints:

pid 42: READY      -> RUNNING
pid 42: RUNNING    -> WAITING
pid 42: WAITING    -> RUNNING  ILLEGAL
pid 42: WAITING    -> READY

Context switching

What a switch does

The CPU has one set of registers, but many processes want to use it. When the kernel takes the CPU from process A and gives it to process B, it performs a context switch: it saves A's CPU state into A's PCB, selects B, and loads B's saved state into the CPU, so that B resumes exactly where it left off, unaware that time passed.

Context switch

A context switch is the act of saving the state (the context) of the currently running process and restoring the saved state of another, so that the CPU changes from running one to running the other. The context includes the program counter, the general and floating-point registers, the stack pointer and the pointer to the page tables.

A switch is triggered either by an interrupt (the timer fires, or a device finishes) or by a system call (the process blocks or exits). In every case the CPU first enters kernel mode, which is itself a small cost, as Week 1 described.

Why the cost matters

During the switch the machine does no useful work for any user program, so a context switch is pure overhead. The direct cost (saving and loading registers, running the scheduler, changing the page-table base register) is typically a few microseconds. There are indirect costs too: B finds the CPU caches full of A's data, so B suffers cache misses until its own working set is loaded, and on many CPUs the TLB (the cache of address translations from Week 8) must be flushed or tagged. Those indirect costs often exceed the direct ones.

If a context switch costs s and the CPU runs each process for a time slice q before switching, the fraction of time lost is s / (q + s). With s = 5 µs and q = 10 ms the overhead is 5 / 10005, about 0.05 percent, negligible. With q = 100 µs it is 5 / 105, about 4.8 percent, and the system starts to feel the cost. This trade-off between responsiveness (short slices) and efficiency (long slices) returns in Week 4.

A context switch is not a mode switch

Entering the kernel for a system call and returning to the same process is a mode switch, and it is much cheaper than a context switch, because no other process's state is loaded. A context switch happens only when the CPU is handed to a different process (or, in Week 3, a different thread).

Creating processes with fork

Parents, children and the process tree

In Unix, processes are created by other processes. The creator is the parent, the new process is the child, and the result is a tree. At boot the kernel starts one first user process (traditionally init, now often systemd) with PID 1, and every other process descends from it. The command pstree draws this tree. Each process has a unique process identifier (PID) that getpid() returns, and getppid() returns the parent's.

The system call that creates a process is fork(). It is unusual because it returns twice, once in each process.

fork()

fork() creates a new process that is a near-exact copy of the caller: the same code, a copy of the data, heap and stack, the same open files and the same program counter. It returns the child's PID to the parent, 0 to the child, and -1 (with errno set) if it fails. After the call returns, the two processes run independently and the scheduler may run either first.

#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int x = 100;
    printf("before fork: pid=%d\n", (int)getpid());
    fflush(stdout);                    /* empty the buffer so it is not copied */
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        x += 1;                        /* changes the child's private copy */
        printf("child : pid=%d parent=%d x=%d\n", (int)getpid(), (int)getppid(), x);
        exit(7);
    } else {
        int status;
        waitpid(pid, &status, 0);
        printf("parent: pid=%d x=%d, child %d exited with status %d\n",
               (int)getpid(), x, (int)pid,
               WIFEXITED(status) ? WEXITSTATUS(status) : -1);
    }
    return 0;
}

Output from a real run (PIDs differ every time):

before fork: pid=219
child : pid=220 parent=219 x=101
parent: pid=219 x=100, child 220 exited with status 7

Read the code as one story told twice. Everything before fork() ran once. Everything after runs in both processes, and pid is the only variable that differs, so the if chain splits the two roles. The child changed x to 101, but the parent's x is still 100: after the fork the two address spaces are separate, so writes in one are invisible to the other. Real kernels do not copy all the memory up front. They use copy-on-write, sharing the physical pages and copying a page only when one process writes to it, a trick we develop in Week 9.

The parent called waitpid to block until that particular child ended and collect its exit status. The child passed 7 to exit, and WEXITSTATUS extracted it.

Photocopying the whole kitchen

Imagine a cook who, at the moment of fork, photocopies the entire kitchen along with themselves, including the half-chopped onion. Both cooks continue from the same instant. The only difference is a note pinned to each: the original gets "your new twin is number 220", the copy gets "you are the twin". They cannot reach into each other's kitchen, so they must send messages (Week 3) to cooperate.

Running new programs: exec and the shell

fork alone only produces copies of the same program. To run a different program, a process calls one of the exec family of functions (execl, execlp, execv, execvp, and others, all wrappers around the execve system call). exec replaces the calling process's code, data, heap and stack with a new program loaded from a file, and starts it at its beginning. The PID stays the same, and open files stay open (unless marked close-on-exec). exec does not create a process; it transforms the one that called it. On success it never returns, because the code that called it is gone.

#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        execlp("echo", "echo", "hello from the new program", (char *)NULL);
        perror("execlp");              /* reached only if exec failed */
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);
    printf("parent: child finished, status %d\n", WEXITSTATUS(status));
    return 0;
}

hello from the new program
parent: child finished, status 0

The first argument names the program to find on the PATH, and the argument list that follows becomes the new program's argv, starting with its own name and ending with a null pointer. The line after execlp is only reachable when exec fails, for example when the program does not exist, so it reports the error and exits with the conventional status 127.

Why two calls instead of one?

Windows has a single CreateProcess call that takes the program name and a long list of options. Unix splits creation into fork and exec, and the gap between them is where the power lies. Between the two calls, the child (still running the shell's code) can rearrange its own environment: redirect standard output to a file, connect a pipe, change directory or drop privileges. Then exec runs the new program, which inherits that rearranged environment without knowing anything about it. That is how ls > out.txt works with a plain ls program that simply writes to file descriptor 1.

This also explains why cd is a shell built-in. If cd were an external program run in a child, it would change the directory of the child, which then exits, and the shell's own directory would be unchanged. A command that must modify the shell's own state has to run inside the shell process.

fork in Unix

The fork and exec pair comes from the earliest versions of Unix at Bell Labs around 1970, designed by Ken Thompson and Dennis Ritchie. The idea of a process cloning itself was borrowed from earlier systems, and the design was praised for its small implementation. Critics note that fork is awkward in multithreaded programs and for processes with large memory, and Linux provides posix_spawn and vfork for the common case of "create and immediately exec".

Ending processes: wait, zombies and orphans

A process ends when it returns from main, calls exit, or is killed by a signal. The kernel then frees its memory and closes its files. But it cannot discard the PCB entirely, because the parent may still want the exit status. So the PCB lingers until the parent collects it with wait or waitpid.

Zombie and orphan

A zombie process has terminated but its parent has not yet called wait, so its PCB (PID, exit status) remains in the table. It uses no CPU or memory beyond that entry. An orphan process is one whose parent has terminated while it still runs. The kernel reparents orphans to PID 1 (or a designated "subreaper" process), which calls wait on them when they finish.

The next program creates a zombie on purpose. The child exits immediately; the parent sleeps for a second without waiting, then reads the child's state letter from /proc:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

/* Read the state letter of a process from /proc/<pid>/stat. */
static char state_of(pid_t pid) {
    char path[64], buf[256];
    snprintf(path, sizeof path, "/proc/%d/stat", (int)pid);
    FILE *f = fopen(path, "r");
    if (!f) return '?';
    if (!fgets(buf, sizeof buf, f)) { fclose(f); return '?'; }
    fclose(f);
    char *p = strrchr(buf, ')');       /* the name sits in parentheses */
    return p ? p[2] : '?';
}

int main(void) {
    pid_t pid = fork();
    if (pid == 0) _exit(0);            /* child ends at once */
    sleep(1);                          /* parent does not wait yet */
    printf("child %d state before wait: %c\n", (int)pid, state_of(pid));
    waitpid(pid, NULL, 0);
    printf("child state after wait:    %c\n", state_of(pid));
    return 0;
}

child 411 state before wait: Z
child state after wait:    ?

Before waitpid, the child is Z, a zombie. After it, the entry is gone, so /proc has no file and the function returns ?. Zombies cannot be killed, because they are already dead; the only cure is for the parent to wait, or to exit so that PID 1 inherits and reaps the child. A long-running server that forks children and never waits fills the process table with zombies until fork starts failing.

The mirror image is the orphan. Here the parent exits first, and the child prints who its parent is afterwards:

#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        sleep(1);                      /* outlive the parent */
        printf("child : my parent is now pid %d\n", (int)getppid());
        return 0;
    }
    printf("parent: exiting, child is %d\n", (int)pid);
    return 0;
}

parent: exiting, child is 413
child : my parent is now pid 1

On a desktop Linux with a per-user service manager the adopting process may be a different PID than 1, but it is always some long-lived "reaper" process.

Process queues and schedulers

With many processes the kernel organizes PCBs into queues. The ready queue holds processes in the Ready state, waiting for a CPU. Each device has a wait queue holding processes blocked on it. A process migrates between these queues as its state changes, and the scheduler's job is to choose the next PCB from the ready queue.

Textbooks describe three scheduling decisions made at different time scales:

Scheduler Decides How often Notes
Long-term (job) Which new jobs are admitted to the ready pool Seconds to minutes Controls the degree of multiprogramming; rare in modern desktop systems
Medium-term Which processes to swap out of memory and back Seconds Used when memory is short (Week 9)
Short-term (CPU) Which ready process runs next Milliseconds Must be very fast; the topic of Week 4

Processes also differ in behaviour. An I/O-bound process spends most of its time waiting for I/O and uses the CPU in short bursts. A CPU-bound process uses long CPU bursts with rare I/O. A good mix of both keeps the CPU and the devices busy together, which is the original reason to multiprogram.

Exercises

Exercise 2.1core

Count the processes

How many processes exist (including the original) after this fragment runs, if every fork succeeds?

fork();
if (fork() == 0)
    fork();
Show solution

After the first fork there are two processes: P and C1. Both then execute the fork() inside the condition. P creates C2 and C1 creates C3, giving four processes. In each of these four the condition tests the value just returned. P and C1 received a non-zero PID, so they skip the body. C2 and C3 received 0, so each executes fork() again, creating C4 and C5. Total: P, C1, C2, C3, C4 and C5, which is 6 processes. As a check, fork is executed once by 1 process, then once by 2, then once by 2, which is 5 calls, each creating one process, so 1 + 5 = 6.

Exercise 2.2warm-up

Predict the output

What does this program print, and in what order? Is the order guaranteed?

int x = 1;
if (fork() == 0) {
    x = 2;
} else {
    wait(NULL);
    x = x + 10;
}
printf("%d\n", x);
Show solution

The child sets its own copy of x to 2 and prints 2, then exits. The parent was blocked in wait until the child exited, so only afterwards does it compute x = 1 + 10 = 11 using its own unchanged copy and print 11. The output is 2 then 11. The order is guaranteed because wait forces the parent to run its printf after the child has finished. Without the wait, the order would depend on the scheduler.

Exercise 2.3challenging

Buffered output and fork

Consider this program.

#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("A\n");
    fork();
    printf("B\n");
    return 0;
}

How many A lines are printed when stdout is a terminal, and how many when it is redirected to a file with ./a.out > out.txt? Explain.

Show solution

On a terminal, stdout is line-buffered: "A\n" is flushed as soon as the newline is written, before fork, so the buffer is empty at the fork. The output has one A and two B lines. When redirected to a file, stdout is fully buffered, so "A\n" is still sitting in the user-space buffer when fork copies the address space. Each process inherits a buffer holding "A\n", appends "B\n" and flushes it on exit. The file therefore contains A, B, A, B: two A lines. The fix is fflush(stdout) before fork, which is why the earlier listing has one.

Exercise 2.4warm-up

Label the transitions

A process is admitted, runs, calls read() on a slow disk, gets its data, runs again until its time slice expires, runs a third time and finally calls exit. Write the sequence of state transitions with the cause of each, and count how many times the process was dispatched.

Show solution

New to Ready (admitted by the OS); Ready to Running (dispatched); Running to Waiting (blocks on read); Waiting to Ready (disk interrupt, data available); Ready to Running (dispatched); Running to Ready (timer interrupt, time slice expired); Ready to Running (dispatched); Running to Terminated (exit). The Ready to Running transition occurs three times, so the process was dispatched 3 times.

Exercise 2.5core

Context-switch overhead

A context switch takes 8 µs. Compute the fraction of CPU time lost to switching for time slices of 100 ms, 1 ms and 50 µs, assuming a switch after every slice. For which of them would you worry?

Show solution

Overhead = s / (q + s) with s = 8 µs. For q = 100 ms = 100,000 µs: 8 / 100,008 = 0.008 percent. For q = 1 ms = 1000 µs: 8 / 1008 = 0.79 percent. For q = 50 µs: 8 / 58 = 13.8 percent. The first two are negligible; the third wastes more than one-eighth of the machine, so a slice that short is a bad design (and the indirect cache costs would make it worse).

Exercise 2.6core

Why is cd a built-in?

Suppose cd were an ordinary program such as /bin/cd that calls chdir. Explain precisely why typing cd /tmp in the shell would then appear to do nothing. Name one other shell command that must be built in for the same reason.

Show solution

The shell would fork a child, and the child would exec /bin/cd, which calls chdir("/tmp"). The current directory is a property of the process that calls chdir, so only the child's directory changes. The child then exits, and the parent shell still sits in its old directory. A command that changes the shell's own state must therefore be executed by the shell itself. Other examples: exit, export (setting an environment variable that later commands inherit) and umask.

Exercise 2.7challenging

Cost of fork with copy-on-write

A parent has 400 MiB of resident memory in 4 KiB pages. It forks a child. Compare the extra physical memory needed (ignoring page tables) if (a) fork copies everything immediately, and (b) the system uses copy-on-write and the child writes to 10 percent of the pages before exiting. How much work does a following exec save?

Show solution

Number of pages = 400 MiB / 4 KiB = 400 × 1024 / 4 = 102,400 pages. (a) Copying everything costs another 400 MiB, all 102,400 pages. (b) With copy-on-write, only the written pages are copied: 10 percent of 102,400 = 10,240 pages, which is 40 MiB, one tenth of the eager cost. If the child immediately calls exec, it discards its address space without writing to almost any page, so (nearly) zero pages are copied: the full 400 MiB copy in (a) would have been wasted entirely. This is why copy-on-write makes the fork then exec pattern cheap.

Lab: build a mini shell

You will write a shell that prints a prompt, reads a line, splits it into words, runs it with fork, execvp and waitpid, and reports non-zero exit statuses. It implements two built-ins, cd and exit. This is the core of Assignment 1 in Week 4. Save the code as mini.c.

#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

/* A tiny shell: read a line, split on spaces, fork, exec, wait. */
int main(void) {
    char line[256];
    for (;;) {
        printf("mini$ ");
        fflush(stdout);
        if (!fgets(line, sizeof line, stdin)) break;
        char *argv[16];
        int n = 0;
        for (char *tok = strtok(line, " \t\n"); tok && n < 15; tok = strtok(NULL, " \t\n"))
            argv[n++] = tok;
        argv[n] = NULL;
        if (n == 0) continue;
        if (strcmp(argv[0], "exit") == 0) break;
        if (strcmp(argv[0], "cd") == 0) {   /* must run in the shell itself */
            if (n > 1 && chdir(argv[1]) != 0) perror("cd");
            continue;
        }
        pid_t pid = fork();
        if (pid == 0) {
            execvp(argv[0], argv);
            perror(argv[0]);
            _exit(127);
        }
        int status;
        waitpid(pid, &status, 0);
        if (WIFEXITED(status) && WEXITSTATUS(status) != 0)
            printf("[exit %d]\n", WEXITSTATUS(status));
    }
    printf("\n");
    return 0;
}

Build and try it, either interactively or by feeding it commands:

gcc -Wall -pthread mini.c -o mini
printf 'echo hi there\nls /nonexistent\nfoo\ncd /tmp\npwd\nexit\n' | ./mini

What to observe. The real output from that run was:

mini$ hi there
mini$ ls: cannot access '/nonexistent': No such file or directory
[exit 2]
mini$ foo: No such file or directory
[exit 127]
mini$ mini$ /tmp
mini$

Each prompt appears right after the previous command finishes because the shell waits. ls fails with status 2, an unknown command makes execvp fail so the child reports the error and exits 127, and after the built-in cd /tmp the next command pwd prints /tmp, proving that the directory change took effect in the shell itself. Try removing the waitpid and run echo hi several times, then in another terminal run ps -o pid,stat,cmd --ppid $(pgrep mini) to watch zombies accumulate.

Extensions.

  1. Run a command in the background when the line ends in & (do not call waitpid immediately) and reap finished children with waitpid(-1, &status, WNOHANG) before each prompt, so that no zombies remain.
  2. Add output redirection cmd > file: in the child, before execvp, open the file and use dup2 to make it file descriptor 1. Explain why this must happen between fork and exec.
  3. Print the state letter of the last child (as in the zombie listing) just before you reap it, and the elapsed time of each command using clock_gettime.

Common mistakes and debugging tips

Symptom Likely cause What to do
Output appears twice or in a surprising order Unflushed stdio buffer copied by fork, or no wait to order parent and child Call fflush(stdout) before fork; use waitpid when order matters
Program creates processes without limit and the machine slows down A child falls through the if (pid == 0) branch and continues into the parent's loop End the child branch with exit or _exit; check fork return values
ps shows entries marked Z or <defunct> Parent never calls wait for terminated children Reap with wait or waitpid, or handle SIGCHLD
Child prints "No such file or directory" then exits with 127 exec failed: wrong program name, not on PATH or not executable Check the name, use execvp to search PATH, and always handle a failing exec
Code after exec never runs That is expected: exec replaces the program and returns only on error Put follow-up logic in the parent, or in the new program
cd in a child has no effect The directory belongs to the process that called chdir Make cd a built-in executed by the shell itself
fork returns -1 Process limit or memory exhausted Print perror, check ulimit -u, and make sure children are being reaped

Key takeaways

Key takeaways

  • A process is a program in execution: an address space (text, data/bss, heap, stack) plus CPU state plus kernel bookkeeping held in its PCB.
  • Processes move among New, Ready, Running, Waiting and Terminated. Only the scheduler's dispatch moves a process from Ready to Running, and a process whose event completes returns to Ready.
  • A context switch saves one process's context in its PCB and loads another's. It is pure overhead, roughly s / (q + s) of CPU time for a switch cost s and slice q.
  • fork clones the caller and returns the child's PID to the parent and 0 to the child; exec replaces the program in place; wait collects the exit status.
  • Splitting creation into fork and exec lets a shell prepare the child's environment (redirection, pipes) before the new program starts.
  • Terminated processes stay as zombies until their parent waits; orphans are adopted by PID 1.
