What you will be able to do

By the end of this week you will be able to:

  • Connect the major mechanisms of the course (processes, memory, storage, protection) into one coherent picture of an operating system
  • Apply the cumulative formulas and algorithms to numeric problems and show the units and conventions used
  • Diagnose a failing program by choosing the right tool for races, deadlocks, memory and descriptor leaks, zombies and permission errors
  • Scope, schedule and evaluate a final project so that its claims are backed by measurements
  • Combine fork, pipe, threads and shared memory in one correct program and explain each ownership and cleanup decision
  • Choose a real kernel or source tree to study next and read it with a clear question in mind
  • Solve a mixed, cumulative set of exam problems under time pressure and check the numeric answers

Fifteen weeks ago Week 1 asked what an operating system is for. The answer was two jobs: manage the hardware resources fairly and efficiently, and present abstractions that make the hardware usable. Everything since then has been one of those two jobs seen up close: the process and the thread as abstractions of the CPU, schedulers and synchronization as the management of it, virtual memory as both an abstraction and a resource policy, files as an abstraction of storage, and protection as the rule that keeps all of it safe to share.

This final chapter does not introduce new mechanisms. It ties the old ones together, gives you a one-page reference of every formula and convention we used, lists the habits that find bugs quickly, and prepares you for the two remaining deliverables: the final project report and the cumulative final exam. It ends with the longest exercise set of the course, a practice final that touches every week, and a lab that deliberately mixes four earlier ideas in one program.

Units and off-by-one traps

Convert everything to one unit before you substitute (1 ms = 1,000,000 ns). Page and block numbers start at 0. In SCAN-family problems state whether the jump of C-SCAN is counted; in this course it is. When a formula uses both a hit ratio and a miss ratio, write (1 − h) explicitly instead of doing it in your head. Finally, write the unit next to every number you carry: most lost marks are wrong units, not wrong ideas.

Debugging checklist

Operating systems bugs have a reputation for being hard because they depend on timing, hidden state or the environment. The cure is a habit: reproduce, shrink, observe, then fix, and always match the tool to the class of bug. Figure 16.3 gives a quick decision path.

Races

Data race

A data race is two threads accessing the same memory location, at least one of them writing, with no synchronization ordering the accesses. It is narrower than a race condition, which is any result that depends on timing.

Compile with gcc -g -fsanitize=thread -pthread and run the program: ThreadSanitizer instruments memory accesses and reports both conflicting stacks. Valgrind's --tool=helgrind does the same without recompiling, but slower. Remember that a clean run proves little, because the bad interleaving may not have happened; a bug that disappears when you add a print statement or run under a debugger is called a Heisenbug, and it nearly always means a race. Run the test many times, on several cores, under load (a stress test), and keep the failing seed or command.

Checklist: Is every shared variable protected by the same lock on every path? Do you hold the lock across the whole read-modify-write? Is every condition-variable wait in a while loop with the predicate in shared state? Did you pass the address of a loop variable to a thread?

Deadlocks

When a program hangs with no CPU use, attach with gdb -p PID and run thread apply all bt. Threads sitting in pthread_mutex_lock or futex wait calls show which lock each one wants; draw the wait-for graph and look for a cycle (Week 7). Fixes in order of preference: impose one global lock order, hold fewer locks, use pthread_mutex_trylock and back off, or keep each critical section free of calls that take other locks. If the hang has CPU use, suspect a spin or a livelock instead.

Memory errors and leaks

A memory leak is memory that was allocated and is still held but can no longer be used, because the last pointer to it was lost. Leaks make a long-running server grow until the OOM killer (Week 10) ends it. A use-after-free is reading or writing memory after free, and a double free releases the same block twice; both corrupt the allocator's lists. Compile with gcc -g -fsanitize=address: AddressSanitizer places guard zones around allocations and reports out-of-bounds access, use-after-free and (on Linux, through its leak detector) leaks at exit. Valgrind (valgrind --leak-check=full ./prog) needs no recompilation and runs the program on a simulated CPU, much more slowly. For a crash, enable a core dump (ulimit -c unlimited), the file the kernel writes holding the memory image of a crashed process, and open it with gdb ./prog core to print the backtrace (the chain of function calls active at the crash, bt in gdb).

Descriptor leaks

Every open, socket, pipe and accept consumes a file descriptor, and each process has a resource limit (RLIMIT_NOFILE, shown by ulimit -n, often 1024 for the soft limit) on how many it may hold. A file descriptor leak is a descriptor that is never closed; the symptom is the error EMFILE, "Too many open files", usually after hours. List them with ls -l /proc/PID/fd or lsof -p PID and look for many copies of the same file or socket. The cure is a clear owner for each descriptor, a close on every exit path (including errors), and closing unused pipe ends after fork so that readers see EOF. Descriptors are inherited across fork and exec unless marked O_CLOEXEC, so a parent's leak can hold a socket open in a child.

Zombies and orphans

A terminated child stays in the process table as a zombie until its parent calls wait or waitpid (Week 2). ps -o pid,ppid,stat,cmd shows them with state Z and <defunct>. Zombies use no CPU, but each holds a process-table slot, so thousands can exhaust PIDs. Fix the parent (find it with ppid): call waitpid in a loop or handle SIGCHLD. Killing a zombie does nothing; when its parent exits, PID 1 adopts and reaps it.

Permissions

"Permission denied" has many causes, so find the one that failed. Run id to see your user and groups, ls -l and stat for the mode and owner, and namei -l /full/path to show the permissions of every directory along the path (a missing x on one directory blocks everything below it). Check getfacl for ACLs, mount options such as ro or noexec, a umask that removed bits at creation, and security modules (SELinux or AppArmor) in the audit log. A setuid program that fails usually sits on a file system mounted nosuid, or has the wrong owner (Week 14). Never fix permissions with chmod 777: that hides the problem and removes the protection.

A general method

  1. Reproduce reliably; make the smallest input that still fails. 2. Form one hypothesis about the class of bug (Figure 16.3). 3. Observe with strace, a sanitizer or a debugger instead of guessing. 4. Change one thing at a time. 5. Write a regression test, so the bug cannot return unnoticed.

The final exam

The final exam is cumulative, with extra weight on Weeks 8 to 15, since the midterm already covered Weeks 1 to 7. Check your syllabus for the date, the length and what you may bring; the practice final below assumes a closed-book exam with a single sheet of formulas, which is why the cheat sheet above is deliberately one page of tables. Two rules help most. First, every numeric problem should show its formula, its substitution and its unit. Second, trace problems (scheduling, page replacement, Banker's, disk scheduling) should be done as a table with one row per step; a table is checkable and gets partial credit when one entry is wrong.

For the last two weeks: re-derive each table above from the definitions on blank paper, redo the in-chapter traces, take the practice final in one sitting under a time limit, then mark it and repeat only the topics you missed. Explaining an answer aloud to a partner is the best test of understanding.

Next steps

Reading real source code

Textbook ideas become concrete in code. The best first stop is xv6, a re-implementation of Sixth Edition Unix for RISC-V, written at MIT for teaching. Its whole kernel is a few thousand lines: proc.c holds fork, scheduling and sleep and wakeup; vm.c the page tables; fs.c, log.c and bio.c an inode file system, a write-ahead log and a buffer cache; pipe.c and sysfile.c the system calls. Because it is small enough to read in full, you can follow a single write from the trap handler to the disk driver. Pair it with the xv6 book and with John Lions' commentary on the original Unix source, which has taught students the same way for decades.

Linux is the opposite: enormous, but organized along the lines of this course. Start where the chapters point. kernel/sched/ has the scheduler classes and CFS (now EEVDF); mm/ the page fault path, the page cache, reclaim and the OOM killer; fs/ the VFS and ext4 (with jbd2 for the journal); block/ the I/O schedulers; kernel/fork.c the clone family; kernel/cgroup/ and kernel/nsproxy.c the container mechanisms; security/ the security modules. Do not read top to bottom. Pick a question, such as "what happens in the kernel during fork?", and follow it with git grep, a cross-referenced source browser or ctags and cscope, reading the function called at each step. Use strace and perf trace to see which system calls a real program issues first, then find those entry points in the source. The kernel's own Documentation/ directory and the weekly articles on LWN.net explain why the code looks the way it does.

Read with a question

Reading a large code base from the first line is like reading a dictionary. Choose a question that this course has taught you to ask ("where is the page table walked?", "where is the lock that protects this list?"), find the answer, and write down the call chain. Ten such chains teach more than ten hours of browsing.

Careers and further study

An OS course prepares you for work well beyond kernels. Systems and infrastructure engineers build servers, databases, storage and cloud platforms, where scheduling, caching, durability and isolation decide cost. Site reliability and performance engineers diagnose production systems with the tools of the debugging checklist. Kernel, driver and embedded developers work near the hardware, with real-time limits (Week 4). Security engineers apply protection and isolation (Week 14). Compiler, runtime and database engineers depend on the memory model, threads and I/O of the OS. To go further, take architecture, networks, distributed systems and databases, read the papers listed below, and contribute a small fix to an open-source project. The habit that transfers everywhere is the one this course practiced: for any component, ask what resource it manages, what abstraction it offers, what invariants it keeps and what happens when something fails.

Exercises

This practice final has 28 questions, ordered by week. Warm-up questions are quick checks, core questions are the typical exam problems, and the challenging ones need two or three ideas together. Try each one on paper before reading the solution.

Exercise 16.1warm-up

1. Privileged or not?

Which of these actions need kernel mode? (a) adding two registers, (b) disabling interrupts, (c) writing the timer's reload register, (d) reading a variable on your own heap, (e) executing the syscall instruction.

Show solution

(b) and (c) are privileged instructions: executing them in user mode causes a trap. (a) and (d) are ordinary user-mode operations. (e) is allowed in user mode, because it is the controlled way to enter the kernel: it switches to kernel mode and jumps to a fixed handler address, so the program cannot choose where kernel code starts.

Exercise 16.2warm-up

2. Process states

A running process calls read() on a disk file that is not cached, the disk finishes, and later the timer interrupt fires while the process is running again. Give the sequence of states and the cause of each transition.

Show solution

Running → Waiting (blocked on the disk I/O, so it gives up the CPU). Waiting → Ready (the I/O completion interrupt wakes it). Ready → Running (the scheduler dispatches it). Running → Ready (the timer interrupt ends its time slice: preemption). Only the scheduler moves a process from Ready to Running.

Exercise 16.3core

3. Context-switch overhead

A context switch costs 0.1 ms. What fraction of CPU time is lost to switching if the quantum is (a) 10 ms and (b) 1 ms? Why not choose a very small quantum?

Show solution

Overhead = s / (q + s). (a) 0.1 / 10.1 = 0.0099, about 0.99%. (b) 0.1 / 1.1 = 0.0909, about 9.09%.

A very small quantum improves response time but spends more and more of the CPU on switching (with q = s half of the time is wasted), and also destroys cache and TLB contents. A quantum should be longer than most CPU bursts but short enough to keep interactive tasks responsive.

Exercise 16.4core

4. Counting processes

How many processes exist (including the original one) after each of these fragments, assuming every fork succeeds?

for (int i = 0; i < 4; i++) fork();            /* (a) */

for (int i = 0; i < 4; i++)                     /* (b) */
    if (fork() == 0) break;
Show solution

(a) Every process, parent and child, continues the loop, so each pass doubles the count: 2⁴ = 16 processes (15 new ones).

(b) Each child breaks out of the loop and creates nothing, while only the original parent continues. The parent creates one child per pass: 1 + 4 = 5 processes.

Exercise 16.5core

5. Why does the reader hang?

The parent creates a pipe and forks. The child writes a message and exits. The parent loops on read(fd[0], ...) until it returns 0, but the program never finishes. Why, and what is the fix?

int fd[2]; pipe(fd);
if (fork() == 0) { write(fd[1], "hi", 2); _exit(0); }
char buf[16]; ssize_t n;
while ((n = read(fd[0], buf, sizeof buf)) > 0) { /* use data */ }
Show solution

read returns 0 (end of file) only when every write end of the pipe is closed. The child's copy closes at exit, but the parent still holds its own copy of fd[1], so the kernel knows a writer could still write and the read blocks forever. Fix: the parent must close(fd[1]) before the loop (and the child should close(fd[0])). Always close the pipe ends a process does not use.

Exercise 16.6core

6. Scheduling trace

Processes (arrival, burst): A (0, 7), B (1, 4), C (2, 1), D (3, 4). Compute the average waiting time under (a) FCFS, (b) SRTF and (c) round robin with q = 2. When a new arrival and a preempted process reach the ready queue at the same moment, the new arrival goes first.

Show solution

(a) FCFS runs A 0 to 7, B 7 to 11, C 11 to 12, D 12 to 16. Waits: A 0, B 6, C 9, D 9. Average = 24 / 4 = 6.0.

(b) SRTF: A runs 0 to 1; B (4) preempts A (6 left) at 1; C (1) preempts B (3 left) at 2; C ends at 3; B resumes 3 to 6; D (4) runs 6 to 10 since 4 < 6; A finishes 10 to 16. Waits = turnaround − burst: A 16 − 7 = 9, B 5 − 4 = 1, C 0, D 7 − 4 = 3. Average = 13 / 4 = 3.25.

(c) RR q = 2: A 0 to 2, B 2 to 4, C 4 to 5, A 5 to 7, D 7 to 9, B 9 to 11, A 11 to 13, D 13 to 15, A 15 to 16. Completion: A 16, B 11, C 5, D 15. Waits: A 9, B 6, C 2, D 8. Average = 25 / 4 = 6.25.

SRTF is lowest, as it is optimal for average waiting time; RR gives more equal response at the cost of a worse average than FCFS here.

Exercise 16.7challenging

7. Rate-monotonic or EDF?

Three periodic tasks (computation time C, period T = deadline) are (1, 4), (2, 6) and (3, 12). (a) Compute the utilization and compare it with the RM bound. (b) Decide by exact response-time analysis whether RM schedules the set. (c) Does EDF?

Show solution

(a) U = 1/4 + 2/6 + 3/12 = 0.8333, above the RM bound 3 × (2^(1/3) − 1) = 0.7798. The bound is only sufficient, so it settles nothing.

(b) RM priorities by period (4, 6, 12). Task 1: R = 1. Task 2: R = 2 + ⌈R/4⌉ = 3. Task 3: R = 3 + ⌈R/4⌉ × 1 + ⌈R/6⌉ × 2, iterating 6 → 7 → 9 → 10 → 10, so R = 10 ≤ 12. All deadlines are met: RM works despite U exceeding the bound.

(c) EDF is feasible whenever U ≤ 1 (deadline = period): yes.

Exercise 16.8warm-up

8. Trace a lost update

counter is 5. Two threads each run counter++, compiled as load, add, store. Give an interleaving that ends with 6, and say how a mutex prevents it.

Show solution

T1 loads 5; T2 loads 5; T1 adds 1 and stores 6; T2 adds 1 and stores 6. Two increments produced one: a lost update. With a mutex around the whole load-add-store, one thread completes all three steps before the other starts, so the result is always 7. The critical section must cover the whole read-modify-write, not only the store.

Exercise 16.9core

9. Swapped waits

In a bounded buffer, a producer executes wait(mutex); wait(empty); ...; signal(mutex); signal(full). Explain the deadlock and name the deadlock conditions that hold.

Show solution

When the buffer is full the producer takes mutex and then blocks on empty, still holding mutex. The consumer, which would signal(empty), must first wait(mutex), so it blocks too. Neither can proceed. The four conditions hold: mutual exclusion (the mutex), hold and wait (the producer holds mutex while waiting), no preemption (a semaphore cannot be taken away), and circular wait (the producer waits for the consumer's signal, the consumer for the producer's mutex). The fix is the right order: wait(empty) first, then wait(mutex).

Exercise 16.10challenging

10. Dining philosophers

Five philosophers each pick up their left fork and then their right fork. (a) Explain why letting at most four sit at the table prevents deadlock. (b) Explain why numbering the forks and always taking the lower-numbered fork first also does.

Show solution

(a) Deadlock needs every one of the five philosophers to hold one fork and wait for the next, a cycle through all five. With at most four seated there are at least five forks for four diners, so the cycle cannot close and someone can always take both forks, eat and release.

(b) With a global order, each wait goes from a held lower-numbered fork to a wanted higher-numbered one. Numbers strictly increase along a chain, so it cannot loop back: no circular wait. The last philosopher (forks 4 and 0) takes fork 0 first, which breaks the symmetry. This is the lock-ordering rule of Week 7.

Exercise 16.11core

11. Banker's algorithm

Three resource types; Available = (2, 1, 1).

Process Allocation Max
P0 (1, 0, 1) (3, 2, 2)
P1 (2, 1, 0) (3, 2, 1)
P2 (1, 2, 1) (2, 3, 2)
P3 (0, 1, 1) (1, 2, 3)

(a) Compute the Need matrix. (b) Is the state safe? Give a safe sequence. (c) P3 requests (0, 1, 1). Should it be granted?

Show solution

(a) Need = Max − Allocation: P0 (2, 2, 1), P1 (1, 1, 1), P2 (1, 1, 1), P3 (1, 1, 2).

(b) Work = (2, 1, 1). P0 cannot run (B: 2 > 1). P1 can: Work = (4, 2, 1). Then P0: (5, 2, 2); P2: (6, 4, 3); P3: (6, 5, 4), the system total. Safe, sequence P1, P0, P2, P3.

(c) (0, 1, 1) ≤ Need of P3 and ≤ Available, so pretend: Available = (2, 0, 0), P3 Need = (1, 0, 1). P0, P1 and P2 each need B ≥ 1, and P3 needs C ≥ 1, but only A is free. Nobody can finish: unsafe, so deny; P3 waits.

Exercise 16.12challenging

12. How many units guarantee freedom?

Four processes each need at most 3 units of one resource type, requesting one unit at a time. What is the smallest number of units that guarantees deadlock cannot occur? Show that one fewer is not enough.

Show solution

The worst case is every process holding as many units as possible without having its maximum: 2 each, 4 × 2 = 8 units, all waiting for a third. With 8 units the system can deadlock. With 9 units, 8 can be held in the worst case and one is free, so some process gets its third unit, finishes and releases 3 units, letting the others finish. General rule: R ≥ n (m − 1) + 1 = 4 × 2 + 1 = 9.

Exercise 16.13warm-up

13. Paged translation

Pages are 4 KiB. The logical address 20,000 belongs to a page that the page table maps to frame 7. What are the page number, the offset and the physical address?

Show solution

Page = 20,000 div 4096 = 4 (4 × 4096 = 16,384). Offset = 20,000 − 16,384 = 3616. Physical address = 7 × 4096 + 3616 = 28,672 + 3616 = 32,288.

Exercise 16.14core

14. Page table size

A 32-bit address space uses 4 KiB pages and 4-byte page-table entries. (a) How large is a single-level page table? (b) With a two-level table (10 + 10 + 12 bits), how much table memory does a process that uses 12 MiB of contiguous, aligned virtual memory need?

Show solution

(a) The offset takes 12 bits, leaving 20 bits for the page number: 2²⁰ entries × 4 B = 4 MiB per process.

(b) One second-level table holds 1024 entries and maps 1024 × 4 KiB = 4 MiB. 12 MiB needs 3 second-level tables plus 1 top-level table, each 1024 × 4 B = 4 KiB: 4 × 4 KiB = 16 KiB, instead of 4 MiB. Multilevel tables allocate table pages only for regions in use.

Exercise 16.15core

15. Which fit works?

Free holes in memory order: 150, 400, 250, 600 (KB). Requests arrive in order: 200, 350, 100, 500, 120. For first fit, best fit and worst fit, say which requests cannot be placed. Each request is placed in a hole and the remainder stays in the hole.

Show solution

First fit: 200 goes to 400 (left 200); 350 to 600 (left 250); 100 to 150 (left 50); 500 fails (largest hole is 250); 120 goes to the first hole that fits, 200 (left 80). Fails: 500.

Best fit: 200 to 250 (left 50); 350 to 400 (left 50); 100 to 150 (left 50); 500 to 600 (left 100); 120 fails (holes 50, 50, 50, 100). Fails: 120.

Worst fit: 200 to 600 (left 400); 350 to 400 (left 50); 100 to the largest hole, now the other 400 (left 300); 500 fails; 120 to 300 (left 180). Fails: 500.

No policy places everything: each leaves a different request unplaced, which shows external fragmentation and why no fit rule dominates.

Exercise 16.16core

16. EAT with a TLB and page faults

TLB lookup t = 20 ns, memory access m = 100 ns, TLB hit ratio 0.9, one-level page table. (a) Compute the translation-plus-access time without page faults. (b) A page fault takes 8 ms and occurs with probability p = 10⁻⁶ per access. Compute the EAT. (c) What largest p keeps the EAT at most 150 ns?

Show solution

(a) Hit: 20 + 100 = 120 ns. Miss: 20 + 100 + 100 = 220 ns. Average: 0.9 × 120 + 0.1 × 220 = 108 + 22 = 130 ns.

(b) EAT = (1 − 10⁻⁶) × 130 + 10⁻⁶ × 8,000,000 = 129.99987 + 8 = 137.99987, about 138 ns, a 6% slowdown from faults.

(c) 130 + p × (8,000,000 − 130) ≤ 150, so p ≤ 20 / 7,999,870 = 2.5 × 10⁻⁶, about one fault in 400,000 accesses.

Exercise 16.17core

17. Copy-on-write accounting

A parent with 200 resident pages (4 KiB each) calls fork. The child writes to 5 different pages. Afterwards the parent writes to one of those 5 pages and to one other shared page. How many pages are copied in total, and why?

Show solution

At fork nothing is copied: both page tables point to the same 200 frames, marked read-only with a share count of 2 (only the page tables are duplicated). The child's 5 first writes each cause a protection fault and a copy: 5 copies (20 KiB). The parent's write to one of those 5 pages finds the frame's share count now 1, so it simply makes the page writable again: no copy. The parent's write to another still-shared page triggers one copy. Total: 5 + 1 = 6 pages copied (24 KiB), instead of 200 up front.

Exercise 16.18core

18. Page replacement

Reference string 2, 3, 2, 1, 5, 2, 4, 5, 3, 2, 5, 2 with 3 frames, initially empty. Count the page faults under FIFO, LRU and OPT.

Show solution

FIFO (faults marked F, victim in parentheses): 2 F, 3 F, 2 hit, 1 F, 5 F (2), 2 F (3), 4 F (1), 5 hit, 3 F (5), 2 hit, 5 F (2), 2 F (4). Total 9 faults.

LRU: 2 F, 3 F, 2 hit, 1 F, 5 F (3), 2 hit, 4 F (1), 5 hit, 3 F (2), 2 F (4), 5 hit, 2 hit. Total 7 faults.

OPT (evict the page whose next use is farthest away): 2 F, 3 F, 2 hit, 1 F, 5 F (evict 1, never used again), 2 hit, 4 F (evict 2: next uses are 5 at position 8, 3 at 9, 2 at 10), 5 hit, 3 hit, 2 F (evict 3 or 4, neither is used again), 5 hit, 2 hit. Total 6 faults.

Result: FIFO 9, LRU 7, OPT 6. OPT is the lower bound; LRU is close to it because recent use predicts future use.

Exercise 16.19core

19. Thrashing

A system has m = 140 frames. Four processes have working set sizes 40, 25, 60 and 30 frames. (a) Is the system likely to thrash? (b) Which process would you suspend, and what is the new total demand?

Show solution

(a) D = 40 + 25 + 60 + 30 = 155 > 140. Processes steal each other's frames, faults rise, the CPU idles on disk waits, and a naive scheduler adds more processes, making it worse.

(b) Remove at least 15 frames of demand. Suspending the 25-frame process gives D = 130 ≤ 140 and stops the least work; suspending the 30-frame one gives 125. Suspending the 60-frame one gives 95 but idles memory. The suspended process is swapped out and resumes when memory frees.

Exercise 16.20warm-up

20. Access time of a disk

A 10,000 RPM disk has an average seek time of 4 ms and a transfer rate of 200 MB/s (1 MB = 10⁶ bytes). Compute the average time for a random 4 KiB read, the number of such reads per second, and the random-read throughput in MB/s.

Show solution

Rotational latency = (60 / 10,000) / 2 = 3 ms. Transfer = 4096 / 200,000,000 s = 0.02048 ms. Access time = 4 + 3 + 0.02048 = 7.02 ms.

Reads per second = 1 / 0.00702 = about 142. Throughput = 142 × 4096 B = about 0.58 MB/s, roughly 340 times slower than the sequential rate of 200 MB/s. Positioning dominates (99.7% of the time).

Exercise 16.21core

21. Disk scheduling

A disk has cylinders 0 to 199. The head is at 50 and moving toward higher cylinders. The queue is 82, 170, 43, 140, 24, 16, 190. Compute the total head movement under FCFS, SSTF, SCAN, C-SCAN and LOOK. In SCAN and C-SCAN the head goes to the disk end; in C-SCAN the return jump to cylinder 0 is counted.

Show solution

FCFS: 32 + 88 + 127 + 97 + 116 + 8 + 174 = 642. SSTF: order 43, 24, 16, 82, 140, 170, 190: 7 + 19 + 8 + 66 + 58 + 30 + 20 = 208. SCAN: up to 199 (149), back to 16 (183) = 332. C-SCAN: up to 199 (149), jump to 0 (199), up to 43 (43) = 391. LOOK: up to 190 (140), back to 16 (174) = 314.

SSTF moves least but can starve distant requests; SCAN and LOOK bound the waiting, and LOOK avoids travelling to an end with nothing to serve.

Exercise 16.22core

22. RAID capacity and parity

Eight disks of 4 TB each, each doing 150 random IOPS. (a) Give the usable capacity of RAID 0, 5, 6 and 10. (b) Give the maximum random small-write IOPS for RAID 5, 6 and 10. (c) Three data blocks hold 0xA5, 0x3C and 0x0F, and the parity block is their XOR. Compute the parity, then recover the block 0x3C if its disk fails.

Show solution

(a) RAID 0: 8 × 4 = 32 TB. RAID 5: 7 × 4 = 28 TB. RAID 6: 6 × 4 = 24 TB. RAID 10: 4 × 4 = 16 TB.

(b) Total raw IOPS is 8 × 150 = 1200. A small write costs 4 I/Os on RAID 5 (read data, read parity, write data, write parity), 6 on RAID 6 and 2 on RAID 10. IOPS = 1200 / 4 = 300 (RAID 5), 1200 / 6 = 200 (RAID 6), 1200 / 2 = 600 (RAID 10).

(c) 0xA5 XOR 0x3C = 0x99; 0x99 XOR 0x0F = 0x96. Parity = 0x96. To recover 0x3C: 0x96 XOR 0xA5 XOR 0x0F = 0x3C. A lost block equals the XOR of all the remaining blocks, including parity.

Exercise 16.23core

23. Inode limits and offsets

A file system has 1 KiB blocks and 4-byte block pointers. Each inode has 10 direct pointers and one single, one double and one triple indirect pointer. (a) What is the maximum file size? (b) For byte offset 300,000, which pointer path leads to its data block?

Show solution

(a) A pointer block holds 1024 / 4 = 256 pointers. Blocks: 10 + 256 + 256² + 256³ = 10 + 256 + 65,536 + 16,777,216 = 16,843,018. Size = 16,843,018 × 1024 = 17,247,250,432 bytes, about 16.06 GiB.

(b) Block = 300,000 div 1024 = 292. 292 − 10 = 282, and 282 − 256 = 26, so it lies in the double-indirect region at index 26: double[0] (26 div 256 = 0), then block[26].

Exercise 16.24core

24. Journal writes

A file append adds 4 data blocks and updates one inode block and one bitmap block. Count the block writes (journal plus home locations) with data journaling and with ordered mode, and explain why ordered mode writes the data first.

Show solution

Data journaling: journal TxB + I + B + 4 data + TxE = 8, checkpoint I + B + 4 data = 6: total 14. Ordered mode: 4 data, journal TxB + I + B + TxE = 4, checkpoint 2: total 10. Ordered mode saves k = 4 writes because each data block is written once, not twice.

It writes data first so that committed metadata never point at a block that still holds stale garbage (the writeback-mode hazard).

Exercise 16.25core

25. Permissions

(a) A process with umask 027 creates a file requesting mode 0666 and a directory requesting 0777. What modes result? (b) A file has mode 0640, owner alice, group staff. Bob is in staff, Carol is not. What can each do? (c) Write 4755 in symbolic form and say what the leading 4 does.

Show solution

(a) Mode AND NOT umask. File: 0666 with the bits 027 cleared = 0640 (rw-r-----). Directory: 0777 with 027 cleared = 0750 (rwxr-x---).

(b) Alice (owner): read and write (6). Bob (group): read only (4). Carol (other): nothing (0). The first matching class decides, so a user who is the owner is judged only by the owner bits, even if the group bits are more generous.

(c) 4755 = rwsr-xr-x. The 4 is the setuid bit: when any user runs the file, the process gets the file owner's effective user ID, so the program must be written very carefully (least privilege).

Exercise 16.26core

26. Nested paging and container limits

(a) How many memory references does a TLB miss need in a virtual machine when both guest and host use 4-level page tables, and when both use 3 levels? (b) A cgroup has cpu.max = 200000 100000 and runs 4 CPU-bound threads on an idle 8-core machine. What do the threads get? (c) Two busy tasks, nice 0 (weight 1024) and nice 5 (weight 335), share one core under CFS. What shares do they get?

Show solution

(a) (n + 1)(m + 1) − 1: 5 × 5 − 1 = 24 for 4 and 4 levels; 4 × 4 − 1 = 15 for 3 and 3.

(b) The quota is 200,000 µs per 100,000 µs period: 2 CPUs. Four busy threads would use 4, so after 50 ms of each period they are throttled until the next one. Together 2 CPUs, each thread 0.5 CPU on average.

(c) 1024 / 1359 = 75.3% and 335 / 1359 = 24.7%, about 3 to 1.

Exercise 16.27challenging

27. Predict the lab program

Consider the review lab program below. For each change, predict what happens and name the concept: (a) the parent does not call close(fd[1]); (b) waitpid is removed and the parent then sleeps 30 s before exiting; (c) the mmap flag MAP_SHARED is changed to MAP_PRIVATE; (d) the mutex around total += s is removed.

Show solution

(a) It still finishes, because one read of a fixed 8-byte record returns once the data are in the pipe. But a loop reading until EOF would hang forever (Exercise 5).

(b) The child is never reaped: ps shows it as Z (defunct) for the 30 seconds, until the parent exits and PID 1 adopts it.

(c) MAP_PRIVATE makes the mapping copy-on-write, so the child's write goes to a private copy; the parent sees flag 0. The sums are unchanged because both processes only read the array.

(d) total += s becomes an unprotected read-modify-write: a data race. It usually still prints 375,250 because each thread does it once, but it can lose a contribution and print 156,375 or 218,875. ThreadSanitizer reports it every time.

Exercise 16.28warm-up

28. Is it durable?

A program creates a new file, writes 4 KiB with write, calls close, and the machine loses power one second later. Is the data safe? What must the program do for a durable create?

Show solution

Not necessarily. write only copies the bytes into the page cache (write-back caching), and close does not force them to disk. For durability the program must call fsync on the file, and, because creating the file also changed the directory, fsync the containing directory as well. To replace an existing file atomically, write a temporary file in the same directory, fsync it, rename it over the old name and fsync the directory.

Lab

This lab combines four earlier ideas in one small program: fork and wait (Week 2), a pipe and a thread pair with a mutex (Weeks 3 and 5), and an anonymous shared mmap (Week 9). The parent fills an array of 1000 integers with 1 to 1000 in shared memory. The child sums the first half and sends the result back through a pipe. Two threads in the parent sum the second half in two quarters, adding their results to one total under a mutex. A shared flag proves the mapping is really shared, and a private global proves fork copies ordinary memory.

An anonymous mapping is a mmap region with no file behind it (MAP_ANONYMOUS), filled with zeros on first use; with MAP_SHARED the same pages stay shared with children created by fork, while with MAP_PRIVATE they become copy-on-write.

Save as review_lab.c.

#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

#define N 1000

static int *shared;                 /* MAP_SHARED: visible to parent and child */
static int private_var = 1;         /* ordinary global: copied by fork */
static long total = 0;              /* guarded by lock */
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

struct range { int lo, hi; };       /* half-open [lo, hi) */

static long sum_range(int lo, int hi) {
    long s = 0;
    for (int i = lo; i < hi; i++) s += shared[i];
    return s;
}

static void *worker(void *arg) {
    struct range *r = arg;
    long s = sum_range(r->lo, r->hi);
    pthread_mutex_lock(&lock);      /* critical section: one update to total */
    total += s;
    pthread_mutex_unlock(&lock);
    return NULL;
}

int main(void) {
    /* 1. mmap: one anonymous shared page holding the array plus a flag */
    shared = mmap(NULL, (N + 1) * sizeof(int), PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shared == MAP_FAILED) { perror("mmap"); return 1; }
    for (int i = 0; i < N; i++) shared[i] = i + 1;
    shared[N] = 0;                  /* flag the child will set */

    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {                 /* child: sum first half, report via pipe */
        close(fd[0]);               /* close the unused read end */
        long s = sum_range(0, N / 2);
        private_var = 99;           /* changes the child's private copy only */
        shared[N] = 1;              /* visible to the parent */
        if (write(fd[1], &s, sizeof s) != sizeof s) _exit(2);
        close(fd[1]);
        _exit(7);
    }
    close(fd[1]);                   /* parent closes the write end, or read never sees EOF */

    /* 2. two threads sum the second half while the child works */
    pthread_t t[2];
    struct range r[2] = { { N / 2, 3 * N / 4 }, { 3 * N / 4, N } };
    for (int i = 0; i < 2; i++) pthread_create(&t[i], NULL, worker, &r[i]);
    for (int i = 0; i < 2; i++) pthread_join(t[i], NULL);

    long from_child = 0;
    if (read(fd[0], &from_child, sizeof from_child) != sizeof from_child) {
        perror("read"); return 1;
    }
    close(fd[0]);
    int status;
    waitpid(pid, &status, 0);       /* reap the child: no zombie */

    printf("threads summed second half : %ld\n", total);
    printf("child summed first half    : %ld (via pipe)\n", from_child);
    printf("grand total                : %ld\n", total + from_child);
    printf("child exit status          : %d\n", WEXITSTATUS(status));
    printf("shared flag set by child   : %d (shared mapping)\n", shared[N]);
    printf("private_var in parent      : %d (child's change was private)\n", private_var);
    munmap(shared, (N + 1) * sizeof(int));
    return 0;
}

Build and run it:

gcc -Wall -pthread -o review_lab review_lab.c
./review_lab

The program compiles without warnings and prints the same lines on every run:

threads summed second half : 375250
child summed first half    : 125250 (via pipe)
grand total                : 500500
child exit status          : 7
shared flag set by child   : 1 (shared mapping)
private_var in parent      : 1 (child's change was private)

Check the numbers by hand: 1 + 2 + … + 1000 = 1000 × 1001 / 2 = 500,500; the first half sums to 500 × 501 / 2 = 125,250, so the second half is 375,250 (156,375 from the first thread plus 218,875 from the second). The threads and the child run concurrently, yet the output is deterministic, because each piece of shared state has exactly one writer or is guarded by the mutex, and the parent waits for everyone before printing.

Now use the debugging tools from this chapter. Build with sanitizers and run again; all three tools report nothing for this program:

gcc -Wall -pthread -g -fsanitize=thread  -o lab_tsan review_lab.c && ./lab_tsan
gcc -Wall -pthread -g -fsanitize=address -o lab_asan review_lab.c && ./lab_asan
valgrind --leak-check=full ./review_lab

Then make the experiments of Exercise 27 for real: remove the mutex and watch ThreadSanitizer report a data race; delete the close(fd[1]) and read in a loop until EOF to see the hang; delete waitpid and add sleep(30) before the end, and run ps -o pid,ppid,stat,cmd --ppid $$ from another terminal to see the Z state.

Extensions

  1. Replace the pipe with a second MAP_SHARED slot protected by a process-shared semaphore (sem_init with pshared = 1, kept in the shared mapping), so the child's result arrives without a system call. Compare the code size and the cost.
  2. Generalize to K child processes, each summing a slice and writing a fixed-size record to one shared pipe, and T threads in the parent. Measure the elapsed time for a large array (10⁸ elements) for several K and T and compare with Amdahl's law (Week 3), estimating the serial fraction from your data.
  3. Make the child count page faults with getrusage before and after touching a freshly mapped region, and use the result as S in the effective access time formula of Week 9 to find the largest tolerable fault rate on your machine.

Common mistakes and debugging tips

Symptom Likely cause What to do
Numeric answer off by a factor of 1000 Mixed ms and ns, or MB and MiB Convert to one unit first; write the unit beside each number
Page number or block number off by one Counted from 1 instead of 0 Use div and mod; the first page is page 0
SCAN total differs from the answer key Forgot to go to the disk end, or did not count the C-SCAN jump State the convention you use and follow the chapter's
Banker's algorithm says "unsafe" for a safe state Used Max instead of Need, or forgot to add the finished process's Allocation to Work Recompute Need = Max − Allocation and update Work after each step
FIFO fault count is wrong Updated the queue order on a hit FIFO changes order only on a fault; LRU updates on every reference
EAT answer is huge or tiny Applied p to the wrong term, or forgot (1 − p) Write (1 − p) × ma + p × S and convert S to ns
Program hangs after fork and pipe A write end still open somewhere Close every unused pipe end in both processes
Result differs run to run Data race or reading an uninitialized value ThreadSanitizer, then Valgrind; protect or remove the sharing

Key takeaways

Key takeaways

  • An operating system has two jobs, managing resources and providing abstractions, and every chapter of this course was one of them seen in detail: CPU, memory, storage and protection.
  • The same few ideas recur: indirection (page tables, inodes, file descriptors), caching (TLB, page cache), locality, policy versus mechanism, and reducing cost by batching (larger reads, group commit, DMA).
  • Quantitative reasoning is part of the subject: the cheat sheet formulas for scheduling, Banker's, address splitting, EAT, page replacement, disk time, RAID and inodes are all short and should be derived, not memorized.
  • Most bugs fall into a few classes (races, deadlocks, leaks, descriptor leaks, zombies, permissions); match the tool to the class, reproduce first and then fix, and write a regression test.
  • A good final project has one mechanism, a reproducible workload, measurements with units and an honest list of limits.
  • Read real kernels with a question in mind. xv6 is the best first kernel; Linux is organized along the lines of this course.
  • The exam rewards tables, units and formulas written out; practice by redoing traces on blank paper and by explaining answers aloud.
