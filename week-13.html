File Systems II: Journaling, Caching and the I/O Subsystem

How file systems survive crashes (fsck, journaling, copy-on-write, log-structured designs), how the kernel caches and schedules disk traffic, and how the I/O subsystem talks to devices through polling, interrupts, DMA and drivers.

What you will be able to do

By the end of this week you will be able to:

  • Enumerate the crash states of a file append and explain which ones leave the file system inconsistent
  • Describe the steps of a journal transaction (begin, commit, checkpoint) and compare ext4 writeback, ordered and data modes
  • Explain why copy-on-write and log-structured file systems do not need a conventional journal
  • Compute the effective access time of a page cache and explain write-back, write-through and read-ahead
  • Explain what fsync guarantees, and why a successful write() alone guarantees nothing about durability
  • Compare polling, interrupt-driven I/O and DMA, and say when each wins
  • Choose between blocking, non-blocking, select/poll/epoll and io_uring for a given workload

In Week 12 we built a file system on paper: a superblock, inodes, bitmaps, directories and data blocks laid out on a disk. That design worked as long as nothing went wrong. Real machines lose power, kernels panic and cables get yanked, and a file system update is almost never a single disk write. This week is about what happens when the power fails in the middle of a multi-block update, and about the machinery that makes file systems both fast and safe: caches, journals, schedulers and the I/O subsystem underneath.

The second half of the week zooms out from files to devices. Every read() that misses the cache eventually becomes a command sent to a controller by a driver. We look at how the CPU finds out that a device is done (polling or interrupts), how bulk data moves (programmed I/O or DMA), and how a user program can wait for many descriptors without wasting threads (select, poll, epoll, io_uring). These ideas connect back to Week 11 (disk scheduling and SSDs) and forward to Week 14, where the same kernel boundary becomes a security boundary.

The crash consistency problem

A file system keeps its on-disk structures in several places: data blocks, inodes, allocation bitmaps and directories. A single logical operation such as "append one block to a file" must change more than one of them. The disk, however, only guarantees that a single sector write is atomic (and even that is a convenience, not always a promise). If the machine dies after some of the writes and before the others, the structures disagree with each other. This is the crash consistency problem.

Crash consistency

A file system is crash consistent if, after a crash and reboot, its on-disk metadata describe a valid file system: every block marked used is owned by exactly one inode, every inode pointer refers to an allocated block, and directory entries refer to live inodes. Consistency is different from durability (your latest data survived) and from atomicity (an operation happened entirely or not at all).

The append example

Suppose a file has one data block and we append a second block. Three on-disk structures must change:

  • Db, the new data block, which must be written for the first time.
  • I, the file's inode, which gets a new pointer to Db and a bigger size.
  • B, the data bitmap, in which the bit for Db must flip from free to used.

The three writes are issued by the kernel, but the disk may complete them in any order, and a crash can strike after any subset has reached the platter or flash. With three writes there are eight subsets; the interesting ones are the six where a crash leaves only part of the update.

Look at what each failure means. If only Db reaches disk, nothing points to the data, so it is as if the append never happened: consistent, but the application's data is lost. If only B reaches disk, we have a space leak: a block marked used that no inode owns. If only I reaches disk, the file system has two problems at once: the inode and the bitmap disagree, and the inode points at a block that holds stale bytes from a previous file, which is a privacy bug as well as a correctness bug. The case Db + I without B is dangerous because the allocator may hand the same block to another file, giving two files one block. The case I + B without Db is the nastiest in practice: all the metadata are perfectly consistent, yet the file contains whatever garbage was in the block before. The file system cannot detect this by looking at metadata alone.

Moving house

Imagine moving house with three steps: pack the box (Db), write the new address in the register (I), and mark the new room as occupied in the building plan (B). If the movers stop halfway, you may have a box nobody knows about, a register entry pointing to an empty room, or a room marked occupied with nobody inside. A journal is the moving company's checklist: it writes down the whole plan first, so after an interruption it can finish or cancel the job.

Why not just order the writes carefully?

You can pick an order that never produces the dangerous states. The classic soft updates technique writes Db first, then I, then B, tracking dependencies in memory. But ordering alone cannot repair the leak states and is hard to get right across many operations, since the disk's own write cache can reorder behind the kernel's back unless the kernel issues explicit cache flush or write-barrier commands. Most modern systems therefore use a journal or copy-on-write instead.

fsck: check everything after the crash

The oldest solution is to do nothing during normal operation and repair after the fact. The tool fsck (file system check) scans the whole file system at boot after an unclean shutdown and fixes inconsistencies. It does not know what the user was doing; it only restores invariants.

fsck pass (simplified) What it checks Typical repair
Superblock Size sanity, block count, mount flags Use a backup superblock
Free blocks Walk every inode; rebuild the set of used blocks Rewrite bitmaps from the inode truth
Inode state Type and link fields valid Clear corrupt inodes
Inode links Count directory entries per inode and compare with the link count Fix count; move orphans to lost+found
Duplicates Two inodes claiming one block Clone or clear one
Bad pointers Pointers outside the partition Clear pointer
Directories Entries . and .. correct, no loops Reconnect or remove

The problem is time. fsck reads essentially all metadata, so its cost grows with the file system, not with the amount of damage. On a 10 TB array it could take hours, while the actual damage might be one block. Also, fsck cannot fix the I + B garbage case at all, because the metadata look right. This led to the idea of write-ahead logging.

Journaling: write-ahead logging

A journal (also called a write-ahead log) is a small area of the disk where the file system first records what it is about to do, and only then does it do it. After a crash, recovery reads the journal and either finishes the logged work or ignores it. Recovery time depends on the size of the journal, not the size of the disk: seconds instead of hours.

Journaling comes to Linux

Database systems used write-ahead logging for decades before file systems adopted it. IBM's JFS and SGI's XFS brought it to Unix in the 1990s. Linux gained journaling with ext3 (2001), which added a journal to ext2 without changing the on-disk format, so an ext3 disk could be mounted as ext2. ext4 (2008) kept the design and added extents, delayed allocation and journal checksums.

The transaction protocol

Each update is wrapped in a transaction. Using the append example in full data journaling form, the steps are:

  1. Journal write. Write a transaction-begin block (TxB, containing a transaction ID and the final locations of the blocks) followed by the logged copies of I, B and Db to the journal. Wait for these to complete.
  2. Journal commit. Write a transaction-end block (TxE) to the journal. When TxE is durable, the transaction is committed. Wait for completion.
  3. Checkpoint. Write I, B and Db to their final locations in the main file system.
  4. Free. Later, mark the transaction free in the journal so that space can be reused (the journal is a circular buffer).

The commit step is separate from the log writes for a reason. If TxB, I, B, Db and TxE were issued together, the disk could persist TxE first and then crash before Db; recovery would see a "committed" transaction with a garbage Db and replay it, copying junk into the file. So the file system waits for step 1 to finish before issuing TxE. The block write of TxE must itself be atomic, so it fits in a single sector. Modern ext4 can also store a checksum of the transaction in the commit block, which lets it issue everything at once and verify afterwards.

The disk's write cache

Waiting for a write to complete means nothing if the drive reports completion when data are only in its volatile cache. File systems rely on cache flush commands (barriers, or FUA writes) to force order. Disabling barriers for speed on a drive without a power-protected cache can silently destroy the journal's guarantee.

Recovery

At boot the file system scans the journal. A transaction with a valid TxB and TxE is replayed: its blocks are copied to their final locations. Because replay is just copying the same bytes again, it is idempotent: if the machine crashes during recovery, we simply recover again. A transaction without a valid commit block is discarded. This style is called redo logging, since the log holds the new values.

Journaling modes in ext3 and ext4

Journaling every data block means writing every byte twice: once to the journal and once to its home. Most file systems therefore journal only metadata by default. ext3 and ext4 offer three modes, chosen with the data= mount option.

Mode What goes through the journal Data written Guarantee after crash Cost
data=journal Metadata and data Data goes to the journal first Strongest: data and metadata consistent together Every byte written twice
data=ordered (default) Metadata only Data written to its final place before the metadata transaction commits Metadata never points at unwritten blocks; no garbage exposure Write ordering waits
data=writeback Metadata only Data written at any time relative to the commit Metadata consistent; files may contain stale data after a crash Fastest

Ordered mode is the interesting compromise. The order is: (1) write the data block Db to its final location, (2) write TxB and the metadata (I and B) to the journal, (3) write TxE, (4) checkpoint I and B. If the crash comes before step 3, the transaction is dropped and the data block is unreferenced garbage that is harmless. If it comes after, the data are already in place. The dangerous I + B without Db state can never occur. In writeback mode the order is not enforced, so I + B can occur and a file may show old contents of the block.

Counting block writes

For an append of one data block with one inode block and one bitmap block affected: data journaling issues 5 journal writes (TxB, I, B, Db, TxE) plus 3 checkpoint writes (I, B, Db), total 8. Ordered mode issues 1 data write, 4 journal writes (TxB, I, B, TxE) plus 2 checkpoint writes, total 7. Writeback also issues 7 writes, in a looser order. Exercise 2 asks you to redo this for a ten-block append.

Copy-on-write and log-structured file systems

Journaling writes everything twice (once to the log, once to its home) at least for metadata. Two other designs avoid that by never overwriting live data.

Copy-on-write (COW) file systems

A COW file system treats the on-disk structure as a tree whose root is the only thing that is ever overwritten in place. To change a data block, it writes a new copy of that block to free space, then writes a new copy of the parent that points to it, and so on up to a new root. Finally a single atomic write flips the root pointer (or a superblock) to the new tree. Before that write the old, consistent tree is untouched; after it, the new, consistent tree is live. A crash can only see one or the other.

This gives a bonus: the old tree can be kept, so snapshots are nearly free (a snapshot is just an extra reference to an old root). ZFS, Btrfs and Apple's APFS all use COW ideas. ZFS adds end-to-end checksums stored in the parent pointers, so silent corruption is detected on read and repaired from a mirror or parity copy. Btrfs uses COW B-trees and supports snapshots and subvolumes. APFS uses COW metadata and cheap clones. The costs are fragmentation (logically sequential files scatter over time), write amplification from rewriting path-to-root blocks, and the complexity of garbage-collecting blocks no tree references.

Log-structured file systems (LFS)

The log-structured file system of Rosenblum and Ousterhout (1992) takes the log idea to its limit: the log is the file system. All writes, data and metadata, are buffered in memory into a large segment (hundreds of KB to MB) and written sequentially to the end of the log. Since the disk head never seeks, write throughput approaches the disk's sequential bandwidth, which matters because Week 11 showed seeks dominate small random writes.

Two problems follow. First, inodes move every time they are written, so LFS keeps an inode map that maps inode numbers to current locations; a fixed checkpoint region records where the inode map pieces are. Second, overwritten blocks leave holes in old segments, so a cleaner must copy live blocks out of mostly-dead segments to produce free segments, a garbage collection step whose cost can eat the gain. The same ideas reappear in flash: an SSD's flash translation layer is log-structured, and F2FS is a Linux file system designed for flash that borrows LFS ideas.

Caching: buffer cache, page cache and the write policy

Disks (even SSDs) are slow compared with RAM, so the kernel keeps recently used file data in memory. Early Unix had a buffer cache of disk blocks; modern Linux unifies this with the virtual memory system in the page cache, in which file contents live in page-sized frames shared with mmap. When you read(), the kernel looks up the (file, page offset) in the cache; on a hit it copies from RAM, on a miss it starts a disk read.

Effective access time of a cache

Suppose a cache hit costs 100 ns and a miss costs 8 ms (8,000,000 ns) with a hit ratio of 0.95. Then EAT = 0.95 × 100 ns + 0.05 × 8,000,000 ns = 95 ns + 400,000 ns = 400,095 ns, about 0.4 ms. Even a 5% miss ratio makes the average 4000 times slower than a hit, which is why the last few percent of hit ratio matter so much. This is the same arithmetic as the effective access time of Week 9.

Write-through and write-back

When an application writes, the kernel must decide when the change reaches disk.

  • Write-through: update the cache and the disk before write() returns. Safe, but every write pays disk latency.
  • Write-back (delayed write): update the cache, mark the page dirty, and return immediately. A flusher thread writes dirty pages later, typically after 5 to 30 seconds, or when dirty memory exceeds a threshold. Fast, and it lets the kernel merge repeated writes to the same page and sort writes by disk address, but data in the cache are lost if the system crashes.

Linux defaults to write-back for ordinary files. That is why write() returning success is not a statement about the disk at all: it means the kernel has accepted the bytes into the page cache.

Read-ahead

Many programs read files sequentially. When the kernel detects a sequential pattern it starts fetching the next pages before they are requested (read-ahead), turning a series of blocking misses into hits and letting one large request replace many small ones. Linux grows the read-ahead window when accesses keep being sequential and shrinks or resets it on random access. Applications can hint with posix_fadvise(POSIX_FADV_SEQUENTIAL) or madvise. Read-ahead is wasteful for random access, which is why the heuristic watches the pattern.

fsync and durability pitfalls

To force data to stable storage the application must say so. fsync(fd) writes back the dirty data and the metadata of that file and returns when the device reports completion (and, with barriers on, after flushing the device cache). fdatasync(fd) skips metadata that is not needed to read the data back (for example, modification time). sync flushes everything.

Durability traps

  1. A successful write() or even close() does not mean the data are on disk. Only fsync does.
  2. After creating or renaming a file, the directory entry is also dirty. For a durable create, fsync the file and then fsync the containing directory.
  3. If fsync fails (for example EIO), the kernel may already have marked pages clean; retrying fsync can falsely succeed. Treat a failed fsync as fatal for that data.
  4. The standard safe way to update a file atomically is: write a new temporary file in the same directory, fsync it, rename() it over the old name, then fsync the directory. rename within one file system is atomic.
  5. Drives and cloud disks can lie about flushes. Test with power-loss tools if durability is critical.

The cost of fsync is the reason databases use group commit: if each transaction needs its own fsync and an fsync takes 200 µs, one thread can do at most 5,000 commits per second. If ten concurrent transactions share one fsync, throughput rises to 50,000 per second with the same latency. Exercise 6 works this out.

The VFS layer and network file systems

A Linux machine mounts ext4, XFS, FAT on a USB stick, NFS from a server and /proc all in one directory tree, and every program uses the same open, read, write calls on all of them. That is the job of the Virtual File System (VFS) layer, an object-oriented interface in the kernel (written in C with tables of function pointers).

VFS defines four main objects. The superblock object describes a mounted file system. An inode object represents a file. A dentry (directory entry) caches one path component and its inode, so repeated lookups of /usr/lib/x avoid disk reads. A file object represents an open file with its position. Each file system registers functions such as read_iter, lookup and write_begin in operation tables. Mounting attaches a file system's root to a directory in the existing tree, so the single tree hides which device is which.

Network file systems and NFS

A network file system makes remote files appear local. The Sun Network File System (NFS) is the classic. The client's VFS calls NFS client code, which sends remote procedure calls (RPCs) such as LOOKUP, READ, WRITE and GETATTR to a server, which executes them on a local file system.

NFS versions 2 and 3 were designed to be stateless: the server remembers nothing about clients between requests. Each request is self-contained, carrying a file handle (a server-chosen identifier, not a path) and an explicit offset instead of relying on a server-side file position. Why? If a stateless server crashes and reboots, the client just retries the request after a timeout, and the server needs no recovery. To make retries safe, requests are made idempotent: repeating WRITE(handle, offset, data) leaves the same result as doing it once. Operations that are not naturally idempotent, such as REMOVE or CREATE, need extra care (duplicate-request caches) because a retry after a lost reply could return an error.

Statelessness has costs. The server cannot track locks or open files, so locking needs a separate protocol, and NFS clients cache aggressively, so consistency is weak: NFS offers close-to-open consistency, where a client that closes a file flushes its changes and a client that opens it checks freshness. NFSv4 added state (open, lock, delegations), better security and compound RPCs, trading the elegance of statelessness for features.

Statelessness

A stateless server is like a library clerk who keeps no notes. You must say "give me page 41 of the book with shelf mark 77" every time rather than "next page". It is a bit more to say, but if the clerk is replaced by a new person halfway through your visit, nothing is lost.

The I/O subsystem

The kernel's I/O subsystem sits between applications and a huge variety of hardware. Its job is to give programs a small set of uniform abstractions while a layer of device drivers hides each device's quirks.

Talking to a device: ports and memory-mapped registers

A device controller exposes registers (status, command, data). The CPU reaches them in one of two ways.

  • Port-mapped I/O: a separate I/O address space accessed with special instructions (in and out on x86).
  • Memory-mapped I/O (MMIO): device registers appear at physical addresses, and ordinary loads and stores reach them. Modern devices (PCIe, NVMe, GPUs) use MMIO. The kernel maps these regions as uncached, and compilers must not reorder or remove such accesses (hence volatile and memory barriers in drivers).

User programs cannot execute in and out or touch these addresses directly because they are privileged; they ask the kernel through system calls (Week 1).

Polling, interrupts and DMA

How does the CPU learn that a device has finished?

  • Polling (busy waiting): the CPU repeatedly reads a status register until the "done" bit appears. Simple and fast for very short waits, but it wastes the CPU if the device is slow.
  • Interrupts: the CPU starts the operation and does other work; the device raises an interrupt line when done, the CPU saves state and runs the interrupt handler. There is overhead per interrupt (typically a few microseconds including cache effects), but the CPU is free meanwhile.
  • Hybrid: interrupts for the first event, then polling while traffic is heavy. Linux networking does this (NAPI), and the block layer can do it for fast NVMe drives (polled I/O, interrupt coalescing).

Moving the bytes is a separate question. With programmed I/O (PIO) the CPU copies every word between the device and memory. With Direct Memory Access (DMA) the CPU programs the controller with a memory address and length, then the DMA engine moves the data over the bus on its own and raises one interrupt at the end.

How much does DMA save?

Reading a 4 KiB block by PIO in 4-byte words needs 4096 / 4 = 1024 transfers. If each costs 100 ns of CPU time the CPU is busy 102.4 µs. With DMA the CPU spends perhaps 2 µs to set up and 3 µs to handle the completion interrupt, 5 µs in all, saving about 97.4 µs per block. At 10,000 blocks per second this is the difference between a CPU 100% busy copying (10,000 × 102.4 µs = 1.024 s of work per second) and one that is 5% busy.

Device drivers, block and character devices

A device driver is kernel code that implements a standard interface for one kind of hardware: it initialises the device, translates generic requests into register writes, handles interrupts and reports errors. Drivers are the largest and the buggiest part of most kernels, which is why Week 14 cares about isolating them. Linux loads many as modules (Week 15).

Linux classifies devices as:

  • Block devices (disks, SSDs, USB sticks): fixed-size blocks, random access, going through the page cache and I/O scheduler. Examples: /dev/sda, /dev/nvme0n1.
  • Character devices (terminals, mice, serial ports, /dev/null, /dev/random): streams of bytes, usually no caching or seeking.
  • Network devices: handled by the networking stack, not /dev files; accessed through sockets.

Kernel I/O schedulers

Between the file system and the driver, Linux's block layer queues requests and may reorder or merge them. Modern kernels use the multi-queue block layer (blk-mq), with several software queues feeding hardware queues. The available schedulers are:

Scheduler Idea Best for
none No reordering (just merging); lowest overhead NVMe SSDs with deep hardware queues
mq-deadline Sorts by sector like an elevator, but gives each request a deadline (reads sooner than writes) so none starves General use, spinning disks, simple SSDs
bfq Budget Fair Queueing: allocates each process a share of the disk's throughput, favouring interactive tasks Desktops, slow disks, fairness and low latency
kyber Token-based latency targets for fast devices Fast SSDs needing latency control

Why does none suit NVMe? Seek time is zero and the device has tens of thousands of internal queue slots, so the CPU time spent sorting is wasted, while the elegant elevator algorithms of Week 11 pay off only when a seek costs milliseconds. You can see and change the scheduler with /sys/block/<dev>/queue/scheduler.

Blocking, non-blocking and asynchronous I/O

How should a program wait for I/O? There are four main models.

  1. Blocking I/O. read() sleeps until data are available. Simplest; one thread per connection.
  2. Non-blocking I/O. With O_NONBLOCK set, read() returns immediately with the error EAGAIN (also EWOULDBLOCK) if no data are ready. The program must try again later; spinning on this is wasteful.
  3. I/O multiplexing. One thread asks the kernel "tell me which of these many descriptors is ready": select, poll or epoll. Then it reads only ready descriptors without blocking.
  4. Asynchronous I/O. The program submits the operation and is notified when it has completed: POSIX aio, Linux native AIO, and io_uring.

select, poll and epoll

select(2) takes bitmaps of descriptors, limited by FD_SETSIZE (usually 1024), and the kernel scans all of them on each call, so cost is O(n) per call, with the bitmaps copied in and out each time. poll(2) takes an array of struct pollfd and removes the 1024 limit, but is still O(n). epoll(7) (Linux) separates registration from waiting: epoll_create1 makes an epoll instance, epoll_ctl adds, modifies or removes descriptors once, and epoll_wait returns only the ready ones, so the cost per wait is proportional to the number of ready descriptors, not the number watched. That is why servers with tens of thousands of mostly idle connections use epoll (BSD has kqueue; Windows has I/O completion ports).

epoll has two modes. Level-triggered (default) reports a descriptor as long as it is ready, so unread data are reported again on the next wait. Edge-triggered (EPOLLET) reports only when the state changes (new data arrive), so you must read until you get EAGAIN or you will never be woken for the leftover data.

io_uring

Readiness-based interfaces tell you "you could read now"; you still make a system call for every read and write. io_uring (Linux 5.1 and later) is completion-based. The application and kernel share two ring buffers in memory: a submission queue (SQ) where the program places requests and a completion queue (CQ) where the kernel posts results. The program can queue many operations (reads, writes, accepts, fsyncs) and submit them with one system call, or with none at all in a polling mode where a kernel thread watches the SQ. Less system call overhead and true asynchrony even for file I/O, which epoll cannot offer (a regular file is always "ready" in epoll, yet reading it can still block on the disk). The price is a newer, larger interface that has had security issues, so some environments disable it.

Spooling

Spooling (Simultaneous Peripheral Operations On-Line) is the technique of buffering output for a device that cannot be shared, such as a printer, on disk. Each process's job is written to a spool directory instantly and a daemon feeds jobs one at a time to the device. This decouples the speed of the program from the speed of the device and lets many programs "use" one printer without interleaving their pages. The same idea survives in print queues, mail queues and job schedulers.

Exercises

Exercise 13.1warm-up

Crash states of an append

A file system appends one block. The writes are Db (data), I (inode) and B (bitmap). For each crash state below, say whether the file system metadata are consistent and whether user data are correct: (a) only I persisted, (b) only B persisted, (c) I and B persisted but not Db, (d) Db and I persisted but not B.

Show solution

(a) Only I: inode points to a block the bitmap says is free and that holds stale data. Metadata inconsistent; data are garbage.

(b) Only B: a block is marked used with no owner, a space leak. Metadata are inconsistent in the sense of a leak (fsck can reclaim it), but the file is unaffected and still correct (the append is lost).

(c) I and B without Db: metadata agree with each other, so they are consistent. But the file's new block contains old garbage: data are wrong. fsck cannot detect this.

(d) Db and I without B: the inode references a block the bitmap says is free, so the allocator can give it to another file. Metadata inconsistent; the data are correct for the moment but at risk.

Exercise 13.2core

Counting journal writes

An application appends 10 new data blocks to a file. The update changes one inode block and one bitmap block. Count the total block writes (journal plus final locations) in data journaling mode and in ordered mode, assuming one transaction, one TxB and one TxE. Which is cheaper and by how many writes?

Show solution

Data journaling: journal writes = TxB + I + B + 10 Db + TxE = 14. Checkpoint writes = I + B + 10 Db = 12. Total = 26.

Ordered mode: 10 data writes directly to final locations; journal = TxB + I + B + TxE = 4; checkpoint = I + B = 2. Total = 16.

Ordered mode is cheaper by 26 − 16 = 10 writes: exactly the number of data blocks, because ordered mode writes each data block once instead of twice.

Exercise 13.3core

Replaying a journal

After a crash the journal contains, in order: TxB(1) I1 B1 Db1 TxE(1), then TxB(2) I2 B2 Db2 (no TxE), then garbage. The file system was in data journaling mode and nothing from either transaction had been checkpointed. What does recovery do, and what is the state of the files afterwards?

Show solution

Transaction 1 has a valid begin and a valid commit block, so it is replayed: I1, B1 and Db1 are copied to their home locations. Transaction 2 has no commit block, so it is discarded. The garbage is ignored because it has no valid transaction header. The result is a file system containing exactly the effects of transaction 1 and none of transaction 2; the update from transaction 2 is lost, but the file system is consistent. Replaying is idempotent, so a crash during recovery just restarts recovery.

Exercise 13.4warm-up

Page cache EAT

A page cache hit takes 200 ns. A miss takes 10 ms. What hit ratio is needed so that the average access time is at most 1 µs?

Show solution

Let h be the hit ratio. EAT = h × 200 ns + (1 − h) × 10,000,000 ns ≤ 1000 ns.

200h + 10,000,000 − 10,000,000h ≤ 1000, so 9,999,800h ≥ 9,999,000, so h ≥ 9,999,000 / 9,999,800 = 0.99992, about 99.992%. A miss rate of just 0.008% (about one miss in 12,500 accesses) is the most you can afford.

Exercise 13.5core

PIO, interrupts and DMA

(a) A device delivers 1,000,000 completions per second. Each interrupt costs 3 µs of CPU time. What fraction of one CPU does interrupt handling take, and what does that suggest? (b) Transferring a 4 KiB block by programmed I/O takes 1024 word copies at 100 ns each. DMA needs 5 µs of CPU time per block. At 10,000 blocks per second, how much CPU time per second does each approach use?

Show solution

(a) 1,000,000 × 3 µs = 3 s of CPU work per second, i.e. 300% of a CPU: three full cores just taking interrupts. The system must reduce the interrupt rate: interrupt coalescing (one interrupt for many completions) or switching to polling under load.

(b) PIO: 1024 × 100 ns = 102.4 µs per block; 10,000 × 102.4 µs = 1.024 s per second, so more than one whole CPU. DMA: 10,000 × 5 µs = 0.05 s per second, 5% of one CPU. DMA saves about 0.974 CPU-seconds per second.

Exercise 13.6core

fsync and group commit

A database must make each transaction durable with an fsync. One fsync takes 200 µs on its SSD. (a) What is the maximum commit rate of a single thread that commits serially? (b) If a group commit lets up to 10 transactions share one fsync, what is the maximum rate? (c) What does group commit do to the latency of a single transaction?

Show solution

(a) 1 s / 200 µs = 5,000 commits per second.

(b) One fsync per 10 transactions: 10 × 5,000 = 50,000 commits per second.

(c) A transaction may have to wait for others to arrive and join the group, so its latency can rise a little (the commit still takes at least one fsync, 200 µs, plus the wait). Group commit trades a small latency increase for much higher throughput; under load the wait is short because many transactions arrive during an fsync anyway.

Exercise 13.7challenging

Atomic file replacement

Write a Python function atomic_write(path, data: bytes) that replaces a file so that after a crash a reader sees either the complete old contents or the complete new contents, never a mix, and that the replacement survives power loss once the function returns. Explain the role of each system call.

Show solution
import os

def atomic_write(path, data):
    d = os.path.dirname(os.path.abspath(path))
    tmp = path + ".tmp"
    fd = os.open(tmp, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    try:
        os.write(fd, data)      # for large data, loop on the return value
        os.fsync(fd)            # new contents durable before the rename
    finally:
        os.close(fd)
    os.rename(tmp, path)        # atomic within one file system
    dfd = os.open(d, os.O_RDONLY)
    try:
        os.fsync(dfd)           # make the directory entry change durable
    finally:
        os.close(dfd)

The temporary file must live in the same directory (same file system) because rename is atomic only within one file system. fsync(fd) before the rename ensures the new file's data are on disk before the name points at it; otherwise a crash could leave the new name referring to an empty or partial file. rename atomically swaps the directory entry, so readers see old or new. The final fsync on the directory persists the rename itself. A crash before the rename leaves the old file plus a stray temp file, which can be cleaned at startup.

Exercise 13.8core

Level-triggered or edge-triggered

A server uses epoll in edge-triggered mode. A client sends 10,000 bytes at once. The server's handler calls read(fd, buf, 4096) exactly once per wake-up. What goes wrong, and what are two ways to fix it?

Show solution

Edge-triggered epoll reports the descriptor once when new data arrive. The single read consumes 4096 bytes, leaving 5,904 bytes in the socket buffer, but no new edge occurs, so epoll_wait never reports the descriptor again until the client sends more; the leftover data stall (and the connection may appear hung).

Fix 1: keep the descriptor non-blocking and loop read() until it returns EAGAIN. Fix 2: use level-triggered mode (the default), where epoll keeps reporting the descriptor while unread data remain, so one read per wake-up is safe.

Exercise 13.9challenging

Why copy-on-write needs no journal

A COW file system stores a file's blocks in a tree of height 4 (root, two interior levels, then the data block). (a) How many blocks must be written to change one data block? (b) Explain why a crash at any point during the update leaves a consistent file system, and what single write is the commit point. (c) Name one cost of this design.

Show solution

(a) The new data block plus a new copy of each ancestor up to the root: 4 blocks in total (data block, two interior blocks, root), followed by the pointer flip (a write of the superblock or uberblock that names the new root).

(b) All 4 new blocks go to previously free space; the old tree is never modified. If the crash comes before the pointer flip, the superblock still names the old root, so the file system is exactly as before. After the flip it names the new, fully written tree. The flip is a single-sector write, so it is atomic and is the commit point. The partly written new blocks are merely unreferenced free space.

(c) Write amplification (4 block writes for 1 changed block) and fragmentation, since consecutive logical blocks get scattered as they are rewritten. A garbage collector or free-space tracking is also required.

Part 1: write() versus write()+fsync() in C

Save as fsync_bench.c.

#define _POSIX_C_SOURCE 200809L
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

static double now_us(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e6 + ts.tv_nsec / 1e3;
}

static int cmp(const void *a, const void *b) {
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}

static void run(const char *label, int n, int do_sync) {
    char buf[4096];
    memset(buf, 'x', sizeof buf);
    int fd = open("bench.dat", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); exit(1); }
    double *lat = malloc(n * sizeof *lat);
    double t0 = now_us();
    for (int i = 0; i < n; i++) {
        double s = now_us();
        if (write(fd, buf, sizeof buf) != (ssize_t)sizeof buf) { perror("write"); exit(1); }
        if (do_sync && fsync(fd) != 0) { perror("fsync"); exit(1); }
        lat[i] = now_us() - s;
    }
    double total = now_us() - t0;
    qsort(lat, n, sizeof *lat, cmp);
    printf("%-18s n=%d  mean=%9.1f us  median=%9.1f us  p99=%9.1f us  total=%.1f ms\n",
           label, n, total / n, lat[n / 2], lat[(int)(n * 0.99)], total / 1000);
    free(lat);
    close(fd);
    unlink("bench.dat");
}

int main(int argc, char **argv) {
    int n = argc > 1 ? atoi(argv[1]) : 500;
    run("write only", n, 0);
    run("write + fsync", n, 1);
    return 0;
}

Build and run:

gcc -O2 -Wall -o fsync_bench fsync_bench.c
./fsync_bench 500

Expected shape (numbers vary widely): write only takes a few microseconds per call (it only copies into the page cache), while write + fsync takes hundreds of microseconds on an SSD and several milliseconds on a spinning disk, so the ratio is often 100 to 1000 times. On a tmpfs both lines look alike, which proves that the cost is the device, not the system call.

Part 2: a toy write-ahead log in Python

This key-value store logs each transaction before applying it, can be "crashed" at chosen points, and recovers by replaying only committed transactions. Save as wal.py.

import json
import os


class Crash(Exception):
    """Simulated power failure."""


class ToyDB:
    def __init__(self, directory):
        self.dir = directory
        os.makedirs(directory, exist_ok=True)
        self.data_path = os.path.join(directory, "data.json")
        self.log_path = os.path.join(directory, "wal.log")
        self.next_tx = 1
        self.data = {}
        if os.path.exists(self.data_path):
            with open(self.data_path) as f:
                self.data = json.load(f)
        self.recover()

    # ---- recovery: redo only committed transactions ----
    def recover(self):
        if not os.path.exists(self.log_path):
            return
        pending, committed = {}, []
        with open(self.log_path) as f:
            for line in f:
                try:
                    rec = json.loads(line)
                except ValueError:
                    break                      # torn last record: stop reading
                if rec["op"] == "set":
                    pending.setdefault(rec["tx"], []).append(rec)
                elif rec["op"] == "commit":
                    committed.append(rec["tx"])
                self.next_tx = max(self.next_tx, rec["tx"] + 1)
        for tx in committed:
            for rec in pending.get(tx, []):
                self.data[rec["k"]] = rec["v"]
        self.checkpoint()

    def checkpoint(self):
        tmp = self.data_path + ".tmp"
        with open(tmp, "w") as f:
            json.dump(self.data, f)
            f.flush()
            os.fsync(f.fileno())
        os.rename(tmp, self.data_path)
        open(self.log_path, "w").close()       # log is now empty

    # ---- normal operation ----
    def transact(self, updates, crash_at=None):
        tx = self.next_tx
        self.next_tx += 1
        with open(self.log_path, "a") as log:
            for k, v in updates.items():
                log.write(json.dumps({"tx": tx, "op": "set", "k": k, "v": v}) + "\n")
            log.flush()
            os.fsync(log.fileno())             # step 1: log durable
            if crash_at == "before_commit":
                raise Crash()
            commit = json.dumps({"tx": tx, "op": "commit"}) + "\n"
            if crash_at == "torn_commit":
                log.write(commit[: len(commit) // 2])   # half a commit record
                log.flush()
                os.fsync(log.fileno())
                raise Crash()
            log.write(commit)
            log.flush()
            os.fsync(log.fileno())             # step 2: commit durable
        if crash_at == "after_commit":
            raise Crash()                      # committed but not checkpointed
        self.data.update(updates)
        self.checkpoint()                      # step 3: checkpoint


if __name__ == "__main__":
    import shutil
    shutil.rmtree("walkv", ignore_errors=True)
    db = ToyDB("walkv")
    db.transact({"alice": 100, "bob": 50})
    for point in ["before_commit", "torn_commit", "after_commit"]:
        try:
            db.transact({"alice": 70, "bob": 80}, crash_at=point)
        except Crash:
            pass
        db = ToyDB("walkv")                    # reboot: memory lost, recover from disk
        print(f"crash at {point:14s} -> {db.data}")
        db.transact({"alice": 100, "bob": 50})  # reset the balances

Run python3 wal.py. Expected output:

crash at before_commit  -> {'alice': 100, 'bob': 50}
crash at torn_commit    -> {'alice': 100, 'bob': 50}
crash at after_commit   -> {'alice': 70, 'bob': 80}

Crashes before the commit record is complete leave the old state; a crash after commit but before checkpoint still ends in the new state because recovery redoes the log. Never do you see alice: 70, bob: 50: the transfer is atomic.

Part 3: a non-blocking echo server with epoll

Save as echo_epoll.c. It serves many clients in one thread.

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <netinet/in.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/epoll.h>
#include <sys/socket.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static void set_nonblock(int fd) {
    int fl = fcntl(fd, F_GETFL, 0);
    if (fl < 0 || fcntl(fd, F_SETFL, fl | O_NONBLOCK) < 0) die("fcntl");
}

int main(int argc, char **argv) {
    int port = argc > 1 ? atoi(argv[1]) : 9000;
    int ls = socket(AF_INET, SOCK_STREAM, 0);
    if (ls < 0) die("socket");
    int one = 1;
    setsockopt(ls, SOL_SOCKET, SO_REUSEADDR, &one, sizeof one);
    struct sockaddr_in a = {0};
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = htons(port);
    if (bind(ls, (struct sockaddr *)&a, sizeof a) < 0) die("bind");
    if (listen(ls, 128) < 0) die("listen");
    set_nonblock(ls);

    int ep = epoll_create1(0);
    if (ep < 0) die("epoll_create1");
    struct epoll_event ev = {.events = EPOLLIN, .data.fd = ls};
    if (epoll_ctl(ep, EPOLL_CTL_ADD, ls, &ev) < 0) die("epoll_ctl");
    printf("echo server on 127.0.0.1:%d\n", port);

    struct epoll_event evs[64];
    for (;;) {
        int n = epoll_wait(ep, evs, 64, -1);
        if (n < 0) { if (errno == EINTR) continue; die("epoll_wait"); }
        for (int i = 0; i < n; i++) {
            int fd = evs[i].data.fd;
            if (fd == ls) {                       /* new connections */
                for (;;) {
                    int c = accept(ls, NULL, NULL);
                    if (c < 0) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                        if (errno == EINTR) continue;
                        die("accept");
                    }
                    set_nonblock(c);
                    struct epoll_event cev = {.events = EPOLLIN, .data.fd = c};
                    if (epoll_ctl(ep, EPOLL_CTL_ADD, c, &cev) < 0) die("epoll_ctl add");
                }
            } else {                              /* data from a client */
                char buf[4096];
                ssize_t r = read(fd, buf, sizeof buf);
                int drop = 0;
                if (r > 0) {
                    ssize_t off = 0;
                    while (off < r) {
                        ssize_t w = write(fd, buf + off, r - off);
                        if (w > 0) off += w;
                        else if (w < 0 && errno == EINTR) continue;
                        else { drop = 1; break; } /* EAGAIN: see extension 1 */
                    }
                } else if (r == 0 || (errno != EAGAIN && errno != EINTR)) {
                    drop = 1;                     /* EOF or real error */
                }
                if (drop) close(fd);              /* close removes it from epoll */
            }
        }
    }
}

Extensions

  1. The server drops a connection if write returns EAGAIN. Add a per-connection output buffer and register EPOLLOUT only while output is pending, so slow clients never lose data.
  2. Add fdatasync and O_DSYNC variants to the C benchmark and compare. Also try posix_fadvise and sequential reads of a large file with and without read-ahead hints, timing them after dropping caches (as root, echo 3 > /proc/sys/vm/drop_caches).
  3. Make the Python WAL handle multi-key transactions with a checksum per record so that a corrupted middle record, not just a torn tail, is detected, then add a test that crashes at every possible byte offset of the log.

Common mistakes and debugging tips

Symptom Likely cause What to do
Data vanish after power loss although write() and close() succeeded Data were only in the page cache fsync the file (and the directory after create or rename); check fsync return values
File is empty or zero-length after a crash following a save Wrote directly over the old file, or renamed without fsync of the new file Write a temp file, fsync it, rename, then fsync the directory
fsync benchmark shows microsecond latency Running on tmpfs or a drive that lies about flushes Benchmark on a real disk; consider power-loss testing
epoll server hangs on a big message Edge-triggered mode with a single read Drain until EAGAIN or use level-triggered mode
Server busy-loops at 100% CPU Non-blocking read in a loop without readiness notification, or EPOLLOUT always registered Wait with epoll; register EPOLLOUT only when you have pending output
select fails for descriptor 1500 FD_SETSIZE is 1024 Use poll or epoll
Journal replay corrupts a file Commit block written before the log blocks were durable, or barriers disabled Keep write barriers enabled; use journal checksums
High system time with an interrupt per packet or I/O Interrupt storm at high rates Coalesce interrupts or poll (NAPI, polled NVMe queues)

Key takeaways

Key takeaways

  • A multi-block file system update is not atomic; a crash after a subset of writes can leave metadata inconsistent or expose stale data.
  • fsck repairs invariants after the fact in time proportional to the disk size. Journaling logs intent first so recovery takes time proportional to the journal size.
  • A journal transaction is: write the log, wait, write the commit block, checkpoint. ext4 ordered mode journals metadata only but writes data first, avoiding garbage exposure at far lower cost than full data journaling.
  • COW and log-structured file systems never overwrite live data and commit by flipping a single root pointer; they buy atomicity and snapshots at the cost of write amplification and cleaning.
  • The page cache with write-back makes write() fast but not durable. Use fsync on the file and, when creating or renaming, on the directory.
  • Polling beats interrupts for short waits and very high rates; DMA frees the CPU from copying; VFS lets many file systems share one interface.
  • For many connections use epoll (readiness) or io_uring (completion) instead of a thread per descriptor.
