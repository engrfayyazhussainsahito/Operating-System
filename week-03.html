Threads and Interprocess Communication

Why a process may contain several threads, how threads are implemented and programmed with POSIX threads, what limits their speedup, and how separate processes exchange data through pipes, shared memory and signals.

  • 2 demos

What you will be able to do

By the end of this week you will be able to:

  • List which resources threads of one process share and which each thread owns privately
  • Create, join and pass data to POSIX threads without the loop-variable address bug
  • Compare user-level, kernel-level and hybrid thread models and state what a blocking call does in each
  • Apply Amdahl's law to compute the speedup and the upper limit for a program with a serial fraction
  • Contrast shared memory with message passing and choose one for a given situation
  • Write C programs that communicate through a pipe, a shared mapping and a signal handler
  • Compute how many processes a fork loop creates and draw the resulting process tree

In Week 2 a process was a self-contained unit: one address space and one flow of control. That design is safe, because processes cannot touch each other's memory, but it is also heavy. Creating a process means building a new address space, and getting two processes to cooperate on one job means sending data between them through the kernel. This week we look at the two answers to those costs. Threads put several flows of control inside one process so that they share memory directly. Interprocess communication (IPC) gives separate processes controlled ways to exchange data.

The chapter then ends by revisiting fork to see how repeated forking builds a tree of processes. One warning before we start: sharing memory is exactly what makes threads fast, and exactly what makes them dangerous. This chapter only shows how to create and use threads. The question of what goes wrong when two threads update the same variable, and the tools that prevent it, is the whole of Week 5, and the scheduler that decides which thread runs is Week 4.

Why threads?

Many flows of control in one process

A thread is a single flow of control inside a process: its own program counter, registers and stack, but running in the address space of the process that contains it. A traditional process has one thread; a multithreaded process has several.

One kitchen, several cooks

In Week 2 a process was a cook in a private kitchen. A multithreaded process is a kitchen with several cooks. They share the same pantry (heap), the same recipe book (code) and the same list of orders pinned on the wall (global variables), but each cook has their own cutting board and a bookmark in their own recipe step (stack and registers). Cooperating is easy because everything is within reach. The danger is two cooks reaching for the last egg at the same time.

Thread

A thread is the basic unit of CPU scheduling. It has a thread ID, a program counter, a set of registers and a stack. The threads of one process share the code, the global data, the heap, the open files and the signal handlers. The kernel records per-thread state in a thread control block, which is smaller than a PCB.

Why use them

There are four standard reasons:

  • Responsiveness. A program with a user interface can keep responding to the user while another thread performs a long computation or waits for the network.
  • Resource sharing. Threads share memory by default. There is no copying and no kernel call needed to pass data between them.
  • Economy. Creating a thread is much cheaper than creating a process, and a switch between threads of the same process avoids changing the address space, so it is cheaper than a full process switch (Week 2).
  • Scalability. A single-threaded process runs on only one core at a time. A process with many threads can use all the cores of a multicore machine.

The price is exactly the sharing. A bug in one thread (a wild pointer, a stack overflow) can corrupt the whole process, and any unprotected access to shared data can produce results that depend on timing.

Process Thread (in the same process)
Address space Private Shared with the other threads
Global variables and heap Private Shared
Stack and registers Private Private per thread
Open files Own table (copied by fork) Shared
Creation cost High Low
Communication Needs IPC through the kernel Reads and writes shared memory
Effect of a crash Only that process dies The entire process dies

Programming with POSIX threads

The standard C interface for threads on Unix is POSIX threads, or pthreads. You compile with gcc -pthread. The two basic calls are:

  • pthread_create(&tid, NULL, function, arg) starts a new thread running function(arg). The function takes and returns a void *, which lets you pass or return a pointer to anything.
  • pthread_join(tid, &result) waits for the thread to finish, in the same way that waitpid waits for a child process, and can retrieve the value it returned.

The following program starts three threads, each working on its own struct job, and collects the results.

#include <pthread.h>
#include <stdio.h>

int shared = 10;                       /* one copy, visible to all threads */

struct job { int id; int result; };

static void *work(void *arg) {
    struct job *j = arg;
    int local = j->id * 100;           /* each thread has its own stack */
    j->result = local + shared;
    return NULL;
}

int main(void) {
    pthread_t t[3];
    struct job jobs[3];
    for (int i = 0; i < 3; i++) {
        jobs[i].id = i + 1;
        pthread_create(&t[i], NULL, work, &jobs[i]);
    }
    for (int i = 0; i < 3; i++) {
        pthread_join(t[i], NULL);
        printf("thread %d returned %d\n", jobs[i].id, jobs[i].result);
    }
    return 0;
}

thread 1 returned 110
thread 2 returned 210
thread 3 returned 310

Each thread has its own local (a different stack variable per thread), but all of them read the same shared. Every thread writes only its own jobs[i], so there is no conflict even though the array is shared. The output order is fixed here only because main joins the threads in order; the threads themselves may have run in any order.

Never pass the address of a loop variable

A very common bug is pthread_create(&t[i], NULL, f, &i) inside a for (int i ...) loop. The thread receives a pointer to i, which the loop keeps changing, so by the time the thread dereferences it, it may see a later value, or the variable may no longer exist when the loop ends. Pass a pointer to a separate element (&ids[i] or &jobs[i], as above), or pass the number itself cast to void *, and make sure the pointed-to data outlives the thread.

Thread-local storage

Sometimes a global-looking variable should have a separate copy for each thread. The classic example is errno, which every thread must see for its own failed calls. C provides this with thread-local storage: __thread (GCC) or _Thread_local (C11).

#include <pthread.h>
#include <stdio.h>

static __thread int tls = 0;           /* one private copy per thread */
static int shared = 0;

static void *bump(void *arg) {
    long id = (long)arg;
    for (int i = 0; i < 1000; i++) tls++;
    printf("thread %ld: tls=%d\n", id, tls);
    shared = 1;
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, bump, (void *)1L);
    pthread_join(a, NULL);
    pthread_create(&b, NULL, bump, (void *)2L);
    pthread_join(b, NULL);
    printf("main: tls=%d shared=%d\n", tls, shared);
    return 0;
}

thread 1: tls=1000
thread 2: tls=1000
main: tls=0 shared=1

Each thread incremented its own tls from 0 to 1000, and main's copy is untouched, while the ordinary global shared was written by a thread and is visible to main. (The threads were joined one at a time here only to keep the output deterministic.)

How threads are implemented

Who knows about a thread, the library or the kernel? That question gives two kinds.

User-level threads are created and scheduled by a library inside the process. The kernel sees one process and knows nothing about the threads. Switching among them needs no system call and is very fast. But because the kernel sees a single schedulable entity, a user-level thread that makes a blocking system call (say, read on a slow disk) blocks the entire process, and the threads cannot run on several cores at once.

Kernel-level threads are created and scheduled by the operating system. A blocking call stops only the calling thread, and different threads can run on different cores. The cost is that creation and switching go through the kernel.

A multithreading model says how user threads map onto kernel threads:

Model Mapping Strengths Weaknesses
Many-to-one Many user threads to 1 kernel thread Cheap, no kernel involvement One blocking call blocks all; no parallelism
One-to-one Each user thread to its own kernel thread True parallelism; blocking is local Each thread costs kernel resources
Many-to-many M user threads multiplexed over N kernel threads Many threads, parallelism Complex to build and tune

Linux, Windows and macOS use the one-to-one model for ordinary threads. In Linux a thread is simply a task created by the clone() system call with flags that say "share the address space, the open files and the signal handlers with the creator". A fork is the same system call with sharing turned off. That is why pthread_create and fork feel like siblings. Modern languages revive many-to-many: Go multiplexes many cheap goroutines over a few kernel threads, and runtimes with async tasks do something similar.

Threads and fork do not mix casually

If a multithreaded process calls fork, the child receives only a copy of the calling thread. Locks held by other threads at that instant stay locked forever in the child, and the other threads simply do not exist there. POSIX therefore advises that in a multithreaded program the child may safely do little more than call exec.

Parallelism, concurrency and Amdahl's law

Two words are often confused. Concurrency means several tasks are in progress during overlapping time periods, even on a single core where the OS switches among them. Parallelism means several tasks are literally executing at the same instant on different cores. Concurrency is a property of the program's structure; parallelism is a property of the hardware and the schedule. A multithreaded program on one core is concurrent but not parallel.

If you convert a program to use N cores, how much faster can it get? Not N times, unless every part of it can be split. Suppose a fraction S of the running time is inherently serial (reading input, a final merge) and the remaining 1 - S parallelizes perfectly.

Amdahl's law

The speedup on N cores is speedup(N) = 1 / (S + (1 - S) / N), where S is the serial fraction of the original execution time (0 ≤ S ≤ 1). As N grows without limit the speedup approaches 1 / S, so the serial part sets an upper bound.

For example, with S = 0.25 and N = 4 cores, speedup = 1 / (0.25 + 0.75/4) = 1 / 0.4375 = 2.29. No matter how many cores you add, the speedup can never exceed 1 / 0.25 = 4. The lesson is that finding and shrinking the serial part often matters more than adding cores. Real programs usually do worse than the formula predicts because it ignores the cost of creating threads, of communication, and of contention for memory bandwidth, which the lab will show you.

Interprocess communication

Processes are isolated on purpose, so cooperation needs help from the OS. There are two fundamental models.

In shared memory, the kernel sets up a region that appears in the address spaces of two or more processes. After the setup, they read and write it as ordinary memory with no system calls, which makes it the fastest IPC. The processes themselves must coordinate access (Week 5).

In message passing, processes exchange discrete messages through the kernel with operations such as send and receive. It is easier to use correctly, since the kernel does the synchronization, and it works across machines (sockets), but each message costs system calls and copies.

Message passing comes in several flavours. Communication may be direct (name the other process) or indirect (use a mailbox or port that several processes can share). It may be synchronous (blocking: send waits until the message is received) or asynchronous, and the buffer may be unbounded or limited. A limited buffer makes the sender wait when it is full, which is a very useful throttle.

Shared memory Message passing
Speed for large data Fastest, no copies Slower, copies through the kernel
Synchronization Programmer's job Provided by the kernel
Across machines No Yes (sockets)
Typical Unix tools mmap, shm_open pipes, sockets, message queues

Pipes, shared memory and signals

Pipes

An ordinary pipe is a one-way byte channel with a write end and a read end. The pipe call returns two file descriptors, and the usual pattern is to create the pipe, fork, and have each side close the end it does not use. This is how the shell builds ls | wc -l.

#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd[2];                         /* fd[0] = read end, fd[1] = write end */
    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid == 0) {                    /* child: the reader */
        close(fd[1]);                  /* close unused write end */
        char buf[64];
        ssize_t n;
        while ((n = read(fd[0], buf, sizeof buf - 1)) > 0) {
            buf[n] = '\0';
            printf("child read %zd bytes: %s", n, buf);
        }
        printf("child saw end-of-file\n");
        close(fd[0]);
        return 0;
    }
    close(fd[0]);                      /* parent: the writer */
    const char *msgs[] = { "first message\n", "second message\n" };
    for (int i = 0; i < 2; i++)
        if (write(fd[1], msgs[i], strlen(msgs[i])) < 0) perror("write");
    close(fd[1]);                      /* without this the child never sees EOF */
    waitpid(pid, NULL, 0);
    return 0;
}

child read 29 bytes: first message
second message
child saw end-of-file

Two points stand out in this real output. First, the child's single read returned both messages together, 29 bytes: a pipe is a byte stream with no message boundaries, so if you need boundaries you must add your own (a length prefix or a newline). Second, the child only sees end-of-file when every copy of the write end is closed, which is why both the child (its unused copy) and the parent (after writing) close fd[1]. If one forgot, the reader would block forever. A pipe also has a finite kernel buffer (64 KiB by default on Linux): a writer blocks when it is full and a reader blocks when it is empty, giving natural flow control. Ordinary pipes need a common ancestor to share the descriptors. Named pipes (FIFOs, made with mkfifo) have a name in the file system, so unrelated processes can use them.

Shared memory

The kernel can also map the same physical pages into two processes. The simplest way between related processes is an anonymous shared mapping made with mmap before fork; unrelated processes use shm_open to name a region.

#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    /* Anonymous shared mapping: survives fork and is shared, not copied. */
    int *counter = mmap(NULL, sizeof *counter, PROT_READ | PROT_WRITE,
                        MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (counter == MAP_FAILED) { perror("mmap"); return 1; }
    int plain = 0;                     /* ordinary memory: copied on fork */
    *counter = 0;

    pid_t pid = fork();
    if (pid == 0) {
        plain = 99;
        *counter = 99;
        return 0;
    }
    waitpid(pid, NULL, 0);
    printf("plain variable  : %d (child's write was private)\n", plain);
    printf("shared mapping  : %d (child's write is visible)\n", *counter);
    munmap(counter, sizeof *counter);
    return 0;
}

plain variable  : 0 (child's write was private)
shared mapping  : 99 (child's write is visible)

This contrasts with the copy-on-write behaviour of ordinary memory after fork. With MAP_SHARED, a write by either process goes to the same physical page, so the other sees it immediately. Here waitpid guarantees the child finished before the parent reads. With real concurrent access you would need the locks of Week 5.

Signals

A signal is a small asynchronous notification delivered to a process, like a software interrupt. Examples: SIGINT (Ctrl-C), SIGTERM (polite request to terminate), SIGKILL (cannot be caught or ignored), SIGCHLD (a child ended) and SIGUSR1 (free for the application). A process may let the default action happen, ignore the signal, or install a handler function with sigaction.

#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t got = 0;

static void on_usr1(int sig) {
    (void)sig;
    got = 1;                           /* do the minimum inside a handler */
}

int main(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_usr1;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    printf("pid %d waiting for SIGUSR1\n", (int)getpid());
    kill(getpid(), SIGUSR1);           /* send the signal to ourselves */
    while (!got) pause();
    printf("handler ran, got=%d\n", got);
    return 0;
}

pid 292 waiting for SIGUSR1
handler ran, got=1

A handler can interrupt the program between any two instructions, so it must do very little: set a flag of type volatile sig_atomic_t and return, and let the main code act on the flag. Most library functions, including printf and malloc, are not safe to call from a handler. Signals carry almost no information (just the number), so they are good for events ("stop", "reload your configuration", "a child ended") but not for data.

Process trees and fork loops

Because every fork clones the caller, calling fork in a loop does not create n processes. Each child continues the loop too, so it forks as well. After the loop for (i = 0; i < n; i++) fork(); there are 2ⁿ processes: every pass doubles the number of live processes.

#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    for (int i = 0; i < 3; i++)
        fork();                        /* every process forks on every pass */
    printf("pid %d\n", (int)getpid());
    fflush(stdout);
    while (wait(NULL) > 0) ;           /* reap all children */
    return 0;
}

This prints eight lines (pid ...), with different PIDs and in an unpredictable order, since 2³ = 8. Which process is the parent of which? A process created during pass k (counting from 0) inherits the loop counter k, so it goes on to fork during passes k + 1, k + 2 and so on.

A fork bomb is this loop without a bound

while (1) fork(); doubles the process count until the machine runs out of process slots or memory. Systems defend themselves with per-user process limits (ulimit -u), which is one of the reasons fork can legitimately return -1.

Exercises

Exercise 3.1warm-up

Shared or private?

For two threads of the same process, say whether each item is shared or private to each thread: (a) a global variable, (b) a local variable in a function, (c) memory from malloc whose pointer is stored in a global, (d) the program counter, (e) an open file descriptor, (f) errno.

Show solution

(a) Shared. (b) Private, it lives on the thread's own stack. (c) The heap block is shared, and any thread that has the pointer can use it. (d) Private; each thread is at a different point in the code. (e) Shared, the descriptor table belongs to the process. (f) Private (thread-local), so one thread's failed system call does not overwrite another thread's error code.

Exercise 3.2core

Amdahl's law by hand

A program spends 20 percent of its time in serial code and 80 percent in code that parallelizes perfectly. Compute the speedup on 8 cores, then the maximum possible speedup. If the 8-core machine were replaced by a 64-core one, would the speedup double?

Show solution

S = 0.2. On 8 cores: speedup = 1 / (0.2 + 0.8/8) = 1 / (0.2 + 0.1) = 1 / 0.3 = 3.33. The maximum, with unlimited cores, is 1 / S = 1 / 0.2 = 5. On 64 cores: 1 / (0.2 + 0.8/64) = 1 / (0.2 + 0.0125) = 1 / 0.2125 = 4.71. Going from 8 to 64 cores (8 times the hardware) improves the speedup only from 3.33 to 4.71, a factor of 1.41, far from double. The serial 20 percent dominates.

Exercise 3.3core

Count processes in fork loops

How many processes exist (including the original) after each fragment? (a) for (int i = 0; i < 4; i++) fork(); (b) for (int i = 0; i < 3; i++) { if (fork() == 0) break; }

Show solution

(a) Each pass doubles the process count: 2⁴ = 16 processes. (b) In each pass, only the process that received a non-zero value (the parent) continues the loop; the child breaks out. Hence only the original process ever forks, and it forks three times, giving 1 + 3 = 4 processes. Variant (b) is the standard idiom for creating exactly n children.

Exercise 3.4core

Why does the reader hang?

In the pipe example, suppose the parent forgets close(fd[1]) after writing but still calls waitpid. What happens, and why? What if the child forgets close(fd[1]) but the parent closes its own copy?

Show solution

In the first case the write end is still open in the parent, so the pipe is never at end-of-file. The child reads the two messages and then blocks in read, waiting for more data that could still arrive. The parent is blocked in waitpid waiting for the child. Neither can proceed: a deadlock. In the second case, the child itself holds an open write end, so the kernel again sees a possible writer, and the child's own read never returns 0. The rule is that EOF appears only when all copies of the write end, in every process, are closed. This is why each side closes the pipe end it does not use immediately after the fork.

Exercise 3.5core

The loop variable bug

A student writes for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, worker, &i); where worker prints *(int *)arg. The output on one run is 4 4 4 4, on another 1 3 3 4. Explain how each can happen and give two ways to fix the code.

Show solution

All four threads receive the same address, that of the single variable i in main. The value they print is whatever i holds at the moment each thread executes its dereference. The loop continues to increment i while the threads start, so a thread that starts late sees a later value. After the final increment i is 4, which gives 4 4 4 4 when all threads were slow to start. Different runs produce different timing and so different mixes. Fixes: (1) keep an array int ids[4] filled with 0 to 3 and pass &ids[i], so each thread has a separate location that does not change; (2) pass the value itself, (void *)(long)i, and in worker convert back with (int)(long)arg. (Allocating a small struct with malloc per thread and freeing it in the thread also works.)

Exercise 3.6challenging

Copies versus mapping

A producer must deliver 1000 messages of 1 MiB each to a consumer process. Through a pipe, each message is copied from the producer's memory into the kernel buffer and then from the kernel buffer into the consumer's memory. Assume memory copies run at 10 GiB/s and ignore all other costs. How much data is copied and how long do the copies take for the pipe design? How does a shared-memory design change this, and what does it cost the programmer?

Show solution

Data size: 1000 × 1 MiB = 1000 MiB per copy direction. Through the pipe there are two copies per message, so 2000 MiB are copied. Time at 10 GiB/s = 10,240 MiB/s: 2000 / 10,240 = 0.195 s, roughly 0.2 seconds, plus the cost of the system calls. With shared memory the producer writes the message directly into the shared region and the consumer reads it in place, so the kernel copies nothing: at most the producer's single write into the buffer remains (1000 MiB, 0.098 s) and the consumer reads the data where it is. The cost to the programmer is that processes must now synchronize themselves (when is the buffer full or empty, who may write) using the tools of Week 5 and Week 6, and must define their own message format and framing.

Exercise 3.7challenging

Blocking in the three thread models

A program has four threads that each need to read from a slow disk and then compute. On a four-core machine, describe what happens when thread 1 calls a blocking read under (a) the many-to-one model, (b) the one-to-one model. Which model can finish the computation of the other three threads while thread 1 is waiting?

Show solution

(a) With many-to-one, all four user threads sit on one kernel thread. The kernel sees only one schedulable entity, so when thread 1 blocks in read, the whole process is blocked, and threads 2, 3 and 4 cannot run even though three cores are idle. Even without blocking, the four threads could use only one core. (b) With one-to-one, each user thread is its own kernel thread. The kernel marks only thread 1 as Waiting; threads 2 to 4 stay Ready or Running and can compute on the other cores while the disk works. So one-to-one (and many-to-many with enough kernel threads) can finish the others' computation while thread 1 waits. Many-to-one cannot.

Lab: speedup of a parallel sum

You will sum an array of 80 million integers with 1, 2, 4 and 8 threads, split into equal ranges, and compare the measured speedup with Amdahl's law. Each thread writes its partial sum to its own slot, so threads never write to the same variable and no locks are needed. The main thread adds up the partial sums. Save the program as psum.c.

#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 80000000L

static int *data;
static long partial[8];
struct range { int id; long lo, hi; };

static void *sum_part(void *arg) {
    struct range *r = arg;
    long s = 0;
    for (long i = r->lo; i < r->hi; i++) s += data[i];
    partial[r->id] = s;                /* each thread writes its own slot */
    return NULL;
}

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    int nthreads = argc > 1 ? atoi(argv[1]) : 2;
    if (nthreads < 1 || nthreads > 8) nthreads = 2;
    data = malloc(N * sizeof *data);
    for (long i = 0; i < N; i++) data[i] = (int)(i % 10);

    pthread_t t[8];
    struct range r[8];
    double start = now();
    for (int k = 0; k < nthreads; k++) {
        r[k].id = k;
        r[k].lo = N / nthreads * k;
        r[k].hi = (k == nthreads - 1) ? N : N / nthreads * (k + 1);
        pthread_create(&t[k], NULL, sum_part, &r[k]);
    }
    long total = 0;
    for (int k = 0; k < nthreads; k++) {
        pthread_join(t[k], NULL);
        total += partial[k];
    }
    printf("threads=%d sum=%ld time=%.3fs\n", nthreads, total, now() - start);
    free(data);
    return 0;
}

Build and run:

gcc -Wall -pthread psum.c -o psum
for n in 1 2 4 8; do ./psum $n; done
taskset -c 0 ./psum 4

What to observe. On a machine with two cores the real output was:

threads=1 sum=360000000 time=0.220s
threads=2 sum=360000000 time=0.116s
threads=4 sum=360000000 time=0.118s
threads=8 sum=360000000 time=0.113s
threads=4 sum=360000000 time=0.217s

The sum is always 360,000,000 (80 million values averaging 4.5), so the parallel version is correct. Two threads run 0.220 / 0.116 = 1.9 times faster, close to the ideal 2. Four and eight threads are no faster, because only two cores exist: extra threads only add scheduling work. The last line pins the whole process to core 0 with taskset, and four threads then take as long as one, confirming that threads give a speedup only when cores are available. The time measured here excludes filling the array, which is the serial part we chose not to count. On your machine, estimate the serial fraction S that Amdahl's law implies from your measured 2-thread and 4-thread speedups.

Common mistakes and debugging tips

Symptom Likely cause What to do
Threads print the same or a wrong argument value Passed the address of a loop variable Give each thread its own argument storage, or pass the value
Program exits and threads never finish their work main returned without pthread_join (returning from main ends all threads) Join every thread, or call pthread_exit in main
Link error: undefined reference to pthread_create Missing -pthread flag Compile and link with gcc -pthread
Totals differ from run to run Several threads update shared data without protection Give each thread private data, or use the locks of Week 5
Reader on a pipe never returns Some process still holds the write end open Close every unused end right after fork
Child of a pipe sees broken pipe (SIGPIPE) when writing The read end was closed in every process Keep a reader open, or handle SIGPIPE
Speedup far below the number of threads Serial fraction, too few cores, or memory bandwidth limits Measure the serial part and compare with Amdahl's law; check nproc
Strange crash in a handler that calls printf Calling a function that is not async-signal-safe Only set a sig_atomic_t flag in the handler

Key takeaways

Key takeaways

  • Threads of one process share code, globals, heap and open files but have private stacks and registers, which makes them cheap and also makes sharing bugs possible.
  • Use pthread_create and pthread_join; never pass the address of a changing loop variable; compile with -pthread.
  • Linux, Windows and macOS use one-to-one threads, so a blocking call stops only one thread and threads can run in parallel on several cores.
  • Amdahl's law, speedup = 1 / (S + (1 - S) / N), shows that the serial fraction S caps the benefit of more cores at 1 / S.
  • IPC is either shared memory (fast, you synchronize) or message passing (the kernel copies and synchronizes). Pipes are byte streams that need their unused ends closed to deliver EOF.
  • Signals carry events, not data; handlers must do almost nothing. A fork loop of n passes produces 2ⁿ processes.
