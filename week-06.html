What you will be able to do

By the end of this week you will be able to:

  • Solve the bounded buffer problem with two counting semaphores and a mutex, and explain why the order of the waits matters
  • Define a monitor and distinguish Mesa (signal and continue) from Hoare (signal and wait) semantics
  • Implement a monitor with a mutex and condition variables, and build a counting semaphore from them
  • Compare the readers-preference and writers-preference solutions and identify who can starve in each
  • Show how the naive dining philosophers solution deadlocks and fix it by resource ordering or by limiting the number of diners
  • Use the ten-item checklist to find gaps in your preparation for the midterm covering Weeks 1 to 7

Week 5 gave you the primitives: atomic instructions, spinlocks, mutexes, semaphores and condition variables. A primitive is like a hammer; knowing how it works does not tell you what to build. This week we study the three problems that have served for sixty years as the standard test of any synchronization tool. Each one isolates a different difficulty. The bounded buffer is about cooperation: one thread must wait for another to produce something. Readers-writers is about asymmetric sharing: some accesses may overlap and some may not. Dining philosophers is about holding several resources at once, and it leads directly to Week 7, where deadlock gets its own chapter and Assignment 2 (threads and synchronization) falls due.

In the middle of the chapter we climb one level of abstraction. Semaphores are powerful but unforgiving: one swapped line and the program deadlocks. A monitor packages the shared data, the lock and the waiting rules into one unit that the compiler or library helps you use correctly. Every listing here is a complete C program that compiles with gcc -Wall -pthread, and the output shown is what they printed on a two-core test machine.

The chapter ends with a midterm review. The midterm covers Weeks 1 to 7 and takes place in Week 8, so the last section is a checklist you can work through now, while the material is fresh.

The bounded buffer problem

The setting

A producer creates items and a consumer uses them. They communicate through a buffer of fixed capacity N, a bounded buffer, shared by all of them. This is not a toy: a Unix pipe is a bounded buffer (the kernel's pipe buffer is typically 64 KiB), a print spooler is one, and so is the queue between a network card driver and the protocol stack. The rules are:

  • A producer must wait when the buffer is full (no free slot).
  • A consumer must wait when the buffer is empty (nothing to take).
  • Only one thread may modify the buffer's indices at a time.

The sushi conveyor

A chef places plates on a conveyor belt with room for N plates. If the belt is full, the chef stands idle. A customer takes plates; if the belt is empty, the customer waits. Nobody should put two plates on the same spot, and nobody should grab a plate that is not there. Two things are being counted: free spots and plates. The chef waits on free spots; the customer waits on plates.

The semaphore solution

The classic solution uses three semaphores, each with one clear job (recall the initial-value table in Week 5):

Semaphore Initial value Meaning Who waits on it
empty_slots N number of free slots producers
full_slots 0 number of filled slots consumers
mutex 1 exclusive access to in, out and the array both

A producer does wait(empty_slots), then locks the buffer and inserts, then signal(full_slots). A consumer does the mirror image. Each side waits on the resource it needs and signals the resource it creates.

The program below runs two producers and two consumers. Each producer inserts the numbers 1 to 10,000, so the total produced is 2 × 10,000 × 10,001 / 2 = 100,010,000, and every item must be consumed exactly once. The code also records the largest occupancy it ever saw, which must never exceed N.

/* bb_sem.c: bounded buffer with two counting semaphores and a mutex. */
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>

#define N      4          /* buffer capacity */
#define ITEMS  10000      /* items made by each producer */
#define NPROD  2
#define NCONS  2

static int buf[N];
static int in = 0, out = 0;           /* next slot to fill / to empty */
static int count = 0, max_count = 0;  /* occupancy, only for checking */
static sem_t empty_slots, full_slots;
static pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
static long psum[NPROD], csum[NCONS];

static void *producer(void *arg) {
    long id = (long)arg;
    for (int i = 1; i <= ITEMS; i++) {
        sem_wait(&empty_slots);               /* wait for a free slot */
        pthread_mutex_lock(&mutex);
        buf[in] = i;
        in = (in + 1) % N;
        if (++count > max_count) max_count = count;
        pthread_mutex_unlock(&mutex);
        sem_post(&full_slots);                /* announce a filled slot */
        psum[id] += i;
    }
    return NULL;
}

static void *consumer(void *arg) {
    long id = (long)arg;
    for (int i = 0; i < ITEMS; i++) {         /* NPROD == NCONS, so equal shares */
        sem_wait(&full_slots);                /* wait for a filled slot */
        pthread_mutex_lock(&mutex);
        int item = buf[out];
        out = (out + 1) % N;
        count--;
        pthread_mutex_unlock(&mutex);
        sem_post(&empty_slots);               /* announce a free slot */
        csum[id] += item;
    }
    return NULL;
}

int main(void) {
    pthread_t p[NPROD], c[NCONS];
    sem_init(&empty_slots, 0, N);             /* N free slots */
    sem_init(&full_slots, 0, 0);              /* 0 filled slots */
    for (long i = 0; i < NPROD; i++) pthread_create(&p[i], NULL, producer, (void *)i);
    for (long i = 0; i < NCONS; i++) pthread_create(&c[i], NULL, consumer, (void *)i);
    for (int i = 0; i < NPROD; i++) pthread_join(p[i], NULL);
    for (int i = 0; i < NCONS; i++) pthread_join(c[i], NULL);
    long ps = 0, cs = 0;
    for (int i = 0; i < NPROD; i++) ps += psum[i];
    for (int i = 0; i < NCONS; i++) cs += csum[i];
    printf("produced sum = %ld, consumed sum = %ld, max occupancy = %d (capacity %d)\n",
           ps, cs, max_count, N);
    return 0;
}

produced sum = 100010000, consumed sum = 100010000, max occupancy = 4 (capacity 4)

If an item were lost or duplicated, the two sums would differ; if the buffer overflowed, the maximum would exceed 4. The sums are updated outside the critical section on purpose: each thread has its own slot in psum and csum, so nothing is shared.

The order of the two waits is not negotiable

Suppose the producer writes wait(mutex) first and wait(empty_slots) second. When the buffer is full, the producer takes the mutex and then sleeps on empty_slots while holding the mutex. The consumer needs the mutex to remove an item, so it blocks too, and no one can ever signal empty_slots. Both threads sleep forever: deadlock. The rule is: wait for the counting semaphore first, take the mutex second, and release them in the opposite order. Never sleep while holding a lock that your wake-up depends on.

Notice the elegant property that makes the solution work: the semaphore values are the predicates. A consumer does not test "is the buffer empty?" in an if; it blocks on a counter that is zero exactly when the buffer is empty. The semaphore remembers wake-ups, so no signal can be lost. Monitors and condition variables

The idea

With semaphores, the programmer must remember which one guards what, and in which order to take them. A monitor, proposed by Per Brinch Hansen and C. A. R. Hoare in the early 1970s, moves that discipline into the structure of the program.

Monitor

A monitor is a module that bundles (1) shared data, (2) the procedures that operate on it, and (3) a lock, with the rule that at most one thread is active inside the monitor at any time. The lock is acquired automatically on entry to any procedure and released on exit. A monitor also provides condition variables, each with wait and signal operations, so a thread can sleep inside the monitor until some predicate about the data becomes true.

A language with built-in monitors (Java's synchronized methods with wait, notify and notifyAll, C#'s lock and Monitor.Wait) makes the lock implicit. In C you build the same structure by hand: a struct holding the data, one mutex, and one condition variable per kind of waiting, with every access going through functions that lock on entry and unlock on exit.

Hoare versus Mesa semantics

What happens at the moment thread A calls signal and thread B, who was waiting, becomes ready? Two answers exist, and the difference matters in every program you write.

  • Hoare semantics (signal and wait). The signaller hands the monitor directly to the woken thread and sleeps itself. When B runs, the condition it waited for is guaranteed true, because nobody else got in between. B may use if. It is elegant and easy to prove correct, but costs extra context switches.
  • Mesa semantics (signal and continue). The signaller keeps the monitor and keeps running. The woken thread is only moved to the ready queue; it must later re-acquire the lock, and by then another thread may have changed the data. signal is a hint, not a guarantee, so the waiter must re-check its predicate in a while loop.

Mesa semantics, named after the Xerox Mesa system described by Lampson and Redell in 1980, is what POSIX threads, Java and C# implement. That is exactly the "while-loop rule" from Week 5: it is not a stylistic preference but a consequence of Mesa semantics.

Hoare Mesa (pthreads, Java, C#)
After signal Signaller sleeps, waiter runs at once Signaller continues; waiter becomes ready
Condition true on wake-up? Guaranteed Not guaranteed
Waiter code if (!cond) wait while (!cond) wait
Cost More context switches Cheaper; allows broadcast and spurious wake-ups

The bounded buffer as a monitor

Compare this version with the semaphore one. The data and its lock live in one struct; the two predicates, "not full" and "not empty", become two condition variables; there is no counting semaphore at all.

/* bb_mon.c: the same bounded buffer written as a monitor (mutex + condition variables). */
#include <pthread.h>
#include <stdio.h>

#define N      4
#define ITEMS  10000
#define NPROD  2
#define NCONS  2

struct monitor {
    pthread_mutex_t lock;        /* the monitor lock: one thread inside at a time */
    pthread_cond_t  not_full;    /* producers wait here  */
    pthread_cond_t  not_empty;   /* consumers wait here  */
    int buf[N];
    int in, out, count;
};

static struct monitor m = { PTHREAD_MUTEX_INITIALIZER, PTHREAD_COND_INITIALIZER,
                            PTHREAD_COND_INITIALIZER, {0}, 0, 0, 0 };
static long psum[NPROD], csum[NCONS];

static void put(struct monitor *mon, int item) {
    pthread_mutex_lock(&mon->lock);
    while (mon->count == N)                         /* Mesa rule: while, never if */
        pthread_cond_wait(&mon->not_full, &mon->lock);
    mon->buf[mon->in] = item;
    mon->in = (mon->in + 1) % N;
    mon->count++;
    pthread_cond_signal(&mon->not_empty);
    pthread_mutex_unlock(&mon->lock);
}

static int get(struct monitor *mon) {
    pthread_mutex_lock(&mon->lock);
    while (mon->count == 0)
        pthread_cond_wait(&mon->not_empty, &mon->lock);
    int item = mon->buf[mon->out];
    mon->out = (mon->out + 1) % N;
    mon->count--;
    pthread_cond_signal(&mon->not_full);
    pthread_mutex_unlock(&mon->lock);
    return item;
}

static void *producer(void *arg) {
    long id = (long)arg;
    for (int i = 1; i <= ITEMS; i++) { put(&m, i); psum[id] += i; }
    return NULL;
}
static void *consumer(void *arg) {
    long id = (long)arg;
    for (int i = 0; i < ITEMS; i++) csum[id] += get(&m);
    return NULL;
}

int main(void) {
    pthread_t p[NPROD], c[NCONS];
    for (long i = 0; i < NPROD; i++) pthread_create(&p[i], NULL, producer, (void *)i);
    for (long i = 0; i < NCONS; i++) pthread_create(&c[i], NULL, consumer, (void *)i);
    for (int i = 0; i < NPROD; i++) pthread_join(p[i], NULL);
    for (int i = 0; i < NCONS; i++) pthread_join(c[i], NULL);
    long ps = 0, cs = 0;
    for (int i = 0; i < NPROD; i++) ps += psum[i];
    for (int i = 0; i < NCONS; i++) cs += csum[i];
    printf("produced sum = %ld, consumed sum = %ld, items left = %d\n", ps, cs, m.count);
    return 0;
}

produced sum = 100010000, consumed sum = 100010000, items left = 0

Each procedure has the same shape: lock, while (predicate is false) wait, do the work, signal whoever the work may have unblocked, unlock. A producer signals not_empty because it just made the buffer non-empty; a consumer signals not_full. With one condition variable per predicate a plain signal is enough, since every waiter on not_empty is waiting for the same thing.

Monitors and semaphores are equally powerful

Each can build the other. The previous chapter showed a semaphore as an integer plus a queue. The next listing builds a counting semaphore from nothing but a mutex and a condition variable, which is a good test of whether you have understood both. The predicate is "value is greater than zero", and the semaphore is used here as a lock by four threads.

/* mysem.c: a counting semaphore built from one mutex and one condition variable. */
#include <pthread.h>
#include <stdio.h>

typedef struct {
    pthread_mutex_t lock;
    pthread_cond_t  nonzero;
    int value;
} mysem;

static void mysem_init(mysem *s, int v) {
    pthread_mutex_init(&s->lock, NULL);
    pthread_cond_init(&s->nonzero, NULL);
    s->value = v;
}
static void mysem_wait(mysem *s) {
    pthread_mutex_lock(&s->lock);
    while (s->value == 0)                      /* the predicate: "value > 0" */
        pthread_cond_wait(&s->nonzero, &s->lock);
    s->value--;
    pthread_mutex_unlock(&s->lock);
}
static void mysem_post(mysem *s) {
    pthread_mutex_lock(&s->lock);
    s->value++;
    pthread_cond_signal(&s->nonzero);
    pthread_mutex_unlock(&s->lock);
}

static mysem gate;
static long counter = 0;

static void *worker(void *arg) {
    (void)arg;
    for (int i = 0; i < 100000; i++) {
        mysem_wait(&gate);                     /* binary semaphore used as a lock */
        counter++;
        mysem_post(&gate);
    }
    return NULL;
}

int main(void) {
    pthread_t t[4];
    mysem_init(&gate, 1);
    for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < 4; i++) pthread_join(t[i], NULL);
    printf("counter = %ld (expected 400000)\n", counter);
    return 0;
}

counter = 400000 (expected 400000)

The converse also works (the textbook construction of a monitor from semaphores is longer and subtle, because wait must release the monitor lock and block as one atomic step). In practice you rarely build either from the other, but the exercise explains why your library offers both: the semaphore remembers signals, while the condition variable lets you wait for any predicate you can write in C.

A monitor-writing recipe

  1. List the shared variables and give them one mutex. 2. For each reason a thread might have to wait, write the predicate in terms of those variables and give it a condition variable. 3. Every procedure starts with lock, loops on its predicate, and ends with unlock. 4. After changing the data, ask "which predicates could this have made true?" and signal those conditions. When two kinds of waiters share one condition variable, use broadcast.

Readers-writers

The problem

A database, a cache or an in-memory table is read far more often than it is written. Any number of readers may look at the data simultaneously, since reading changes nothing, but a writer needs exclusive access: no other writer and no reader. Plain mutual exclusion would be correct but needlessly slow, because it would also forbid concurrent readers. The requirement is:

  • Many readers may be inside at once.
  • A writer excludes everyone else.

First solution: readers preference

The first solution of Courtois, Heymans and Parnas (1971) uses one semaphore rw_mutex for "the data is taken" and a counter read_count of active readers, protected by a second semaphore. The first reader in locks writers out on behalf of the whole group; the last reader out lets them back in.

/* rw.c: readers-writers with semaphores (readers preference). */
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <sched.h>
#include <semaphore.h>
#include <stdio.h>

#define NREADERS 3
#define NWRITERS 2
#define READS    20000
#define WRITES   1000

static sem_t rw_mutex;              /* held by a writer, or by the group of readers */
static sem_t mutex;                 /* protects read_count */
static int read_count = 0;

static int a = 0, b = 0;            /* invariant: a == b whenever nobody is writing */
static long torn = 0, reads_done = 0;
static pthread_mutex_t stats = PTHREAD_MUTEX_INITIALIZER;

static void *reader(void *arg) {
    (void)arg;
    long bad = 0;
    for (int i = 0; i < READS; i++) {
        sem_wait(&mutex);
        if (++read_count == 1) sem_wait(&rw_mutex);   /* first reader locks writers out */
        sem_post(&mutex);

        int x = a;
        sched_yield();                                /* widen the window on purpose */
        int y = b;
        if (x != y) bad++;

        sem_wait(&mutex);
        if (--read_count == 0) sem_post(&rw_mutex);   /* last reader lets writers in */
        sem_post(&mutex);
    }
    pthread_mutex_lock(&stats);
    torn += bad;
    reads_done += READS;
    pthread_mutex_unlock(&stats);
    return NULL;
}

static void *writer(void *arg) {
    (void)arg;
    for (int i = 0; i < WRITES; i++) {
        sem_wait(&rw_mutex);                          /* exclusive access */
        int v = a + 1;
        a = v;
        sched_yield();
        b = v;
        sem_post(&rw_mutex);
    }
    return NULL;
}

int main(void) {
    pthread_t r[NREADERS], w[NWRITERS];
    sem_init(&rw_mutex, 0, 1);
    sem_init(&mutex, 0, 1);
    for (int i = 0; i < NREADERS; i++) pthread_create(&r[i], NULL, reader, NULL);
    for (int i = 0; i < NWRITERS; i++) pthread_create(&w[i], NULL, writer, NULL);
    for (int i = 0; i < NREADERS; i++) pthread_join(r[i], NULL);
    for (int i = 0; i < NWRITERS; i++) pthread_join(w[i], NULL);
    printf("reads = %ld, torn reads = %ld, final a = %d, b = %d (expected %d)\n",
           reads_done, torn, a, b, NWRITERS * WRITES);
    return 0;
}

The invariant a == b makes the correctness check visible. A writer sets a, yields the CPU on purpose, and then sets b. A reader that saw a and b in the middle of a write would notice a mismatch, a torn read. The sched_yield() calls widen the window to make such a bug likely if the locking were wrong.

reads = 60000, torn reads = 0, final a = 2000, b = 2000 (expected 2000)

Who starves?

In this solution a steady stream of overlapping readers can keep read_count above zero forever, so the writer never gets in: writer starvation. The second readers-writers problem demands the opposite, writers have priority: once a writer is waiting, no new reader may enter. That solution starves readers when writers keep coming. A fair (third) variant queues arrivals in order and lets whole groups of consecutive readers through together. The lesson is that there is no free lunch: you choose whom to favour.

POSIX packages the problem as pthread_rwlock_t with pthread_rwlock_rdlock, pthread_rwlock_wrlock and pthread_rwlock_unlock. The default policy in glibc prefers readers, and you can request writer preference with pthread_rwlockattr_setkind_np. The lab at the end of this chapter measures the difference. One more caution: a read-write lock pays off only when reads dominate and the critical section is long enough to amortize its bookkeeping; for tiny sections a plain mutex is often faster, because the rwlock's own counter becomes a contended cache line.

Dining philosophers

The problem

Five philosophers sit around a table. Between each pair of neighbours lies one fork, so there are five forks. A philosopher alternates between thinking and eating, and eating needs both the left and right fork. Philosopher i uses fork i on the left and fork (i + 1) mod 5 on the right. Forks are picked up one at a time. Dijkstra posed a version of this in 1965 as an examination question about tape drives; Hoare later gave it the form with philosophers and (originally) forks and spaghetti.

Why a story about spaghetti?

The problem is a deliberately minimal model of a process that needs two resources at once, such as a transfer between two bank accounts (two locks) or a program that needs a tape drive and a printer. The philosophers are processes and the forks are resources. If you can solve this problem with no deadlock, no starvation and good concurrency, you have a recipe for the general case.

The obvious solution deadlocks

Each philosopher takes the left fork and then the right one. If all five take their left fork at the same moment, every fork is held and every philosopher waits for a fork held by his neighbour. Nobody can proceed and nobody will give up a fork.

The probability of hitting this at any single meal is small, which is exactly why the bug survives testing. Deadlock needs a precise alignment, as with the races of Week 5, but unlike a race it does not corrupt data: it freezes the program.

Two fixes that work

  • Resource ordering. Number the forks and always pick up the lower-numbered one first. Philosophers 0 to 3 behave as before; philosopher 4 needs forks 4 and 0 and takes fork 0 first. The cycle in Figure 6.4 can no longer form, because P4 would be waiting on F0 without holding F4. This is the standard cure for circular wait and you will meet it again in Week 7.
  • Limit the diners. Allow at most four philosophers to try to eat at once, using a counting semaphore room initialized to N - 1 = 4. With four diners and five forks, at least one philosopher can always get both forks (the diner next to the empty seat finds a free fork on that side), so progress is guaranteed.

A third family of solutions, the asymmetric one, has odd-numbered philosophers pick up the left fork first and even-numbered ones the right fork first, which also breaks the cycle. Chandy and Misra (1984) gave a fully distributed solution where forks are "clean" or "dirty" and are passed by request, with no central arbiter and no starvation.

A program that shows all three behaviours

The next program starts five philosopher threads and takes the strategy from the command line. To make the deadlock reproducible, each philosopher pauses for 2 ms after picking up the first fork, and the second fork is requested with a 1.5 second timeout so that a stuck philosopher reports itself instead of hanging your terminal. Each philosopher eats 50 times.

/* phil.c: five dining philosophers with three strategies: naive, ordered, limited. */
#define _DEFAULT_SOURCE
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

#define N      5
#define MEALS  50

static pthread_mutex_t fork_[N];
static sem_t room;                 /* "limited" strategy: at most N-1 may try to eat */
static int strategy;               /* 0 naive, 1 ordered, 2 limited */
static int meals[N], stuck[N];

static int lock_with_timeout(pthread_mutex_t *m, long ms) {
    struct timespec t;
    clock_gettime(CLOCK_REALTIME, &t);
    t.tv_sec  += ms / 1000;
    t.tv_nsec += (ms % 1000) * 1000000L;
    if (t.tv_nsec >= 1000000000L) { t.tv_sec++; t.tv_nsec -= 1000000000L; }
    return pthread_mutex_timedlock(m, &t);       /* 0 on success, ETIMEDOUT otherwise */
}

static void *philosopher(void *arg) {
    int i = (int)(long)arg;
    int left = i, right = (i + 1) % N;
    int first = left, second = right;
    if (strategy == 1 && right < left) { first = right; second = left; }  /* lower number first */

    for (int k = 0; k < MEALS; k++) {
        if (strategy == 2) sem_wait(&room);
        pthread_mutex_lock(&fork_[first]);
        usleep(2000);                            /* think a little: gives the others time to grab too */
        if (lock_with_timeout(&fork_[second], 1500) != 0) {
            stuck[i] = 1;      /* 1.5 s holding one fork and still no second one: deadlock */
            return NULL;       /* give up but keep the fork, exactly as a deadlocked thread would */
        }
        meals[i]++;                              /* eat */
        usleep(100);
        pthread_mutex_unlock(&fork_[second]);
        pthread_mutex_unlock(&fork_[first]);
        if (strategy == 2) sem_post(&room);
    }
    return NULL;
}

int main(int argc, char **argv) {
    const char *name = argc > 1 ? argv[1] : "naive";
    if      (!strcmp(name, "naive"))   strategy = 0;
    else if (!strcmp(name, "ordered")) strategy = 1;
    else if (!strcmp(name, "limited")) strategy = 2;
    else { fprintf(stderr, "usage: %s naive|ordered|limited\n", argv[0]); return 2; }

    for (int i = 0; i < N; i++) pthread_mutex_init(&fork_[i], NULL);
    sem_init(&room, 0, N - 1);
    pthread_t t[N];
    for (long i = 0; i < N; i++) pthread_create(&t[i], NULL, philosopher, (void *)i);
    for (int i = 0; i < N; i++) pthread_join(t[i], NULL);

    int nstuck = 0;
    printf("%-8s meals:", name);
    for (int i = 0; i < N; i++) { printf(" %d", meals[i]); nstuck += stuck[i]; }
    printf("  deadlocked philosophers: %d\n", nstuck);
    return 0;
}

Build it with gcc -Wall -pthread phil.c -o phil and run each strategy:

$ ./phil naive
naive    meals: 0 0 0 0 0  deadlocked philosophers: 5
$ ./phil ordered
ordered  meals: 50 50 50 50 50  deadlocked philosophers: 0
$ ./phil limited
limited  meals: 50 50 50 50 50  deadlocked philosophers: 0

The naive run takes the full 1.5 s timeout and nobody eats once; the other two finish in about 0.6 s. Now try it interactively. In the demo, start with the deadlock-prone strategy and step until every philosopher holds exactly one fork, which is the state of Figure 6.4. Then switch to the ordered strategy and to the limited strategy and compare how many philosophers can eat at the same time (the maximum is two, since each diner uses two of the five forks).

Midterm review: a ten-item checklist

The midterm covers Weeks 1 to 7 and happens in Week 8. The checklist below has one item per topic cluster. For each, the test is "can I do this on a blank sheet without looking?" Anything you cannot do goes on a list for the week-8 review session.

  1. Dual mode and system calls (Week 1). Draw the path of a read() call from user code through the trap to the kernel and back. State why privileged instructions exist and what a timer interrupt is for. Contrast monolithic, layered and microkernel structure.
  2. Processes (Week 2). Draw the five-state diagram with the event that causes each transition. List what a PCB contains. Explain exactly what a context switch saves and restores, and what fork, exec and wait each do.
  3. Threads and IPC (Week 3). State what threads share and what they keep private. Compare many-to-one, one-to-one and many-to-many mapping. Compare pipes, shared memory and message passing.
  4. Scheduling traces (Week 4). Given arrivals and bursts, draw the Gantt chart and compute waiting, turnaround and response times for FCFS, SJF, SRTF, round robin and a multilevel feedback queue. Do the exponential-average prediction by hand.
  5. Scheduling models (Week 4). Compute CFS shares from nice-value weights (weight divided by total weight), and apply the rate-monotonic bound n(2^(1/n) - 1) and the EDF test U ≤ 1.
  6. Races and critical sections (Week 5). Trace a lost update through load, add and store. State mutual exclusion, progress and bounded waiting and decide which one a given protocol violates.
  7. Locks and semaphores (Week 5). Explain atomic test-and-set and compare-and-swap, when to spin and when to block, and priority inversion with its cure. Trace a counting semaphore with negative values.
  8. Condition variables and monitors (Weeks 5 and 6). Explain the while-loop rule. Distinguish Mesa and Hoare semantics. Write a small monitor with lock, wait and signal.
  9. Classic problems (Week 6). Write the bounded buffer with three semaphores and say what breaks if the waits are swapped. Compare readers preference with writers preference. Give two fixes for dining philosophers.
  10. Deadlock (Week 7). List the four necessary conditions, read a resource-allocation graph, run the Banker's safety algorithm to completion and say when a request is granted, and run the detection algorithm.

Exercises

Exercise 6.1warm-up

Trace the semaphores

A bounded buffer has N = 3 slots, with empty_slots = 3 and full_slots = 0 initially (blocking implementation, values may go negative). One producer calls put four times, with no consumer running. Then a consumer calls get once. Give the values of both semaphores after each of the five operations, and say which calls block.

Show solution

Start: empty = 3, full = 0. Put 1: empty 2, full 1. Put 2: empty 1, full 2. Put 3: empty 0, full 3. Put 4: wait(empty) makes empty = -1, so the producer blocks (full stays 3). The consumer's get does wait(full): full 2, takes an item, then signal(empty): empty becomes 0, which is not above zero, so the sleeping producer is woken. It then inserts its item and does signal(full): full 3. Final values: empty 0, full 3, so the buffer is full again with three items (four were produced, one consumed). Only the fourth put blocked.

Exercise 6.2core

Swapped waits

In the bounded buffer, the consumer code is changed to wait(mutex); wait(full_slots); ...; signal(mutex); signal(empty_slots). The producer code is unchanged. Describe the interleaving that deadlocks.

Show solution

Start with an empty buffer (full_slots = 0). The consumer runs wait(mutex) and gets the mutex, then calls wait(full_slots) and blocks because the count is 0, still holding the mutex. The producer runs wait(empty_slots), which succeeds, and then wait(mutex), which blocks because the consumer holds it. The producer would signal full_slots, but only after it gets the mutex; the consumer would release the mutex only after it gets an item. Each waits for the other: deadlock. The fix is to wait for the counting semaphore before the mutex in both roles.

Exercise 6.3core

Signal or broadcast?

A memory pool monitor has alloc(n): while (free < n) wait(&more); free -= n; and release(m): free += m; signal(&more);. Thread A waits in alloc(8), then thread B waits in alloc(2) (A first in the queue); free is 0. A third thread calls release(3). What happens, and what change fixes it?

Show solution

release(3) sets free = 3 and signals one waiter, normally the oldest: A. A wakes, finds free < 8 (3 < 8), and goes back to sleep. B, which needs only 2 and could proceed, was never woken, so 3 units of memory sit free while B waits. Nothing else will wake B until another release happens. The waiters have different predicates but share one condition variable, so signal can wake the wrong one. Replace signal by pthread_cond_broadcast: both wake, A goes back to sleep and B finds 3 ≥ 2 and proceeds. (Alternatively use one condition variable per waiter.)

Exercise 6.4core

Readers-writers trace

With the readers-preference semaphore solution, events happen in this order: R1 arrives (and starts reading), R2 arrives, W1 arrives, R3 arrives, R1 leaves, R2 leaves, R3 leaves. Give the value of read_count after each event, say who blocks where, and say when W1 gets in. What changes under writers preference?

Show solution

R1 arrives: read_count 1, it is the first reader so it does wait(rw_mutex) (succeeds) and reads. R2: read_count 2, reads. W1 arrives: wait(rw_mutex) blocks, because the reader group holds it. R3 arrives: read_count 3; it is not the first reader, so it does not touch rw_mutex and reads at once, even though W1 is waiting. R1 leaves: 2. R2 leaves: 1. R3 leaves: read_count 0, so it does signal(rw_mutex) and W1 enters. W1 waited for all three readers, including R3, which arrived after it. Under writers preference, R3 would be held back as soon as W1 was waiting, so W1 would enter when R2 leaves (after R1 and R2 only), and R3 would read after W1 finishes.

Exercise 6.5challenging

Why limiting diners to N - 1 works

Five philosophers use the limited strategy with a semaphore room = 4 (each takes the left fork, then the right). Prove that deadlock cannot occur.

Show solution

Number the seats 0 to 4; philosopher i needs fork i first and fork (i + 1) mod 5 second. At most four philosophers are inside the room, so at least one seat is empty. If nobody is inside there is nothing to prove; otherwise, walking round the circle we find an occupied seat s whose next seat s + 1 is empty. Fork s + 1 is philosopher s's second fork and also the first fork of seat s + 1; nobody sits there, so fork s + 1 is free. Who could be holding philosopher s's first fork, fork s? Only philosopher s - 1, and only as his second fork, which means he holds both forks and is eating, so he will finish and release it. Hence philosopher s either already holds fork s and takes the free fork s + 1, or gets fork s soon and then takes fork s + 1. Either way philosopher s eats and leaves, so some philosopher always makes progress and a circular wait among the diners is impossible.

Exercise 6.6challenging

Write a reusable barrier

Using one mutex and one condition variable, write barrier_wait so that N threads all wait until the last one arrives, and the barrier can be used again in a loop. Explain why a plain arrived counter and a while (arrived < N) loop is not enough.

Show solution
typedef struct {
    pthread_mutex_t lock;
    pthread_cond_t  all_here;
    int needed, arrived;
    unsigned generation;            /* distinguishes one use of the barrier from the next */
} barrier_t;

void barrier_wait(barrier_t *b) {
    pthread_mutex_lock(&b->lock);
    unsigned my_gen = b->generation;
    if (++b->arrived == b->needed) {            /* last thread to arrive */
        b->arrived = 0;
        b->generation++;                        /* start a new round */
        pthread_cond_broadcast(&b->all_here);   /* release everyone waiting in this round */
    } else {
        while (my_gen == b->generation)         /* predicate: my round has not finished */
            pthread_cond_wait(&b->all_here, &b->lock);
    }
    pthread_mutex_unlock(&b->lock);
}

The last thread resets arrived to 0 so the barrier is ready for the next round. With a plain while (arrived < N) loop, a fast thread that is released and immediately calls barrier_wait again would increase the counter of the next round while slow threads from the previous round have not yet woken up and re-checked; the reset to 0 would also make a sleeping thread see arrived < N again and sleep forever. The generation number gives each round its own predicate that, once true, stays true. We ran this code with four threads and three rounds, and a checker found no violation.

Exercise 6.7core

Sizing the buffer

A producer makes one item every 2 ms; a consumer needs 5 ms per item. The buffer holds N = 10 items and both start at time 0 with an empty buffer. Using a smooth (fluid) approximation, (a) when does the buffer fill, (b) what is the long-run throughput, and (c) what fraction of time is the producer blocked? Does doubling N help the throughput?

Show solution

(a) The producer adds 1 / 2 = 0.5 items per ms and the consumer removes 1 / 5 = 0.2 items per ms, a net gain of 0.3 items per ms. The buffer reaches 10 items after 10 / 0.3 ≈ 33 ms. (b) Once full, the producer can insert only as fast as the consumer removes, so the long-run throughput is the consumer's rate: 1 item per 5 ms = 200 items per second, even though the producer could do 500. (c) The producer is busy making items for 2 ms out of every 5 ms, so it is blocked 3 / 5 = 60 percent of the time. Doubling N to 20 only delays the point at which the buffer fills, from about 33 ms to about 67 ms; the throughput is unchanged because the consumer is the bottleneck. A buffer smooths out bursts; it cannot fix a sustained rate mismatch.

Lab: read-write locks and starvation

This lab makes the starvation of the previous sections measurable. Four reader threads loop forever (for one second), each holding a read lock for 2 ms and starting 0.5 ms apart so that at least one reader is always inside. After 50 ms a single writer asks for the lock and we time how long it waits. The program takes one argument, reader or writer, choosing the lock's preference policy. Save it as rwstarve.c.

/* rwstarve.c: can continuous readers starve a writer? Compare two pthread_rwlock policies. */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

#define NREADERS 4
#define RUN_MS   1000                  /* readers keep going for 1 second */

static pthread_rwlock_t rw;
static double deadline_ms;            /* readers stop at this time */

static double now_ms(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1000.0 + t.tv_nsec / 1e6;
}

static void *reader(void *arg) {
    long id = (long)arg;
    usleep(id * 500);                          /* stagger so the read periods overlap */
    while (now_ms() < deadline_ms) {
        pthread_rwlock_rdlock(&rw);
        usleep(2000);                          /* hold the read lock for 2 ms */
        pthread_rwlock_unlock(&rw);
    }
    return NULL;
}

int main(int argc, char **argv) {
    const char *mode = argc > 1 ? argv[1] : "reader";
    pthread_rwlockattr_t attr;
    pthread_rwlockattr_init(&attr);
    pthread_rwlockattr_setkind_np(&attr, strcmp(mode, "writer") == 0
        ? PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP
        : PTHREAD_RWLOCK_PREFER_READER_NP);
    pthread_rwlock_init(&rw, &attr);

    deadline_ms = now_ms() + RUN_MS;
    pthread_t r[NREADERS];
    for (long i = 0; i < NREADERS; i++) pthread_create(&r[i], NULL, reader, (void *)i);

    usleep(50000);                             /* let the readers get going */
    double t0 = now_ms();
    pthread_rwlock_wrlock(&rw);                /* one writer asks for the lock */
    double waited = now_ms() - t0;
    pthread_rwlock_unlock(&rw);
    printf("%-6s preference: writer waited %.1f ms\n", mode, waited);

    for (int i = 0; i < NREADERS; i++) pthread_join(r[i], NULL);
    return 0;
}

Build and run:

gcc -Wall -Wextra -pthread -O2 rwstarve.c -o rwstarve
./rwstarve reader
./rwstarve writer

What to observe. On our test machine the output was:

reader preference: writer waited 951.7 ms
writer preference: writer waited 1.4 ms

With reader preference the writer waited until the readers stopped on their own, about 950 ms, which is the entire remaining run: textbook starvation, produced by four readers that are individually well behaved. With writer preference, new readers are held back as soon as the writer is waiting; it only waits for the (at most 2 ms) readers already inside. Run each several times: the first number changes by a few milliseconds and the second stays near the reader hold time, and the gap between them is the cost of the policy choice. Note that PTHREAD_RWLOCK_PREFER_WRITER_NP is a trap: in glibc it behaves like reader preference; only PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP gives writers priority, and it forbids a thread from taking the read lock twice.

Common mistakes and debugging tips

Symptom Likely cause What to do
Program hangs with every thread asleep Waits taken in the wrong order (mutex before counting semaphore), or a signal that never comes Print which call each thread is stuck in (attach gdb and use thread apply all bt); fix the order
Consumer reads a stale or garbage item if instead of while around pthread_cond_wait, or reading buf[out] outside the lock Loop on the predicate and keep every buffer access inside the critical section
Some waiters never wake, memory or tokens sit idle One condition variable shared by waiters with different predicates, signal wakes the wrong one Use broadcast, or one condition variable per predicate
Writer waits forever while readers keep arriving Readers-preference policy Choose writer-preferring or fair locking; check the lock's documentation
Philosophers freeze occasionally, only under load Circular wait with a tiny window Order the locks globally, or limit the number of concurrent acquirers
Lost wake-up: thread sleeps although the condition is already true Predicate not stored in shared data, or checked outside the mutex Update and test the predicate only while holding the mutex
Semaphore count drifts over time A post on an error path with no matching wait, or the reverse Pair every wait with a post on all paths; assert with sem_getvalue while debugging
Barrier deadlocks on its second use Counter reset too early or no generation number Use a generation counter as in Exercise 6

Key takeaways

Key takeaways

  • Bounded buffer: empty_slots starts at N, full_slots at 0, and a mutex guards the indices; wait on the counting semaphore first and the mutex second.
  • A monitor couples shared data, one lock and condition variables. Practical systems use Mesa semantics (signal and continue), so every wait sits in a while loop.
  • Semaphores and monitors can each be built from the other; semaphores remember signals, condition variables wait for arbitrary predicates.
  • Readers-writers has no neutral solution: readers preference starves writers, writers preference starves readers, and fair variants cost throughput.
  • Dining philosophers deadlock through circular wait; global resource ordering or limiting the diners to N - 1 breaks it.
  • Review for the midterm by re-deriving traces (scheduling, semaphores, Banker's) on blank paper, one table row per step.
