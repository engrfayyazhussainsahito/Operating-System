Virtual Memory

How an OS lets programs use more memory than exists by loading pages only when they are touched, how fork stays cheap with copy-on-write, and how the kernel and malloc hand out memory.

What you will be able to do

By the end of this week you will be able to:

  • Explain why virtual memory enables larger-than-RAM programs, sharing and isolation
  • Trace the steps the OS takes to service a page fault
  • Compute effective access time given a memory access time, TLB behaviour and a page-fault rate
  • Explain how copy-on-write makes fork cheap and when the copying actually happens
  • Describe memory-mapped files and the layout of a Linux process address space
  • Simulate buddy-system allocation and explain what slab allocation adds
  • Evaluate the page-size trade-off and compute TLB reach

In Week 8 we built paging: a page table maps each virtual page of a process to a physical frame, and a TLB caches recent translations. That chapter quietly assumed that every page of every running process sits in RAM. This week we drop that assumption. A page table entry may say "this page exists, but it is not in memory right now", and the hardware and OS cooperate to fetch it only when the program actually touches it. That is virtual memory, and it is the single most important trick in a modern OS.

Once pages can be loaded lazily, many other tricks fall out almost for free: a child process that shares its parent's pages until it writes, files that appear as arrays in memory, memory that costs nothing until used. Next week, in Week 10, we face the follow-up question: when RAM is full, which page do we throw out?

Why virtual memory?

Think of a library with a small reading room. The library owns a million books (the virtual address space), but the reading room holds only a few hundred (physical RAM). Readers do not carry every book to their desk; they request a book when they need it, and a clerk fetches it from the stacks. As long as readers mostly reuse the books on their desk, they never notice the stacks exist.

Virtual memory

Virtual memory is a technique that separates the logical (virtual) address space seen by a program from the physical memory actually installed. Only part of a program must be resident in RAM for it to run; the rest lives on a backing store (disk or SSD) and is brought in on demand.

Virtual memory buys us four things.

  • Larger-than-RAM programs. A program may be bigger than physical memory, or a process may reserve a huge sparse address space (for example, a database that maps a 2 TB file) and use only the parts it needs.
  • More processes in memory. Since each process needs only its active pages resident, more processes fit at once, which raises CPU utilization (we revisit this in Week 10).
  • Isolation. Each process has its own page table, so it cannot name another process's memory. Bugs and attacks stay inside the process.
  • Sharing. Two page tables can point at the same frame: shared libraries, shared memory, and the copy-on-write trick below.

Many programs never use all their code. Error handlers, rarely used features and the tail of a large array may never run. Loading them would waste both RAM and start-up time.

Demand paging

Demand paging loads a page into memory only when it is first referenced. Contrast this with loading the whole program at start-up, as simple systems once did. A system that brings pages in lazily is sometimes called a lazy pager; one that guesses which pages will be needed and loads them early does prepaging.

The valid/invalid bit

Each page-table entry gets a valid/invalid bit. We met it in Week 8 for protecting addresses outside the process; now it carries a second meaning.

  • Valid (1): the page is legal and currently in memory; the entry holds a frame number.
  • Invalid (0): either the page is outside the process's address space (a genuine error), or it is legal but not currently in memory.

The OS distinguishes these two cases by keeping extra information elsewhere (for example, a record of which address ranges the process legally owns, and where on disk each page lives). A reference to an invalid entry makes the hardware raise a page fault, a trap into the kernel.

A page fault is not (always) an error

The word "fault" is misleading. A page fault is a request: "the page I need is not mapped, please arrange it". Only if the access is illegal (outside any valid region, or a write to a read-only page) does the OS kill the process with a segmentation fault. A well-behaved program takes thousands of harmless faults every time it starts.

Handling a page fault

Here is the sequence, assuming a legal access to a page that is on disk.

  1. The program issues a load, store or instruction fetch. The MMU looks in the TLB (miss), then the page table, and finds the valid bit is 0.
  2. The hardware traps to the kernel, saving the faulting address (on x86 it is placed in the CR2 register) and the program counter of the faulting instruction.
  3. The kernel checks its own records: is this address legal for this process, and is the access type allowed? If not, send the process a SIGSEGV and stop.
  4. Otherwise find a free frame. If none is free, run page replacement to choose a victim frame (next week); if the victim is dirty, write it to disk first.
  5. Schedule a disk read for the needed page into that frame. The process is blocked and the CPU is given to another process.
  6. When the disk interrupt signals completion, update the page table: store the frame number and set the valid bit. (The TLB is updated on the next access.)
  7. Mark the process ready. When it runs again, restart the faulting instruction from the beginning; it now succeeds.

Step 7 needs care from the hardware designer. The CPU must be able to restart an instruction after a fault in the middle of it. An instruction that moves a block of bytes may fault halfway through; architectures either check that all pages are present before starting, or keep enough state to undo the partial effects.

Pure demand paging

In pure demand paging a process starts with no pages in memory at all. The very first instruction fetch faults, then the first stack access faults, and so on until the working set (the pages in active use) is resident. The program then runs fast. In practice real systems start with a few pages mapped, or prepage the first pages of the executable, but the idea is the same: never load what is not touched.

Atlas and the one-level store

Virtual memory was invented for the Atlas computer at the University of Manchester around 1962, where it was called the "one-level store": programmers saw a single large memory, and the system moved pages between a small core memory and a drum automatically. Within a decade almost every mainframe had it, and today it is in every phone.

Performance: effective access time

Page faults are rare but catastrophically slow, so the question is how rare they must be. Let

  • ma = the memory access time (for a normal access that hits),
  • p = the page-fault rate (probability that an access faults), 0 ≤ p ≤ 1,
  • S = the page-fault service time.

Then the effective access time (EAT) is

EAT = (1 − p) × ma + p × S

Worked example 1: the cost of one fault in a thousand

Take ma = 200 ns and a disk-backed fault service time of S = 8 ms = 8,000,000 ns.

Suppose one access in 1,000 faults, so p = 0.001.

EAT = 0.999 × 200 + 0.001 × 8,000,000 = 199.8 + 8,000 = 8,199.8 ns

That is about 8.2 microseconds: the program is 41 times slower (8,199.8 / 200 ≈ 41.0), even though 99.9 percent of accesses are fast. The 0.1 percent of faults contribute 8,000 of the 8,199.8 ns.

How low must p be to keep slowdown under 10 percent? We need EAT ≤ 220 ns:

220 > 200 + p × (8,000,000 − 200) so p < 20 / 7,999,800 = 2.5 × 10⁻⁶

That is fewer than one fault in about 400,000 accesses (the exact figure is 399,990). The lesson: the fault rate must be extraordinarily small, which is why locality (below) matters so much.

Worked example 2: including the TLB

Let the TLB lookup take 10 ns, a memory access 100 ns, and the TLB hit ratio 90 percent. With a single-level page table:

  • TLB hit: 10 + 100 = 110 ns
  • TLB miss: 10 + 100 (page table) + 100 (data) = 210 ns
  • Average with no faults: 0.9 × 110 + 0.1 × 210 = 99 + 21 = 120 ns

Now add page faults with p = 0.0001 and S = 5 ms = 5,000,000 ns:

EAT = 0.9999 × 120 + 0.0001 × 5,000,000 = 119.988 + 500 = 619.988 ns (about 620 ns).

Faults, at only 0.01 percent, now cost more than four times the whole translation machinery.

Where does S come from? On a hard disk it is roughly: seek 5 ms plus rotational latency 3 ms plus transfer 0.05 ms, around 8 ms (see Week 11). If the victim is dirty, we also write it out, doubling the I/O. On an SSD the service time is closer to 100 microseconds: the same p = 0.001 with ma = 200 ns then gives 0.999 × 200 + 0.001 × 100,000 = 199.8 + 100 = 299.8 ns, only 1.5 times slower.

Try your own numbers in the calculator: change the fault rate, and watch how EAT explodes as p rises past one in a hundred thousand.

Locality of reference

Why do real programs get away with such tiny fault rates? Locality of reference. Temporal locality: a recently used location is likely to be used again soon (loop variables, hot functions). Spatial locality: nearby locations are likely to be used next (sequential array walks, consecutive instructions). A process executing a loop touches a small set of code and data pages repeatedly; after the initial faults it runs fault-free until it moves to a new phase. Demand paging works because programs have locality, and thrashing (next week) happens when they cannot keep their locality resident.

Copy-on-write and fork

Recall from Week 2 that fork() creates a child that is an exact copy of the parent. Literally copying hundreds of megabytes would be slow, and it is usually wasted, because the child typically calls exec() right away and throws the copy away.

Copy-on-write (COW) avoids the copy. At fork() the kernel gives the child its own page table, but both page tables point to the same physical frames, and the kernel marks every writable page read-only in both. Reading is free. The first time either process writes a shared page, the hardware raises a protection fault; the kernel sees the page is a COW page, allocates a new frame, copies the 4 KB, points the writer's page table at the copy with write permission restored, and restarts the write.

The kernel keeps a reference count per frame. When a COW fault finds the count is already 1 (the other process has since copied or exited), it just flips the page back to writable, with no copy at all.

Why this makes fork() plus exec() cheap

With COW, fork() copies only the page tables, not the data. If the child then calls exec(), the shared pages are simply dropped from the child with no copy ever made. The shell in your Assignment 1 relies on this: every command line you type forks the shell. Historically a separate vfork() existed to avoid even copying page tables; with COW it is rarely needed, although posix_spawn and vfork remain cheaper for very large parents.

COW also explains a subtle memory-accounting effect: after a fork(), the sum of the two processes' resident sizes (RSS) is larger than the physical memory used, because shared pages are counted in both. Tools that report proportional set size (PSS) divide shared pages among the sharers to remove this double counting.

Zero-fill-on-demand

When a process asks for fresh anonymous memory (a new heap region, a stack that grows, a huge calloc), the kernel must not show it another process's old data. So the first touch of such a page must give it zeros. Linux does this lazily: all untouched pages of an anonymous mapping are mapped to one shared zero page that is read-only. A read returns zeros at no cost. The first write faults, and the kernel allocates a frame, fills it with zeros (or, equivalently, takes a pre-zeroed frame), and maps it writable. This is zero-fill-on-demand, and it is why malloc(1 GB) followed by touching only a few pages uses only a few pages of RAM.

Memory-mapped files

A memory-mapped file associates a range of a process's virtual addresses with a file. The system call mmap() sets up the mapping and returns a pointer; no data is read yet. Touching a byte of the mapping page-faults, the kernel reads the corresponding 4 KB of the file into the page cache, maps it, and the load completes. Reads and writes become ordinary memory operations instead of read() and write() system calls.

Two flavours matter.

  • MAP_SHARED: writes go to the page-cache page and eventually to the file, and are visible to other processes that map it. This is also how processes share memory (even with MAP_ANONYMOUS, among parent and children).
  • MAP_PRIVATE: copy-on-write semantics. Reads see the file; a write makes a private copy that is never written back. The kernel loads program code and initialized data of an executable this way.

Benefits: no extra copy between kernel buffer and user buffer, lazy loading, and shared pages between processes mapping the same library. Dangers: a sparse pattern of faults can be slower than one large read(), and an I/O error on the file arrives as a signal (SIGBUS) instead of a return value. Section "Lab" has a program that maps a file and edits it in place.

The Linux virtual address space

On x86-64 Linux, pointers are 64 bits wide but the hardware uses 48 bits of virtual address (four-level page table; 57 bits with five levels on newer CPUs). The address space is split: user space occupies the lower 128 TiB, the kernel the upper half. All user processes share the same kernel mapping, so a system call does not need to switch page tables for the kernel's own data.

You can inspect any process with cat /proc/self/maps. Each line shows the address range, permissions (r-xp: readable, executable, private), the file offset, and the file name or [heap], [stack]. Address-space layout randomization (ASLR) shifts the stack, heap and mmap base on every run to make exploits harder.

Allocating memory inside the kernel

When a process takes a page fault, the kernel needs a frame. But the kernel also needs memory for its own data structures: process descriptors, page tables, file buffers, network packets. Some of those need physically contiguous memory (devices doing DMA cannot follow a page table), and many are far smaller than a page.

The buddy system

The buddy system allocates physically contiguous memory in power-of-two sizes. Memory starts as one block of size 2ᵏ. To satisfy a request, round it up to the next power of two. If a block of that size is free, use it; otherwise split a larger free block in half repeatedly. The two halves of a split are buddies. When a block is freed and its buddy is also free, they merge back into the larger block, recursively. The buddy of a block of size s at address a is at address a XOR s, which makes finding it trivial.

Worked example: buddy allocation in 256 KB

Start with one free 256 KB block at address 0. Addresses below are in KB.

  1. Request A = 21 KB. Round up to 32. Split 256 into 128@0 and 128@128; split 128@0 into 64@0 and 64@64; split 64@0 into 32@0 and 32@32. Give 32@0 to A. Free list: 32@32, 64@64, 128@128. Internal fragmentation: 32 − 21 = 11 KB.
  2. Request B = 60 KB. Round up to 64. Take 64@64. Free: 32@32, 128@128.
  3. Request C = 30 KB. Round up to 32. Take 32@32. Free: 128@128.
  4. Free A. Its buddy is 32@(0 XOR 32 = 32), which is C and allocated: no merge. Free: 32@0, 128@128.
  5. Free C. Block 32@32 has buddy 32@0, which is free: merge into 64@0. Its buddy is 64@(0 XOR 64 = 64), which is B: stop. Free: 64@0, 128@128.
  6. Free B. 64@64 merges with 64@0 into 128@0, whose buddy 128@128 is free, so they merge into the original 256@0.

The system returns to one clean block, which is the whole point of buddy merging.

Strengths: fast splitting and merging, and merging fights external fragmentation. Weakness: internal fragmentation, up to nearly 50 percent when a request is just over a power of two (a 33 KB request takes 64 KB). Linux uses a buddy allocator for physical page frames (orders 0 to 10, i.e. 4 KB up to 4 MB blocks); cat /proc/buddyinfo shows the free blocks of each order.

Slab allocation

Kernel objects such as inodes and task structures are small (a few hundred bytes) and allocated and freed constantly. Asking the buddy system for a page each time would waste memory, and initializing each object from scratch wastes time. The slab allocator keeps a cache per object type. A cache consists of one or more slabs, each slab being one or more contiguous pages carved into equal-sized object slots. A slab is full, partial or empty. To allocate, take a slot from a partial slab; if none, take an empty slab; if none, ask the buddy system for pages and make a new slab. Freed objects return to their slab still initialized, so the next allocation skips construction work.

Benefits: no internal fragmentation per object, fast allocation, and recycled, already-initialized objects. Linux's current implementations (SLUB is the default) follow this design; see /proc/slabinfo.

User-level memory allocation

Programs call malloc and free, which live in the C library, not the kernel. malloc manages a pool of memory obtained from the kernel in large pieces and hands out small chunks.

The classic design is a free list: a linked list of free chunks, each chunk preceded by a small header recording its size. malloc(n) searches the list for a chunk of at least n bytes (first fit, best fit and so on, exactly the policies from Week 8), splits it if much bigger, and returns a pointer just past the header. free(p) reads the header and puts the chunk back, coalescing with adjacent free chunks. Modern allocators (glibc's ptmalloc, jemalloc, tcmalloc) use many size-segregated bins and per-thread arenas to avoid lock contention.

When the pool runs out, malloc asks the kernel for more in one of two ways.

Mechanism What it does Typical use
brk / sbrk Moves the end of the contiguous heap ("program break") up or down Small and medium allocations
mmap (anonymous) Maps a fresh region of zero-filled pages anywhere in the address space Large allocations (glibc default threshold 128 KB) and extra arenas

Large blocks come from mmap because free can then munmap them and give the memory straight back to the OS, whereas memory at the middle of a brk heap cannot be returned while chunks above it are still in use. Both paths are lazy: neither actually allocates RAM until the pages are touched.

malloc succeeding does not mean memory exists

On Linux with default overcommit settings, malloc can return a valid pointer for far more memory than RAM plus swap, because pages are only allocated on first touch. The failure arrives later, as the OOM killer (see Week 10) terminating a process. Always check malloc's result, but do not expect the check to prove the memory is really available.

Page size and TLB reach

What page size should a system choose? The trade-offs pull in opposite directions.

Smaller pages Larger pages
Less internal fragmentation (average waste = half a page per region) More internal fragmentation
Better match to locality, less unwanted data read in Fewer, larger disk transfers (seek time is amortized)
Larger page tables (more entries) Smaller page tables
More page faults, more TLB entries needed Fewer faults, better TLB coverage

A classic formula: for a process of s bytes with e bytes per page-table entry and page size p, the overhead is the page table s × e / p plus internal fragmentation p / 2 on average, so overhead = s × e / p + p / 2. Setting the derivative to zero gives the optimum p = √(2 × s × e). For s = 1 MiB and e = 8 bytes: p = √(2 × 2²⁰ × 8) = √(2²⁴) = 2¹² = 4096 bytes, which is the very 4 KB most systems use. Check the overhead at this point: 2²⁰ × 8 / 4096 = 2048 plus 4096 / 2 = 2048, total 4096 bytes.

TLB reach

TLB reach is the amount of memory covered by the entries in the TLB: reach = (number of TLB entries) × (page size). If the working set of a process fits within the TLB reach, almost all translations hit.

A TLB with 64 entries and 4 KB pages reaches only 64 × 4 KB = 256 KB. With 2 MiB pages the same 64 entries reach 128 MiB, a 512-fold increase. That is why Linux offers huge pages (2 MiB, 1 GiB on x86-64), explicitly via hugetlbfs or automatically as transparent huge pages, for databases and virtual machines. The cost is internal fragmentation and costlier zeroing and copying on faults.

Exercises

Exercise 9.1warm-up

EAT with a rare fault

Memory access time is 100 ns, the page-fault service time is 10 ms, and one access in 10,000 faults. Compute the effective access time and the slowdown relative to no faults.

Show solution

p = 1/10,000 = 0.0001, S = 10 ms = 10,000,000 ns.

EAT = 0.9999 × 100 + 0.0001 × 10,000,000 = 99.99 + 1,000 = 1,099.99 ns.

Slowdown = 1,099.99 / 100 ≈ 11.0. Even one fault in 10,000 accesses makes the program eleven times slower, and almost all of the added time (1,000 of 1,099.99 ns) is fault service.

Exercise 9.2core

Largest tolerable fault rate

With ma = 200 ns and S = 8 ms, what is the largest page-fault rate p that keeps the slowdown at 20 percent or less? Express it as "one fault per N accesses".

Show solution

We need EAT ≤ 1.2 × 200 = 240 ns.

EAT = 200 + p × (8,000,000 − 200) = 200 + p × 7,999,800 ≤ 240

p ≤ 40 / 7,999,800 ≈ 5.0 × 10⁻⁶

Taking the reciprocal, 7,999,800 / 40 = 199,995, so about one fault per 200,000 accesses. (Compare 10 percent slowdown, one per 399,990: halving the tolerated slowdown halves the allowed N, as expected.)

Exercise 9.3core

EAT with a TLB and two-level page table

TLB lookup 5 ns, memory access 80 ns, TLB hit ratio 95 percent, two-level page table (a TLB miss costs two extra memory accesses to walk the table), p = 10⁻⁵, S = 4 ms. Compute EAT.

Show solution

TLB hit: 5 + 80 = 85 ns. TLB miss: 5 + 2 × 80 + 80 = 245 ns.

Average without faults: 0.95 × 85 + 0.05 × 245 = 80.75 + 12.25 = 93 ns.

Faults: S = 4,000,000 ns, p × S = 10⁻⁵ × 4,000,000 = 40 ns.

EAT = (1 − 10⁻⁵) × 93 + 40 = 92.99907 + 40 ≈ 133.0 ns.

Even at one fault per 100,000 accesses, faults contribute 40 of 133 ns, about 30 percent of the total.

Exercise 9.4core

Buddy system trace

A buddy allocator manages 512 KB (addresses in KB, starting at 0). Requests arrive in order: A = 70 KB, B = 35 KB, C = 80 KB, D = 60 KB. Show where each is placed (take the lowest-addressed block when there is a choice), compute the total internal fragmentation, then free A, B and D in that order and give the final free list.

Show solution

Round up: A to 128, B to 64, C to 128, D to 64.

  • A: split 512 into 256@0 and 256@256; split 256@0 into 128@0 and 128@128. A = 128@0. Free: 128@128, 256@256.
  • B: split 128@128 into 64@128 and 64@192. B = 64@128. Free: 64@192, 256@256.
  • C: no free 128; split 256@256 into 128@256 and 128@384. C = 128@256. Free: 64@192, 128@384.
  • D: take 64@192. Free: 128@384.

Internal fragmentation: A 128 − 70 = 58, B 64 − 35 = 29, C 128 − 80 = 48, D 64 − 60 = 4. Total = 58 + 29 + 48 + 4 = 139 KB.

Free A: buddy of 128@0 is 128@128, which is split and in use: no merge. Free B: buddy 64@192 is D: no merge. Free D: merges with 64@128 into 128@128; its buddy 128@0 (A, now free) merges into 256@0; its buddy 256@256 holds C: stop.

Final free list: 256 KB at 0 and 128 KB at 384. Allocated: C (128@256).

Exercise 9.5core

Copy-on-write accounting

A process has 200 MB resident and calls fork(). The child then writes one byte in each of 10 MB worth of distinct pages (4 KB pages), and the parent writes nothing. (a) How much additional physical memory does the system use right after the fork? (b) After the child's writes? (c) How many COW page faults does the child take?

Show solution

(a) Essentially none for data: only the child's page tables and kernel structures are allocated, since all 200 MB of frames are shared.

(b) Each written page is copied, so 10 MB more, plus the page-table overhead. The system now holds 210 MB of data frames.

(c) 10 MB / 4 KB = 10 × 1024 / 4 = 2,560 pages, each taking one COW fault (the first write to each page; later writes to the same page do not fault again). If the child had called exec instead of writing, there would have been zero copies.

Exercise 9.6core

Optimal page size

Using overhead = s × e / p + p / 2, find the optimal page size for a process with s = 4 MiB and page-table entries of e = 8 bytes. Compute the overhead at the optimum and at 4 KB for comparison.

Show solution

p = √(2 × s × e) = √(2 × 2²² × 2³) = √(2²⁶) = 2¹³ = 8192 bytes (8 KB).

Overhead at 8 KB: 2²² × 8 / 8192 = 2²⁵ / 2¹³ = 2¹² = 4096 plus 8192 / 2 = 4096, total 8192 bytes.

At 4 KB: 2²⁵ / 2¹² = 8192 plus 4096 / 2 = 2048, total 10,240 bytes. So 8 KB is better by this simple model (20 percent less overhead), but real systems also weigh TLB reach and disk transfer sizes.

Exercise 9.7warm-up

TLB reach and huge pages

A data TLB has 64 entries. (a) What is its reach with 4 KB pages and with 2 MiB pages? (b) A program randomly accesses an 8 MiB array. Roughly what fraction of that array can the TLB cover with each page size?

Show solution

(a) 64 × 4 KB = 256 KB; 64 × 2 MiB = 128 MiB.

(b) With 4 KB pages: 256 KB / 8 MiB = 1/32 ≈ 3.1 percent, so random accesses mostly miss the TLB (about 97 percent of the time, ignoring the other levels). With 2 MiB pages the array needs only 4 entries and is entirely covered (100 percent), so TLB misses almost vanish after warm-up.

Exercise 9.8challenging

Prepaging and cluster faults

A program reads 100 consecutive pages of a freshly mapped file, each a major fault. (a) How many faults occur under pure demand paging? (b) The kernel reads ahead in clusters of 8 pages on each fault. How many major faults now occur, and what is the I/O time if one cluster read costs 8.3 ms (a single seek plus 8 transfers) versus 8.05 ms per single-page read? (c) Explain when read-ahead hurts.

Show solution

(a) 100 faults; I/O time 100 × 8.05 = 805 ms.

(b) Each fault brings in 8 pages, so ⌈100 / 8⌉ = 13 faults (12 full clusters cover 96 pages, a 13th covers the remaining 4). I/O time 13 × 8.3 = 107.9 ms, about 7.5 times faster (805 / 107.9 ≈ 7.46). The seek and rotation are paid 13 times instead of 100.

(c) Read-ahead wastes I/O and memory when access is random or sparse: the 7 extra pages are never used, and they displace useful pages. Linux therefore adapts: it grows the read-ahead window only while it detects sequential access, and madvise(MADV_RANDOM) turns it off.

Lab

You will observe three behaviours with real programs: a memory-mapped file, copy-on-write after fork, and the cost of a page fault. Compile each with gcc -Wall -Wextra -o name name.c.

Part 1: mmap a file and edit it in place

#define _GNU_SOURCE
#include <ctype.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/stat.h>
#include <unistd.h>

static void report(const char *when) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("%-14s minor faults = %ld, major faults = %ld\n",
           when, ru.ru_minflt, ru.ru_majflt);
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s file\n", argv[0]);
        return 1;
    }
    int fd = open(argv[1], O_RDWR);
    if (fd < 0) { perror("open"); return 1; }

    struct stat st;
    if (fstat(fd, &st) < 0) { perror("fstat"); return 1; }
    if (st.st_size == 0) { fprintf(stderr, "empty file\n"); return 1; }

    report("before mmap");
    char *p = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    report("after mmap");

    long lines = 0;
    for (off_t i = 0; i < st.st_size; i++)
        if (p[i] == '\n') lines++;
    report("after scan");
    printf("file has %ld bytes and %ld lines\n", (long)st.st_size, lines);

    /* Upper-case the first line directly in the page cache. */
    for (off_t i = 0; i < st.st_size && p[i] != '\n'; i++)
        p[i] = toupper((unsigned char)p[i]);
    if (msync(p, st.st_size, MS_SYNC) < 0) perror("msync");
    report("after write");

    munmap(p, st.st_size);
    close(fd);
    return 0;
}

Create a test file and run it: printf 'hello world\nsecond line\nthird\n' > t.txt; ./mmap_file t.txt; cat t.txt. The first line of the file becomes HELLO WORLD although the program never called write(). Observe that mmap itself adds only a handful of faults, the scan adds about one, and the write adds one or two more. The exact baseline counts (around 80) come from program start-up and vary between systems. Now try a large file (dd if=/dev/zero of=big bs=1M count=200) and watch the minor-fault count grow by roughly one per 4 KB page scanned (51,200 pages).

Part 2: copy-on-write after fork

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

#define MB (1024UL * 1024UL)

/* Return the Private_Dirty figure (in kB) from /proc/self/smaps_rollup. */
static long private_dirty_kb(void) {
    FILE *f = fopen("/proc/self/smaps_rollup", "r");
    if (!f) return -1;
    char line[256];
    long kb = -1;
    while (fgets(line, sizeof line, f))
        if (sscanf(line, "Private_Dirty: %ld kB", &kb) == 1) break;
    fclose(f);
    return kb;
}

static long minflt(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(int argc, char **argv) {
    size_t total_mb = argc > 1 ? strtoul(argv[1], NULL, 10) : 64;
    size_t write_mb = argc > 2 ? strtoul(argv[2], NULL, 10) : 16;
    long page = sysconf(_SC_PAGESIZE);
    size_t bytes = total_mb * MB;

    char *buf = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (buf == MAP_FAILED) { perror("mmap"); return 1; }
    memset(buf, 1, bytes);  /* parent touches every page */
    printf("parent: Private_Dirty = %ld kB\n", private_dirty_kb());

    fflush(stdout);  /* avoid duplicating buffered output in the child */
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        long f0 = minflt();
        printf("child : right after fork, Private_Dirty = %ld kB\n",
               private_dirty_kb());
        for (size_t off = 0; off < write_mb * MB; off += page)
            buf[off] = 2;  /* first write to each page triggers a COW fault */
        long f1 = minflt();
        printf("child : wrote %zu MB (%zu pages): %ld new minor faults\n",
               write_mb, write_mb * MB / page, f1 - f0);
        printf("child : after writing, Private_Dirty = %ld kB\n",
               private_dirty_kb());
        fflush(stdout);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("parent: buf[0] is still %d (child's write was private)\n", buf[0]);
    return 0;
}

Run ./cow 64 16. Expected output (numbers approximate):

parent: Private_Dirty = 65664 kB
child : right after fork, Private_Dirty = 36 kB
child : wrote 16 MB (4096 pages): 4114 new minor faults
child : after writing, Private_Dirty = 16424 kB
parent: buf[0] is still 1 (child's write was private)

Right after the fork the child owns almost no private pages (they are all shared), and after writing 16 MB it owns about 16 MB privately, with about one fault per page (4,096 plus a few extra from library and stdio). Also try /usr/bin/time -v ./cow 64 16 and compare "Minor (reclaiming a frame) page faults" and "Maximum resident set size" with a run using ./cow 64 0. Note that RSS counts shared pages, so it hardly changes between runs; the private-dirty counter is what shows the copying.

Part 3: what does a page fault cost?

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <time.h>
#include <unistd.h>

static double now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e9 + ts.tv_nsec;
}

static long minflt(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(int argc, char **argv) {
    size_t pages = argc > 1 ? strtoul(argv[1], NULL, 10) : 100000;
    long psz = sysconf(_SC_PAGESIZE);
    volatile char *p = mmap(NULL, pages * psz, PROT_READ | PROT_WRITE,
                            MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    long f0 = minflt();
    double t0 = now_ns();
    for (size_t i = 0; i < pages; i++) p[i * psz] = 1;   /* first touch */
    double t1 = now_ns();
    long f1 = minflt();
    for (size_t i = 0; i < pages; i++) p[i * psz] = 2;   /* already mapped */
    double t2 = now_ns();

    printf("pages touched        : %zu (%ld bytes each)\n", pages, psz);
    printf("minor faults         : %ld\n", f1 - f0);
    printf("first touch          : %.0f ns per page\n", (t1 - t0) / pages);
    printf("second touch         : %.0f ns per page\n", (t2 - t1) / pages);
    return 0;
}

A typical result on a laptop or virtual machine is a first touch of one to several microseconds per page (this includes the kernel finding a frame and zeroing 4 KB) against a few tens of nanoseconds for the second touch: a ratio of 50 to 150. That is a minor fault, with no disk I/O. A major fault would cost thousands of times more. To provoke one, create a file bigger than your RAM cache, run sync; echo 3 | sudo tee /proc/sys/vm/drop_caches (this only discards clean cache and is safe), then scan it with Part 1's program and watch major faults rise.

Use your measured per-fault time as S in the EAT formula. What fault rate keeps the slowdown under 10 percent for your machine?

Common mistakes and debugging tips

Symptom Likely cause What to do
EAT answer is off by a factor of 1,000 Mixed up milliseconds and nanoseconds Convert everything to ns first (1 ms = 1,000,000 ns)
EAT too high in a hand calculation Used p × S plus the full ma instead of (1 − p) × ma Write the formula with (1 − p) explicitly
Child's RSS equals the parent's after fork, so "COW does not work" RSS counts shared pages in both processes Compare PSS or Private_Dirty in /proc/PID/smaps_rollup
mmap returns MAP_FAILED for a zero-length file Length 0 is invalid Check st_size first, or ftruncate the file to the desired size
Bus error (SIGBUS) while reading a mapped file File was truncated by another process after the mapping Avoid shrinking mapped files; handle SIGBUS or use read()
Buddy exercise answer ends with wrong buddy Computed buddy as address + size The buddy is address XOR size (matters when the block is the upper half)
malloc(1 GB) succeeds but the process is later killed Overcommit: memory is reserved lazily Touch the memory early (or MAP_POPULATE) if you need it guaranteed
Duplicate output lines after fork() with stdout piped Unflushed stdio buffer copied into the child fflush(stdout) before fork(), and before _exit() in the child

Key takeaways

Key takeaways

  • Virtual memory lets a process run with only some of its pages resident; the valid bit marks which, and a page fault is the trap that fetches a missing page.
  • A fault is serviced in seven steps ending with restarting the faulting instruction; the I/O step makes it a million times slower than a normal access.
  • EAT = (1 − p) × ma + p × S: with S of milliseconds, p must be below about one in a few hundred thousand to avoid a visible slowdown, which locality makes possible.
  • Copy-on-write shares frames after fork() and copies a page only on its first write; zero-fill-on-demand and mmap rely on the same lazy machinery.
  • The kernel allocates frames with the buddy system (power-of-two blocks merged with address XOR size) and small objects with slabs; user malloc uses free lists on top of brk and mmap.
  • Page size trades fragmentation and fault cost against page-table size and TLB reach; reach is entries times page size.
