Deadlocks

When threads wait forever for each other's resources. The four necessary conditions, resource-allocation graphs, prevention by lock ordering, avoidance with the Banker's algorithm (fully traced), detection with wait-for graphs, and recovery.

What you will be able to do

By the end of this week you will be able to:

  • State the four necessary conditions for deadlock and name the condition that each prevention technique breaks
  • Draw a resource-allocation graph and decide whether a cycle means deadlock for single-instance and multi-instance resources
  • Decide whether a system state is safe, and explain why unsafe does not mean deadlocked
  • Carry out the Banker's safety algorithm and resource-request algorithm by hand on a Need matrix
  • Run the detection algorithm on an Allocation and Request matrix and identify the deadlocked processes
  • Remove a lock-ordering deadlock in C code by imposing a global lock order

Week 5 gave you locks, and Week 6 ended with the dining philosophers, five diners who each pick up the left fork and then wait forever for the right one. That program did not crash and did not compute a wrong answer. It simply stopped, with every thread alive and none able to move. This chapter studies that failure, called deadlock, which is the price of holding one resource while asking for another.

We first define deadlock and extract the four conditions that must all hold for it to occur. Then we look at three families of defence in order of increasing cost: prevention (make one condition impossible), avoidance (refuse requests that could lead to deadlock, using the Banker's algorithm) and detection and recovery (allow deadlock, find it, break it). Assignment 2 (threads and synchronization) is due this week, and the lock-ordering rule here is the tool for keeping your solution deadlock-free. Week 8 then moves from CPU and synchronization to main memory.

What a deadlock is

The four-way stop

Gridlock

Four cars arrive at the four corners of an intersection with no traffic light, and each driver politely waits for the car on the right to go first. Nobody moves. Every car holds a piece of road (its own corner) and wants the piece held by the next car. No driver will back up, no police officer will tow a car away, and the pattern is circular. That is deadlock: a set of parties each holding something and waiting for something another member of the set holds.

Deadlock

A set of threads is deadlocked if every thread in the set is waiting for an event (typically the release of a resource) that can only be caused by another thread in the set. Because every member is waiting, none can ever cause the event, so the wait is permanent.

A resource here means anything a thread must hold exclusively for a while: a mutex, a semaphore, a database row lock, a file lock, a printer, a slot in a fixed-size table. We concentrate on reusable resources, which are taken, used and given back unchanged.

The smallest possible deadlock uses two locks. Thread T1 runs lock(A); lock(B); and thread T2 runs lock(B); lock(A);. If T1 gets A and T2 gets B before either asks for its second lock, each now waits for the lock the other holds. Whether this happens depends on timing, so the program may run correctly a thousand times and then hang in production. Like the races of Week 5, it is a bug that shows itself only under one interleaving.

The four necessary conditions

In 1971 Coffman, Elphick and Shoshani showed that deadlock can occur only if four conditions hold at the same time. They are necessary, not sufficient: all four can be present without a deadlock yet, but if any one is absent a deadlock is impossible.

Condition Meaning Example
Mutual exclusion At least one resource can be held by only one thread at a time A mutex, a printer
Hold and wait A thread holding at least one resource is waiting to acquire more T1 holds A and requests B
No preemption A resource can only be released voluntarily by the thread holding it The OS cannot take a mutex away
Circular wait There is a cycle T0 → T1 → ... → Tk → T0 where each thread waits for a resource held by the next T1 waits on T2 and T2 waits on T1

Coffman, Dijkstra and the Banker

The four conditions come from E. G. Coffman Jr., M. J. Elphick and A. Shoshani, "System Deadlocks" (ACM Computing Surveys, 1971), which is still the reference survey. The avoidance idea is older: Edsger Dijkstra invented the Banker's algorithm in 1965 (for a single resource type), and A. N. Habermann extended it to several resource types in 1969. Like a bank that never lends out so much that it cannot meet every customer's declared credit line, the OS never grants a request that could leave it unable to satisfy everyone's declared maximum.

The first three conditions are properties of how resources work; the fourth is a situation that arises at runtime. That is why prevention mostly attacks the fourth.

Resource-allocation graphs

A resource-allocation graph makes the circular-wait condition visible. It has two kinds of vertices, threads drawn as circles and resource types drawn as rectangles, with one dot inside the rectangle for each instance of that resource. A request edge Ti → Rj means thread Ti is waiting for an instance of Rj. An assignment edge Rj → Ti means an instance of Rj is held by Ti.

The rule for reading these graphs is short and worth memorizing.

  • If the graph has no cycle, no deadlock exists.
  • If every resource type on a cycle has exactly one instance, the cycle means deadlock.
  • If some resource types have several instances, a cycle is necessary but not sufficient: the system may or may not be deadlocked.

Handling deadlocks: four strategies

An operating system has four broad choices, and real systems mix them: ignore the problem, prevent it by making a condition impossible, avoid it by refusing risky requests, or detect and recover after it happens. Ignoring is a respectable engineering decision: if deadlock happens once a year, an expensive scheme that slows every request is a bad trade (Tanenbaum calls it the ostrich algorithm). The rest of this chapter covers the other three, in order of cost.

Deadlock prevention

Prevention makes one of the four conditions fail. Take them in turn and ask what the price is.

Break mutual exclusion. Make resources sharable, as with read-only files or a read-write lock. A genuinely non-sharable resource (a printer mid-page, a list being updated) cannot be, so the reach is limited.

Break hold and wait. Either a thread must request all its resources at once before starting (so it never holds one while waiting for another), or it must release everything it holds before asking for more. The price is idle resources and possible starvation, since a thread needing a popular combination may never see all of it free at once.

Break no preemption. If a thread holding resources requests one that is not available, take away what it holds, and restart it when everything is available. This suits resources whose state can be saved and restored (CPU registers, memory pages) but not mutexes or printers. In lock-based code the equivalent is pthread_mutex_trylock with back-off: if the second lock is busy, release the first and retry.

Break circular wait. Give every resource type a unique number and require every thread to acquire resources in increasing order of number. A cycle would need some thread to wait for a lower-numbered resource while holding a higher-numbered one, which the rule forbids. This is the only technique with a tiny cost, which is why it is the practical workhorse.

Lock ordering in practice

Pick a global order and write it down in the code: "lock the account with the lower id first", "the directory lock comes before the file lock", "the table lock comes before any row lock". When objects of the same type must be locked together, order them by address or by a stable id. The Linux kernel checks its lock order at run time with a tool called lockdep, and ThreadSanitizer reports lock-order inversions even on runs that did not deadlock.

The program below is the standard recipe. It locks the account with the lower address first, so transfer(&a, &b) and transfer(&b, &a) agree on the order.

include

struct account { pthread_mutex_t lock; long balance; };

static struct account a = { PTHREAD_MUTEX_INITIALIZER, 1000 }; static struct account b = { PTHREAD_MUTEX_INITIALIZER, 1000 };

/ Always lock the account with the lower address first, whatever the argument order. / static void transfer(struct account from, struct account to, long amount) { struct account first = (uintptr_t)from < (uintptr_t)to ? from : to; struct account second = first == from ? to : from; pthread_mutex_lock(&first->lock); pthread_mutex_lock(&second->lock); from->balance -= amount; to->balance += amount; pthread_mutex_unlock(&second->lock); pthread_mutex_unlock(&first->lock); }

static void t1(void arg) { (void)arg; for (int i = 0; i < 100000; i++) transfer(&a, &b, 1); return NULL; } static void t2(void arg) { (void)arg; for (int i = 0; i < 100000; i++) transfer(&b, &a, 1); return NULL; }

int main(void) { pthread_t x, y; pthread_create(&x, NULL, t1, NULL); pthread_create(&y, NULL, t2, NULL); pthread_join(x, NULL); pthread_join(y, NULL); printf("a = %ld, b = %ld, total = %ld\n", a.balance, b.balance, a.balance + b.balance); return 0; }

Two threads transferring in opposite directions finish at once with the money conserved (a = 1000, b = 1000, total = 2000). Lock from then to instead, and the program can hang, as the lab shows.

Ordering must cover every path

One code path that breaks the order closes the cycle: a callback invoked while a lock is held, or a function that locks one more object "just for a moment". Document the order as part of each function's contract.

Deadlock avoidance and the Banker's algorithm

Prevention restricts how threads may ask. Avoidance lets them ask freely but has the OS examine each request and say no when granting it could lead to deadlock. For this to work, each thread must declare in advance the maximum number of instances of each resource type it will ever need.

Safe states

Safe state

A state is safe if there exists an order of the processes, a safe sequence P(1), P(2), ..., P(n), such that each P(i) can obtain all it may still need from what is currently free plus what P(1), ..., P(i-1) will release when they finish. If no such order exists the state is unsafe.

Safe means deadlock is avoidable; unsafe means deadlock is possible, not certain. The OS cannot rely on luck, so the avoidance rule is: grant a request only if the resulting state is safe.

The data structures

With n processes and m resource types, the Banker's algorithm keeps four structures.

  • Available[j]: the number of free instances of resource type j.
  • Max[i][j]: the maximum demand of process i for resource j (declared in advance).
  • Allocation[i][j]: the instances of j currently held by process i.
  • Need[i][j] = Max[i][j] - Allocation[i][j]: what process i may still request.

For vectors, X ≤ Y means X[j] ≤ Y[j] for every j.

The safety algorithm

The safety algorithm asks: starting from the current state, can all processes finish one after another? It tries to build a safe sequence.

1. Work = Available;  Finish[i] = false for every i.
2. Find an i such that  Finish[i] = false  and  Need[i] ≤ Work.
   If there is no such i, go to step 4.
3. Work = Work + Allocation[i];  Finish[i] = true;  go to step 2.
4. If Finish[i] = true for every i, the state is safe; otherwise it is unsafe.

Each pass of step 2 scans n processes and compares m numbers, and there are at most n passes, so the cost is O(m × n²).

Work is the pool of resources that would be free if the processes chosen so far had all finished and handed their allocations back.

The resource-request algorithm

When process Pi asks for a vector Request, the system runs these steps.

1. If Request > Need[i]:       error, the process exceeded its declared maximum.
2. If Request > Available:     Pi must wait, the resources are not free.
3. Pretend to allocate:
       Available  = Available  - Request
       Allocation[i] = Allocation[i] + Request
       Need[i]    = Need[i]    - Request
   Run the safety algorithm on this new state.
   If safe:    the request is granted.
   If unsafe:  restore the old state and make Pi wait.

Note that it is the safety test of the hypothetical state, not just availability, that decides.

A full worked example

Five processes P0 to P4 and three resource types A, B and C. There are 10 instances of A, 5 of B and 7 of C in total. The current state is:

Process Allocation (A B C) Max (A B C) Need = Max - Allocation
P0 0 1 0 7 5 3 7 4 3
P1 2 0 0 3 2 2 1 2 2
P2 3 0 2 9 0 2 6 0 0
P3 2 1 1 2 2 2 0 1 1
P4 0 0 2 4 3 3 4 3 1

Allocated in total: A = 0+2+3+2+0 = 7, B = 1+0+0+1+0 = 2, C = 0+0+2+1+2 = 5. Subtracting from the totals gives Available = (10-7, 5-2, 7-5) = (3, 3, 2). The totals and availability agree, a check that always pays off.

Step 1: is the initial state safe?

Start with Work = (3, 3, 2) and compare each Need row with it.

Round Work before Candidate Need ≤ Work? Finish, Work after (Work + Allocation)
1 3 3 2 P1 (1,2,2) ≤ (3,3,2) yes 3 3 2 + 2 0 0 = 5 3 2
2 5 3 2 P3 (0,1,1) ≤ (5,3,2) yes 5 3 2 + 2 1 1 = 7 4 3
3 7 4 3 P4 (4,3,1) ≤ (7,4,3) yes 7 4 3 + 0 0 2 = 7 4 5
4 7 4 5 P0 (7,4,3) ≤ (7,4,5) yes 7 4 5 + 0 1 0 = 7 5 5
5 7 5 5 P2 (6,0,0) ≤ (7,5,5) yes 7 5 5 + 3 0 2 = 10 5 7

Everyone finishes, so the state is safe with the safe sequence P1, P3, P4, P0, P2. In round 1 only P1 and P3 could have started (P0 needs 7 of A, P2 needs 6, P4 needs 4, and only 3 are free). Work ends at (10, 5, 7), the system totals, which is a good arithmetic check: after everyone finishes, every resource is back in the pool.

Safe sequences are not unique: at round 3, P0 would also have fit, since (7,4,3) ≤ (7,4,3).

Step 2: P1 requests (1, 0, 2)

P1 asks for one more A and two more C.

  1. Request ≤ Need[1]: (1,0,2) ≤ (1,2,2). Yes.
  2. Request ≤ Available: (1,0,2) ≤ (3,3,2). Yes.
  3. Pretend to allocate: Available = (3,3,2) - (1,0,2) = (2,3,0), Allocation[1] = (2,0,0) + (1,0,2) = (3,0,2), Need[1] = (1,2,2) - (1,0,2) = (0,2,0).

Now run the safety algorithm on the new state with Work = (2, 3, 0). P1 needs (0,2,0) ≤ (2,3,0), so it finishes: Work = (2,3,0) + (3,0,2) = (5,3,2). Then P3: (7,4,3); P4: (7,4,5); P0: (7,5,5); P2: (10,5,7). The new state is safe with the same safe sequence P1, P3, P4, P0, P2, so the request is granted. The system now has Available = (2,3,0).

Step 3: two more requests from the new state

P4 requests (3, 3, 0). The Need of P4 is (4,3,1), so step 1 passes. But Available = (2,3,0) and 3 > 2 in the A column, so step 2 fails: P4 must wait. No safety test is needed, because the resources simply are not free.

P0 requests (0, 2, 0). Step 1: (0,2,0) ≤ (7,4,3) yes. Step 2: (0,2,0) ≤ (2,3,0) yes. Pretend: Available = (2,1,0), Allocation[0] = (0,3,0), Need[0] = (7,2,3). Safety with Work = (2,1,0):

  • P0 needs (7,2,3), more than (2,1,0). No.
  • P1 needs (0,2,0), but only 1 of B is free. No.
  • P2 needs (6,0,0). No. P3 needs (0,1,1), but no C is free. No. P4 needs (4,3,1). No.

No process can proceed, so the state is unsafe and the request is denied, although the resources are free. P0 must wait.

Unsafe does not mean deadlocked

Granting P0's request would not deadlock the system immediately. P0 might never ask for its full maximum, and P1 might release early. The Banker's algorithm is conservative: it assumes every process will claim its entire declared maximum, and refuses any move after which it could not cope with that. The price of the guarantee is that some safe-in-practice requests are delayed.

The program scans from P0 each time, so it finds P1, P3, P0, P2, P4 rather than the hand-traced P1, P3, P4, P0, P2. The check_order line confirms that the hand-chosen order is also valid; any one safe sequence proves the state is safe. The three request outcomes match the hand trace.

One safety check costs O(m × n²), and every request needs one. The scheme also needs every process to declare its maximum in advance and a fixed process count, which most programs cannot honour. That is why general-purpose operating systems do not run it on mutexes.

Deadlock detection and recovery

If we neither prevent nor avoid deadlock, we must be ready to find it.

Wait-for graphs

When every resource has a single instance, the resource-allocation graph can be collapsed into a simpler wait-for graph by deleting the resource nodes: an edge Ti → Tj means "Ti is waiting for a resource held by Tj". A deadlock exists exactly when this graph has a cycle. The OS (or a database) periodically runs a cycle-finding search, which takes O(n²) time for n threads with an adjacency matrix.

Detection on a wait-for graph is a depth-first search that keeps the current path and reports a cycle when it meets a vertex already on that path. Suppose T0 waits for T1, T1 for T2, T2 for T3 and T3 for T1. The search from T0 finds the cycle T1 → T2 → T3 → T1. T0 is also stuck, but it is not on the cycle: it stays blocked until the cycle is broken, though it does not cause the deadlock.

The detection algorithm for several instances

With several instances of each type we need a matrix algorithm that looks like the safety algorithm, with one difference: it uses the current Request matrix instead of the worst-case Need. It asks "can the processes finish if they ask only for what they are asking for now?", an optimistic assumption.

1. Work = Available.  Finish[i] = false if Allocation[i] is non-zero, else true.
2. Find an i with Finish[i] = false and Request[i] ≤ Work.  None: go to step 4.
3. Work = Work + Allocation[i];  Finish[i] = true;  go to step 2.
4. Any process with Finish[i] = false is deadlocked.

Like the safety algorithm, it costs O(m × n²).

Here is an example with the same five processes and three types, now with Available = (0,0,0).

Process Allocation (A B C) Request (A B C)
P0 0 1 0 0 0 0
P1 2 0 0 2 0 2
P2 3 0 3 0 0 0
P3 2 1 1 1 0 0
P4 0 0 2 0 0 2

Start with Work = (0,0,0). P0 requests nothing, so it can finish and returns (0,1,0): Work = (0,1,0). P2 requests nothing: Work = (3,1,3). P1 requests (2,0,2) ≤ (3,1,3): Work = (5,1,3). P3 requests (1,0,0): Work = (7,2,4). P4 requests (0,0,2): Work = (7,2,6). Everyone can finish, in the order P0, P2, P1, P3, P4, so there is no deadlock.

Now suppose P2 makes one more request, for one instance of C, so its Request row becomes (0,0,1). Only P0 can finish (Work becomes (0,1,0)). Every other request needs A or C, and neither is free, so P1, P2, P3 and P4 are deadlocked. They hold (2,0,0), (3,0,3), (2,1,1) and (0,0,2) between them, and none of it can be released.

When to run detection

Run the detector often and you waste CPU; run it rarely and deadlocked threads pile up. Common policies are to run it whenever a request cannot be granted at once, or periodically, or when CPU utilization drops below a threshold such as 40%.

Recovery

Once a deadlock is found there are two ways to break it.

  • Terminate processes. Abort all deadlocked processes (certain, but their work is lost) or one at a time until the cycle disappears (less lost work, but a detection run after each abort). Choose victims by priority, work done and resources held.
  • Preempt resources. Take a resource from a victim and give it to another process, rolling back the victim to a safe point. Guard against starvation by counting past rollbacks in the victim's cost.

Databases do exactly this: a transaction manager finds cycles in its wait-for graph, aborts the cheapest transaction in each, rolls it back from its log and tells the application to retry.

Related problems: livelock and starvation

Deadlock is not the only way to make no progress.

Problem Threads are... Example
Deadlock Blocked, using no CPU T1 holds A and wants B; T2 holds B and wants A
Livelock Running but making no progress Two people in a corridor who keep stepping aside the same way; trylock back-off with identical timing
Starvation One waits unboundedly while others progress Reader-preferring lock with a steady stream of readers

Livelock is the typical failure of naive recovery: if both threads release and retry at the same moment, they can repeat forever. Different or randomized back-off delays break the symmetry, as the lab shows.

Exercises

Exercise 7.1warm-up

Which condition does each fix break?

For each fix, name the Coffman condition it removes. (a) Every thread must acquire all its locks in one atomic step before it starts. (b) A global numbering of locks that threads must follow. (c) The OS may forcibly take memory pages from a process. (d) A read-only file is opened without any lock.

Show solution

(a) Hold and wait: no thread ever holds a lock while waiting for another. (b) Circular wait: a cycle would require a thread to request a lower-numbered lock while holding a higher-numbered one, which the rule forbids. (c) No preemption: the resource can be taken away. (d) Mutual exclusion: the resource is made sharable, so no one waits for it.

Exercise 7.2core

A cycle that is not a deadlock

Resource R1 has two instances and R2 has one. P1 holds R2 and requests R1. P2 holds one instance of R1 and requests R2. P3 holds the other instance of R1 and requests nothing. Draw the edges, find the cycle, and decide whether the system is deadlocked.

Show solution

Edges: R2 → P1 (assigned), P1 → R1 (request), R1 → P2 (assigned), R1 → P3 (assigned), P2 → R2 (request). The cycle is P1 → R1 → P2 → R2 → P1. R1 has two instances, so a cycle is not sufficient. P3 is not waiting: it finishes and releases its instance of R1. P1's request is then satisfied, P1 finishes and releases R2, and P2 gets R2. No deadlock.

Exercise 7.3core

Safe or unsafe with one resource type

A system has 10 identical tape drives. Processes A, B and C hold 3, 2 and 2 drives and have declared maximums of 9, 4 and 7. Three drives are free. (a) Is the state safe? (b) A now requests one more drive. Should the Banker's algorithm grant it?

Show solution

Need = Max - held: A 6, B 2, C 5. Check totals: 3+2+2+3 = 10. (a) Work = 3. B needs 2 ≤ 3, so B finishes and Work = 3 + 2 = 5. C needs 5 ≤ 5, so C finishes and Work = 5 + 2 = 7. A needs 6 ≤ 7, so A finishes, Work = 10. Safe sequence B, C, A. (b) Pretend: A holds 4 (Need 5), Available = 2. B needs 2 ≤ 2, finishes, Work = 2 + 2 = 4. C needs 5 > 4 and A needs 5 > 4, so neither can finish. The new state is unsafe, so the request is denied and A waits, even though a drive is free.

Exercise 7.4core

Run the detection algorithm

Two resource types, Available = (0,0). Allocation / Request: P0 (1,0) / (0,1); P1 (0,1) / (1,0); P2 (1,1) / (0,1); P3 (0,0) / (0,0). Which processes, if any, are deadlocked?

Show solution

Work = (0,0). P3 holds nothing and requests nothing, so it finishes, but it returns (0,0) and Work stays (0,0). P0 requests (0,1) > Work. P1 requests (1,0) > Work. P2 requests (0,1) > Work. No further progress is possible, so P0, P1 and P2 are deadlocked. P3 is not deadlocked.

Exercise 7.5core

Find and fix the lock-order bug

void swap_owner(file *x, file *y) { lock(&x->m); lock(&y->m); ...; unlock(&y->m); unlock(&x->m); } is called by T1 as swap_owner(f, g) and by T2 as swap_owner(g, f). Describe the deadlock and give two fixes.

Show solution

T1 locks f->m and T2 locks g->m. Then T1 blocks on g->m (held by T2) and T2 blocks on f->m (held by T1): circular wait. Fix 1 (break circular wait): inside the function, compare the two pointers or ids and always lock the lower first, as transfer does in this chapter. Fix 2 (break no preemption): lock the first mutex, use pthread_mutex_trylock on the second, and if it fails release the first, back off for a different delay in each thread, and retry. Fix 1 is simpler and cannot livelock. Also handle x == y, which would lock the same mutex twice.

Exercise 7.6challenging

Minimum resources for guaranteed freedom

n processes share identical units of one resource. Each process needs at most m units (m ≥ 1) and requests one unit at a time. Show that the system cannot deadlock if the total number of units R satisfies R ≥ n(m - 1) + 1. How many units are enough for 4 processes with m = 3?

Show solution

The worst case for deadlock is that every process holds m - 1 units, one short of its maximum, so n(m - 1) units are in use and nobody can finish. If R ≥ n(m - 1) + 1 there is at least one free unit even in that worst case. Whoever receives it holds its maximum m and can finish, and releases its units, so the others can proceed. By repeating the argument all processes finish; no deadlock is possible. For n = 4 and m = 3: R ≥ 4 × 2 + 1 = 9 units. With 8 units, all four can hold 2 each with none free and none able to finish.

Exercise 7.7challenging

Apply the request algorithm at the initial state

Use the five-process example in its initial state, Available (3,3,2). (a) P4 requests (3,3,0). (b) Independently, P0 requests (0,2,0). Is each granted? Give the safety reasoning.

Show solution

(a) Request (3,3,0) ≤ Need[4] = (4,3,1) and ≤ Available (3,3,2). Pretend: Available = (0,0,2), Allocation[4] = (3,3,2), Need[4] = (1,0,1). Safety with Work = (0,0,2): P0 needs (7,4,3), no; P1 (1,2,2), no; P2 (6,0,0), no; P3 (0,1,1), needs 1 B, no; P4 (1,0,1), needs 1 A, no. Nobody can proceed: unsafe, so the request is denied and P4 waits. (b) Request (0,2,0) ≤ Need[0] and ≤ (3,3,2). Pretend: Available = (3,1,2), Allocation[0] = (0,3,0), Need[0] = (7,2,3). Safety: P1 (1,2,2) needs 2 B, only 1 free, no; P3 (0,1,1) ≤ (3,1,2), yes: Work = (5,2,3). Then P1 (1,2,2) ≤ (5,2,3): Work = (7,2,3). Then P0 (7,2,3) ≤ (7,2,3): Work = (7,5,3). Then P2 (6,0,0): Work = (10,5,5). Then P4 (4,3,1): Work = (10,5,7). The state is safe, so the request is granted. The same request is unsafe after P1's (1,0,2) has been granted, because the free pool is then smaller.

Lab: a two-lock deadlock and two cures

The program below runs two threads that need locks A and B. In mode naive, T1 takes A then B while T2 takes B then A, with a short sleep between the two acquisitions to make the bad interleaving certain. To keep the demo from freezing your terminal, each lock attempt uses pthread_mutex_timedlock with a 2-second limit and reports when it gives up. Mode ordered makes both threads take A first. Mode trylock keeps the opposite order but releases the first lock when the second is busy, then backs off for a different time in each thread.

define _POSIX_C_SOURCE 200809L

include

include

include

include

static pthread_mutex_t A = PTHREAD_MUTEX_INITIALIZER; static pthread_mutex_t B = PTHREAD_MUTEX_INITIALIZER; static void msleep(int ms) { struct timespec d = { ms / 1000, (ms % 1000) * 1000000L }; nanosleep(&d, NULL); }

static int mode; / 0 naive, 1 ordered, 2 trylock /

/ Lock m with a 2-second limit so the demo reports a hang instead of freezing. / static int lock_or_report(pthread_mutex_t m, const char who, const char *name) { struct timespec t; clock_gettime(CLOCK_REALTIME, &t); t.tv_sec += 2; if (pthread_mutex_timedlock(m, &t) != 0) { printf("%s: still waiting for %s after 2 s -> deadlock\n", who, name); return -1; } return 0; }

static void worker(void arg) { int id = (int)(long)arg; / 1 or 2 / const char who = id == 1 ? "T1" : "T2"; pthread_mutex_t first = id == 1 ? &A : &B; / naive: opposite orders / pthread_mutex_t second = id == 1 ? &B : &A; const char fn = id == 1 ? "A" : "B", sn = id == 1 ? "B" : "A"; if (mode == 1) { / ordered: always A before B / first = &A; second = &B; fn = "A"; sn = "B"; } for (;;) { if (lock_or_report(first, who, fn)) return NULL; msleep(100); / widen the window / if (mode == 2) { / trylock: give up and retry / if (pthread_mutex_trylock(second) != 0) { printf("%s: %s busy, releasing %s and retrying\n", who, sn, fn); pthread_mutex_unlock(first); msleep(id == 1 ? 10 : 350); / different back-offs */ continue; } } else if (lock_or_report(second, who, sn)) { return NULL; } printf("%s: holds both locks, working\n", who); pthread_mutex_unlock(second); pthread_mutex_unlock(first); return NULL; } }

int main(int argc, char *argv) { const char m = argc > 1 ? argv[1] : "naive"; if (strcmp(m, "naive") == 0) mode = 0; else if (strcmp(m, "ordered") == 0) mode = 1; else if (strcmp(m, "trylock") == 0) mode = 2; else { fprintf(stderr, "usage: %s naive|ordered|trylock\n", argv[0]); return 2; } pthread_t t1, t2; pthread_create(&t1, NULL, worker, (void )1L); pthread_create(&t2, NULL, worker, (void )2L); pthread_join(t1, NULL); pthread_join(t2, NULL); printf("main: both threads returned (mode %s)\n", m); return 0; }

Build and run each mode:

gcc -Wall -Wextra -pthread deadlock.c -o deadlock
./deadlock naive
./deadlock ordered
./deadlock trylock

What to observe. A run on a two-core test machine printed this (naive pauses 2 seconds, and the order of its two lines can vary).

--- naive
T2: still waiting for A after 2 s -> deadlock
T1: still waiting for B after 2 s -> deadlock
main: both threads returned (mode naive)
--- ordered
T2: holds both locks, working
T1: holds both locks, working
main: both threads returned (mode ordered)
--- trylock
T1: B busy, releasing A and retrying
T2: A busy, releasing B and retrying
T1: holds both locks, working
T2: holds both locks, working
main: both threads returned (mode trylock)

In naive mode each thread holds one lock and waits for the other, so both time out. With plain pthread_mutex_lock the program would hang forever, and gdb -p <pid> with thread apply all bt would show both threads blocked inside pthread_mutex_lock. In ordered mode there is no cycle. In trylock mode the first attempt collides and both back off, but T1 waits 10 ms and T2 waits 350 ms, so T1 gets both locks next time and T2 follows.

Without the msleep(100) between the two acquisitions the deadlock almost never appears in a short test, which is why deadlock is dangerous. A delay between acquisitions is a standard way to expose lock-order bugs.

Extensions.

  1. Change the back-off in trylock mode so both threads sleep exactly 10 ms. Run it several times and describe what you see: livelock, or eventual success by chance? Then replace the fixed delays with random ones.
  2. Extend deadlock.c to three locks and three threads (T1: A then B, T2: B then C, T3: C then A) and confirm that all three deadlock. Which single pair of acquisitions do you need to reverse to remove the cycle?
  3. Add a fourth, banker, mode: put each thread's maximum claim into the Banker's structure from this chapter and let a thread request its second lock only if the request algorithm says it is safe. Verify that the program never deadlocks and measure what it costs in waiting.

Common mistakes and debugging tips

Symptom Likely cause What to do
Program hangs, CPU usage near 0, threads alive Deadlock (circular wait on locks) Attach a debugger, print every thread's stack, look for two threads each waiting in lock on the other's lock
Program hangs with CPU at 100% Livelock or a spinning lock holder Look for retry loops; add randomized back-off; check for spinlocks on one core
Hang appears only under load or on one machine Lock-order bug that needs one specific interleaving Run under ThreadSanitizer or Helgrind, which report order inversions without needing the hang
Two functions each work alone, but hang together Each takes the same locks in a different order Define one global lock order and make both functions obey it
Deadlock with a single thread Locking a non-recursive mutex twice, often through a callback Restructure, or use an error-checking mutex to get an error instead of a hang
Banker's check always denies requests Max declared too high, or Need computed from the wrong row Recompute Need = Max - Allocation and check that Available plus the sum of Allocation equals the total

Key takeaways

Key takeaways

  • Deadlock needs all four conditions: mutual exclusion, hold and wait, no preemption and circular wait. Remove one and deadlock cannot happen.
  • A cycle in a resource-allocation graph means deadlock only when every resource on it has a single instance; with multi-instance resources it is necessary, not sufficient.
  • Lock ordering (a global order on resources) is the cheapest and most widely used prevention technique.
  • A state is safe if some order lets every process finish; unsafe does not mean deadlocked, only that deadlock is possible. The Banker's algorithm grants a request only if the resulting state stays safe, at O(m × n²) cost per check.
  • In the worked example, the initial state is safe (sequence P1, P3, P4, P0, P2), P1's request (1,0,2) is granted, and P0's request (0,2,0) from that new state is denied as unsafe.
  • Detection uses current requests instead of maximum needs; recovery means terminating or preempting victims and guarding against starvation.
