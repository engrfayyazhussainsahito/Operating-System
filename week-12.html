File Systems I: Interface and Implementation

What a file and a directory are, how the kernel tracks open files, how blocks are allocated (contiguous, linked, FAT, indexed), how Unix inodes reach terabytes with a few pointers, and how links, free-space maps, mounting and the VFS layer fit together.

What you will be able to do

By the end of this week you will be able to:

  • Distinguish a file's contents, its attributes and its name, and say where each is stored
  • Trace an open call through the per-process fd table, the system-wide open file table and the inode table
  • Compare contiguous, linked, FAT and indexed allocation for sequential and random access
  • Convert a byte offset to a logical block and to a path through direct, single, double or triple indirect pointers
  • Compute the maximum file size of an inode design from block size and pointer size
  • Compare a bitmap with a free list and compute the bitmap size for a given disk
  • Explain the difference between hard and symbolic links, and how mounting and the VFS layer merge file systems into one tree

In Week 11 a disk became a flat array of numbered blocks that can be read and written, and the device itself knows nothing about names, owners or folders. This week we build the layer that supplies them. A file system turns that array into the abstraction every programmer knows: named files organised in a tree of directories, with permissions and sizes. We look first at the interface a program sees, then at the structures the kernel builds to implement it.

The ideas here carry directly into Week 13, where we ask what happens when the power fails in the middle of an update, and into Week 14, where the permission bits stored in the inode become a protection mechanism. Back in Week 2 we saw redirection work by rearranging file descriptors between fork and exec; this chapter explains what those descriptors point to.

Files, attributes and operations

Think of a library. A book has contents, a catalogue card (title, author, shelf number, loan status) and a place on a shelf. The card is not the book, and the shelf position is not the title. A file system keeps the same three things apart.

File

A file is a named, persistent collection of related bytes, managed by the operating system. To the kernel a file is an unstructured sequence of bytes. Any structure (lines of text, records, images) is imposed by the programs that read it.

Along with its bytes, each file has attributes (also called metadata): its type, size, owner, group, permission bits, timestamps (access, modification, status change), the link count, and the location of its data blocks. On Unix these all live in one on-disk record, the inode (index node). Notice what is missing: the file's name. Names belong to directories, which we reach shortly.

The interface is a small set of system calls: open, read, write, lseek, close, unlink (delete a name), rename, truncate, and stat (read the attributes). Two details deserve attention.

First, open returns a small integer, the file descriptor, and does the expensive work once: path lookup and permission checking. After that, read(fd, ...) needs no path at all. Second, the kernel keeps a current file offset per open file, so consecutive read calls move through the file. lseek changes it; pread and pwrite take an explicit offset instead. Access is sequential (the default, offset moves forward) or direct (jump anywhere with lseek), and files are also commonly accessed through mmap (Week 9).

Directories and path names

A directory is a special file whose contents are a table mapping names to inode numbers. Looking up a name means searching that table. The directory entry ("report.txt", 4821) says "the name report.txt refers to inode 4821". The inode, not the entry, holds the size, permissions and block pointers.

This split explains many Unix behaviours. Renaming a file inside a directory changes only a directory entry, so it is instant, whatever the size. Two entries (in the same or different directories) may name the same inode; these are hard links. A file is deleted when its link count (the number of directory entries pointing to the inode) reaches zero and no process still has it open.

Every directory contains two special entries: . (itself) and .. (its parent). The root directory's .. is itself. A path is resolved component by component, starting from the root / for an absolute path or from the process's current directory for a relative one.

Resolving /usr/bin/ls on a cold cache

Assume every directory fits in one block and the root inode is at a well-known location. The kernel must read: the root inode, the root directory's data block (find usr), the inode of usr, its directory block (find bin), the inode of bin, its directory block (find ls), and finally the inode of ls. That is 4 inode reads plus 3 directory-block reads, 7 disk accesses before a single byte of the program is read. This is why the kernel caches directory entries (the dentry cache) so that repeated lookups of popular paths cost no disk I/O at all.

Directories form a tree because Unix forbids hard links to directories (they would create cycles that make tree walks and reference counting unsafe). Symbolic links, described later, may point anywhere and can create cycles, so path resolution limits the number of links it follows.

The open-file tables

When a process calls open, the kernel does not simply hand back a pointer to the inode. It uses three tables, and understanding their relationship answers many classic puzzles.

  1. The per-process file descriptor table: an array indexed by the descriptor number (0 is standard input, 1 standard output, 2 standard error). Each slot points to an entry in the next table. It lives in the process's kernel data and is copied by fork.
  2. The system-wide open file table: one entry per open file description. Each entry stores the current offset, the access mode (read, write, append), flags and a reference count, and points to an inode.
  3. The inode table: the in-memory copies of inodes for every file currently in use, shared by everyone. Each stores the attributes, the block pointers and an in-memory count of how many open file entries refer to it.

Why two levels above the inode? The answer is what must be shared. Two processes that independently open the same file need independent offsets, so each gets its own open file entry. But a parent and child after fork, or two descriptors made by dup, are meant to share an offset: this is exactly how a shell pipeline (cmd1; cmd2) > out.txt writes both outputs one after the other rather than overwriting. The reference count on the entry records how many descriptors share it; close decrements it and frees the entry at zero.

Listing 1 demonstrates it. Parent opens data.txt twice (a and b), reads 5 bytes through a, forks, and the child reads 3 more through its inherited copy of a.

#include <fcntl.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

static void show(const char *who, const char *name, int fd) {
    printf("%-7s %-6s fd=%d offset=%ld\n", who, name, fd, (long)lseek(fd, 0, SEEK_CUR));
    fflush(stdout);
}

int main(void) {
    int a = open("data.txt", O_RDONLY);
    int b = open("data.txt", O_RDONLY);    /* separate open file entry */
    char buf[8];
    if (a < 0 || b < 0) { perror("open"); return 1; }

    if (read(a, buf, 5) < 0) return 1;      /* advance a only */
    show("parent", "a", a);
    show("parent", "b", b);

    pid_t pid = fork();                     /* child inherits the fd table */
    if (pid == 0) {
        if (read(a, buf, 3) < 0) _exit(1);  /* moves the SHARED offset */
        show("child", "a", a);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    show("parent", "a", a);                 /* offset moved by the child */
    show("parent", "b", b);
    return 0;
}

Listing 1. Shared and independent file offsets (create data.txt first, for example with echo "hello world" > data.txt).

parent  a      fd=3 offset=5
parent  b      fd=4 offset=0
child   a      fd=3 offset=8
parent  a      fd=3 offset=8
parent  b      fd=4 offset=0

The parent's a jumped from 5 to 8 although the parent did nothing: the child moved the shared entry. Descriptor b is unaffected.

A descriptor is not a file

Closing a descriptor does not delete anything. A file's data go away only when the inode's link count is zero and its in-memory reference count is zero. This is why you can unlink a file that a process still has open: the name disappears, but the program keeps reading and writing until it closes the descriptor. Log files deleted while a daemon still writes to them keep consuming disk space for exactly this reason.

Allocation methods

Now to the central implementation question: given a file of n bytes, which disk blocks hold it? The disk is a pool of fixed-size blocks (4 KiB is typical), so a file occupies ⌈n / 4096⌉ of them. The file system's allocation method records which. We compare four classical ones on three criteria: speed of sequential access, speed of random access, and waste.

Contiguous allocation

Each file occupies a run of consecutive blocks; the directory records the start block and length. Sequential access is as fast as the disk can go (no seeks), and random access is trivial: block k is at start + k. The costs are those of Week 8 all over again: external fragmentation (free space splits into holes that no file fits), difficulty growing a file (the next block may be taken), and the need to know the final size at creation. Contiguous allocation survives where files are written once, such as CD and DVD file systems, and in the extents of modern file systems (below).

Linked allocation

Each block holds the data plus a pointer to the next block; the directory records the first block. There is no external fragmentation and a file can grow anywhere. But random access is awful: to reach logical block k you must read all of blocks 0 to k − 1, one disk read each. Pointers also cost space (4 bytes of a 4096-byte block leaves 4092 for data) and one lost block breaks the rest of the chain.

FAT: linked allocation with the pointers moved

The File Allocation Table keeps the idea but moves every pointer out of the data blocks into one table at the start of the volume, with one entry per block (or per cluster of blocks). Entry i holds the number of the block that follows block i in its file, or a special end-of-file mark, or a zero for free. The directory entry stores the first block.

With the FAT cached in memory, random access needs only table lookups (fast) and one data read. The price is that the whole table must be resident: a 32 GiB volume with 4 KiB clusters has 2³⁵ / 2¹² = 2²³ = 8,388,608 entries; at 4 bytes each the FAT is 32 MiB, and it grows with the disk. FAT is simple and still used on memory cards and USB sticks (FAT32, exFAT), but it has no per-file permissions and weak crash recovery.

Indexed allocation

Give each file an index block: an array of pointers to its data blocks. Block k of the file is simply index[k], so random access costs one extra read (and none once the index is cached). Only the files that need a big index pay for it, and there is no external fragmentation. The problem is the index's size: a small file wastes a whole block on its index, and a large file needs more entries than one block holds. Solutions are to link index blocks, use a multilevel index, or combine schemes, which is exactly what the Unix inode does.

Method Sequential Random Grows easily Main weakness
Contiguous Best One computation No External fragmentation
Linked Good k disk reads Yes Slow random access, fragile chain
FAT Good k memory lookups Yes Whole table in RAM
Indexed Good 1 extra read (or 0 if cached) Yes Index overhead for tiny files

Extents

Modern file systems such as ext4, XFS and NTFS often store not a list of blocks but a list of extents, each a pair (start block, length). A well-allocated 1 GiB file may need a handful of extents instead of 262,144 pointers. It is contiguous allocation and indexed allocation combined: the index stays tiny when the allocator finds long runs, and the file system still copes when it cannot.

Unix inodes and the multilevel index

The classic Unix file system (and ext2, ext3 and their relatives) stores per-file information in a fixed-size inode. Besides the attributes, the inode holds 15 block pointers: 12 direct pointers to data blocks, one single indirect pointer, one double indirect and one triple indirect.

  • A direct pointer names a data block.
  • The single indirect pointer names a block that is itself a table of pointers, each naming a data block.
  • The double indirect pointer names a table whose entries each point to a single-indirect-style table.
  • The triple indirect adds one more level.
struct inode {                 /* simplified ext2-style layout */
    unsigned short mode;       /* type and permission bits       */
    unsigned short nlink;      /* number of directory entries    */
    unsigned int   uid, gid;   /* owner                          */
    unsigned long  size;       /* bytes                          */
    unsigned long  atime, mtime, ctime;
    unsigned int   block[15];  /* 0-11 direct, 12 single,
                                  13 double, 14 triple indirect  */
};

Listing 2. The block pointers in a simplified inode.

This design reflects a measured fact: most files are small, but most bytes belong to large files. Small files get a fast, compact structure; large files get a deep tree.

How big can a file be?

Let the block size be B = 4096 bytes and a pointer be 4 bytes. One indirect block holds 4096 / 4 = 1024 pointers, so call N = 1024. The number of data blocks reachable is:

Region Blocks reached Size
12 direct 12 48 KiB
Single indirect N = 1,024 4 MiB
Double indirect N² = 1,048,576 4 GiB
Triple indirect N³ = 1,073,741,824 4 TiB

The maximum file size is (12 + N + N² + N³) × B = 1,074,791,436 × 4096 = 4,402,345,721,856 bytes, which is 4 TiB plus 4 GiB plus 4 MiB plus 48 KiB, about 4.004 TiB. In practice other limits (the width of the size field, file system design) can be smaller.

From a byte offset to a block

Given a byte offset off, the logical block number is off / B (integer division) and the position inside the block is off % B. Then subtract region sizes in order. Listing 3 does exactly this.

Worked example: byte offset 5,000,000

5,000,000 / 4096 = 1220 remainder 5,000,000 − 1220 × 4096 = 2,880. So the byte is at position 2,880 of logical block 1220.

  • Direct covers blocks 0 to 11. 1220 > 11, so subtract 12: 1208.
  • Single indirect covers the next 1,024 blocks (logical 12 to 1035). 1208 ≥ 1024, so subtract 1024: 184.
  • Double indirect starts at logical block 1036, and 184 < N² = 1,048,576. The first-level index is 184 / 1024 = 0 and the second is 184 % 1024 = 184.

The path is: inode → double indirect block → entry double[0] → single-indirect block → entry block[184] → data block. A cold read needs 3 disk reads (the double block, the second-level block, the data block) once the inode is in memory.

#include <stdio.h>
#include <stdlib.h>

#define NDIRECT 12

int main(int argc, char **argv) {
    unsigned long long block = 4096, ptr = 4;
    if (argc < 2) {
        fprintf(stderr, "usage: %s offset [block_size] [ptr_size]\n", argv[0]);
        return 1;
    }
    unsigned long long off = strtoull(argv[1], NULL, 10);
    if (argc > 2) block = strtoull(argv[2], NULL, 10);
    if (argc > 3) ptr = strtoull(argv[3], NULL, 10);

    unsigned long long n = block / ptr;          /* pointers per block */
    unsigned long long lb = off / block;         /* logical block number */
    unsigned long long in = off % block;         /* byte within that block */
    printf("block size %llu, %llu pointers per block\n", block, n);
    printf("offset %llu = logical block %llu, byte %llu\n", off, lb, in);

    if (lb < NDIRECT) {
        printf("direct[%llu]\n", lb);
    } else if ((lb -= NDIRECT) < n) {
        printf("single indirect: block[%llu]\n", lb);
    } else if ((lb -= n) < n * n) {
        printf("double indirect: double[%llu] -> block[%llu]\n", lb / n, lb % n);
    } else if ((lb -= n * n) < n * n * n) {
        printf("triple indirect: triple[%llu] -> double[%llu] -> block[%llu]\n",
               lb / (n * n), (lb / n) % n, lb % n);
    } else {
        printf("beyond the maximum file size\n");
        return 2;
    }
    unsigned long long maxblocks = NDIRECT + n + n * n + n * n * n;
    printf("max blocks %llu, max file size %llu bytes (%.3f TiB)\n",
           maxblocks, maxblocks * block, maxblocks * (double)block / (1ULL << 40));
    return 0;
}

Running ./blockmap 5000000 prints:

block size 4096, 1024 pointers per block
offset 5000000 = logical block 1220, byte 2880
double indirect: double[0] -> block[184]
max blocks 1074791436, max file size 4402345721856 bytes (4.004 TiB)

Boundary values are the best tests: offset 49151 is the last byte of direct block 11, offset 49152 is single indirect: block[0], offset 4243455 is block[1023] of the single region, and offset 4243456 is the first byte reached through double[0] -> block[0].

Why not a deeper tree everywhere?

Each indirect level multiplies reach by 1024 but costs one more disk read per cold access. Direct pointers make the common case (small files) free, and the tree depth grows only as the file does. The rare 4 TiB file pays three extra reads per block, a cost that caching of the indirect blocks quickly hides: a sequential read of a large file touches each indirect block once and then uses its 1024 pointers.

Free-space management

To allocate a block the file system must know which are free. Two classic structures do this.

A bitmap (bit vector) has one bit per block: 1 if used, 0 if free (the opposite convention is also seen). Finding a free block, or a run of consecutive free blocks, means scanning for a zero bit, which CPUs do fast with word-at-a-time and bit-scan instructions. The bitmap is compact and good at finding contiguous space, which helps keep files together. For a disk with 2²⁸ blocks (1 TiB of 4 KiB blocks) it needs 2²⁸ bits = 32 MiB, or 8,192 bitmap blocks. ext2 and ext4 keep one bitmap per block group, so only the part near the file's inode need be consulted.

A free list links free blocks together: the head pointer is in the superblock and each free block holds the number of the next. Allocation pops the head, which is cheap, but finding a contiguous run is hard and traversing the list costs a read per block. The usual refinement is grouping: the first free block holds the addresses of n − 1 other free blocks and one pointer to the next such block, so one read yields many free blocks. Another is counting, which stores (start, run length) pairs, the same idea as extents.

Listing 4 implements a bitmap with first-fit run allocation on a 64-block disk whose first 6 blocks hold metadata.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define NBLOCKS 64
static unsigned char bm[NBLOCKS / 8];       /* bit = 1 means in use */

static int  test(int i)  { return (bm[i / 8] >> (i % 8)) & 1; }
static void set(int i)   { bm[i / 8] |=  (1u << (i % 8)); }
static void clear(int i) { bm[i / 8] &= ~(1u << (i % 8)); }

/* First-fit search for n consecutive free blocks; -1 if none. */
static int alloc_run(int n) {
    int run = 0;
    for (int i = 0; i < NBLOCKS; i++) {
        run = test(i) ? 0 : run + 1;
        if (run == n) {
            int start = i - n + 1;
            for (int j = start; j <= i; j++) set(j);
            return start;
        }
    }
    return -1;
}

static void dump(const char *label) {
    printf("%-14s ", label);
    for (int i = 0; i < NBLOCKS; i++) {
        putchar(test(i) ? '#' : '.');
        if (i % 16 == 15) putchar(' ');
    }
    putchar('\n');
}

int main(void) {
    memset(bm, 0, sizeof bm);
    for (int i = 0; i < 6; i++) set(i);     /* metadata blocks */
    dump("initial");
    int a = alloc_run(10), b = alloc_run(20), c = alloc_run(8);
    printf("a=%d b=%d c=%d\n", a, b, c);
    dump("after a,b,c");
    for (int i = a; i < a + 10; i++) clear(i);
    dump("free a");
    printf("alloc 12 -> %d (needs a hole of 12)\n", alloc_run(12));
    printf("alloc 9  -> %d\n", alloc_run(9));
    dump("final");
    int used = 0;
    for (int i = 0; i < NBLOCKS; i++) used += test(i);
    printf("used %d, free %d of %d\n", used, NBLOCKS - used, NBLOCKS);
    return 0;
}

Listing 4. A bitmap allocator with first-fit runs.

initial        ######.......... ................ ................ ................ 
a=6 b=16 c=36
after a,b,c    ################ ################ ############.... ................ 
free a         ######.......... ################ ############.... ................ 
alloc 12 -> 44 (needs a hole of 12)
alloc 9  -> 6
final          ###############. ################ ################ ########........ 
used 55, free 9 of 64

The 12-block request skips the 10-block hole that a left behind and lands at block 44, the same external fragmentation story as the memory allocators of Week 8. The 9-block request then fits the hole and starts at 6.

Links: hard and symbolic

A hard link is a second directory entry for an existing inode. Both names are equal citizens; the inode's link count is 2. Neither is "the original". Deleting one name decrements the count, and the data survive until the last name goes. Because a hard link stores an inode number, it works only within one file system (inode numbers are meaningful only per file system), and directories cannot be hard-linked.

A symbolic link (symlink) is a different kind of file whose content is a path string. When the kernel meets it during path resolution, it substitutes that string and continues. A symlink can cross file systems, can point at a directory, and can dangle if its target no longer exists.

Property Hard link Symbolic link
What it is Another name for the same inode A small file containing a path
Own inode No (shares) Yes
Across file systems No Yes
Link to directory No Yes
After target is removed Still works (data survive) Dangles (error on use)
Link count of target Increased Unchanged 
echo hello > f.txt
ln f.txt hard.txt            # second name, same inode
ln -s f.txt soft.txt         # new file containing the text "f.txt"
ls -li                       # first column is the inode number
rm f.txt
cat hard.txt                 # still prints hello
cat soft.txt                 # fails: No such file or directory

Listing 5. Hard versus symbolic links.

After rm f.txt, hard.txt still prints hello and soft.txt fails with No such file or directory, because its stored path f.txt no longer resolves. If you later create a new file named f.txt, the symlink works again, since it is bound to a name, not to an inode.

Mounting and the VFS layer

A machine usually has several file systems: the root partition, a USB stick, a network share, and virtual ones such as /proc. Unix does not give each a drive letter. Mounting attaches the root of one file system to a directory (the mount point) in the existing tree, and the directory's old contents are hidden while it is mounted. The kernel keeps a mount table; path resolution checks at each directory whether it is a mount point and, if so, crosses into the mounted file system. Inode numbers are unique only within one file system, so a file is identified by the pair (device, inode), which is what stat returns in st_dev and st_ino.

How can one read call work on ext4, FAT and NFS alike? Through the Virtual File System (VFS) layer, a kernel interface of generic objects (superblock, inode, directory entry, open file) with a table of function pointers per file system, covered further in Week 13. The system call layer talks only to the VFS, and the VFS calls the right file system's lookup, read or write. Adding a new file system means filling in the table, not changing any application.

Inspecting mounts on Linux

On Linux, df shows mounted file systems with their sizes and mount points, mount lists the table, and stat -f . reports the block size and file system type of the file system that holds the current directory.

Exercises

Exercise 12.1warm-up

Smaller blocks

An inode has 12 direct pointers, one single, one double and one triple indirect pointer. Blocks are 1 KiB and pointers are 4 bytes. Compute the pointers per block and the maximum file size.

Show solution

Pointers per block N = 1024 / 4 = 256. Reachable blocks: 12 + 256 + 256² + 256³ = 12 + 256 + 65,536 + 16,777,216 = 16,843,020. Multiply by 1024 bytes: 17,247,252,480 bytes, about 16.06 GiB. Compare with 4 KiB blocks (about 4 TiB): quartering the block size shrank the limit by a factor of about 256, because the number of pointers per block falls with B and appears cubed.

Exercise 12.2core

Offsets to blocks

Blocks are 4 KiB and pointers 4 bytes, with 12 direct pointers. For each byte offset give the logical block, the byte within it, and the path: (a) 100,000; (b) 3,000,000,000.

Show solution

(a) 100,000 / 4096 = 24 (since 24 × 4096 = 98,304), byte 100,000 − 98,304 = 1,696. Block 24 is past the direct region; 24 − 12 = 12 < 1024, so it is single indirect: block[12].

(b) 3,000,000,000 / 4096 = 732,421 (since 732,421 × 4096 = 2,999,996,416), byte 3,584. Subtract 12 direct and 1,024 single: 732,421 − 1,036 = 731,385, which is below 1,048,576, so the double region. First index 731,385 / 1024 = 714 (since 714 × 1024 = 731,136), second index 731,385 − 731,136 = 249. Path: double[714] -> block[249].

Exercise 12.3core

Index overhead of a 100 MiB file

How many data blocks and how many pointer (indirect) blocks does a 100 MiB file need with 4 KiB blocks and 4-byte pointers? What fraction is overhead?

Show solution

Data blocks: 100 × 2²⁰ / 4096 = 25,600. Direct pointers cover 12 and the single indirect covers 1,024, leaving 25,600 − 1,036 = 24,564 for the double region. Those need ⌈24,564 / 1024⌉ = 24 second-level blocks (23 full ones cover 23,552, the 24th holds the remaining 1,012 pointers) plus the one double indirect block itself. Pointer blocks: 1 (single) + 1 (double) + 24 = 26. Total 25,626 blocks; overhead 26 / 25,626 ≈ 0.10 percent. Large files pay almost nothing for the index.

Exercise 12.4core

Linked allocation versus FAT

In linked allocation each 4096-byte block stores a 4-byte pointer, leaving 4092 data bytes. (a) To read the byte at offset 1,000,000 of a file, which logical block holds it, and how many disk reads are needed? (b) How many disk reads does a FAT with the table cached in memory need? (c) How large is a FAT for a 32 GiB volume with 4 KiB clusters and 4-byte entries?

Show solution

(a) 1,000,000 / 4092 = 244 (since 244 × 4092 = 998,448), byte 1,552 within it. Blocks 0 to 244 must be read in turn: 245 disk reads.

(b) Following the chain of 244 links is 244 memory lookups with no disk access, then one disk read of the data block.

(c) 32 GiB / 4 KiB = 2²³ = 8,388,608 entries times 4 bytes is 32 MiB.

Exercise 12.5warm-up

Bitmap versus free list

A 1 TiB disk has 4 KiB blocks. (a) How big is a bitmap with one bit per block, in MiB and in blocks? (b) With a grouped free list, each free block holds 1023 free block numbers and one link (4 bytes each). If the whole disk were free, about how many blocks would be used as list nodes, and where do they live?

Show solution

(a) 2⁴⁰ / 2¹² = 2²⁸ blocks, so 2²⁸ bits = 2²⁵ bytes = 32 MiB, which is 32 MiB / 4 KiB = 8,192 blocks.

(b) 2²⁸ / 1023 ≈ 262,400.25, so 262,401 list nodes. They are free blocks themselves, so the list costs no space beyond the blocks it describes. The trade-off: the bitmap is a fixed 32 MiB (0.003 percent of the disk), searchable for contiguous runs; the list has no fixed size but is slow to search for runs.

cat c
Show solution

After echo one > a the inode has link count 1. ln a b makes it 2. ln -s a c creates a new small file c containing the text a; the data inode stays at 2. rm a removes one name: count 1, data kept. cat b prints one. cat c fails with No such file or directory, since it names a, which no longer exists. echo two > a creates a brand-new file a with a new inode, so cat c now prints two, not one. The original data inode (one) still has link count 1, reachable only through b.

Exercise 12.7challenging

Three tables

Process P runs: fd1 = open("f", O_RDONLY); fd2 = open("f", O_RDONLY); fd3 = dup(fd1); fork(); where fd1, fd2 and fd3 are the descriptor numbers returned. (a) How many open file table entries and inode table entries exist for f? Give the reference count of each open file entry after the fork. (b) The child reads 10 bytes through its copy of fd1. What offsets do the parent's fd1, fd2 and fd3 show? (c) The parent calls close(fd1) and the child then calls unlink("f"). Can the parent still read through fd3?

Show solution

(a) open twice creates two open file entries, A (from fd1, also shared by fd3 through dup) and B (fd2). One inode table entry serves both. After fork the child has its own fd table copying the same pointers, so entry A has reference count 4 (parent fd1, parent fd3, child fd1, child fd3) and entry B has 2 (parent fd2, child fd2).

(b) The read advances the offset in entry A to 10, so the parent's fd1 and fd3 both show 10, while fd2 (entry B) stays at 0.

(c) Yes. close(fd1) just drops entry A's count to 3. unlink removes the directory entry and lowers the link count to 0, but the inode is still referenced by open file entries, so the kernel keeps the data and inode until the last descriptor is closed. The parent reads on through fd3 normally.

Lab

You will inspect inodes with stat, list directories with readdir, and use the block-map calculator from Listing 3. Compile everything with gcc -Wall -Wextra -pthread. Use a real disk (your home directory), because some virtual file systems report zero or fake block counts.

Part 1: stat

#include <stdio.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>
#include <time.h>

static const char *kind(mode_t m) {
    if (S_ISREG(m)) return "regular file";
    if (S_ISDIR(m)) return "directory";
    if (S_ISLNK(m)) return "symbolic link";
    if (S_ISCHR(m)) return "character device";
    if (S_ISBLK(m)) return "block device";
    return "other";
}

int main(int argc, char **argv) {
    for (int i = 1; i < argc; i++) {
        struct stat st;
        if (lstat(argv[i], &st) < 0) { perror(argv[i]); continue; }
        printf("%s\n", argv[i]);
        printf("  type        : %s\n", kind(st.st_mode));
        printf("  inode       : %lu on device %u:%u\n", (unsigned long)st.st_ino,
               major(st.st_dev), minor(st.st_dev));
        printf("  links       : %lu\n", (unsigned long)st.st_nlink);
        printf("  size        : %ld bytes\n", (long)st.st_size);
        printf("  blocks      : %ld x 512 bytes = %ld bytes allocated\n",
               (long)st.st_blocks, (long)st.st_blocks * 512);
        printf("  I/O block   : %ld bytes\n", (long)st.st_blksize);
        printf("  mode        : %04o\n", st.st_mode & 07777);
    }
    return 0;
}

Listing 6. A small stat tool using lstat, which does not follow symbolic links.

Make a scratch directory with echo hello > f.txt; ln f.txt hard.txt; ln -s f.txt soft.txt; head -c 10000 /dev/zero > ten.bin; truncate -s 1M sparse.bin and run ./mystat f.txt soft.txt ten.bin sparse.bin. On one test machine the relevant lines (condensed) were:

f.txt        links: 2   size: 6 bytes        blocks: 8 x 512 = 4096 bytes allocated
soft.txt     type: symbolic link   size: 5 bytes   blocks: 0
ten.bin      links: 1   size: 10000 bytes    blocks: 24 x 512 = 12288 bytes allocated
sparse.bin   links: 1   size: 1048576 bytes  blocks: 0 x 512 = 0 bytes allocated

Observe four things. A 6-byte file occupies a whole 4096-byte block. A 10,000-byte file occupies ⌈10,000 / 4096⌉ = 3 blocks, 12,288 bytes. The symlink's size is 5, the length of the string f.txt, and it owns no data block (on ext4, targets under 60 bytes are stored inside the inode). And sparse.bin is a sparse file: its size is 1 MiB but no blocks are allocated, because blocks that were never written are not allocated and read as zeros. st_blocks counts 512-byte units regardless of the file system block size.

Part 2: readdir

#include <dirent.h>
#include <stdio.h>
#include <sys/stat.h>

int main(int argc, char **argv) {
    const char *path = argc > 1 ? argv[1] : ".";
    DIR *d = opendir(path);
    if (!d) { perror(path); return 1; }
    struct dirent *e;
    while ((e = readdir(d)) != NULL) {
        char full[4096];
        snprintf(full, sizeof full, "%s/%s", path, e->d_name);
        struct stat st;
        if (lstat(full, &st) < 0) { perror(full); continue; }
        printf("%8lu  links=%lu  %c  %s\n", (unsigned long)e->d_ino,
               (unsigned long)st.st_nlink,
               S_ISDIR(st.st_mode) ? 'd' : S_ISLNK(st.st_mode) ? 'l' : '-',
               e->d_name);
    }
    closedir(d);
    return 0;
}

Listing 7. Listing a directory: each entry is a (name, inode number) pair.

Run ./lsdir . in the scratch directory. Entries appear in directory order, not sorted, and the inode numbers differ from machine to machine, but f.txt and hard.txt print the same inode number and links=2, while soft.txt has its own. The . entry shows links= equal to 2 plus the number of subdirectories, because each subdirectory's .. points back to it. Now run rm f.txt, list again, and confirm hard.txt shows links=1.

Common mistakes and debugging tips

Symptom Likely cause What to do
Maximum file size answer off by a factor of 4 Used pointer size as 1 byte or forgot that N = B / pointer size Compute N first, then 12 + N + N² + N³
Block index off by 12 or 1,036 Forgot to subtract the direct or single region before indexing Subtract region sizes in order, and test the boundary offsets
Offset 4243456 placed in the single indirect region Used lb <= 1036 instead of lb < 1036 Logical blocks are zero based: 0..11, 12..1035, 1036..
ls shows file size 1 MiB but du reports 0 Sparse file: unwritten blocks are not allocated Compare st_size with st_blocks * 512
Disk is full after deleting a big log A process still has the file open, so the inode is alive lsof +L1 to list open deleted files; restart or truncate the process
ln fails with "Invalid cross-device link" Hard links cannot span file systems Use ln -s, or copy the file
Symlink "does not work" Relative target resolved relative to the link's directory, not to the current directory Use an absolute target or recheck the relative path
Two descriptors write over each other Two separate open calls have separate offsets Share one open file entry with dup, or open with O_APPEND

Key takeaways

Key takeaways

  • A file's name lives in a directory entry, while its size, permissions and block pointers live in the inode; the link count says how many names refer to it.
  • Opening a file creates an entry in the system-wide open file table (offset and mode) pointed to by a per-process descriptor and reaching the shared inode; fork and dup share entries, separate open calls do not.
  • Contiguous allocation is fast but fragments; linked is flexible but slow for random access; FAT keeps the chain in memory; indexed gives direct access and underlies the Unix inode.
  • With 4 KiB blocks and 4-byte pointers an inode with 12 direct and 3 indirect pointers reaches (12 + 1024 + 1024² + 1024³) × 4 KiB, about 4 TiB, while small files never need an indirect block.
  • To map an offset, divide by the block size, then subtract the direct, single and double region sizes in turn; offset 5,000,000 is logical block 1220, reached by double[0] then block[184].
  • Bitmaps are compact and find contiguous runs easily; free lists are cheap to pop but poor at finding runs.
  • A hard link is another name for an inode (same file system only), a symlink is a file containing a path; mounting and the VFS layer merge many file systems into one tree.
