Virtualization, Containers and Case Studies: Linux and Windows

How one machine pretends to be many (hypervisors, trap-and-emulate, binary translation, paravirtualization, VT-x and nested page tables), how containers get a similar effect with Linux namespaces and cgroups, and how Linux and Windows put the course ideas together.

What you will be able to do

By the end of this week you will be able to:

  • Distinguish type 1 and type 2 hypervisors and state the Popek and Goldberg condition for classical virtualization
  • Explain how trap-and-emulate, binary translation, paravirtualization and hardware-assisted virtualization each handle sensitive instructions
  • Compute the cost of a two-dimensional (nested) page walk and explain why TLBs make it tolerable
  • Describe what namespaces and cgroups each isolate or limit, and why a container is not a virtual machine
  • Compute CFS CPU shares from nice-derived weights and explain vruntime
  • Map Windows concepts (executive, object manager, handles, priority levels, working sets, MFT) onto ideas from earlier weeks
  • Use unshare and cgroup v2 files to observe and limit a process

In Week 14 a protection domain was a set of rights around a process, enforced by the kernel. This week we draw the domain around something larger: a whole operating system (a virtual machine) or a group of processes that believe they own the machine (a container). Both reuse mechanisms you know: privilege levels from Week 1, page tables and TLBs from Week 8 and the scheduler from Week 4.

In the second half we read two real kernels as applications of the whole course. Linux builds everything on one primitive (clone); Windows makes different choices for the same problems: an object manager, handles, fixed priority levels and NTFS. The aim is to see the same few ideas recur with different trade-offs.

Virtual machines and hypervisors

Think of an apartment building: each tenant has a private flat, but all share one foundation and one boiler, and the landlord decides who gets how much hot water. A virtual machine (VM) is a flat: software that looks to the operating system inside it like a complete computer. The landlord is the hypervisor.

Hypervisor

A hypervisor, or virtual machine monitor (VMM), creates and runs virtual machines. It multiplexes the real CPU, memory and devices among guests, giving each guest OS the illusion of a private machine. The real machine is the host.

Popek and Goldberg (1974) asked three things of a VMM: fidelity (programs behave as on real hardware), safety (the VMM keeps control of real resources, so a guest cannot harm the host or other guests) and efficiency (most guest instructions run directly on the CPU).

A type 1 hypervisor is the most privileged software on the machine: Xen, VMware ESXi and Microsoft Hyper-V. A type 2 hypervisor is an application on a normal OS, like VirtualBox: easy to install, but with one more layer. The line blurs: KVM is a Linux module that makes Linux itself a type 1 hypervisor, with QEMU emulating devices.

Trap-and-emulate

The classic technique uses the privilege levels of Week 1. The guest kernel believes it runs in kernel mode, but the VMM runs it in user mode. Ordinary instructions run at full speed. When the guest executes a privileged instruction (disable interrupts, load a page-table base, touch a device) the CPU traps into the VMM, which emulates the instruction against the guest's virtual state and resumes the guest.

The model below is not real virtualization, only the control flow. The guest runs six instructions, three privileged; the "VMM" keeps a virtual interrupt flag and never touches a real one. Save as toyvm.c.

#include <stdio.h>

enum op { MOVI, ADD, CLI, STI, OUT, HALT };
struct insn { enum op op; int a, b; };
struct vcpu { int reg[4], pc, virt_if; long executed, traps; };

static int is_privileged(enum op o) { return o == CLI || o == STI || o == OUT; }

/* The VMM's trap handler: emulate the instruction on virtual state. */
static void emulate(struct vcpu *v, struct insn *i) {
    v->traps++;
    if (i->op == CLI) v->virt_if = 0;
    else if (i->op == STI) v->virt_if = 1;
    else printf("  [vmm] emulated OUT: guest wrote %d to virtual device\n", v->reg[i->a]);
}

int main(void) {
    struct insn prog[] = {
        {MOVI, 0, 40}, {MOVI, 1, 2}, {ADD, 0, 1},   /* r0 = 42, unprivileged */
        {CLI, 0, 0}, {OUT, 0, 0}, {STI, 0, 0},      /* privileged */
        {HALT, 0, 0},
    };
    struct vcpu v = { .virt_if = 1 };
    for (;;) {
        struct insn *i = &prog[v.pc++];
        if (i->op == HALT) break;
        v.executed++;
        if (is_privileged(i->op)) { emulate(&v, i); continue; }   /* trap */
        if (i->op == MOVI) v.reg[i->a] = i->b;                    /* direct */
        else v.reg[i->a] += v.reg[i->b];
    }
    printf("executed=%ld trapped=%ld direct=%ld r0=%d virtual IF=%d\n",
           v.executed, v.traps, v.executed - v.traps, v.reg[0], v.virt_if);
    return 0;
}

Built with gcc -Wall -pthread -o toyvm toyvm.c, it prints:

  [vmm] emulated OUT: guest wrote 42 to virtual device
executed=6 trapped=3 direct=3 r0=42 virtual IF=1

Half the instructions trapped, so this guest would be slow. A real guest traps on well under 1% of instructions, which is what makes the approach efficient; each real trap still costs microseconds (Exercise 2).

Why x86 was hard to virtualize

A sensitive instruction reads or changes machine configuration (mode, page-table base, interrupt state) or behaves differently depending on it. A privileged instruction traps in user mode. Popek and Goldberg's theorem: trap-and-emulate works if every sensitive instruction is privileged. The original x86 broke this: about seventeen instructions were sensitive but did not trap. popf, which restores the flags register, silently ignores the interrupt-flag bit in user mode, so the VMM never learns the guest tried to change it.

Technique Idea Catch Example
Binary translation The VMM rewrites guest kernel code before running it, replacing problem instructions with safe sequences, and caches the result Complex; translation overhead VMware (1999)
Paravirtualization The guest kernel is modified to call the VMM through hypercalls (system calls from guest to hypervisor) Guest source must be changed Xen (2003), virtio
Hardware-assisted New CPU mode traps sensitive operations by design Needs recent CPUs; VM exits cost time KVM, Hyper-V, modern Xen

Paravirtualization survives mainly for I/O, as virtio devices: shared-memory request rings that avoid many traps per packet.

Hardware support: VT-x, AMD-V and nested page tables

Around 2005 to 2006 Intel (VT-x) and AMD (AMD-V) added hardware virtualization. The CPU gains a root mode (the VMM) and a non-root mode (the guest). In non-root mode the guest kernel runs in its own ring 0 and executes privileged instructions directly. A control structure in memory (the VMCS on Intel, VMCB on AMD) holds guest register state and lists the events that force a VM exit, a switch to the VMM. The VMM handles the exit (say, an access to an emulated device) and does a VM entry to resume. Everything not configured to exit runs at native speed, and sensitive instructions now exit by design, so the Popek and Goldberg condition holds again.

A program can ask whether it is a guest by reading CPUID, the CPU feature instruction. Save as cpuid.c (x86 only).

#include <cpuid.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    unsigned a, b, c, d;
    __cpuid(1, a, b, c, d);
    int hv = (c >> 31) & 1;                          /* CPUID.1:ECX bit 31 */
    printf("hypervisor bit : %d\n", hv);
    printf("VMX (Intel VT-x): %d\n", (c >> 5) & 1);  /* CPUID.1:ECX bit 5 */
    __cpuid(0x80000001, a, b, c, d);
    printf("SVM (AMD-V)     : %d\n", (c >> 2) & 1);  /* CPUID.80000001:ECX bit 2 */
    if (hv) {
        char id[13];
        __cpuid(0x40000000, a, b, c, d);             /* hypervisor vendor leaf */
        memcpy(id, &b, 4); memcpy(id + 4, &c, 4); memcpy(id + 8, &d, 4);
        id[12] = 0;
        printf("hypervisor id   : \"%s\"\n", id);
    }
    return 0;
}

The course sandbox, itself a KVM guest, printed:

hypervisor bit : 1
VMX (Intel VT-x): 0
SVM (AMD-V)     : 0
hypervisor id   : "KVMKVMKVM"

VMX and SVM are 0 because this guest may not run VMs of its own (nested virtualization is off). On bare metal you would see the hypervisor bit 0 and VMX or SVM equal to 1.

Memory: shadow page tables and nested paging

The guest believes it controls physical memory, but its "physical" addresses are guest-physical (GPA) and must be mapped to host-physical (HPA) memory. With guest virtual addresses (GVA) there are three address spaces, yet the MMU of Week 8 walks one table.

  • Shadow page tables (software): the VMM builds a hidden table mapping GVA directly to HPA and write-protects the guest's own tables, trapping every guest update. Correct, but slow for page-table-heavy work such as process creation.
  • Nested paging (hardware): EPT on Intel and NPT on AMD (2007 to 2008). The MMU walks the guest table (GVA to GPA) and a hypervisor-owned nested table (GPA to HPA). The guest edits its tables with no traps.

How bad is a nested walk?

Natively a 4-level walk costs 4 references. Under nested paging each of the 4 guest levels holds a GPA: translating it takes a 4-reference nested walk, then 1 reference reads the entry, so 4 × (4 + 1) = 20. The final data page's GPA needs one more nested walk of 4. Total 24 references, six times native (Exercise 3 generalises this).

Containers: namespaces and cgroups

A VM virtualizes hardware, so every guest brings a whole kernel. Often we only need isolation between programs on one kernel. A container gives a group of processes their own view of the system and a limit on resource use, with no second kernel.

Container

A container is not a kernel object. It is a set of processes running on the host kernel inside chosen namespaces (what they can see) and a cgroup (how much they can use), usually with a restricted root file system, fewer capabilities and a seccomp filter (Week 14).

Namespaces: what a process can see

A namespace wraps a global resource so that processes inside see a private instance. Every process belongs to one namespace of each kind; /proc/<pid>/ns/ lists them.

Namespace Flag Isolates Effect inside
Mount CLONE_NEWNS Mount table Own root file system
UTS CLONE_NEWUTS Hostname Own hostname
IPC CLONE_NEWIPC System V and POSIX IPC Private shared memory, queues
PID CLONE_NEWPID Process IDs First process is PID 1
Network CLONE_NEWNET Interfaces, routes, ports Own lo, own port numbers
User CLONE_NEWUSER User and group IDs Root inside, ordinary user outside
Cgroup CLONE_NEWCGROUP Cgroup root view Sees its group as /
Time CLONE_NEWTIME Clock offsets Own uptime (Linux 5.6 and later)

Three system calls manage them: clone (child in new namespaces), unshare (move the caller into new ones) and setns (join an existing one, as docker exec does). A process has a PID in each PID namespace containing it, so a container's PID 1 may be PID 4711 on the host; that PID 1 reaps orphans there like init (Week 2). The user namespace maps IDs: UID 0 inside may be unprivileged UID 1000 outside, which is how rootless containers work. Creating most namespaces needs CAP_SYS_ADMIN, but a new user namespace grants that capability inside itself, so an ordinary user can create the rest.

Cgroups: how much a process can use

Control groups (cgroups) arrange processes in a tree and attach resource controllers to nodes. They were developed at Google and merged into Linux in 2008; the redesigned cgroup v2 (one unified hierarchy) is the default on current distributions. The interface is a file system, normally at /sys/fs/cgroup: mkdir creates a group, writing a number into a file sets a limit, and writing a PID into cgroup.procs moves a process in.

File Meaning
cpu.max quota period in microseconds: 50000 100000 is 50% of one CPU
cpu.weight Relative share under contention (1 to 10000, default 100)
memory.max Hard limit; exceeding it triggers reclaim, then the OOM killer inside the group
pids.max Maximum number of tasks (stops fork bombs)

The two are independent: unshare alone gives a "container" with no limits; a cgroup alone limits a process that still sees everything.

Containers versus virtual machines

Property Virtual machine Container
Virtualized Hardware OS view and resources
Kernel One per guest Shared with the host
Start-up Seconds to minutes (boots an OS) Milliseconds to a second (starts a process)
Isolation Strong: narrow hypervisor interface Weaker: whole system call interface of the shared kernel

Docker added images: stacked read-only file system layers merged by overlayfs, plus a thin writable layer. Containers from one image share its layers on disk and in the page cache (Week 13).

A container is not a security boundary like a VM

All containers share one kernel. A kernel bug reachable from a container, or a careless configuration (real root, --privileged, the Docker socket mounted), can give an attacker the host and every other container. Hypervisors expose a much narrower interface, so multi-tenant clouds often run each container inside a micro-VM (Firecracker, Kata Containers) or add a user-space kernel (gVisor).

Case study: Linux

Linux is a monolithic kernel (all major services in kernel mode) extended by loadable modules. We look at four subsystems.

The process model: everything is a task

Linux has no separate kernel notion of "process" and "thread". Both are tasks described by a task_struct; they differ only in what they share, which the flags of clone choose.

Created by clone flags Shares with parent
fork() SIGCHLD only Nothing (copy-on-write, Week 9)
pthread_create() CLONE_VM, CLONE_FILES, CLONE_FS, CLONE_SIGHAND, CLONE_THREAD Address space, files, handlers
Container's first process CLONE_NEWPID, CLONE_NEWNS, CLONE_NEWNET, ... Nothing, plus new namespaces

Each task has a unique thread ID (gettid()); tasks in one thread group share a thread group ID, which is what getpid() returns. Process 1 (init, normally systemd) adopts orphans and reaps zombies. In a shell, ls /proc/self/task lists the tasks of a process, one per thread.

Scheduling: CFS and EEVDF

Linux checks scheduling classes in order: stop, deadline (SCHED_DEADLINE), real-time (SCHED_FIFO, SCHED_RR), the fair class for ordinary processes, then idle. Each CPU has its own run queue, with periodic load balancing.

The fair class was the Completely Fair Scheduler (CFS), Linux 2.6.23 (2007). With n runnable tasks each should ideally get 1/n of the CPU. Since a CPU runs one task at a time, CFS tracks how far each task has fallen behind.

Virtual runtime (vruntime)

vruntime is the CPU time a task has used, scaled by its weight: vruntime += delta × 1024 / weight, where delta is the real time just run. The weight comes from the nice value: 1024 for nice 0, about 1.25 times less per nice step up (nice 5 is 335). A heavier task's vruntime grows more slowly, so it is picked more often.

CFS keeps runnable tasks in a red-black tree ordered by vruntime and runs the leftmost, the task that has received the least scaled service, at O(log n) per operation. In the long run all vruntimes advance equally, so share = weight / total weight. The same weights drive cpu.weight for cgroups, which divide the CPU between groups first and tasks second. Since Linux 6.6 (2023) the fair class uses EEVDF (Earliest Eligible Virtual Deadline First, a 1995 algorithm): each task has a lag and a virtual deadline, and the scheduler picks the eligible task with the earliest deadline, so a task asking for a short slice gets low latency without heuristics. Weighted sharing is unchanged. Part 4 of the lab simulates the rule.

Memory management

Linux uses demand paging with 4-level page tables (47 bits, 128 TiB, for user space) and 4 KiB pages, plus optional huge pages. The buddy allocator hands out frames in power-of-two blocks; slab caches serve small kernel objects. Faults are resolved from the page cache, swap or a zero page; fork uses copy-on-write. When free memory drops below watermarks, kswapd reclaims pages from LRU lists, writing dirty ones back first (Week 10). By default Linux overcommits: malloc can succeed beyond RAM plus swap because many pages are never touched. If memory truly runs out, the OOM killer picks a victim by score; inside a cgroup with memory.max only that group is a candidate.

The VFS

As in Week 13, the VFS gives every file system the same objects (superblock, inode, dentry, file) and operation tables: ext4, XFS, NFS, tmpfs, overlayfs and the pseudo file systems /proc and /sys all plug in. The pseudo file systems matter here: namespaces, cgroups and task lists are read and controlled by reading and writing files, so a shell script is a full administration tool, as the lab shows.

Case study: Windows

Windows NT (designed from 1988 under Dave Cutler, shipped 1993) is the ancestor of all current Windows. It is a hybrid kernel: most services run in kernel mode as in a monolithic kernel, but are organised as layered components with defined interfaces.

The executive and objects

Applications call the Win32 API, which wraps the native Nt* functions in ntdll.dll that issue the system call. The executive holds the major managers of Figure 15.4; below it the small kernel does low-level scheduling and interrupt dispatch and the HAL hides hardware differences.

Windows is object-based. Processes, threads, files, events, mutexes, semaphores, sections (memory-mapped files) and registry keys are kernel objects managed by the Object Manager, each with a type, a reference count and a security descriptor holding an ACL. User code holds a handle, an index into a per-process handle table whose entry records the object and the rights granted at open time. The ACL is checked once, when the handle is created; in the vocabulary of Week 14 the descriptor is an ACL and the handle a capability, as with Unix permission bits and file descriptors. CreateProcess builds the address space and loads an image in one call, instead of fork plus exec.

Scheduling

The scheduler is priority-based and preemptive with 32 levels, and its unit is the thread. Levels 16 to 31 are real-time (fixed priorities, not hard real time), 1 to 15 are variable and used by ordinary programs. It always runs a ready thread of the highest priority; equal priorities share the CPU round-robin in quanta. Normal applications start at base priority 8 and get dynamic boosts, decaying one level per quantum, for example after I/O or a window event, and the foreground application gets a longer quantum. A thread ready but starved for about four seconds is boosted to 15 briefly, much like aging in Week 4.

Memory manager

The Memory Manager provides demand-paged virtual memory with 4 KiB pages and optional large pages. A tree of virtual address descriptors (VADs) describes each address space, and each process has a working set, its resident pages, with minimum and maximum sizes. Under pressure the manager trims working sets: trimmed pages go to the standby list (clean; reclaimed cheaply by a soft fault) or the modified list (dirty; written to the paging file). A section object represents a mapped file or shared memory, the analogue of mmap, and underlies image loading and copy-on-write.

NTFS at an overview level

NTFS divides the volume into clusters (commonly 4 KiB) and keeps everything in a Master File Table (MFT): one record, typically 1,024 bytes, per file or directory. A record is a list of attributes: standard information (timestamps), file name, security descriptor and data. A small file's data is resident inside the record; a larger file is non-resident and the record holds a compact list of runs (start cluster, length), so a contiguous huge file needs one run and a fragmented one many. Directories are B+ trees of names, and even metadata are files ($MFT, $Bitmap, $LogFile). For crash safety NTFS write-ahead logs metadata in $LogFile (Week 13); user data are not logged. It also offers per-file ACLs, alternate data streams and Volume Shadow Copy snapshots.

Exercises

Exercise 15.1warm-up

Sensitive versus privileged

(a) Define sensitive and privileged instructions. (b) State the Popek and Goldberg condition for trap-and-emulate. (c) On the original x86, popf in user mode silently ignores interrupt-flag changes. Why does this break trap-and-emulate, and what are three fixes?

Show solution

(a) Sensitive: reads or changes machine configuration or behaves differently depending on it. Privileged: traps in user mode.

(b) Every sensitive instruction must be privileged, so each one the VMM must intercept does trap.

(c) popf is sensitive but not privileged, so nothing traps, the VMM never sees the request and the guest's virtual interrupt flag is wrong. Fixes: binary translation, paravirtualization (hypercalls) or hardware virtualization (VM exit).

Exercise 15.2core

Cost of trapping

A guest executes 1,000,000 instructions. Each ordinary one takes 1 ns. 0.5% are privileged and each trap-and-emulate costs 2 µs in total. (a) How long does the guest take and what is the slowdown? (b) With binary translation each of those instructions becomes an inline sequence of 20 ns. What are the time and slowdown?

Show solution

(a) Privileged: 0.005 × 1,000,000 = 5,000. Ordinary: 995,000 × 1 ns = 0.995 ms. Traps: 5,000 × 2 µs = 10 ms. Total 10.995 ms against a native 1 ms: slowdown 10.995, about 11 times.

(b) 5,000 × 20 ns = 0.1 ms. Total 0.995 + 0.1 = 1.095 ms, slowdown 1.095 (about 9.5% overhead).

Exercise 15.3challenging

Nested page walks

A TLB miss under nested paging walks a guest table of n levels and a nested table of m levels. (a) Show that translating one address, not counting the final data access, takes (n + 1)(m + 1) − 1 references, and evaluate for n = m = 4. (b) Evaluate for n = m = 5. (c) Evaluate for n = 4 and a nested table of 2 MiB pages, so m = 3. (d) Why do VMs depend more on the TLB hit ratio than native programs?

Show solution

(a) Each of the n guest levels reads an entry at a GPA: m nested references plus 1 to read it, so n(m + 1). The final data page's GPA needs m more. Total n(m + 1) + m = (n + 1)(m + 1) − 1. For n = m = 4: 24 (native: 4).

(b) 6 × 6 − 1 = 35. (c) 5 × 4 − 1 = 19.

(d) A miss costs up to six times more than native, so the same miss ratio hurts more; a TLB hit avoids the walk entirely.

Exercise 15.4core

Namespace and ID mappings

A user namespace has the map 0 100000 65536 in /proc/self/uid_map (inside start, outside start, length). (a) Which host UID is container UID 1000? (b) Which container UID is host UID 100500? (c) How does a file owned by host UID 70000 appear inside? (d) A process is PID 1 in its container and PID 4711 on the host. What do kill -9 1 inside and kill -9 4711 on the host do?

Show solution

(a) 100000 + 1000 = 101000. (b) 100500 − 100000 = 500. (c) UID 70000 is outside the mapped range 100000 to 165535, so it shows as the overflow ID 65534 (nobody).

(d) Inside, signals to the namespace's init are ignored unless it has a handler, so nothing happens. From the host, kill -9 4711 kills init, and the kernel then kills the rest of that PID namespace.

Exercise 15.5core

cpu.max, cpu.weight and throttling

(a) What does cpu.max containing 150000 100000 mean? (b) A group with that limit runs 4 always-busy threads on a machine with at least 4 idle cores. How far into each period does it run before throttling, how long is it throttled, and how much CPU does each thread get in 10 s of wall time? (c) Two sibling groups with cpu.weight 200 and 100 both want one whole CPU, with no cpu.max. What shares do they get?

Show solution

(a) A quota of 150,000 µs per 100,000 µs period: 1.5 CPUs.

(b) Four threads use 4 ms of CPU per ms of wall time, so the 150 ms quota lasts 150 / 4 = 37.5 ms and the group is throttled for the remaining 62.5 ms. In 10 s there are 100 periods of 150 ms: 15 CPU-seconds, so 15 / 4 = 3.75 s per thread.

(c) 200 / 300 = 66.7% and 100 / 300 = 33.3%. Weights act only under contention; cpu.max limits even an idle machine.

Exercise 15.6core

CFS shares and vruntime

Tasks A and B (nice 0, weight 1024) and C (nice 5, weight 335) are runnable on one CPU. (a) What long-run fraction of the CPU does each get? (b) How fast does each task's vruntime grow per ms of CPU time? (c) Over 100 ms, how much CPU does each get and by how much does each vruntime grow?

Show solution

(a) Total weight 1024 + 1024 + 335 = 2383. A and B: 1024 / 2383 = 42.97% each; C: 335 / 2383 = 14.06%.

(b) 1024 / weight per ms: 1.000 for A and B, 1024 / 335 = 3.057 for C.

(c) A and B get 42.97 ms each, C gets 14.06 ms. A and B's vruntime grows by 42.97; C's by 14.06 × 3.057 = 42.98, equal up to rounding. Equal vruntime growth is exactly what turns weights into shares.

Exercise 15.7core

NTFS clusters and Windows priorities

(a) A 10,000-byte file sits on a volume with 4,096-byte clusters. How many clusters and how many bytes of slack? (b) A contiguous 1 GiB file is on the same volume. How many clusters, and how many runs does its data attribute need? (c) Threads T1 (priority 10), T2 (priority 8) and T3 (priority 10) are ready on one CPU. Who runs, and what could change that?

Show solution

(a) ceil(10,000 / 4,096) = 3 clusters, which is 12,288 bytes, leaving 12,288 − 10,000 = 2,288 bytes of slack.

(b) 1 GiB = 1,073,741,824 bytes; divided by 4,096 that is 262,144 clusters. Contiguous, it is one run (start cluster, length 262,144).

(c) T1 and T3 share the CPU round-robin (highest ready level); T2 waits until they block or its starvation boost (about four seconds) lifts it to 15.

Part 2: clone() with new namespaces (needs root)

The same effect through the system call. Save as clonens.c, run sudo ./clonens.

#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

static char stack[1024 * 1024];

static int child(void *arg) {
    (void)arg;
    sethostname("sandbox", 7);
    char host[64];
    gethostname(host, sizeof host);
    printf("child : pid=%d ppid=%d hostname=%s\n", getpid(), getppid(), host);
    fflush(stdout);                 /* clone() children skip the stdio flush at exit */
    return 0;
}

int main(void) {
    char host[64];
    gethostname(host, sizeof host);
    printf("parent: pid=%d hostname=%s\n", getpid(), host);
    fflush(stdout);                 /* do not copy buffered text into the child */
    pid_t p = clone(child, stack + sizeof stack,   /* stack grows down: pass the top */
                    CLONE_NEWPID | CLONE_NEWUTS | SIGCHLD, NULL);
    if (p < 0) { perror("clone (needs root)"); return 1; }
    printf("parent: child is pid %d in my namespace\n", p);
    waitpid(p, NULL, 0);
    gethostname(host, sizeof host);
    printf("parent: hostname still %s\n", host);
    return 0;
}

Captured output (PIDs vary):

parent: pid=268 hostname=vm
child : pid=1 ppid=0 hostname=sandbox
parent: child is pid 270 in my namespace
parent: hostname still vm

The child is PID 1 with parent 0 (its parent lies outside its namespace) yet the parent knows it as 270.

Part 3: a cgroup v2 limit (needs root; typical output)

Limit a group to half a CPU, 64 MiB and 64 tasks. stat -fc %T /sys/fs/cgroup should print cgroup2fs.

sudo sh -c '
cd /sys/fs/cgroup
echo "+cpu +memory +pids" > cgroup.subtree_control
mkdir lab && cd lab
echo "50000 100000" > cpu.max        # 50 ms per 100 ms = half a CPU
echo 67108864 > memory.max           # 64 MiB
echo 0 > memory.swap.max
echo 64 > pids.max                   # at most 64 tasks
echo $$ > cgroup.procs               # move this shell into the group
timeout 5 sh -c "while :; do :; done"
grep -E "usage_usec|nr_periods|nr_throttled" cpu.stat
python3 -c "x = b\"x\" * (100 * 1024 * 1024)"; echo "exit status: $?"
grep -E "^(max|oom_kill)" memory.events
'
sudo rmdir /sys/fs/cgroup/lab        # the group is empty once the shell exits

usage_usec 2501334
nr_periods 50
nr_throttled 49
Killed
exit status: 137
max 27
oom_kill 1

Five seconds hold about 50 periods; the loop got 50 ms of each, so it used about 2.5 s of CPU (usage_usec, in microseconds) and was throttled nearly every period. The 100 MiB allocation exceeds memory.max, so with swap off the OOM killer ended it (exit status 128 + 9 = 137).

Part 4: a CFS simulator

Save as cfs.c. It applies the vruntime rule to a nice 0 task (weight 1024) and a nice 5 task (weight 335) for 1,000 slices of 1 ms.

#include <stdio.h>

struct task { const char *name; int nice; double weight, vruntime, cpu; };

int main(void) {
    struct task t[] = { {"A", 0, 1024, 0, 0}, {"B", 5, 335, 0, 0} };
    const int n = 2;
    for (int step = 1; step <= 1000; step++) {
        int best = 0;                               /* smallest vruntime wins */
        for (int i = 1; i < n; i++)
            if (t[i].vruntime < t[best].vruntime) best = i;
        t[best].cpu += 1.0;                         /* run one 1 ms slice */
        t[best].vruntime += 1.0 * 1024.0 / t[best].weight;
        if (step <= 8)
            printf("step %d: ran %s  vruntime A=%.2f B=%.2f\n", step,
                   t[best].name, t[0].vruntime, t[1].vruntime);
    }
    double total = t[0].cpu + t[1].cpu;
    for (int i = 0; i < n; i++)
        printf("%s nice %d: %6.1f ms  (%.1f%%)\n", t[i].name, t[i].nice,
               t[i].cpu, 100 * t[i].cpu / total);
    printf("ideal share of A = 1024/(1024+335) = %.1f%%\n", 100 * 1024.0 / (1024 + 335));
    return 0;
}

Captured output:

step 1: ran A  vruntime A=1.00 B=0.00
step 2: ran B  vruntime A=1.00 B=3.06
step 3: ran A  vruntime A=2.00 B=3.06
step 4: ran A  vruntime A=3.00 B=3.06
step 5: ran A  vruntime A=4.00 B=3.06
step 6: ran B  vruntime A=4.00 B=6.11
step 7: ran A  vruntime A=5.00 B=6.11
step 8: ran A  vruntime A=6.00 B=6.11
A nice 0:  753.0 ms  (75.3%)
B nice 5:  247.0 ms  (24.7%)
ideal share of A = 1024/(1024+335) = 75.3%

B's vruntime jumps 3.06 per run, so A runs about three times per run of B and the split matches the weights. On a real machine pin two busy loops to one CPU, taskset -c 0 nice -n 5 sh -c 'while :; do :; done' & and one at nice 0, and read %CPU in top.

Extensions

  1. Add a third task at nice −5 (weight 3121) to cfs.c and compare simulated shares with weight / total weight.
  2. In unshare --mount, mount a tmpfs and check with findmnt from another terminal that the host cannot see it.
  3. In a cgroup with pids.max 20, run a loop of sleep 100 & and watch pids.events. Never do this outside a limited group.

Common mistakes and debugging tips

Symptom Likely cause What to do
unshare failed: Operation not permitted No CAP_SYS_ADMIN Use sudo, or add --user --map-root-user
ps in a new PID namespace still lists host processes /proc not remounted Use --mount-proc (and --fork)
cpu.max or memory.max missing or unwritable Controller not enabled in the parent, or cgroup v1 Write +cpu +memory to the parent's cgroup.subtree_control; check stat -fc %T /sys/fs/cgroup
A container is assumed as isolated as a VM The kernel is shared Add seccomp, drop capabilities, run rootless or use a micro-VM
Guest very slow in a VM No hardware virtualization, or too many VM exits Check /dev/kvm and the vmx or svm flag in /proc/cpuinfo; use virtio

Key takeaways

Key takeaways

  • A hypervisor gives each guest OS a virtual machine; type 1 runs on hardware, type 2 on a host OS. Most guest instructions run directly and only sensitive ones involve the VMM.
  • Trap-and-emulate needs every sensitive instruction to be privileged. Original x86 failed, so VMware used binary translation, Xen paravirtualization and VT-x and AMD-V finally added VM exits in hardware.
  • Nested paging lets the guest manage its page tables, but a TLB miss costs (n + 1)(m + 1) − 1 references, 24 for 4-level tables.
  • Linux containers are ordinary processes inside namespaces (what they see) and cgroups (what they may use), sharing the host kernel: fast and dense, but less isolated than VMs.
  • Linux treats processes and threads as tasks made by clone; CFS (now EEVDF) shares CPU by weight using vruntime, and cgroups reuse the weights.
  • Windows builds an executive of managers around typed objects reached through handles, schedules 32 priority levels with boosts, and keeps NTFS metadata in the MFT with a metadata journal.
