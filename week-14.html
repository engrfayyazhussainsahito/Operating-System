Protection and Security

How an operating system decides who may do what: domains and rings, the access matrix, ACLs and capabilities, Unix permissions, setuid and umask, least privilege, authentication, memory-safety defenses, seccomp, the confused deputy and TOCTOU races.

What you will be able to do

By the end of this week you will be able to:

  • Distinguish protection (mechanism) from security (defense against adversaries) and describe a protection domain
  • Read an access matrix and derive both the ACL of an object and the capability list of a subject
  • Convert between octal and symbolic Unix modes and compute the mode a new file gets under a given umask
  • Trace the kernel's permission check, including directory search permission and the setuid, setgid and sticky bits
  • Apply least privilege by dropping setuid privilege permanently and explain what capabilities and seccomp add
  • Explain what stack canaries, NX and ASLR each prevent and why none replaces fixing the bug
  • Identify a confused deputy and a TOCTOU race in a code fragment and repair it

In Week 13 we saw that device drivers and the kernel I/O path are the largest and buggiest part of an operating system, and that the system call boundary then becomes a security boundary. This week we study that boundary. Every earlier chapter assumed processes cooperate. Here we assume some do not: a user may try to read another user's files, a downloaded program may be malicious, and a network service may be fed hostile input.

We separate two ideas. Protection is the set of mechanisms that control which processes and users may access which resources. Security is the wider goal of defending a system against deliberate misuse, which needs protection plus authentication, careful design and defenses against bugs. In Week 15 the same ideas return as virtual machines and containers, which are protection domains drawn around whole programs.

Protection domains and privilege rings

Think of a hotel: a guest card opens your room and the gym, a housekeeper's card opens one floor, and nobody carries the master key all day. An operating system gives each activity exactly the access it needs.

Protection domain

A protection domain specifies a set of objects (files, memory pages, devices, sockets) and, for each, the operations (rights) a process executing in that domain may perform. On Unix the domain of a process is essentially its user ID, group IDs and capabilities; the kernel runs in a more powerful domain.

The most basic split is enforced by hardware: in user mode privileged instructions (changing page tables, disabling interrupts, device I/O) trap; in kernel mode everything is allowed (Week 1). x86 numbers its levels as rings 0 to 3, ring 0 being most privileged. Linux and Windows use ring 0 for the kernel and ring 3 for applications. ARM calls them exception levels, EL0 for applications up to EL3 for firmware, and a hypervisor (Week 15) adds a level below the guest kernel.

Rings come from Multics

Rings come from Multics (1960s), which had eight in hardware; Unix simplified this to two levels plus user IDs. The design principles below come from a 1975 paper by Saltzer and Schroeder about Multics.

The access matrix

To reason about protection independently of any system we use a model, the access matrix. Rows are subjects (users, processes or domains), columns are objects, and the entry at row s, column o is the set of rights s holds over o.

A real matrix is huge and almost empty, so nobody stores it as a table. There are two ways to keep only the non-empty cells.

  • Access control list (ACL). Store each column with the object. The ACL of notes.txt is "alice: read, write; bob: read". On open, the kernel looks up the caller's identity in the list. Unix permission bits are a compressed three-entry ACL (owner, group, others); POSIX ACLs and NTFS allow arbitrary lists.
  • Capability list. Store each row with the subject. A capability is an unforgeable token naming an object and the rights its holder has. The kernel protects the token so user code cannot forge it. A Unix file descriptor is a capability in miniature: after open succeeds, read(fd, ...) needs no further identity check, and the descriptor can be passed to another process over a Unix-domain socket.

Guest list or key card

An ACL is the bouncer with the guest list: he checks who you are every time, and striking a name works at once. A capability is a key card: whoever holds it gets in with no name check, which makes it easy to lend, but once copies are out you cannot easily take them back.

Question ACL (column) Capability (row)
Who can access this object? Read one list Hard: search all subjects
What can this subject access? Hard: search all objects Read one list
Revoke one user's access Easy: delete one entry Hard: copies may be scattered
Delegate a right to a helper Awkward: edit the ACL Natural: pass the token
Check is made At open, by identity At use, by possession

Modern systems mix both: Linux checks permission bits at open (an ACL decision) and returns a descriptor (a capability). seL4, Capsicum on FreeBSD and Fuchsia are capability-based throughout. Silberschatz Ch. 17 adds rights to copy rights and switch domains; the lesson is that who may change the matrix is itself a right to protect.

Unix permissions

Every file and directory has an owner (user ID), a group (group ID) and a 12-bit mode. The low nine bits are three triples of read, write and execute for the owner (u), the group (g) and everyone else (other, o). The top three bits are the special bits.

Octal and symbolic modes

Each triple is written as a number: read = 4, write = 2, execute = 1, added. So rwx = 4 + 2 + 1 = 7, r-x = 5, r-- = 4, and rwxr-xr-- is octal 754. The special bits form a fourth, leading digit: setuid = 4, setgid = 2, sticky = 1, so 4755 is setuid plus rwxr-xr-x.

chmod accepts octal (chmod 640 f) or symbolic modes: who (u, g, o, a), an operator (+ add, - remove, = set exactly) and permissions (r, w, x, s, t). Thus chmod u=rw,g=r,o= f gives 640, chmod g+w f adds group write and chmod u+s prog sets setuid. ls -l writes special bits over the execute position: s for setuid or setgid with execute, S without it (usually a mistake), t for sticky with other-execute, T without.

What the bits mean

For a file the meaning is obvious. For a directory it differs, and students often get it wrong.

Bit On a file On a directory
r Read contents List the names inside (ls)
w Modify contents Create, delete or rename entries (also needs x)
x Execute as a program Search: pass through to reach a name inside

Deleting a file needs write permission on the directory, not on the file. Reaching /home/ann/data/report.txt needs x on /, home, ann and data, so one restrictive directory hides everything below it.

The permission check

On open, the kernel compares the process's effective user ID, effective group ID and supplementary groups with the file's owner and group. Only the first matching class is used.

Permission bits are not additive

Because only the first matching class counts, a file with mode 0460 denies write to its own owner even though the group class allows it: the owner matches the owner class (r--) and the check stops. Likewise mode 0604 denies a group member who would be allowed as "other".

setuid, setgid and the sticky bit

Normally a process runs with the identity of whoever started it. But changing your password needs writing the protected password database. Dennis Ritchie's solution was setuid: when a file with bit 4000 is executed, the new process's effective user ID becomes the file's owner while its real user ID stays the caller's. /usr/bin/passwd is owned by root and setuid, so it edits /etc/shadow (mode 0640) on behalf of an ordinary user. Setgid (2000) does the same for the group.

On a directory, setgid makes new files inherit the directory's group, which is how shared project directories work. The sticky bit (1000) means that although many users may write in the directory, only a file's owner, the directory's owner or root may delete or rename it. That is why /tmp is mode 1777 (drwxrwxrwt).

A setuid program is a deliberate hole in the wall between domains, so it must be small and careful. Linux ignores setuid on scripts (a race between kernel and interpreter), and a nosuid mount ignores it entirely. Each process holds three IDs, the real, effective and saved set-user-ID, so that a privileged program can drop its power and later regain it.

umask

Programs create files asking for a mode, typically 0666 for files and 0777 for directories. The process's umask removes bits from every request: mode_given = mode_requested AND NOT umask. It is inherited from the parent, so the shell's setting applies to everything you run.

Computing with umask

With umask 022, a request for 0666 becomes 666 AND NOT 022 = 644 (rw-r--r--) and 0777 becomes 755. With umask 077 the results are 600 and 700, private to the owner. A umask can only remove permissions, never add them, and it does not affect a later chmod.

Least privilege

The principle of least privilege says every program and user should run with the minimum authority needed, for the minimum time. Bugs are inevitable, and the authority a buggy program holds is the authority an attacker inherits. A web server that needs only to bind port 80 and read files should not stay root; an image converter should not open network connections. Saltzer and Schroeder's other principles are the vocabulary of the field.

Principle In practice
Least privilege Run services as dedicated unprivileged users; drop root after binding the port
Fail-safe defaults Deny unless explicitly permitted
Complete mediation Check every access, every time, as the system call gate does
Separation of privilege Require more than one condition, such as password plus second factor

Dropping privilege and Linux capabilities

A setuid-root program should do its privileged work first and then give up root permanently. The call must set all three user IDs: if only the effective ID changes, the saved ID still holds root and the process can regain it, a classic bug. Group IDs are dropped first, because an unprivileged process may no longer be allowed to change them. Part 3 of the lab does this and verifies that regaining root fails.

Linux also divides root's all-or-nothing power into about forty capabilities, such as CAP_NET_BIND_SERVICE (bind ports below 1024), CAP_KILL and CAP_DAC_OVERRIDE (bypass file permission checks). A program can be given only the one it needs (setcap cap_net_bind_service=+ep prog), so compromising it does not mean full root. These split-up root privileges are not the object capabilities of the access matrix; the name is unfortunate.

Authentication basics

Protection checks identities; authentication decides who you really are. Evidence comes in three families: something you know (a password), have (a phone, a hardware token) or are (a fingerprint). Multi-factor authentication combines different families so that stealing one does not suffice.

For passwords the storage rule is: never store the password, store a salted, deliberately slow hash of it. Early Unix kept hashes in the world-readable /etc/passwd; modern systems use /etc/shadow, readable only by root and the shadow group. A salt is a random value stored beside the hash and mixed in, so identical passwords give different hashes and one precomputed table cannot attack the whole file. A slow hash (bcrypt, scrypt, argon2, yescrypt) has a tunable work factor that makes each guess expensive. Login hashes your input with the stored salt and compares. Linux delegates the decision to PAM (Pluggable Authentication Modules), a configurable stack used by login, sudo and ssh.

Why slow matters

An 8-letter lowercase password has 26⁸ = 208,827,064,576 (about 2.1 × 10¹¹) possibilities. At 10⁹ guesses per second against a fast hash that takes about 209 seconds; if a slow hash limits the attacker to 10³ per second it takes 2.09 × 10⁸ seconds, about 6.6 years.

Memory-safety defenses at the concept level

Most serious break-ins exploit a memory-safety bug: a program that reads or writes outside the memory it was given, such as copying 100 bytes into a 32-byte array on the stack. Input data can then overwrite nearby control data such as a saved return address, and redirect the program. The best fix is to remove the bug, with bounds-checked code or a memory-safe language, but the OS and compiler add layers that make the remaining bugs harder to exploit. Each layer blocks one step.

  • Stack canaries. The compiler (-fstack-protector-strong in GCC) places a random value, the canary, between a function's local arrays and its saved return address, and checks it just before returning. A contiguous overflow that reached the return address must have changed the canary, so the program aborts instead of returning. On x86-64 glibc the 8-byte canary is random per process with a zero low byte so string functions stop at it. It does nothing against writes that skip the canary or leak it.
  • NX (non-executable memory), also called DEP or W^X. Page tables carry an execute-disable bit. Stack and heap are writable but not executable, and code is executable but not writable, so injected data cannot simply run as instructions. It does not stop reuse of code already in the program.
  • ASLR (address space layout randomization). The kernel places the stack, heap, libraries and (for position-independent executables, PIE) the program itself at random addresses each run, so an attacker must guess an address and usually crashes the program. It is probabilistic: one information leak of a pointer reveals the layout, and 32-bit systems have too few random bits to resist guessing.

Mitigations are not fixes

Canaries, NX and ASLR raise the attacker's cost; they do not make a buggy program correct. Hardware shadow stacks and control-flow integrity close more gaps, and memory-safe languages remove whole bug classes. Mitigations are seat belts, not permission to drive badly. Exercise 7 puts numbers on the guessing odds.

Sandboxing with seccomp

Least privilege applies to system calls too. An image converter needs read, write, mmap and exit; it has no reason to call socket, execve or ptrace, and each unneeded call is kernel attack surface. seccomp lets a process restrict its own system calls, irrevocably.

The original strict mode allowed only read, write, _exit and sigreturn. The practical interface is seccomp-bpf: the process installs a small program in the Berkeley Packet Filter instruction set that the kernel runs on every system call. It inspects a struct seccomp_data (call number, architecture, six arguments) and returns a verdict: allow, fail with an errno, kill, trap or log. Filters are inherited by children and can only be tightened. An unprivileged process must first set no_new_privs, which promises that it and its descendants never gain privilege through execve, so a setuid program cannot be used to escape. Browsers, container runtimes and systemd services use seccomp; Part 5 of the lab writes a filter by hand.

Allow-lists beat deny-lists

The lab filter denies two calls and allows the rest, which is easy to read. Real sandboxes allow a short list, deny everything else and check the architecture field so a 32-bit call number is not misread as a 64-bit one: fail-safe defaults for system calls.

Two classic design flaws

The confused deputy

In 1988 Norm Hardy described a compiler service that could write to a protected system directory, where it kept a statistics file. A user could ask it to compile a program and name the output file. If the user named the statistics file, the compiler overwrote it using its own authority, which the user lacked. The compiler is the confused deputy: it holds authority from one party (the system) and is tricked into using it for another (the user), because a request names an object while the authority comes from somewhere else.

The same shape recurs in a setuid program opening a user-supplied path as root, a web application fetching an internal URL for an outside visitor, and cross-site request forgery. The root cause is ambient authority: rights come from who the program is, not from what it was handed for this request. In an ACL system the deputy must act with the caller's authority for caller-named objects, for example by temporarily setting its effective user ID to the caller's real ID before opening the file. In a capability system the caller passes a descriptor it opened itself, and the deputy cannot name anything the caller could not.

TOCTOU races

A time-of-check to time-of-use (TOCTOU) race arises when a program checks a condition and later acts as if it still held, but another process changed the world in between. The classic version checks a path with access() and then opens the same path. A path is only a name, and names can be rebound (for example by replacing a file with a symbolic link) in the gap, so the object opened may differ from the one checked. Each system call is atomic, but a sequence of two is not.

The cure is to remove the gap, not shrink it. Act and let the kernel check, with the identity of the person you serve. Where a check is unavoidable, do one lookup (open) and base every later decision on the descriptor (fstat(fd)), which refers to one object whatever happens to its name. Use O_NOFOLLOW to refuse symbolic links, O_CREAT | O_EXCL for files that must not exist, mkstemp instead of predictable /tmp names, and openat relative to a directory descriptor. Part 4 of the lab shows the pattern.

Exercises

Exercise 14.1warm-up

Octal and symbolic conversions

(a) Write 0754 as an ls -l string. (b) Write rw-r----- as octal. (c) Give the string and octal mode of a setuid program with owner rwx and group and other r-x. (d) A file has mode 644. What is its mode after chmod g+w,o-r file? (e) Which symbolic chmod gives exactly 750?

Show solution

(a) 7 = rwx, 5 = r-x, 4 = r--, so rwxr-xr--. (b) rw- = 6, r-- = 4, --- = 0, so 640. (c) 7, 5, 5 plus setuid 4 as the leading digit: 4755, shown rwsr-xr-x. (d) Group becomes 4 + 2 = 6 and other becomes 4 − 4 = 0, so 660. (e) chmod u=rwx,g=rx,o= file.

Exercise 14.2core

umask arithmetic

A program creates a file with open(..., 0666) and a directory with mkdir(..., 0777). Compute the resulting modes for umask (a) 022, (b) 002, (c) 077, (d) 0137. For (d), is the directory usable by its owner?

Show solution

Use mode AND NOT umask, digit by digit.

(a) File 644, directory 755. (b) File 664, directory 775. (c) File 600, directory 700.

(d) 0137 is owner 001, group 011, other 111 in binary. File: owner 6 AND NOT 1 = 6; group 6 AND NOT 3 = 4; other 6 AND NOT 7 = 0, so 640. Directory: owner 7 AND NOT 1 = 6; group 7 AND NOT 3 = 4; other 0, so 640. A directory without the search (x) bit cannot be entered even by its owner, so it is practically unusable. A umask suited to files can break directories.

Exercise 14.3core

Tracing the permission check

plan.txt is owned by alice, group staff, mode 0460. Alice and bob are in staff; carol is not. For alice, bob, carol and root, say whether opening for reading and for writing succeeds. Then repeat for bob if the mode were 0604.

Show solution

Mode 0460 is owner r--, group rw-, other ---.

  • alice matches the owner class, which has only read: read succeeds, write is denied even though her group could write.
  • bob is in staff, so the group class rw- applies: both succeed.
  • carol falls to other, ---: both denied.
  • root bypasses read and write checks: both succeed.

Mode 0604 is owner rw-, group ---, other r--. Bob matches the group class and the check stops, so both are denied, although carol could read through the other class.

Exercise 14.4core

ACL or capability storage

A system has 100 users and 1,000 files, and each user can access exactly 10 files. (a) How many cells does the full matrix have and how many are non-empty? (b) How many ACL entries exist in total, how many per file on average, and how long is each capability list? (c) Which representation answers "who can read file F?" cheaply? (d) Compare the work of removing a departed user's access in each.

Show solution

(a) 100 × 1,000 = 100,000 cells; 100 × 10 = 1,000 are non-empty, which is 1%.

(b) 1,000 ACL entries in total, 1,000 / 1,000 = 1 per file on average; each capability list has 10 entries.

(c) ACLs (one list per file); capability lists answer "what can alice read?" instead.

(d) ACLs: delete her entry from each of her 10 files (finding them may need a scan of all 1,000 ACLs unless indexed). Capabilities: delete her 10 tokens, but copies she passed on stay valid unless the system supports revocation, for example an indirection object the owner can invalidate.

Exercise 14.5challenging

A setuid program and the confused deputy

A setuid-root program savecopy SRC copies the file the user names into /var/backups/, where a backup group can read it. It calls open(SRC, O_RDONLY) as root. (a) What attack does this allow, and why is the program a confused deputy? (b) Give two repairs, one using identity and one using descriptors.

Show solution

(a) The user can pass /etc/shadow. The open succeeds because the effective ID is root, not because the user may read the file. The program applies its own authority to an object the user chose.

(b) Identity: call seteuid(getuid()) before open, so the kernel decides on the user's authority, and restore privilege only for writing into /var/backups. Descriptors: an unprivileged front end opens SRC itself and passes the descriptor to the privileged helper over a Unix-domain socket; the helper can never name a file the user could not open. The privileged part should also drop whatever privilege it no longer needs.

Exercise 14.6challenging

Repair a TOCTOU race

This setuid program should append a line only if the real user may write the file:

if (access(path, W_OK) == 0) {                  /* check, real uid */
    int fd = open(path, O_WRONLY | O_APPEND);   /* use, effective uid */
    write(fd, line, len);
}

(a) Describe the window and what an attacker could try, without attack code. (b) Give a repair that removes the race. (c) Why does shortening the gap not fix it?

Show solution

(a) Two separate name lookups occur. A local user who controls the directory can swap the name from their own file to a link to a protected file in between. access examined the first object with the real user's rights; open opens the second with root's, so a file the user may not modify is appended to.

(b) Let the kernel decide at use time with the right identity: seteuid(getuid()); fd = open(path, O_WRONLY | O_APPEND | O_NOFOLLOW); seteuid(0);. One lookup, one decision, made with the user's authority.

(c) An attacker can retry, so a small window is only less reliable, not safe. Make check and use one operation.

Exercise 14.7core

Counting the odds of mitigations

(a) A 32-bit program has 8 bits of library randomness (256 equally likely placements). A server restarts a crashed worker with the same layout, and the attacker never repeats a guess. What is the expected number of guesses and the worst case? (b) What if the layout is re-randomized on each restart? (c) A 64-bit process has 28 bits of mmap randomness and an attacker makes 1,000 independent guesses per second against fresh layouts. What is the expected time? (d) The 8-byte canary has a zero low byte. How many random values protect it? (e) Why can one leaked pointer undo ASLR?

Show solution

(a) Without repeats the target is equally likely at attempts 1 to 256: expected (256 + 1) / 2 = 128.5, worst case 256.

(b) Each guess succeeds with probability 1/256 independently, so the expectation is 256 (geometric distribution).

(c) 2²⁸ = 268,435,456 layouts, so about 268,435,456 expected guesses; at 1,000 per second that is about 268,435 s, roughly 74.6 hours or 3.1 days.

(d) 7 random bytes = 56 bits, so 2⁵⁶ = 72,057,594,037,927,936 (about 7.2 × 10¹⁶) values.

(e) ASLR moves a whole region by one random offset, and distances inside the region are fixed, so one leaked address reveals all others in it.

Part 1: inspect permission bits

Save as perm_inspect.c. It decodes a mode into the ls -l string and octal digits and flags the special bits.

#include <stdio.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <pwd.h>
#include <grp.h>

/* Build the 10-character string used by ls -l, e.g. "-rwsr-xr-x". */
static void mode_string(mode_t m, char out[11]) {
    out[0] = S_ISDIR(m) ? 'd' : S_ISLNK(m) ? 'l' : S_ISREG(m) ? '-' : '?';
    const char *rwx = "rwxrwxrwx";
    for (int i = 0; i < 9; i++)
        out[i + 1] = (m & (0400 >> i)) ? rwx[i] : '-';
    if (m & S_ISUID) out[3] = (m & S_IXUSR) ? 's' : 'S';
    if (m & S_ISGID) out[6] = (m & S_IXGRP) ? 's' : 'S';
    if (m & S_ISVTX) out[9] = (m & S_IXOTH) ? 't' : 'T';
    out[10] = '\0';
}

int main(int argc, char **argv) {
    for (int i = 1; i < argc; i++) {
        struct stat st;
        if (lstat(argv[i], &st) != 0) { perror(argv[i]); continue; }
        char s[11];
        mode_string(st.st_mode, s);
        struct passwd *pw = getpwuid(st.st_uid);
        struct group  *gr = getgrgid(st.st_gid);
        printf("%s  %04o  %-8s %-8s  %s%s%s  %s\n", s, st.st_mode & 07777,
               pw ? pw->pw_name : "?", gr ? gr->gr_name : "?",
               (st.st_mode & S_ISUID) ? "[setuid]" : "",
               (st.st_mode & S_ISGID) ? "[setgid]" : "",
               (st.st_mode & S_ISVTX) ? "[sticky]" : "", argv[i]);
    }
    return 0;
}

Each is attack surface.

Part 2: umask

Save as umask_demo.c. It requests 0666 and 0777 under several umasks and reports what the kernel created. Run it from an empty directory (it creates and removes f.tmp and d.tmp).

#include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

static void try(mode_t mask) {
    umask(mask);
    unlink("f.tmp"); rmdir("d.tmp");
    int fd = open("f.tmp", O_CREAT | O_WRONLY, 0666);   /* request rw-rw-rw- */
    close(fd);
    mkdir("d.tmp", 0777);                               /* request rwxrwxrwx */
    struct stat f, d;
    stat("f.tmp", &f);
    stat("d.tmp", &d);
    printf("umask %03o: file asked 0666 got %04o, dir asked 0777 got %04o\n",
           mask, f.st_mode & 07777, d.st_mode & 07777);
    unlink("f.tmp"); rmdir("d.tmp");
}

int main(void) {
    try(0000);
    try(0022);
    try(0027);
    try(0077);
    return 0;
}

Part 3: dropping setuid privilege

Save as ids.c. If the effective ID is root, it drops all user and group IDs to the unprivileged nobody account (65534) and checks it cannot go back.

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>

static void show(const char *when) {
    uid_t r, e, s;
    getresuid(&r, &e, &s);
    printf("%-22s real=%u effective=%u saved=%u\n", when, r, e, s);
}

int main(void) {
    show("at start:");
    if (geteuid() == 0) {
        /* Drop privilege PERMANENTLY: set real, effective and saved IDs.
           Order matters: drop the group first, then the user. */
        if (setresgid(65534, 65534, 65534) != 0) { perror("setresgid"); exit(1); }
        if (setresuid(65534, 65534, 65534) != 0) { perror("setresuid"); exit(1); }
        show("after dropping:");
        if (setuid(0) == 0) { puts("BUG: regained root"); return 1; }
        puts("setuid(0) after drop:   refused, as it must be");
    } else {
        puts("not running with root privilege; nothing to drop");
    }
    return 0;
}

Run it normally, then make a setuid-root copy (needs root) and run that as an ordinary user. The output below came from the setuid copy run as user ID 1000.

gcc -Wall -pthread -o ids ids.c
./ids                                   # ordinary run: nothing to drop
sudo chown root:root ids && sudo chmod u+s ids
./ids                                   # as an ordinary user: setuid in action

at start:              real=1000 effective=0 saved=0
after dropping:        real=65534 effective=65534 saved=65534
setuid(0) after drop:   refused, as it must be

The first line is the signature of a setuid process: real ID is the caller, effective and saved IDs are the file owner. Now replace the setresuid line with seteuid(65534). The sandbox then printed after dropping: real=1000 effective=65534 saved=0 followed by BUG: regained root, because the saved ID still held root. That is why all three IDs must change.

Part 4: an open with no check-then-use gap

Save as safe_open.c. It does one open with O_NOFOLLOW and judges the file through the descriptor with fstat.

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

/* Open a file for reading only if it is a regular file we may read.
   There is exactly one name lookup (open); every later check uses the
   descriptor, so the object checked is the object used. */
static int open_regular(const char *path) {
    int fd = open(path, O_RDONLY | O_NOFOLLOW | O_CLOEXEC);
    if (fd < 0) return -1;                      /* kernel checks permission */
    struct stat st;
    if (fstat(fd, &st) != 0 || !S_ISREG(st.st_mode)) {
        close(fd);
        errno = EINVAL;
        return -1;
    }
    return fd;
}

int main(int argc, char **argv) {
    for (int i = 1; i < argc; i++) {
        int fd = open_regular(argv[i]);
        if (fd < 0) printf("%-12s refused: %s\n", argv[i], strerror(errno));
        else { printf("%-12s ok (fd %d)\n", argv[i], fd); close(fd); }
    }
    return 0;
}

gcc -Wall -pthread -o safe_open safe_open.c
echo hi > a.txt; ln -s a.txt sl; mkdir dd
./safe_open a.txt sl dd nothere

a.txt        ok (fd 3)
sl           refused: Too many levels of symbolic links
dd           refused: Invalid argument
nothere      refused: No such file or directory

The link is refused (ELOOP) because of O_NOFOLLOW, the directory by our own fstat test, and the missing file by the kernel. No step looked at the name a second time.

Part 5: a seccomp filter

Save as sandbox.c. The filter makes openat and socket fail with EPERM and allows everything else. (On 64-bit glibc, open() uses the openat system call.) Instruction 0 loads the system call number; instruction 1 jumps two ahead, to the ERRNO return, if it is openat; instruction 2 jumps one ahead, to the same return, if it is socket; otherwise instruction 3 allows the call. No root is needed.

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stddef.h>
#include <stdio.h>
#include <string.h>
#include <sys/prctl.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <linux/filter.h>
#include <linux/seccomp.h>

/* A tiny seccomp-bpf policy: openat() and socket() fail with EPERM;
   every other system call is allowed. (A real sandbox does the
   opposite: allow a short list, deny everything else.) */
static int install_filter(void) {
    struct sock_filter prog[] = {
        /* A = syscall number */
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_openat, 2, 0),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_socket, 1, 0),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
    };
    struct sock_fprog fp = { .len = sizeof prog / sizeof prog[0], .filter = prog };
    /* Without this bit an unprivileged process may not install a filter:
       it guarantees setuid programs cannot be used to escape the policy. */
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) != 0) return -1;
    return prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &fp);
}

int main(void) {
    int fd = open("/etc/hostname", O_RDONLY);
    printf("before filter: open -> %d\n", fd);
    if (fd >= 0) close(fd);

    if (install_filter() != 0) { perror("install_filter"); return 1; }

    fd = open("/etc/hostname", O_RDONLY);
    printf("after  filter: open -> %d (%s)\n", fd, fd < 0 ? strerror(errno) : "ok");
    printf("after  filter: getpid -> %d (still allowed)\n", (int)getpid());
    return 0;
}

gcc -Wall -pthread -o sandbox sandbox.c && ./sandbox

before filter: open -> 3
after  filter: open -> -1 (Operation not permitted)
after  filter: getpid -> 235 (still allowed)

The process ID will differ on your machine. Run it under strace to see the denied openat return -1 EPERM.

Part 6: observe ASLR, canaries and NX

Save as aslr.c. It prints one address from each memory region.

#include <stdio.h>
#include <stdlib.h>

int global_var;                              /* .bss: part of the program image */

int main(void) {
    int local = 0;                           /* stack */
    void *heap = malloc(16);                 /* heap (brk or mmap) */
    printf("code  (main)   : %p\n", (void *)main);
    printf("data  (global) : %p\n", (void *)&global_var);
    printf("heap  (malloc) : %p\n", heap);
    printf("libc  (printf) : %p\n", (void *)printf);
    printf("stack (local)  : %p\n", (void *)&local);
    free(heap);
    return 0;
}

gcc -Wall -pthread -o aslr aslr.c
./aslr; ./aslr                           # two runs: every region moves
setarch -R ./aslr                        # -R switches ASLR off for this run
cat /proc/sys/kernel/randomize_va_space  # 2 = full randomization

One ordinary run printed the block below; a second run put main at 0x55600064f199 and the stack at 0x7ffd1fd4863c. With setarch -R, main was at 0x555555555199 on every run. randomize_va_space was 2 and /proc/sys/vm/mmap_rnd_bits was 28 (the figure in Exercise 7). A -no-pie build keeps its code at a fixed address (0x401186 here) even with ASLR on, which is why distributions build everything as PIE.

code  (main)   : 0x5555eeab9199
data  (global) : 0x5555eeabc014
heap  (malloc) : 0x5556094de2a0
libc  (printf) : 0x7f4fbd260100
stack (local)  : 0x7ffd962f247c

Now look for canaries and NX in a compiled binary. perm_inspect.c has a local char array, so the protector instruments it:

gcc -O0 -fstack-protector-strong -o pi_sp  perm_inspect.c
gcc -O0 -fno-stack-protector     -o pi_nosp perm_inspect.c
nm -D pi_sp   | grep -c __stack_chk_fail    # prints 1
nm -D pi_nosp | grep -c __stack_chk_fail    # prints 0
readelf -lW pi_sp | grep GNU_STACK          # flags RW: stack not executable
gcc -z execstack -o pi_x perm_inspect.c
readelf -lW pi_x  | grep GNU_STACK          # flags RWE: stack executable
objdump -d pi_sp --no-show-raw-insn | grep -c 'fs:0x28'   # prints 2

The two %fs:0x28 accesses are the canary load on entry and the comparison before return, which calls __stack_chk_fail on a mismatch. The sandbox printed the counts and flags shown in the comments.

Common mistakes and debugging tips

Symptom Likely cause What to do
chmod 777 "fixes" a permission error Hides the real problem and opens the file to everyone Find which class the process is in and which directory lacks x; use namei -l path
Permission denied although the mode looks fine A directory on the path lacks x, or the owner class matched first Check every path component; first match wins
Cannot delete a file you own No write permission on the directory, or sticky bit and you are not the owner Check the directory mode
"Dropped" privilege can be regained Only the effective ID changed; saved ID still root Use setresuid for all three IDs, groups first; verify with getresuid
seccomp filter works on one machine but kills the program on another Different architecture or libc (open versus openat) Check seccomp_data.arch; trace with strace and log before enforcing
access() then open() in a privileged program TOCTOU race Open once with O_NOFOLLOW or the right effective ID; test with fstat

Key takeaways

Key takeaways

  • A protection domain is a set of (object, rights) pairs; hardware rings separate kernel from user code, and the system call gate forces every request through the kernel's checks.
  • The access matrix is stored by column (ACLs: easy "who can use this?" and revocation) or by row (capabilities: easy delegation, no ambient authority). Unix checks like an ACL at open and then hands out capability-like descriptors.
  • Unix modes are three triples written in octal as r = 4, w = 2, x = 1; the first matching class decides; directories use x to search and w to create or delete; setuid, setgid and sticky add a leading digit; umask removes bits from every request.
  • Run with least privilege for the least time: drop all three user IDs (groups first), split root into capabilities, and confine system calls with a seccomp allow-list and no_new_privs.
  • Store passwords as salted, slow hashes and add a second factor.
  • Canaries, NX and ASLR each block a different step of a memory-corruption attack; they raise cost but do not remove the bug.
  • Beware ambient authority (the confused deputy) and check-then-use sequences (TOCTOU): act with the caller's authority, do one lookup and test the descriptor, not the name.
